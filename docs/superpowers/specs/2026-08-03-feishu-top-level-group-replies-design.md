# 飞书群聊普通消息回复设计

## 背景

当前飞书群聊发送路径同时传入 `replyTo` 和 `replyInThread: true`。官方 Channel SDK 因此调用消息回复接口，把机器人答案放入原消息的话题容器。飞书主会话只显示折叠预览，多商品答案中的物理换行也会在预览中被压成一段，不符合实际使用要求。

## 已确认行为

- 群聊中只有明确 `@机器人` 的消息继续触发处理。
- 机器人答案作为群里的独立普通文本消息发送，不再回复原消息，也不进入话题。
- 群聊答案继续使用 SDK 原生 `mentions` 参数，在正文前真实 `@提问人`；应用不手工拼接 mention 标记。
- 私聊答案仍作为普通文本消息发送，并且不 `@` 提问人。
- 库存答案正文保持确定性格式，不返回内部商品编码；一个商品一行，多个商品以真实 `\n` 分隔；货架、供应商、库存和备注继续使用实际查询结果。

示例：

```text
@求精轴承 6001ZZ（12×28×8）（货架号：A-2-1）虎旺轴承库存177，备注：2026-07-11
6001ZZ（清油）（12×28×8）（货架号：B-11-13）天宇轴承库存200，备注：2024-7-20
```

## 发送设计

群聊投递只向 Channel `send(...)` 传入 `mentions`，不再传 `replyTo` 或 `replyInThread`。固定版本 SDK 在没有 `replyTo` 时调用消息创建接口，因此答案出现在群聊主时间线；有 `replyTo` 时才调用消息回复接口。

入站消息的 `threadID`、`rootID` 和现有会话标识规则不改变，它们仍用于识别用户发来的消息上下文。此次只改变机器人最终答案的投递形态，不改接纳、持久化、查询、恢复或重试流程。

## 错误处理与恢复

现有投递结果分类、超时、重试和不确定发送保护保持不变。任务继续持久化提问人的 `open_id` 和可选显示名称，重启恢复或重试时仍能生成相同的原生 mention；持久化答案仍只保存不含 mention 的正文。

## 测试与验收

- Channel 单元测试证明群聊发送参数包含原生 `mentions`，且不存在 `replyTo` 和 `replyInThread`。
- Channel 单元测试证明私聊发送参数仍为空，不包含 mention。
- 恢复与重试测试证明群聊 mention 元数据和答案正文不变。
- 完整测试、类型检查和 lint 全部通过。
- 重启网关后，在群聊发送 `6001ZZ @open机器人`：机器人答案必须作为独立普通消息显示，不出现“回复话题”；多条商品结果必须各占一行。

## 非目标

- 不改变库存 SQL、供应商回退、货架聚合或备注规则。
- 不改变群聊必须先 `@机器人` 才受理的策略。
- 不新增消息卡片、富文本或数据库迁移。
