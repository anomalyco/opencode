# 飞书对话网关设计

状态：已批准

日期：2026-07-23

## 目标

在现有 OpenCode 项目中增加一个运行于当前 Windows 电脑的飞书对话入口，通过飞书长连接接收消息，调用已经连通的 DeepSeek 模型，并向原消息发送一条最终文本回复。

本阶段只验证“飞书消息进入 OpenCode、模型生成回答、回答返回飞书”的完整链路。后续查询 T1 SQL Server、沉淀业务问题以及迁移到 MySQL 的目标不变，但数据库能力不属于本次实现范围。

## 已确认范围

本次交付包含：

- 飞书机器人单聊。
- 群聊中只有明确 `@机器人` 的消息才触发回答。
- 单聊按“用户 + 单聊会话”持续记忆。
- 群聊按同一消息串持续记忆。
- 每次模型生成完成后发送一条最终文本回复。
- 在当前 Windows 电脑上通过飞书 WebSocket 长连接常驻运行，不要求公网地址。
- 为每一轮对话保存可追溯的追加式全链路日志。

本次交付不包含：

- 文件读取、文件写入或项目代码修改能力。
- Shell、PowerShell、终端或其他本机命令执行能力。
- SQL Server、MySQL 或其他数据库连接与操作能力。
- 飞书卡片流式更新、中间思考过程或多条进度消息。
- 项目自建用户、角色和权限系统。
- 旧 `/feishu` 转发到 Discord 的链路改造。

## 方案比较

### 方案 A：飞书官方 Channel + 内嵌 OpenCode（采用）

新增独立的 `packages/feishu`，使用飞书官方 Node SDK 的 Channel 高层接口接收和回复消息，并使用 `packages/sdk-next` 在同一进程中调用 OpenCode。

该方案直接提供长连接、消息标准化、去重、重连和按会话串行处理能力；OpenCode 不需要额外启动 TUI、HTTP 服务或公网端口。单进程也便于保持会话映射、日志和故障恢复的一致性。

### 方案 B：飞书 WSClient + EventDispatcher

直接使用底层 WebSocket 客户端和事件分发器。它能提供更多底层控制，但需要自行处理消息解析、`@机器人` 判断、去重、重连和并发顺序，首版风险和测试面都更大，因此不采用。

### 方案 C：飞书进程 + 独立 OpenCode HTTP 服务

飞书适配器和 OpenCode 分成两个进程，通过本机 HTTP 调用。它便于未来独立部署，但首版会增加服务发现、端口、进程管理、鉴权和跨进程恢复问题。在当前单机链路验证阶段没有收益，因此不采用。

## 总体架构

```text
飞书单聊 / 群聊 @机器人
        |
        v
飞书官方 Channel（WebSocket 长连接）
        |
        v
消息过滤、标准化、去重和快速接收
        |
        v
会话路由与追加式事件日志
        |
        v
内嵌 OpenCode sdk-next
        |
        v
专用 feishu-chat Agent（禁止全部工具）
        |
        v
DeepSeek
        |
        v
一条最终文本回复到原单聊或原消息串
```

### 飞书入口

新包 `packages/feishu` 只负责飞书接入、会话路由、任务调度、回复和网关日志，不承载业务查询逻辑。

接入采用飞书官方 Node SDK 的 Channel 接口。配置使用 `requireMention: true` 和开放单聊模式，默认使用 WebSocket 长连接。首版固定 `@larksuiteoapi/node-sdk@1.71.1`，升级必须经过长连接、去重和回复回归测试。

飞书应用凭据只从 `packages/feishu/.env.local` 或等价的本机环境变量读取。DeepSeek 凭据继续使用 OpenCode 已有的认证状态。任何凭据都不得写入仓库、日志、错误回复或测试快照。

### OpenCode 调用

网关通过 `packages/sdk-next` 内嵌 OpenCode，不依赖全局安装的 `opencode` 命令，也不额外开放 HTTP 端口。

所有飞书消息固定使用专用 `feishu-chat` Agent。该 Agent 的工具集合为空，同时采用拒绝全部工具调用的权限策略，形成双重约束。用户即使要求读取文件、执行终端命令或访问数据库，当前版本也只能用文本说明该能力尚未开放，不能执行动作。

### 会话路由

会话路由必须稳定且可重复计算：

- 单聊键由飞书单聊 `chat_id` 和发送者 `sender_id` 组成。
- 群聊消息串键由群 `chat_id` 和消息串标识组成；标识优先使用 `thread_id`，其次使用 `root_id`。新发起且尚无上述标识的消息以当前 `message_id` 作为该消息串的根。
- 规范化会话键通过稳定哈希生成 OpenCode Session ID，避免把外部标识直接暴露为内部主键。
- 同一个会话键始终采用同一个 OpenCode Session ID，因此进程重启后可以继续上下文。
- 不同会话使用不同 Session，可以并行运行；同一 Session 内的消息保持顺序。

飞书 `message_id` 经过稳定映射后作为 OpenCode 的 prompt message ID。重复投递同一飞书消息时，OpenCode 的精确重试语义和网关去重共同保证不会重复生成。

## 消息处理流程

1. Channel 接收并标准化飞书消息。
2. 单聊消息进入处理队列；群聊消息只有在明确 `@机器人` 时进入处理队列，其余消息静默忽略。
3. 网关先在本机 SQLite 网关存储中追加“消息已接收”事件并持久化任务，然后尽快结束飞书事件回调。回调中的工作以三秒内完成为设计目标，模型推理在后台继续。
4. 网关生成本轮 `trace_id`、`turn_id`、确定性 prompt message ID 和 OpenCode Session ID。
5. 网关创建或接管对应 Session，使用 `feishu-chat` Agent 和已选定的 DeepSeek 模型提交 prompt。
6. 网关监听该 Session 的持久事件，取得最终完整文本以及耗时、Token 和费用信息。
7. 网关先记录最终回答，再向原单聊消息或原群聊消息串回复一条最终文本。
8. 网关记录发送结果，并将该轮标记为成功、确定失败或投递状态不确定。

进程启动时检查已接收但尚未完成的任务。尚未提交给 OpenCode 的任务可以继续提交；已经使用相同 prompt message ID 接纳的任务采用精确重试；已经确认发送成功的任务不得再次回复。

## 幂等与并发

- Channel 去重和本地任务状态共同阻止飞书重复事件触发重复模型调用。
- 飞书 message ID 到 OpenCode prompt message ID 的映射是确定性的。
- 同一会话的任务按接收顺序串行处理，避免上下文交错。
- 不同单聊和不同群聊消息串可以并行处理。
- 对已确认成功的回复不再发送。
- 只有明确返回“未发送”的可重试错误才允许重试发送。
- 网络中断等无法判断飞书是否已收到的情况记录为 `uncertain_delivery`，不盲目重发，防止用户收到重复答案。

## 全链路日志

日志遵循根目录 [T1 临时业务库与全链路逐句日志说明](../../../T1临时业务库与全链路逐句日志说明.md) 的追加式原则。网关使用 Bun 内置 SQLite，在 OpenCode 本机数据目录保存任务状态和追加式事件表；已写入的历史事件不更新、不覆盖。该数据库不写入 Git 仓库。

每一轮对话至少记录：

- `event_id`、`trace_id`、`parent_event_id`、`conversation_id`、`turn_id`。
- 飞书 message ID、规范化会话键的不可逆标识和 OpenCode Session ID。
- 消息方向、消息状态、事件时间和顺序。
- 用户完整原文及按原顺序拆分的逐句事件。
- Agent、模型和 variant。
- OpenCode prompt 接纳、模型开始、模型结束和失败事件。
- 最终回答完整原文及按原顺序拆分的逐句事件。
- 总耗时、模型耗时、Token、费用、重试次数和最终状态。
- 飞书回复目标、发送结果和投递状态。
- 后续人工纠正与原始事件的关联。

无法可靠拆句时，把完整消息作为一个句子保存，不改写原意。日志不得保存飞书应用密钥、Token、DeepSeek API Key、Cookie、会话令牌、完整连接字符串、数据库密码、私钥或模型隐藏思考过程。

如果 SQLite 主日志写入失败，任务不能被伪装成“日志成功”。网关同时向 OpenCode 本机日志目录的独立降级错误文件追加记录并输出本机错误，保留恢复和排查线索。

## 错误处理

- 缺少环境变量时启动失败，只报告缺少的字段名，不输出已有值。
- 飞书应用凭据无效、权限不足或长连接握手失败时启动失败，并给出不含凭据的原因。
- 长连接中断由官方 SDK 自动重连，网关记录断开、重连和恢复时间。
- DeepSeek 超时、限流、认证失败或提供商错误时，向用户发送一条简短失败说明和 `trace_id`，不得编造业务答案。
- 飞书回复明确失败时按错误类别决定是否重试；投递状态不确定时不盲目重发。
- `feishu-chat` Agent 出现任何工具调用请求时立即中断该调用，记录策略违规事件，并且不执行工具。
- 单条消息失败不能阻塞其他会话；同一会话在失败任务完成状态落盘后才能继续下一条。

## 飞书侧配置

飞书应用需要：

- 启用机器人能力。
- 使用长连接接收事件。
- 订阅 `im.message.receive_v1`。
- 开通接收单聊消息、接收群聊中 `@机器人` 消息以及以机器人身份发送消息所需的权限。
- 发布可用版本，并把测试人员加入应用可用范围。

本项目不再建立一套用户授权系统。当前聊天 MVP 依赖飞书应用可用范围和飞书身份上下文控制入口；本阶段没有数据库或本机工具可被调用。后续数据库变更仍需沿用飞书上下文，但其准确率、事务和操作安全策略必须在独立 OpenSpec 变更中定义。

## 验收标准

实现完成后必须通过以下可重复验证：

1. 给机器人发送单聊消息，收到一条 DeepSeek 最终文本回复。
2. 在群聊中 `@机器人`，回复出现在原消息串。
3. 群聊中未 `@机器人` 的普通消息不触发模型调用，也不回复。
4. 同一单聊中的后续问题能够使用此前上下文。
5. 不同用户、不同单聊和不同群聊消息串之间不会串话。
6. 重复投递同一飞书事件不会重复调用模型或重复回复。
7. 进程重启后，同一会话继续采用原 OpenCode Session。
8. 要求读取文件、执行终端或操作数据库时，不发生任何工具执行。
9. 每轮对话的完整消息和逐句事件使用同一个 `trace_id` 且可以完整串联。
10. 日志和错误输出中不存在应用密钥、API Key、Token 或其他认证秘密。
11. 使用一条本机启动命令即可运行，且不需要公网回调地址。

## 后续数据库阶段

数据库目标没有改变，只是与当前链路验证解耦：

1. 飞书纯对话链路稳定后，单独创建 T1 SQL Server 只读变更，用于理解真实业务语义、员工常见问题、统计口径和迁移证据。
2. T1 阶段只允许批准的查询和结构读取，不延长旧服务器、旧 Windows 或旧 SQL Server 的生命周期。
3. 对话日志、人工纠正和高频问题持续转化为 gold cases，用于衡量业务意图、SQL、执行结果和回答解释的准确率。
4. 正式 MySQL 就绪后，保留飞书入口、会话、Agent、日志和 gold cases，更换数据库适配和物理结构。
5. 正式 MySQL 工具按既定目标支持完整 CRUD 和数据库侧最高权限；准确率优先，并通过事务、影响行数检查、写后复核和失败回滚控制执行正确性。

T1 只读接入和正式 MySQL CRUD 分别建立独立 OpenSpec 变更，不把数据库能力偷渡进本次聊天 MVP。
