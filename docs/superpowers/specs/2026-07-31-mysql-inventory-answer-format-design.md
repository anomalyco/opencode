# MySQL 商品库存与位置回答格式设计

## 目标

员工询问商品库存或货架位置时，系统只返回业务可读的一行文本，不展示内部商品编码，不使用表格、标题、字段分段、汇总前言或结尾追问。多个结果仅以换行分隔。

运行时数据源固定为迁移后的 MySQL。系统不连接、不查询，也不回退到 T1 SQL Server。现有 T1 排查与迁移记录作为历史资料保留，不作为运行链路或新功能依赖。

## 采用方案

采用确定性格式化器。MySQL 查询结果先映射为不含内部编码的回答对象，再由格式化器生成最终文本。模型不得自行选择字段、组织表格或改写格式。

没有采用仅修改提示词的方案，因为模型可能继续输出商品编码或表格。也没有采用“SQL 隐藏编码、模型自由组织语言”的方案，因为最终标点、字段顺序和多结果展示仍不稳定。

## 输出格式

标准示例：

```text
6001ZZ（清油）（12×28×8）（货架号：B-11-13）上海涂众轴承库存200，备注：xxx
```

字段顺序固定为：

1. 商品业务名称或型号。
2. 商品属性，例如“清油”。
3. 商品规格，例如“12×28×8”。
4. 货架号，格式为“（货架号：B-11-13）”。
5. 供应商名称。
6. 对应库存数量，在供应商名称后固定添加“库存”再接数量，不添加“来货”或“数量”等其他标签。
7. 备注，格式为“，备注：原备注内容”。

每个回答对象只生成一行。多个回答对象按原查询顺序用换行连接，不添加项目符号、序号、空行、Markdown 表格、匹配数量汇总或解释文字。

可选字段为空时省略该字段及其配套标点，不输出“无”“—”“未归属”等占位文本。没有匹配商品时只返回“未找到相关商品。”；查询失败时返回不包含数据库结构、SQL 或凭据的单句错误，不编造商品数据。

## 数据边界

回答对象只允许包含业务名称或型号、商品属性、规格、货架号、供应商名称、对应数量和备注。`Product.s_ID`、`Product.u_Code`、`SP000...` 形式的编码以及其他内部主键不得进入回答对象或最终回复。

内部查询可以使用主键完成关联，但原始数据库行不得直接交给模型生成答案。商品规格、型号和备注沿用迁移后 MySQL 的既有字段语义：

- `Product.ProdSpec` 是规格来源。
- `Product.ProdType` 是型号来源。
- `Product.u_Remark` 是备注原文，不作为型号或货架号来源。
- 商品与货架使用 `Product.s_ID` 的关系关联；`u_Code` 可能重复，不能作为唯一商品身份。

供应商和数量的物理表、字段与统计口径必须在实现前从目标 MySQL schema 只读确认，不根据旧 T1 表结构猜测。货架查询使用迁移后已经确认的商品—货架关系，不从备注字段临时解析货架号。

## 规划调整

- 从项目当前架构、工作流和后续路线中移除 T1 SQL Server 只读运行阶段。
- 保留两份 T1 排查文档及已有历史证据，不删除、不改写为当前运行事实。
- `feishu-chat-gateway` 仍是数据库无关的纯聊天网关；其中提到的后续 T1 路线改为直接接入 MySQL。
- 商品库存与位置查询及本回答格式作为独立 OpenSpec 变更规划和实现，避免把数据库能力混入纯聊天网关。

## 测试与验收

自动化测试必须覆盖：

- 标准输入生成与示例逐字一致的一行文本。
- 最终回复不含 `u_Code`、`s_ID`、`SP000...`、表头或 Markdown 表格标记。
- 多个回答对象严格一对象一行，中间没有空行。
- 可选字段缺失时不产生多余括号、逗号或占位文本。
- 供应商名称后固定输出“库存”和对应数量，输出中不出现“来货”。
- 规格尺寸统一使用 `×`，货架号保持规范化格式。
- 备注只来自备注字段原文，不参与型号、规格或货架识别。
- 运行路径只使用 MySQL 适配器，不存在 T1 SQL Server 连接、查询或回退分支。

数据库查询与回答解释继续纳入追加式 trace 和 gold case 验收，但历史 T1 记录只作为保留资料，不作为新测试或运行时回放的必需依赖。
