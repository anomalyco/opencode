# 飞书群聊原生 @ 回复设计

## 背景

当前飞书网关在群聊中通过 `replyTo` 和 `replyInThread` 回复原消息，但回复正文不会显示 `@提问人`。实际使用需要机器人在群聊回复时明确提醒提问者，同时继续保持库存回答的一商品一行格式。私聊不需要 @。

## 目标

- 群聊最终回复使用飞书 SDK 原生 `mentions` 参数真实 `@提问人`。
- 私聊回复保持现状，不增加 @。
- 库存格式化器返回的正文保持不变，例如 `6001ZZ（清油）（12×28×8）（货架号：A-2-1）上海涂众轴承库存177，备注：2026-07-11`。
- 供应商只使用数据库中可靠的结构化归属，没有可靠供应商时省略且不猜测；备注使用每条商品当前映射到的实际值，不写死示例内容。
- 回复重试和进程重启恢复后仍能使用同一个提问人身份。
- 不在正文、模型提示或库存 trace 中拼接飞书 `<at>` 标记。

## 非目标

- 不 @ 群内其他成员或 `@所有人`。
- 不改变群聊必须先 @ 机器人才受理的规则。
- 不改变线程归属、库存查询、模型路由或确定性回答格式。
- 不为历史任务反向推断提问人。

## 设计

### 接收与持久化

标准化飞书消息保留 SDK 已提供的 `senderId` 和可选 `senderName`。接纳群聊任务时，将它们复制为可选的 `replyMentionID` 和 `replyMentionName`；私聊任务不写这两个字段。

`gateway_task` schema 升级到版本 2，新增可空列 `reply_mention_id`、`reply_mention_name`。新数据库直接创建这两列，版本 1 数据库通过只追加列的迁移升级。旧任务列值为空，恢复时保持原发送行为。

重复消息一致性比较包含 @ 身份字段，避免同一飞书消息 ID 被不同发送人信息冲突复用。

### 回复发送

群聊任务调用 Channel `send(...)` 时继续使用原有：

- `replyTo: task.replyRootID`
- `replyInThread: true`

同时传入：

```ts
mentions: [{
  key: task.replyMentionID,
  openId: task.replyMentionID,
  name: task.replyMentionName,
}]
```

飞书 SDK 负责把 mention 渲染为真实 @。最终显示示例为 `@求精轴承 6001ZZ（清油）（12×28×8）（货架号：A-2-1）上海涂众轴承库存177，备注：2026-07-11`。其中供应商和备注仍由现有 MySQL 映射及确定性格式化器按每条实际数据生成。

应用传给发送端的 `text` 仍是原始最终回答，SQLite 中的 `answer_recorded` 也只保存正文，因此内部格式断言、逐句事件和库存准确率不受展示层影响。

私聊任务以及缺少可靠提问人 ID 的旧任务不传 `mentions`。

### 失败与恢复

@ 元数据与回复目标一起持久化，发送失败后的有界重试复用相同内容和 mention。网络结果不确定时仍进入 `uncertain_delivery`，不因增加 @ 而改变重复发送策略。

如果 SDK 把 mention 判定为格式错误，沿用现有非重试发送失败分类，不降级成可能误导用户的纯文本用户名。

## 测试

- 标准化测试：群聊保留 `senderID` 和可选 `senderName`，私聊数据不改变。
- Store 迁移测试：版本 1 数据库升级到版本 2；新任务可持久化并恢复 mention 字段。
- Admission 测试：群聊任务写入 mention，私聊任务不写。
- Channel 测试：群聊发送包含 SDK 原生 `mentions`、线程回复参数和未改写正文；私聊不包含 mentions。
- Worker/Gateway 测试：重试和恢复使用相同 mention；库存正文仍逐字等于格式化器结果。
- 全包测试、类型检查和 lint 通过后再重启本机网关进行飞书实测。
