Product decisions For anyone reviewing the hiring-agent direction Updated Aug 11, 2026

moks is to hiring
what OpenCode is to coding

Same kind of AI workbench. Different job. We keep the engine — sessions, tools, permissions, plans — and point it at requisitions and candidates instead of repositories and pull requests.

The big idea

“Code is everything” — the workflow shape travels

Software teams already know how agents should feel: open a project, see local changes, plan, review, then push to the remote. Hiring can feel the same — if we map the pieces carefully.

Software engineering

OpenCode

Help people ship software: explore a repo, write code, review a PR, push to GitHub.

maps to

Talent acquisition

moks

Help people fill roles: open a req, score candidates, draft outreach, review the packet, push decisions to the ATS.

What we keep: the harness — chat sessions, planning mode, skills, permissions, multi-model support.

What we change: defaults, wording, what “a project” means, and what “push” writes to.

What we refuse: renaming the product to “moks” while it still behaves like a coding IDE (AGENTS.md, PR review, language servers as the main story).

Shared language

Plain dictionary: coding → hiring

Use this table when anyone asks “what does this feature mean for recruiters?” If a feature doesn’t fit a row, question whether it belongs on the hiring product path.

In coding tools… In moks (hiring)…
The job Fill requisitions; move candidates with evidence
A repo / project A requisition (req) — the unit of work you open
GitHub (the remote) The ATS (e.g. Ashby) — system of record
Files on your machine Local req folder (JD, scorecard, notes, drafts)
Live diff / “what changed?” Live diff of local candidate & req changes — same muscle memory as watching code change
Review before merge Packet review — resume vs scorecard, outreach, disposition
Commit / stage intent Commit (moks commit) — write a receipt of intended ATS changes
Push to remote Push (moks push) — only then the remote write path
“Start a new project” (`/init`) Start a new req — scaffold the hiring workspace
Build agent (does the work) Recruit agent (Build stays hidden for developers)
Plan, then implement Plan hiring strategy, then execute next steps
Language servers / IDE polish Not for hiring product — turn off by default

Important nuance: Diff shows local work (notes, scores, drafts, pending commits) — like uncommitted changes. Remote ATS updates when someone pushes, not on every keystroke.

Glossary

Short definitions so the rest of the page stays readable.

Req / requisition
An open role you’re hiring for. In moks this is the “project” you work inside.
ATS
Applicant Tracking System (e.g. Ashby). The remote system of record — like GitHub for code.
Recruit
The default AI persona that does hiring work.
Plan
Strategy mode: think and write a plan without recording final decisions yet.
Commit
moks commit — record intended ATS changes as a receipt (stage your intent).
Push
moks push — push a committed decision on the remote write path (confirm adverse actions).
Diff
A live view of what changed locally (notes, scores, drafts) — same idea as a code diff.
Packet review
Reading a candidate against the JD/scorecard and checking outreach or disposition quality before you push.
LSP
Language server — IDE intelligence for programming languages. Useful for coding; not for the hiring product.
Build (agent)
The old coding doer. Hidden in the product; kept so we can still build moks itself.
Harness
The underlying agent engine (sessions, tools, permissions). We mold it; we don’t rewrite it from scratch.
OpenCode
The open-source coding-agent project moks was forked from. Lineage only — not our product name or affiliation.
