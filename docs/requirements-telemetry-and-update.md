# 需求规格文档:DeskFox 使用统计与升级通知

> **状态**:V1.0 — 经一轮 Socratic 对话确认
> **日期**:2026-04-29
> **后续动作**:本文档完成后可直接交给 `/sc:design` 进入架构设计阶段

---

## 1. 项目目标

### 1.1 业务目标
- **G1(增长可见性)**:以可量化方式呈现项目装机量、版本分布、地理分布,用于对外展示与对内复盘
- **G2(产品决策)**:通过核心功能使用频次,识别"被使用的"与"无人问津的"功能,指导后续优先级
- **G3(用户可达)**:发布新版时,能让现有用户在合理时间内升级到最新版本

### 1.2 用户与利益相关者
- **终端用户**:三类客户端使用者(CLI / 桌面 Electron / Web)
- **维护者**:本项目维护团队(数据消费方)
- **隐私敏感用户**:开源社区中关注遥测的用户(必须保留关闭权)

---

## 2. 范围

### 2.1 In Scope
- 三类客户端(CLI、桌面 Electron、Web)的下载量与启动量统计
- 桌面 Electron 的静默自动更新
- CLI 启动时检查新版并提示用户手动升级
- 5–10 个核心事件的计数埋点(L4-lite)
- 用户级 opt-out 关闭开关
- 服务端采集、存储、可视化(基于 Plausible 自托管,东京服务器)

### 2.2 Out of Scope(明确不做)
- 用户身份识别 / 邮箱收集 / 账户体系
- 深度行为追踪(会话录屏、点击热力图、漏斗分析)
- Web 端的"升级通知"(部署即升级,无此问题)
- 错误/崩溃上报(可作为未来 Phase 2)
- 强制升级机制(本期不做版本封禁)
- 邮件订阅 / 推送通知

## 3. 功能需求

### FR-1 使用统计 · L1 下载量
- **FR-1.1** 在 Gitee/GitHub Release 页面记录每个 Release Asset 的累计下载次数(平台原生支持,无需自建)
- **FR-1.2** 维护者可在统一看板上看到各分发渠道的下载汇总(Release / npm / Homebrew 等)

### FR-2 使用统计 · L2 安装/启动心跳
应用首次启动与每次启动时,向遥测端点发送一条匿名心跳,字段:

| 字段 | 类型 | 说明 |
|---|---|---|
| `install_id` | UUID v4 | 安装时本地生成,持久化于本地配置目录,**不与任何身份关联** |
| `client_type` | enum | `cli` / `desktop` / `web` |
| `app_version` | string | 语义化版本号 |
| `os` | string | `darwin` / `linux` / `win32` |
| `arch` | string | `x64` / `arm64` |
| `country` | string | 服务端从 IP 推断后立即丢弃 IP,只存国家码 |
| `event` | enum | `install` / `launch` |
| `timestamp` | ISO8601 | 服务端补 |

- **FR-2.1** IP 地址**不得**入库,仅在请求处理瞬时用于推断国家码
- **FR-2.2** `install_id` 一台机器一个,用户重装应用时重新生成

### FR-3 使用统计 · L4-lite 核心事件埋点
- **FR-3.1** 选定 **5–10 个核心事件** 进行计数埋点(具体清单见 OQ-1)
- **FR-3.2** 事件结构:`{ install_id, client_type, app_version, event_name, timestamp }` — **无任何业务参数**(不带文件名、不带项目名、不带提示词等用户内容)
- **FR-3.3** 事件采用本地批量缓冲,默认 5 分钟或 20 条触发一次上报,降低请求量

### FR-4 升级通知 · 桌面 Electron(静默自动更新)
- **FR-4.1** 启动时静默检查 `GET /v1/latest?client=desktop`,若有新版则后台下载
- **FR-4.2** 下载完成后,在用户下次重启应用时自动应用更新(类似 VSCode 行为)
- **FR-4.3** 用户可在设置中关闭自动更新(默认开启)
- **FR-4.4** 更新包必须签名校验(防止中间人投毒)
- **FR-4.5** 检查频率:每次启动 + 后续每 24 小时一次(运行中)

### FR-5 升级通知 · CLI(启动提示)
- **FR-5.1** 每次启动时,异步检查最新版,**不阻塞**正常命令执行
- **FR-5.2** 若有新版,在命令输出末尾追加一行提示,例如:
  `opencode 0.5.2 is available (you're on 0.5.0). Run: <upgrade command>`
- **FR-5.3** 检查结果本地缓存 24 小时,避免每次执行都打网络
- **FR-5.4** 升级命令文案需根据安装方式(npm/bun/homebrew/curl)分别给出 — **检测安装方式见 OQ-2**

### FR-6 升级通知 · Web — 不适用
Web 端在服务端部署即升级,无客户端通知需求。

### FR-7 隐私控制(opt-out)
- **FR-7.1** **首次启动时**显示一次性告知卡片/横幅,说明:
  - 收集了什么(版本、OS、国家码、核心事件计数)
  - 不收集什么(代码内容、提示词、IP、账户)
  - 如何关闭
  - 链接到隐私政策(见 OQ-3)
- **FR-7.2** 关闭开关至少有 **3 个等价入口**:
  1. 应用设置中的"使用统计"开关(默认开)
  2. 环境变量 `OPENCODE_TELEMETRY=0`
  3. 配置文件项 `telemetry: false`
- **FR-7.3** 关闭后,客户端**不再**发起任何遥测请求(升级检查端点除外,但该端点也支持单独关闭)
- **FR-7.4** README、隐私政策、文档站均需有显著入口说明如何关闭

## 4. 非功能需求

### NFR-1 隐私合规
- **NFR-1.1** 默认 opt-out 模式,但首启必须显著告知(防止"未告知遥测"舆情)
- **NFR-1.2** 数据最小化原则:只收集本文档明确列出的字段
- **NFR-1.3** 数据保留期上限 **24 个月**,过期自动删除
- **NFR-1.4** 隐私政策需明确"不向第三方共享数据"

### NFR-2 性能与容量(2C4G 东京服务器约束)
- **NFR-2.1** 采集端点 P95 响应时间 < 200ms(东京 → 大陆约 50–80ms,可接受)
- **NFR-2.2** 服务端目标承载:**5 万 DAU 心跳 + 2 万 DAU L4 事件批次**(即 ~7 万 req/天,约 1 req/s 平均、峰值 < 20 req/s)
- **NFR-2.3** 客户端单次心跳请求 < 1KB,L4 批次 < 10KB
- **NFR-2.4** 客户端任何遥测/升级检查异常**不得**影响主功能(网络失败静默)
- **NFR-2.5** **该服务器与其他服务共用**(部署中转、GA4 代理、OSS 上传跳板、域名 Bootstrap),Plausible 与 Grafana 部署须考虑共存,内存为主要风险点

### NFR-3 可靠性
- **NFR-3.1** 升级检查端点(`/v1/latest`)需要更高 SLA(99.5%)— 它影响用户感知
- **NFR-3.2** 心跳端点 SLA 99% 即可,丢失少量数据不致命
- **NFR-3.3** 客户端有本地缓冲与指数退避重试(最多 3 次)

### NFR-4 安全
- **NFR-4.1** 全链路 HTTPS,服务端禁用 HTTP
- **NFR-4.2** 端点开放在公网 → 必须配置 **rate limiting**(单 IP 每分钟 < 60 请求)
- **NFR-4.3** Plausible / Grafana 管理后台**不暴露公网**,通过 SSH 隧道或 VPN 访问
- **NFR-4.4** 自动更新包采用签名校验(代码签名证书 + checksum)

### NFR-5 可观测性(给维护者的)
- **NFR-5.1** Plausible 自带看板:DAU/MAU、版本分布、国家分布、客户端类型分布
- **NFR-5.2** Grafana 二次看板(读取 Plausible 后端 PostgreSQL):自定义事件趋势、版本升级速度、关闭率
- **NFR-5.3** 服务自身监控:磁盘、CPU、错误率

### NFR-6 国际化与可达性
- **NFR-6.1** 用户可见文案(首启告知、CLI 升级提示、设置项)需中英双语
- **NFR-6.2** 东京机房对中国大陆/日韩/东南亚延迟可接受;若未来扩展欧美,考虑加 CDN 边缘(本期不做)

## 5. 用户故事与验收标准

### US-1 维护者:看到装机量
> **作为**项目维护者
> **我希望**在一个仪表盘看到日活/月活、版本分布、国家分布
> **以便**对外展示项目影响力,并判断旧版用户的升级速度

**验收标准**:
- 维护者打开 Plausible 看板,能看到当日 / 7 日 / 30 日活跃安装数
- 能按 `app_version` 过滤,看到各版本占比
- 能按 `country` / `os` / `client_type` 拆分

### US-2 维护者:看到核心功能使用频次
> **作为**维护者
> **我希望**看到 5–10 个核心事件的每日触发次数
> **以便**判断哪些功能值得继续投入

**验收标准**:
- Grafana 看板呈现各事件 7 日 / 30 日趋势
- 能区分 CLI / 桌面 / Web 来源

### US-3 终端用户:升级到新版桌面应用
> **作为**桌面应用用户
> **我希望**新版发布后我无需任何操作就用上新版
> **以便**专注本职工作

**验收标准**:
- 新版发布后,用户下次启动时已是新版(或在运行中提示重启)
- 网络异常时,旧版仍能正常使用,不会卡死

### US-4 CLI 用户:被告知有新版
> **作为** CLI 用户
> **我希望**在使用过程中被告知有新版可用,以及升级命令
> **以便**自主决定何时升级

**验收标准**:
- 命令执行末尾出现一行升级提示(无新版时不出现)
- 升级命令文案对应当前安装方式(npm / brew / curl)
- 在 24 小时内不会重复打扰

### US-5 隐私敏感用户:关闭遥测
> **作为**隐私敏感用户
> **我希望**有清晰的方式关闭遥测
> **以便**保留我对自己数据的控制

**验收标准**:
- 首次启动看到告知,3 秒内能找到关闭开关
- 关闭后用 tcpdump / mitmproxy 验证不再发任何遥测请求
- 三种关闭方式(UI / 环境变量 / 配置文件)均生效

## 7. 遗留问题(进入 `/sc:design` 前需确认)

- **OQ-1** **L4-lite 具体事件清单**:需要维护者确定 5–10 个最关心的事件名(例如 CLI 端 `cli.session_start` / `cli.tool_run` / `cli.error`,桌面端 `desktop.project_open` / `desktop.ai_request`)。建议在设计阶段开一次小会敲定。
- **OQ-2** **CLI 安装方式探测**:CLI 升级提示需要识别用户是用 `npm` / `bun` / `brew` / `curl` 安装的,以给出正确升级命令 — 探测方式待设计
- **OQ-3** **隐私政策文档**:需要法务/维护者审过的中英双语隐私政策正式文本(在哪个域名/路径托管)
- **OQ-4** **域名**:遥测端点用什么子域?(如 `telemetry.<your-domain>` 与 `updates.<your-domain>`)
- **OQ-5** **代码签名证书**:桌面 Electron 静默自动更新需要 macOS / Windows 代码签名证书 — 是否已有?成本约 $300–500/年
- **OQ-6** **是否对外公开聚合数据**:如"我们的项目有 N 个安装" — 是否做一个公开页面?(可选)
- **OQ-7** **数据备份**:Plausible 后端 PostgreSQL 的备份策略(单机故障时数据是否容忍丢失)
- **OQ-8** **服务器资源评估**:目前已运行 nginx / GA4 代理 / 部署中转等服务,Plausible 部署前需先实测剩余可用内存与磁盘
