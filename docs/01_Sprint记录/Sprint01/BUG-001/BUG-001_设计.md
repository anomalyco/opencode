## 1. 需求背景

BUG-001 目标是修复 OpenCode 在调用 `review-mcp` 的 `review` 工具时，长耗时评审（10~20 分钟）出现 `-32001` 超时的问题。

已知事实：

1. `review-mcp` 服务端已经实现进度通知与 12 秒心跳（`D:/Tony/projects/review_mcp/src/handlers/review_handler.js:187`）。
2. OpenCode 客户端当前已设置 `resetTimeoutOnProgress: true`（`D:/Tony/projects/viber-coding/opencode/packages/opencode/src/mcp/index.ts:142`）。
3. 但仍然出现 `-32001`，说明“心跳存在”与“客户端续时生效”之间存在链路断点。

用户约束（已确认）：

- 仅修改 OpenCode 客户端。
- 不依赖“固定拉长超时”作为主策略。
- 需要覆盖 design / implementation 两类长评审场景。

### 2.4 第一性原理分析

**表面问题**：明明有心跳，为什么还超时？  
**根本问题**：客户端续时机制依赖“有效进度链路”，而不是“服务端单边发送心跳”。  

基本要素：

1. 客户端请求必须携带可回传的 `progressToken`。
2. 客户端必须注册 progress 回调，才能在收到心跳时重置超时计时器。
3. 任一环节缺失，`resetTimeoutOnProgress` 都无法实际生效。

设计方向：修复 OpenCode 客户端 progress 回调链路，确保 `progressToken` 注入 + 心跳续时闭环成立。

### 5.2 闭环分析

- 闭环状态：❌ 存在断点。
- 断点位置：环节 3 -> 4（OpenCode 未提供 `onprogress`，导致 SDK 不注入 `progressToken`）。
- 直接后果：服务端无法感知 token，心跳通知等价降级；客户端计时器无法被 progress 重置，长评审触发 `-32001`。

## 6. 方案选择

### 6.1 候选方案

| 方案 | 核心思路 | 成本 | 风险 | 结论 |
|:-----|:---------|:-----|:-----|:-----|
| A | 仅拉长/关闭 timeout | 低 | 不能覆盖不可预测 10~20 分钟，且偏离约束 | 不选 |
| B | 在 `callTool` 选项中补齐 `onprogress`，建立 progressToken 注入与续时链路 | 低 | 需补充回归测试防止后续回退 | 选定 |
| C | 修改服务端协议或心跳机制 | 高 | 跨仓库侵入，违背“仅改 OpenCode” | 不选 |

### 6.2 选定方案（方案 B）

在 OpenCode 的 MCP 调用处显式提供 progress 回调（可先做轻量 no-op 或 debug 记录），让 SDK 自动：

1. 在请求 `_meta` 注入 `progressToken`。
2. 在收到 progress 通知时触发 `_resetTimeout()`。

这满足“只改客户端 + 不依赖固定长超时”的约束。

## 7. 设计方案

### 7.1 技术验证结果

验证目标：确认“没有 `onprogress` 时，`resetTimeoutOnProgress` 不会形成有效续时”。

验证过程与结果：

| 验证点 | 证据 | 结果 |
|:-------|:-----|:-----|
| OpenCode 当前 callTool 选项 | `D:/Tony/projects/viber-coding/opencode/packages/opencode/src/mcp/index.ts:142` 仅见 `resetTimeoutOnProgress` 与 `timeout`；`onprogress` 检索为空 | ✅ 复现 |
| SDK token 注入条件 | `protocol.ts` 中 `if (options?.onprogress) { ... _meta.progressToken ... }` | ✅ 复现 |
| SDK 续时触发条件 | `protocol.ts` 中 progress handler 命中后才执行 `if (progress.resetTimeoutOnProgress) this._resetTimeout()` | ✅ 复现 |
| review-mcp 对 token 依赖 | `D:/Tony/projects/review_mcp/src/index.js:29` 与 `:65`（无 token 时心跳退化） | ✅ 复现 |

复现结论：

- BUG 已在“源码链路级”稳定复现。
- 根因闭环：`onprogress` 缺失 -> token 不注入 -> 心跳无效 -> 续时失败 -> `-32001`。

### 7.2 集成设计

#### 7.2.1 变更点

1. 在 `convertMcpTool` 的 `client.callTool(..., options)` 中新增 `onprogress` 回调。
2. 维持 `resetTimeoutOnProgress: true` 不变。
3. `timeout` 继续作为兜底上限，不作为主治理策略。

建议改动草案：

```ts
return client.callTool(
  {
    name: mcpTool.name,
    arguments: (args || {}) as Record<string, unknown>,
  },
  CallToolResultSchema,
  {
    onprogress: (event) => {
      log.debug("mcp progress", {
        tool: mcpTool.name,
        progress: event.progress,
        total: event.total,
      })
    },
    resetTimeoutOnProgress: true,
    timeout,
  },
)
```

#### 7.2.2 兼容性与影响面

- 协议兼容：不改 MCP 工具输入/输出 schema。
- 配置兼容：不新增强制配置项。
- 行为变化：仅在长请求期间启用 progress 续时；短请求行为不变。
- Worktree 兼容：仅修改相对稳定的 `packages/opencode/src/mcp/index.ts`，不依赖绝对路径。

## 12. 结论

本设计确认 BUG-001 的根因不在“服务端是否发心跳”，而在“客户端是否形成 progressToken + progress handler + resetTimeoutOnProgress 的完整续时闭环”。

选定方案为仅修改 OpenCode 客户端调用链，补齐 `onprogress`，在不依赖固定长超时的前提下解决长评审 `-32001` 超时问题。
