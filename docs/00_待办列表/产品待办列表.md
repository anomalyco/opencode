## BUG-001 OpenCode MCP工具调用未注入progressToken导致长评审超时（-32001）

> 作为 OpenCode 用户，我希望在 design/implementation 评审中不再出现 `-32001` 超时，以便长时评审能够稳定完成。

**状态**：方案已选择

**来源issue**：review_mcp/Sprint01/BUG-005 MCP评审请求超时（-32001）
**衍生原因**：review-mcp 侧已实现心跳，但 OpenCode MCP 调用链未形成稳定续时闭环，导致长评审仍超时。

**关联issue**：review_mcp/Sprint01/BUG-005

**如何出现**：

1. 通过 OpenCode 调用 `review-mcp` 的 `review` 工具（`design` 或 `implementation`）。
2. Codex 执行评审耗时较长（目录较大或历史文件较多）。
3. MCP 客户端等待最终结果超时，返回 `-32001`。

**原始错误信息**：

```
MCP 响应超时（-32001）
```

**查原始记录方法**：

- 在 OpenCode 侧复现同参数调用；
- 检查 OpenCode MCP 调用日志与 review-mcp 返回错误块；
- 对照 review_mcp/Sprint01/BUG-005 的回归记录与触发场景。

**环境信息**：

- 调用端：OpenCode
- MCP 服务：review-mcp（stdio 模式）
- 触发场景：长时评审（10~20分钟级别）

**验收标准**：

- [ ] design 场景评审不再出现 `-32001` 超时
- [ ] implementation 场景评审不再出现 `-32001` 超时
- [ ] 超时治理策略有明确记录（非仅“延长固定超时”）
- [ ] 端到端测试必须通过
---
**方案选择记录 [2026-02-19]**（OpenCode客户端修复优先）：
- 用户选择：方案1
- 核心思路：仅改 OpenCode 客户端，补齐 `callTool` 进度回调链路，确保注入 `progressToken`，让服务端心跳能够持续续时。
- 硬约束：不依赖“固定拉长超时”作为主策略；必须覆盖 design/implementation 两类场景。
- 下一步：进入技术方案设计（`design-plan BUG-001`）

**估算点数**：3
