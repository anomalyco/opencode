Architecture

KanCode is a TUI/CLI AI coding agent — a Bun monorepo fork of OpenCode with Effect-domain services, typed HttpApi, dual LLM backends, and KanCode-branded user config while keeping OpenCode project compatibility.

Overview Package layers Packages Runtime LLM Tools & permissions Config Codegen Stack kancode layout

Product overview

Mental model: Bun TUI/CLI shell (packages/kancode → bin kancode) around Effect domain Core + typed Protocol/Server API, with Schema contracts, dual LLM backends, Drizzle SQLite persistence, and OpenCode-compatible project config under a KanCode-only user home.

Surfaces

Primary UX is the terminal TUI (bun dev). CLI commands cover run, serve, MCP, ACP, models, session, db, and plugins. There is no app / desktop / web / console package in this fork.

Agents

default — full-access development. plan — read-only exploration (denies edits; asks before bash). @general — internal multistep subagent.

Package dependency layers

Runtime direction: Schema → Core and Schema → Protocol → Server. Client may depend on Schema and Protocol but never Core or Server at runtime. sdk-next composes Client, Core, and Server for an in-process host.

Runtime: request path

User prompts enter through TUI or CLI, hit the HttpApi server (or in-memory sdk-next transport), then Session + Processor. Persistence is Core SQLite. LLM events converge on one stream whether AI SDK or native runtime handled the turn.

LLM routing

packages/kancode/src/session/llm.ts owns auth, config, model resolution, plugins, and runtime selection. Adapters live under session/llm/:

  • ai-sdk.ts — AI SDK fullStream → shared LLMEvents (default)
  • native-request.ts — session input → @kancode/llm LLMRequest
  • native-runtime.ts — gate, tool bridge, LLMClient handoff

Native path is opt-in via OPENCODE_EXPERIMENTAL_NATIVE_LLM=true (or umbrella experimental). Supports selected OpenAI / OpenAI-compatible / Anthropic API-key routes; unsupported cases fall back to AI SDK. Tool execution stays opencode/core-owned on both paths.

Tools, permissions, database

Tools

Canonical type: Tool.make in packages/core/src/tool/. Application registrations are process-scoped; location-scoped registry overlays win. Built-ins (bash, edit, write, grep, glob, LSP, plan, …) live under packages/kancode/src/tool/. Settlement and model-output bounding happen in the registry; authorization stays in each leaf via PermissionV2.

Permissions

Schema contracts for permission modules and saved decisions; Core owns SQL and runtime modules. Agents like plan deny edits and ask before bash through config rules.

Database

Owned by @kancode/core: Drizzle schemas (*.sql.ts), migrations under packages/core/src/database/migration/, SQLite via Bun/Node with @kancode/effect-drizzle-sqlite as the Effect adapter. Session / message / event / project / credential tables evolve through dated migrations.

Config merge
