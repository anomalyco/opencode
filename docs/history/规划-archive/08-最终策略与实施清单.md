# 08 — 最终策略与实施清单

## 最终策略(已确定)

**双轨并行**:

### 轨道 1 — 撰写 issue,探 sst 官方态度

目的: 让官方知道这个需求,争取未来合入主线,长期用户规模零维护。

### 轨道 2 — 自己做 fork 版本,服务自己 + 小范围人群

目的: 立刻能用、立刻能分享给几个朋友/同事/内部团队。不追求"很多普通用户"级别的分发。

**关键决策**: 因为是"自己或小范围"而不是"很多普通用户",**大幅砍掉分发侧成本**:

| 原来给大众分发要做 | 小范围版本要不要 |
|---|---|
| EV 代码签名证书 (¥3000-8000/年) | ❌ 不要。用户首次跑点"仍要运行"即可 |
| 自动更新 server | ❌ 不要。手动升级,发版时群里发包 |
| CDN 托管 | ❌ 不要。阿里云盘 / GitHub Release / 自建 HTTP 服务器都行 |
| 品牌替换(避开 OpenCode logo/名字) | 🟡 小范围内部不强求,公开分享要避 |
| 用户支持 | ❌ 群里答疑即可 |

**省下的成本**: 年均 ¥5000+ + 多人力维护;**只剩"跟随上游 rebase"的开发时间成本**。

## 轨道 1 实施清单 — 写 issue 探官方态度

### fork + PR 机制说明

```
sst/opencode (官方主仓)
    ↑ Pull Request (PR)
    │
  your-username/opencode (你的 fork)
    │
  你在 fork 里写 feature/editable-viewer 分支,改代码
    ↓
  提 PR → sst 维护者 review → 同意 → merge 到官方
```

**两种场景**:
- **在 fork 里改,不提 PR**: 自己维护分支,每次官方更新要自己 rebase,永远跟官方并行
- **在 fork 里改,提 PR 给 sst**: 是否被合入取决于维护者看改动是否符合产品理念、代码质量等。文件查看器可编辑是较大的架构级改动,合入门槛较高。

**为什么 PR 路线可能是最优解**: 如果 PR 被合入,分发问题直接消失 —— 所有官方用户自动获得功能,你不用签名/不用搭更新 server/不用 CDN/不用长期 rebase fork。

**合入周期不可控**: 2 周到永不合入都有可能。实战最优策略是"三步走"(见下)。

### 三步走策略

**1. 立刻**: 在 sst/opencode 提 issue/discussion,描述"File Tab Content 可编辑"的需求和方案草图,探维护者态度。成本 1 天。

**2. 等态度期间 / 维护者不反对时**:
- 发布插件 P1(调外部编辑器)作为过渡版本给普通用户,解决燃眉之急。成本 2 天。
- 同时在 fork 里做 MVP 开发(Phase 0-2),准备提 PR。

**3. PR 结果**:
- ✅ 合入 → 几周后官方版带上此功能,插件作为老用户的降级选项保留,分发问题彻底解决
- ⏳ 修改中 → 插件 P1 继续服务,PR 继续迭代
- ❌ 被拒 → 插件 P1 是长期方案;fork 版自用;或改成"独立伴生编辑器"

这个路线把所有方案组合成一个渐进策略,每一步都有成果,失败成本有限。

### 1.2 写 issue 初稿(建议结构)

```markdown
Title: Feature Request: Editable mode for File Tab Content / Text File Viewer

## Background
Currently, when opening a file in the right-side Session Side Panel,
the Text File Viewer (powered by @pierre/diffs) is read-only with
optional line comments. This is great for AI-reviewed changes and
discussion, but limits the app's usefulness when users just want to
make a quick edit (e.g., fix a typo in a .md note).

## Proposal
Add an "edit" mode toggle in FileTabContent. When enabled:
- Replace the PierreFile-rendered viewer with a lightweight CodeMirror 6 editor
- Hide the Line Comment Layer (line anchors become unstable during edit)
- Show Save / Cancel buttons with dirty indicator
- On save, write through a new Tauri command `write_text_file`

Review tab remains untouched — diff views stay read-only.

## Use cases
- Quick .md edits without context-switching to VS Code
- Adjusting small files the AI generated before moving on
- Typo fixes in notes / configs / docs

## Open questions
1. Should edit mode be feature-flagged or always available?
2. How to handle conflict when AI's Write tool modifies the same file
   during an edit session? (My suggestion: mtime check + conflict dialog)
3. Are there stability concerns with mounting CodeMirror alongside
   SolidJS reactive system?

Happy to submit a PR if this aligns with the roadmap.
```

## 轨道 2 实施清单 — fork + 小范围分发

### Phase 0 — 独立 prototype(不动 opencode)

**目录**: `D:\project\opencode-editable-prototype`

**目标**: 验证"SolidJS + CodeMirror 6 + Tauri write_text_file"链路。

**步骤**:
1. `bun create solid` → TypeScript template
2. 装 CodeMirror 6 依赖(`@codemirror/state` `@codemirror/view` `@codemirror/commands` `@codemirror/lang-markdown` `@codemirror/lang-javascript` `@codemirror/language`)
3. `bun add @tauri-apps/api @tauri-apps/cli` + `bun tauri init`
4. 写最小页面: 文件路径输入 + 加载按钮 + CodeMirror 区 + 保存按钮
5. Rust 两个 command:
   ```rust
   #[tauri::command]
   fn read_text_file(path: String) -> Result<String, String> {
       std::fs::read_to_string(&path).map_err(|e| e.to_string())
   }
   #[tauri::command]
   fn write_text_file(path: String, content: String) -> Result<(), String> {
       std::fs::write(&path, content).map_err(|e| e.to_string())
   }
   ```

**验收**:
- [ ] CodeMirror mount/unmount 100 次无 DOM 泄漏
- [ ] .md 加载有高亮
- [ ] 中文输入法候选词正常
- [ ] 5MB 文件流畅
- [ ] 保存后磁盘内容确实改变

**预计**: 0.5-1 天

**核心逻辑伪代码**(详见 02 文档):
```tsx
// FileTabContent
const [editing, setEditing] = createSignal(false)
const [draft, setDraft] = createSignal<string | null>(null)
const dirty = () => draft() !== null && draft() !== contents()

<Toolbar>
  <Show when={!editing()} fallback={<><SaveBtn/><CancelBtn/></>}>
    <EditBtn disabled={isBinary(path) || tooLarge(size)}/>
  </Show>
</Toolbar>

<Show when={editing()} fallback={renderFile(contents())}>
  <CodeMirrorView value={contents()} language={langFromExt(path)} onChange={setDraft}/>
</Show>
```

**防呆**(必做):
- 二进制文件禁用编辑按钮(png/jpg/exe/zip 等)
- 文件 > 10MB 禁用(避免 CodeMirror 卡死)
- 只读文件(Windows readonly attribute)禁用
- dirty 切 tab / 关 tab / 关程序 → 弹未保存提示

**预计**: 2-4 天

### Phase 3 — 保存 + 冲突处理

**Rust command**:
```rust
#[tauri::command]
async fn write_text_file(path: String, content: String) -> Result<(), String> {
    tokio::fs::write(&path, content).await.map_err(|e| e.to_string())
}
```

**前端 save handler**:
- 调 `invoke("write_text_file", { path, content })`
- 成功 → `setEditing(false); setDraft(null); await refetchFile(path)`
- 失败 → 显示错误,编辑内容保留

**冲突处理(v1 简化版)**:
- 加载时记录 mtime
- 保存前读当前 mtime,不一致 → 弹对话框:
  - "磁盘上的文件被修改了。[覆盖] [取消并重新加载]"

**预计**: 1-2 天

### Phase 5 — 长期维护

**固定动作**:
- 每 2-4 周 `git fetch upstream dev && git rebase upstream/dev`
- 每次官方更新后 `bun run tauri build` 出新包发群
- 观察官方是否合入自己的 PR(轨道 1),若合入 → 宣布停止维护 fork,用户迁回官方
