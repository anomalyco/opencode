# 04 — 风险与备选方案

## 阻塞风险分级

| 风险 | 概率 | 严重度 | 触发时机 | 应对 |
|---|---|---|---|---|
| `@pierre/diffs` 拉不到 | 高 | 致命 | Phase 1 第一次 `bun install` | Plan B(下方) |
| 上游版本快迭代,fork 落后 | 必然 | 中-高 | 1-3 个月后 | 持续 rebase 或放弃 fork |
| Windows SmartScreen 拦截 | 必然(不签名) | 致命(对分发) | 用户首次运行 | 买 EV 签名证书 |
| 自动更新链路被官方覆盖 | 中 | 高 | 任何时候 | 改 Tauri Updater 配置指向自家 server |
| AI 同时改文件冲突 | 中 | 中 | 用户日常使用 | mtime 检查 + 冲突 UI + 自动备份 |
| 大文件 / 二进制误编辑 | 低-中 | 中 | 用户点错 | 文件大小阈值 + 二进制检测 |
| opencode 登录态在 fork 失效 | 未知 | 中-高 | Phase 1 跑 fork 时 | 看官方 identity 包实现,可能要本地 mock |
| Rust toolchain 装不上 | 低 | 中 | Phase 1 | 跟 sst 官方 README 走 |

## Plan B — 如果 `@pierre/diffs` 拉不到

**前提**: Phase 1 `bun install` 报 401/404,无法获取 `@pierre/diffs`。

**思路**: 把 `packages/ui/src/components/file.tsx` 整个换成基于 CodeMirror 6 的实现,review tab 也用 CodeMirror 的 merge view 替代 PierreFile 的 diff 渲染。

**改造点**:
1. 重写 `packages/ui/src/components/file.tsx`:
   - `<TextFile>`: CodeMirror EditorView,默认 `EditorView.editable.of(false)` 模拟只读
   - `<DiffFile>`: 用 `@codemirror/merge` 的 `MergeView` 渲染 diff
2. 适配现有的 `annotations / selectedLines / commentedLines / onLineNumberSelectionEnd` 接口:
   - selectedLines: CodeMirror 的 selection API
   - commentedLines: CodeMirror Decoration 加背景色
   - onLineNumberSelectionEnd: 监听 gutter mousedown/mouseup
3. 行评论叠层 (`line-comment.tsx`) 适配新的行高度计算

**额外工作量**: +2-3 周。整体 MVP 从 2-3 周变成 4-6 周。

**风险**: 跟上游 rebase 时几乎所有 file 相关改动都会 conflict,长期维护成本翻倍。

## Plan C — 完全不 fork 的路径

### C1. 插件 + 外部编辑器跳转 ⭐

**架构**: 参考 `D:\project\getbot-plugins\getbot-opencode`

**实施**:
```
opencode-edit-plugin/
├── 一键安装.bat
├── 一键卸载.bat
├── install.mjs
├── plugins/edit.js          # 注册 /edit 命令
└── 使用说明.txt
```

`edit.js` 伪代码:
```js
export default {
  commands: {
    edit: {
      description: "在外部编辑器打开当前选中文件",
      handler: async (ctx) => {
        const path = ctx.activeFile?.path
        if (!path) return ctx.reply("没有选中文件")
        // 优先 VS Code,fallback 到 notepad
        const cmd = await which("code") ? `code "${path}"` : `notepad "${path}"`
        exec(cmd)
      }
    }
  }
}
```

**优点**:
- 0 编译,1-2 天可分发
- 跟随官方更新
- 用户熟悉的编辑体验

**缺点**:
- 不在文件查看器内,要切窗口
- 用户得装 VS Code 或接受 notepad

### C2. Userscript 注入(WebView2)

**架构**: 写一个外部小工具,通过 WebView2 调试协议注入 JS 到 opencode 进程,把红框 DOM 设 `contenteditable="true"`,监听 input 事件用 Tauri sidecar 写文件。

**优点**: 不动 opencode 任何文件,跟随官方更新
**缺点**:
- 极不稳定(opencode 任何 DOM 改动就崩)
- WebView2 调试端口默认关,需要修改启动参数
- 反作弊嫌疑,违反 ToS 风险
- 普通用户根本装不上
- ❌ **不推荐**

### C3. 给 sst 提 PR

**做法**: 在自己 fork 上做完 Phase 0-2 的核心改动,提 PR 到 sst/opencode。

**优点**: 合入后所有用户受益,你不用维护
**缺点**: 周期不可控(2 周到不被接受都有可能),需要符合官方代码风格

### C4. 独立伴生编辑器 app

**做法**: 用 Tauri / Electron 独立写一个 mini editor,跟 opencode 共享 `~/.config/opencode/sessions/` 数据目录,可以读 opencode 当前打开的文件路径。

**优点**: 完全自主
**缺点**: 用户要装两个程序,体验割裂

## 路径选择决策树

```
是否目标"分发给很多普通用户"?
├─ 否 (自己用 / 几个开发者)
│   └─ 走 02-改造方案.md 的 fork 路线
│
└─ 是
    ├─ 接受"跳出去编辑"体验?
    │   └─ ✅ 选 Plan C1(插件 + 外部编辑器)
    │
    ├─ 必须"文件查看器内编辑"且预算充足(¥3-5万 + 长期维护投入)?
    │   ├─ Phase 1 验证 @pierre/diffs 能拉
    │   │   ├─ 能 → 走 02 方案
    │   │   └─ 不能 → 走 Plan B(重写 file.tsx)
    │   └─ + 必须做: 签名、自动更新、品牌替换、用户支持
    │
    └─ 想推动官方支持?
        └─ 选 Plan C3(提 PR / issue)
```
