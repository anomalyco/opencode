# 06 — 插件方案能否实现"文件查看器可编辑"

## 一句话结论

**不能**。opencode 插件机制**没有任何往桌面 app WebView 前端注入 UI / 改 DOM / 覆盖文件查看器的能力**。这是插件 API 层面的硬限制,不是绕得过去的。

## 证据

### 证据 1 — 官方 docs (opencode.ai/docs/plugins/) 明确列出插件能力

插件**能做**:
- Hook 进各种事件: command / file / installation / LSP / message / permission / server / session / todo / shell / tool / TUI
- 拦截工具执行 (`tool.execute.before` / `tool.execute.after`)
- 注册自定义工具(给 AI 调用)
- 注入 shell 环境变量
- 发系统级通知
- 修改 session 压缩行为
- 监听 session 生命周期(created / updated / deleted / compacted)
- 结构化日志

跟前端最相关的 hook 只有 3 个,**全部是 TUI(终端 UI)级**,跟桌面 app 的 WebView 完全无关:
- `tui.prompt.append` — 往 prompt 里追加内容
- `tui.command.execute` — 触发命令
- `tui.toast.show` — 弹 toast

**官方 docs 原话**: 没有任何 API 能创建自定义面板、改文件查看器、或往桌面 app 注入 React/Web 组件。

### 证据 2 — 你本机现有插件 `getbot.js` 印证了这个边界

`C:\Users\yuexi\.config\opencode\plugins\getbot.js` 的实现方式:
- `import { tool } from "@opencode-ai/plugin"` — 注册的是 sidecar 端的 AI 工具(getbot_image / getbot_tts / getbot_asr / getbot_md2html)
- TUI 部分: 命令面板条目(切模型、刷新模型列表) + Ctrl+Shift+V 全局快捷键(语音输入)
- **没有一行代码碰前端 DOM**,因为根本碰不到

### 证据 3 — 架构层面隔离

opencode 桌面是**两个进程**:
1. **Tauri 壳 + WebView2(前端)** — 渲染 UI,加载 `@opencode-ai/app`(SolidJS)
2. **opencode-cli sidecar(Node.js)** — 跑业务逻辑、AI 调用、文件 IO

**插件运行在 sidecar 进程,通过 HTTP/IPC 跟前端通信**,没有 IPC 通道允许插件:
- 把 JS 推到 WebView 执行
- 注册 SolidJS 组件
- 替换 file viewer 实现
- 改右侧面板 layout

要绕过这层隔离,只有两种路径,**都不属于"插件"**:
- 改前端源码 → 必须 fork(回到方案 02)
- 用 WebView2 调试协议外挂注入 JS → 不稳定 + 违反 ToS,见 04 文档 Plan C2

## 插件能做的"接近编辑"的方案(都需要跳出红框)

### 方案 P1 — `/edit` 斜杠命令调外部编辑器 ⭐

```js
// ~/.config/opencode/plugins/edit-current.js
import { tool } from "@opencode-ai/plugin"
import { spawn } from "node:child_process"

export const EditCurrentPlugin = async () => ({
  // 注册 TUI 命令:在命令面板搜 "edit"
  "tui.command.execute": async ({ args }) => {
    if (args[0] !== "edit") return
    const path = args[1]  // 用户传文件路径,或从 session 上下文拿
    if (process.platform === "win32") {
      spawn("cmd", ["/c", "code", path], { detached: true, stdio: "ignore" }).unref()
    } else {
      spawn("code", [path], { detached: true, stdio: "ignore" }).unref()
    }
  },
})
```

**用户体验**: 命令面板里输 `edit foo.md` → VS Code 弹出来 → 改完 ctrl+s → opencode 自带的 file watcher 自动刷新右侧 tab。

**需要解决**: 怎么拿到"当前在右侧 tab 打开的文件路径"?
- 插件能拿到 session 上下文,但**不一定能拿到 UI 当前焦点的 file tab** — 前端 WebView 的 UI 状态对 sidecar 不可见
- 折中: 让用户手动输入路径,或从 session 最近读过的文件列表里选

### 方案 P2 — 注册一个 AI 工具 `open_in_editor`

```js
import { tool } from "@opencode-ai/plugin"

tool({
  name: "open_in_editor",
  description: "在外部编辑器打开文件供用户手动编辑",
  parameters: { path: { type: "string" } },
  execute: async ({ path }) => {
    spawn("code", [path], { detached: true }).unref()
    return `已在 VS Code 打开 ${path},编辑后保存即可`
  },
})
```

**用户体验**: 跟 AI 说"帮我编辑 foo.md",AI 调这个工具弹出 VS Code。

**优点**: 自然语言驱动,用户不用记命令。
**缺点**: 多绕一层 AI。

### 方案 P3 — 全局快捷键监听 + 当前文件感知

参考 getbot.js 的 Ctrl+Shift+V 实现,注册一个 Ctrl+Shift+E:
- 按下 → 弹 OS 文件选择对话框 / 或读取一个临时约定文件(由 session 写入)/ 或调起命令面板
- 选好文件后调 VS Code

**复杂度**: 比 P1 高,但用户体验更"无缝"。

## 工程量(插件方案 P1)

| 项 | 时间 |
|---|---|
| 写 plugin 主体 | 半天 |
| 适配 getbot-opencode 安装包模板 | 半天 |
| 跨平台测试(Windows / macOS) | 半天 |
| 文档 + zip 分发包 | 半天 |
| **合计** | **2 天** |

签名 / 自动更新 / CDN: **零成本**(用户解压跑安装脚本,跟现有 getbot-opencode 一样)。

跟随官方版升级: **自动跟随**(插件不锁版本,opencode 自更新不影响插件)。

| 工程量 MVP | 2 天 | 2-3 周 |

## 最终建议

**给"很多普通用户"分发,选插件方案 P1**。失去的那 2/10 体验(切窗口)换来的是:
- 永远跟随官方版本
- 零年维护成本
- 用户出问题,问题域很小(只是个调起命令的脚本)
- 你不用接 opencode 本身的客服压力(账号/付费/AI 等问题都是官方的)

**坚持要"文件查看器内编辑"只在以下条件下成立**:
- 个人 / 小团队自用,不分发
- 或愿意把维护这个 fork 当一个长期产品做

不存在"插件 + 文件查看器内编辑"这个第三种可能。
