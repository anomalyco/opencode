# 07 — 外部程序就地改造已装 opencode 的可行性

## 术语统一(从本文档开始)

| 用语 | 指代 |
|---|---|
| **Session Side Panel(会话侧边面板)** | 截图整个红框范围 |
| **File Tabs(文件标签栏)** | 红框顶部的 tab 条(审查 / 公司信息.txt / 临时性问题.md / +) |
| **File Tab Content(文件标签内容区)** | 每个文件 tab 下方的内容显示区 |
| **Text File Viewer(文件查看器)** | 真正渲染文件内容的 SolidJS 组件,源码在 `packages/ui/src/components/file.tsx` 的 `<TextFile>`,底层是 `@pierre/diffs` 的 `PierreFile` |
| **Line Comment Layer(行评论层)** | 浮在文件查看器上的行内评论叠层 |

**改造目标**: 把 **Text File Viewer** 从只读改为可编辑。

## 核心问题

用户想知道: **能不能写一个外部程序,让已经安装好的官方 opencode 实现 Text File Viewer 可编辑**,而不需要 fork 或重新打包?

## 整体结论

**不能稳定地做到**。每条技术路径都有阻塞性问题,要么是工程不可行,要么是分发不可行。下面逐条分析。

## 路径 A — 解包并 patch 已装的 OpenCode.exe

**思路**: 解开 `D:\Program Files\OpenCode\OpenCode.exe`,定位到内嵌的前端 JS bundle,字符串替换或注入新 JS,重新打包。

**技术细节**:
- Tauri 把前端资源(HTML/JS/CSS)用 `tauri-bundler` 嵌到 binary 的 PE section 里
- 现代 Tauri 版本(v2)有资源完整性校验,binary 改了启动会校验失败
- 即使绕过校验,改完 binary 数字签名失效,Windows SmartScreen / 防病毒会拦
- 重新签名需要 patch 工具自带的 EV 证书(等于又回到代码签名问题)
- opencode 频繁更新(本机已见 1.4.x 到 1.14.20 多个版本),每次官方更新后 patch 工具要适配新 bundle 结构,**等于把 fork 维护负担换成了 patch 适配负担**

**对"分发给普通用户"的可行性**:
- 用户首次跑 patch 工具会触发 SmartScreen + 杀毒(因为它在改另一个签名 exe)
- 官方自动更新会覆盖回原版,patch 失效 → 用户每次升级都要重新跑工具
- 工程复杂度: 高于 fork 路线
- 合规风险: 修改他人签名二进制,跟 sst 商业产品的 ToS 可能冲突

**结论**: ❌ 技术上勉强可做,**实际分发不可行**。

## 路径 B — DLL 注入 / API hook

**思路**: 写一个 Windows DLL,用 EasyHook / Detours 等技术注入到 OpenCode.exe 进程,hook 它对 WebView2 的调用,在合适时机往 WebView 里 evaluate 一段 JS,把 Text File Viewer 替换成自定义编辑器。

**技术细节**:
- 注入需要管理员权限或 LoadLibrary 注入器
- WebView2 的 `ICoreWebView2::ExecuteScript` 是 COM 接口,hook 难度高
- 即便注入成功,opencode 前端 SolidJS 任何 DOM 变化都会让你的 patch 失效
- DLL 注入器在 Windows Defender 眼里就是恶意行为,99% 会被实时防护拦截

**对"分发给普通用户"的可行性**:
- 杀软误报率极高
- 普通用户不会关闭 Defender 或加白名单
- 跟外挂同质,有 ToS 和合规风险

**结论**: ❌ 不可行。

## 路径 C — WebView2 远程调试协议外挂

**思路**: 让 OpenCode.exe 启动时把 WebView2 远程调试端口打开(`--remote-debugging-port=9222`),然后写一个外部程序通过 Chrome DevTools Protocol 连上去,在 WebView 内 evaluate JS,替换 Text File Viewer。

**技术细节**:
- WebView2 默认**不开**远程调试
- Tauri 通过 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 环境变量可以传参给 WebView2
- 用户需要每次用包装脚本启动 OpenCode(设环境变量后再启动 .exe)
- 即便开了调试端口,注入的 JS 跟 SolidJS 反应式系统是两套体系,SolidJS 重新渲染就会冲掉你的改动
- 要稳,需要 monkey-patch SolidJS 的 createMemo / createEffect,极度脆弱
- opencode 任何前端版本变化就要重写 patch

**对"分发给普通用户"的可行性**:
- 用户要改启动方式(不能直接双击桌面图标)
- 维护成本高于 fork
- 调试端口开着是潜在安全问题(本机任何进程都能连进去操作 WebView)

**结论**: ❌ 不可行。

## 路径 D — UI 自动化(RPA / Win32 模拟)

**思路**: 用 PyAutoGUI / Win32 SendInput / Microsoft UI Automation 模拟键鼠操作,实现"伪编辑"。

**技术细节**:
- WebView2 内部 DOM **不暴露给 UIA**(只暴露 WebView2 这一个控件)
- 看不到行号、看不到文字位置,无法精准操作
- 只能"复制全文 → 弹外部窗口编辑 → 写回",但要回写还得自己起编辑器,等于 P1 插件方案的下位替代

**结论**: ❌ 不可行。

## 路径 E — 旁路监听 + 跳出去编辑(实质=插件方案)

**思路**: 写一个外部程序,通过 opencode 自己暴露的 sidecar HTTP API 监听当前选中的文件,弹外部编辑器,改完写回。

**技术细节**:
- opencode sidecar 有 HTTP API(主要给前端用),理论上外部程序也能调
- 但**外部程序拿不到"用户正在 File Tabs 里看哪个文件"** — 这是前端 UI 状态
- 等于绕一大圈做的还是"调外部编辑器"

**结论**: 🟡 能做,但等价于插件方案 P1,没有比插件更优势,反而失去插件的命令面板集成。

## 路径 F — 补丁包形式分发

思路: fork 完 opencode,但不让用户重新装大包,做一个小工具下载 patch.bin 替换/合并到安装目录。

技术细节:
- Tauri 资源全嵌入 binary,patch.bin 实际就是新的 OpenCode.exe(几十 MB)
- "补丁"等于"全量替换"
- 完整性校验 + 签名问题同路径 A
- 自动更新被官方覆盖问题同路径 A

结论: ❌ 跟路径 A 等价,只是换了包装。

## 路径横向对比

| 路径 | 阻塞点 |
|---|---|
| Patch OpenCode.exe binary | Tauri 资源完整性校验 + 签名失效 + 官方更新覆盖 + 杀软告警 |
| DLL 注入 / API hook | Windows Defender 实时拦截,普通用户安装即失败 |
| WebView2 远程调试外挂 | 调试端口默认关 + 注入 JS 跟 SolidJS 反应式系统冲突 + 安全风险 |
| UI 自动化(RPA) | WebView2 内 DOM 不暴露给 UIA,看不到行号/位置 |
| 旁路监听 + 跳外部 | 等价于插件 P1,反而失去命令面板集成 |
| 补丁包形式 | 实质就是替换 binary,问题同 patch |

## 横向对比

| 路径 | 技术可行 | 分发可行 | 维护成本 | 杀软友好 | 合规 |
|---|---|---|---|---|---|
| A. patch binary | 勉强 | ❌ | 极高 | ❌ | ⚠️ |
| B. DLL 注入 | 是 | ❌ | 高 | ❌❌ | ❌ |
| C. WebView2 远程调试 | 是 | ❌ | 极高 | ⚠️ | ⚠️ |
| D. UI 自动化 | ❌ | — | — | — | — |
| E. 旁路+外部编辑 | ✅ | ✅ | 低 | ✅ | ✅ |
| F. 补丁包 | = A | ❌ | 极高 | ❌ | ⚠️ |
| **fork(02)** | ✅ | 🟡 | 高 | 需要签名 | ✅ |
| **插件 P1(06)** | ✅ | ✅ | ~0 | ✅ | ✅ |

## 最终判定

针对"用外部程序改造已装 opencode 实现文件查看器内可编辑"的命题:

> ❌ **不存在能稳定分发给普通用户的方案**

## 三难悖论

**"文件查看器内原地编辑 + 分发给普通用户 + 不 fork" — 这三个目标不可能同时成立，必须放弃一个。**

| 放弃哪个 | 走什么方案 | 后果 |
|---|---|---|
| 放弃"文件查看器内" | 插件 P1(跳外部编辑器) | ⭐ 最优解。零维护、自动跟随官方、普通用户友好 |
| 放弃"分发普通用户" | 自己 fork 或自己 patch | 你一个人用，体验完整 |
| 放弃"不 fork" | 方案 02(fork + CodeMirror) | 高维护成本、要签名、要自更新服务器 |

## 我的推荐

**保持插件方案 P1 作为分发版本**,你自己机器上想体验"文件查看器内编辑"可以单独跑一份本地 fork 自用。这是技术现实下的最优组合。
