# 09 — 改动规则（大型项目防误伤指南）

> **核心问题**：opencode 是大型项目（fork 后约数百个文件），改动稍有不慎会波及无关模块，导致整体崩溃。
> **本规则的目的**：用**机制护栏**（不是约定）把误伤风险压到最低，每次改动可追溯、可回滚、可定位。
> **核心原则**：信任建立在机制上，不在意愿上。任何"我会小心"的承诺都不算护栏。

---

## 1. 适用范围

| 场景 | 是否适用 |
|---|---|
| `opencode-fork/` 改动（Phase 1+） | ✅ **强制适用** |
| `opencode-plan/` 仓库自身改动（规划文档） | ⚠️ 简化版（只走 baseline tag + 改动日志） |
| `prototype/` 改动（Phase 0） | ⚠️ 简化版（从零写，无"无关地方"破坏，但仍需 改动日志） |

下文规则若未标注，默认指 **fork 改动**。

## 3. baseline tag 策略

任何"可能改坏"的动作之前，必须先打 tag。打 tag = 0 成本，回退 = 1 命令。

### 3.1 tag 命名规范

| 时机 | 命名 | 例 |
|---|---|---|
| upstream 克隆完 | `upstream-baseline` | — |
| 进入新 Phase 前 | `pre-phase-<N>` | `pre-phase-2` |
| 大改动前 | `pre-<动作>-<日期>` | `pre-cm-integration-2026-04-25` |
| 每次 rebase upstream 前 | `pre-rebase-<日期>` | `pre-rebase-2026-05-01` |
| 里程碑完成后 | `<里程碑名>` | `phase-2-cm-mounted` |

### 3.2 标准回退流程

```bash
# 出问题，回到上一个 tag
git status                          # 确认当前状态
git stash                           # 保存有用的未提交改动（可选）
git reset --hard <tag-name>         # 硬回退到 tag
git stash pop                       # 恢复未提交改动（如果之前 stash 了）
```

### 3.3 tag 清理

`pre-*` 前缀的 tag 在确认安全后保留至少 30 天，之后可批量删除。
里程碑 tag（`phase-*`、`upstream-baseline`）永不删除。

### 3.4 上游同步与协作架构 → 见 12

跟随上游升级 + 自有开发 + 维护成本最低,这三件事的协作规范单独成文,见 [`12-fork-跟随升级与协作规范.md`](12-fork-跟随升级与协作规范.md):

- **节奏**:默认被动按需 cherry-pick + 季度强制基线对齐
- **元原则**:稳定 > 简洁 > 一切;不分层、不双套、不双轨;一套界面一套规范
- **五条设计原则**(P1-P5):隔离 / 配置化 / 适配层 / 可逆 / 显性化(改上游必加 `// FORK:` marker)
- **三个健康指标**:fork 偏离指数 < 5% / 漂移 commit ≤ 100 / override 累计 ≤ 2/季

## 4. 自动化护栏（pre-commit / pre-push hook）

> 安装位置：`opencode-fork/.git/hooks/pre-commit` 和 `pre-push`。
> 这些 hook 不会跟着 git clone 走，每次 fork 后必须重新装一次。
> 推荐放一份 `scripts/install-hooks.sh` 在 fork 仓内，一键安装。

### 4.1 pre-commit 白名单检查

> **2026-04-23 更新**：白名单 / 黑名单基于 `anomalyco/opencode dev` 分支真实结构（clone `upstream-baseline` 时核对的 20 个 packages）重写。

**目的**：staged 文件路径碰到黑名单 → 拒绝 commit。

**白名单**（允许改）:
```
packages/app/src/pages/session/         # file-tabs.tsx 主战场
packages/app/src/components/            # 新增 code-mirror-view.tsx
packages/app/src/utils/                 # 新增 lang-from-ext.ts
packages/app/src/addons/                # CodeMirror addon 候选位置
packages/app/package.json               # 仅追加 CodeMirror 依赖
packages/desktop/src-tauri/src/         # 整个目录（lib.rs + 新增 commands.rs）
packages/desktop/src-tauri/Cargo.toml   # 仅追加依赖
packages/desktop/package.json           # 仅追加依赖
改动日志.md
scripts/install-hooks.sh                # 自己加的 hook 安装脚本（例外）
.gitattributes / .editorconfig          # 跨平台配置
```

**黑名单**（禁改 / 改前必须显式 override）:

opencode 实际有 20 个 packages（`app` `console` `containers` `desktop` `desktop-electron` `docs` `enterprise` `extensions` `function` `identity` `opencode` `plugin` `script` `sdk` `shared` `slack` `storybook` `ui` `web`），除了 `app` 和 `desktop` 我们要改，**其他 17 个全部黑名单**。

```
packages/console/       packages/containers/    packages/desktop-electron/
packages/docs/          packages/enterprise/    packages/extensions/
packages/function/      packages/identity/      packages/opencode/   ← 核心，绝对不动
packages/plugin/        packages/script/        packages/sdk/
packages/shared/        packages/slack/         packages/storybook/
packages/ui/            packages/web/

packages/desktop/src-tauri/tauri.*.conf.json   # 构建配置敏感
packages/desktop/src-tauri/build.rs
packages/desktop/src-tauri/capabilities/        # 安全权限配置
packages/desktop/src-tauri/icons/               # 品牌资源
packages/desktop/src-tauri/entitlements.plist   # macOS 签名

.github/                scripts/ (除 install-hooks.sh)   bunfig.toml
*.config.{ts,js,mjs}    package.json (根)                bun.lock
tsconfig.json (根)      flake.lock                       LICENSE
```

**hook 脚本骨架**（`pre-commit`）:
```bash
#!/usr/bin/env bash
set -e

BLACKLIST_REGEX='^(packages/(console|containers|desktop-electron|docs|enterprise|extensions|function|identity|opencode|plugin|script|sdk|shared|slack|storybook|ui|web)/|packages/desktop/src-tauri/(tauri\..+\.conf\.json|build\.rs|capabilities/|icons/|entitlements\.plist)|\.github/|bunfig\.toml$|.*\.config\.(ts|js|mjs)$|^package\.json$|^bun\.lock$|^tsconfig\.json$|^flake\.lock$|^LICENSE$)'
SCRIPTS_ALLOWED='^scripts/install-hooks\.sh$'

violations=$(git diff --cached --name-only | grep -E "$BLACKLIST_REGEX" || true)
# scripts/ 黑名单的特例：install-hooks.sh 允许
scripts_violations=$(git diff --cached --name-only | grep -E "^scripts/" | grep -vE "$SCRIPTS_ALLOWED" || true)

if [ -n "$violations" ] || [ -n "$scripts_violations" ]; then
  echo "❌ pre-commit: 以下文件在黑名单内，禁止 commit:"
  [ -n "$violations" ] && echo "$violations"
  [ -n "$scripts_violations" ] && echo "$scripts_violations"
  echo ""
  echo "如果确认要改，请用: git commit --no-verify -m '... [override-blacklist: 理由]'"
  echo "且必须在 改动日志.md 显式记录 override 理由。"
  exit 1
fi

echo "✅ pre-commit: 文件路径白名单检查通过"
```

### 4.2 diff 体量阈值

**默认阈值**：单 commit `git diff --cached --shortstat` 改动行数 ≤ 200 行。

**超阈值动作**：hook 拒绝并提示拆 commit；显式 `--no-verify` 时必须在 commit 信息标注 `[large-diff: <理由>]`。

**hook 脚本骨架**（追加到 pre-commit）:
```bash
DIFF_LINES=$(git diff --cached --shortstat | awk '{print $4+$6}')
THRESHOLD=200

if [ "${DIFF_LINES:-0}" -gt "$THRESHOLD" ]; then
  echo "⚠️  pre-commit: 本次 staged diff = ${DIFF_LINES} 行，超过 ${THRESHOLD} 行阈值"
  echo "请考虑拆分 commit。如确实必要，用 --no-verify + commit 信息加 [large-diff: 理由]"
  exit 1
fi
```

### 4.3 强制 feature 分支(2026-04-30 起**正式废除**)

> ⚠️ **本节于 2026-04-30 正式废除**,理由如下:
>
> 1. **该规则文档写了但 hook 从未实装** —— `.husky/pre-push` 实际只跑 `bun typecheck`,从未拦保护分支。文档与实现长期脱节,协作者直推 `dev` 全程畅通无阻(2026-04-30 实测),"文档撒谎"风险大于规则本身价值
> 2. **新分支策略 v2 的核心模型是"`dev` 单一稳定主干 + DeskFox官方本人直 push"** —— 强制 PR-based 与单人/小团队工作流不匹配,反成阻碍。详见 [`docs/features/分支策略-v2/1-spec.md`](../features/分支策略-v2/1-spec.md)
> 3. **陌生人无写权限** —— 本仓 PR 默认状态是"待审批",仓库主人不点 Merge 不会合入(详见分支策略 v2 spec 附录 C)。"防陌生人"诉求由平台 PR 审批机制天然保障,不需要本地 hook 兜底
>
> **新规则**:DeskFox官方本人可直 push `dev` / `feat/*`;协作者(mac 端等)走 `feat/<name>` 分支(本人开 PR / 直推由协作者酌情)。
>
> **老规则原文(已废除,仅供历史溯源)**:
> - 禁止直 push 到 `main`、`dev`、`master`、任何 upstream 同名分支
> - 配套 hook 骨架(从未实装):`.husky/pre-push` 检查 `^refs/heads/(main|master|dev)$` 即拦截

### 4.4 大小写冲突检查（跨平台）

> **背景**：Linux 文件系统区分大小写，Windows / macOS 默认不区分。Linux 上同时存在 `Foo.tsx` 和 `foo.tsx` 不会冲突，但 push 到 gitee 后 Windows 端 pull 下来会**直接坏掉**（同一文件名抢位）。

**目的**：commit 前自动检测大小写冲突，第一时间在 Linux 端拦下来。

**hook 脚本骨架**（追加到 `pre-commit`）:
```bash
# 检查大小写冲突（含已有文件 + 本次 staged 新增文件的合集）
casefold_dups=$(git ls-files | sort -fu | awk 'NR==FNR{a[tolower($0)]++; next} a[tolower($0)]>1' - <(git ls-files) 2>/dev/null | sort -u)

if [ -n "$casefold_dups" ]; then
  echo "❌ pre-commit: 检测到大小写冲突文件名（Windows / macOS 上会冲突）:"
  echo "$casefold_dups"
  echo ""
  echo "请 git mv 改成统一大小写后再 commit"
  exit 1
fi

echo "✅ pre-commit: 大小写检查通过"
```

更轻量的写法（用 `uniq -di`）:
```bash
dups=$(git ls-files | sort -fu | uniq -di)
[ -z "$dups" ] || { echo "❌ 大小写冲突: $dups"; exit 1; }
```

> **交叉引用**:本节是**文件名层级**的大小写规则(同目录下两个文件名只差大小写会跨平台冲突)。**分支名层级**的大小写规则见 [`双端协作-SOP.md` 1.2 节(分支命名规范)](./双端协作-SOP.md#12-分支命名规范) —— 那里规定"`<type>/<name>` 中 `<name>` 全小写 + kebab-case",成因相同(case-insensitive FS 跨平台冲突),scope 不同。

## 5. 改前预清单 + 事后比对

> 这是流程护栏，配合 改动日志.md 使用。目的：让"无意中多改了 X 文件"立刻暴露。

### 5.1 改前必填（在 改动日志.md 占位）

```markdown
## #N <日期> <标题>（草稿，改动中）

**改前预清单**:
- 预计触动文件: `a.tsx`, `b.rs`
- 预计 diff 行数上限: ~50 行
- 预期影响功能点: <列举>
```

### 5.2 改完事后比对（commit 前填）

```bash
# 对比预清单 vs 实际
git diff --cached --name-only      # 实际触动文件
git diff --cached --shortstat      # 实际行数
```

补全到改动日志:
```markdown
**事后比对**:
- 实际触动文件: a.tsx, b.rs ✅ 与预清单一致
- 多出的文件: 无 ✅
  - 若有 `c.ts` 等多出文件：必须在此显式解释为什么多
- 实际 diff 行数: 47 行 ✅ 在预期内
```

**多出的文件 / 行数 = 红灯**。要么补充解释（也许合理），要么 `git reset` 重做（多半是误伤）。

## 6. 冒烟测试

> 目的：每次改动后 30 秒内确认"主链路没崩"。不替代完整测试，但能拦掉 80% 的低级破坏。

### 6.1 prototype 冒烟（Linux 本地）

```bash
cd prototype/
bun run tauri dev &
PID=$!
sleep 5
# 检查窗口是否起来（platform-specific，Linux 上检查 wmctrl 或日志）
kill $PID
```

### 6.2 fork 冒烟（每次 commit 后）

```bash
cd opencode-fork/packages/desktop
bun run tauri dev &
PID=$!
sleep 10
# 1. 主窗口起来
# 2. 加载已知文件
# 3. 切换 tab
# 4. 关闭
kill $PID
```

将冒烟脚本放在 `opencode-fork/scripts/smoke-test.sh`，post-commit hook 触发。

### 6.3 失败处理

冒烟失败 → 立即 `git reset --hard HEAD~1` 退出 commit，回到上一个 commit 重新分析。**不允许"先 commit 再修"**。

## 7. AI 操作内化护栏（Claude / 其他 AI 协作）

> 当用 AI 改代码时，AI 容易出现的失误：盲目大范围 read，看到无关代码就"顺手优化"；用 sed/find 批量替换没看清边界；改一个符号没查依赖导致外部断裂。下面是 AI 必须遵守的工作方式。

### 7.1 改前必查依赖

修改任何被外部引用的符号（函数 / 类 / 类型 / 组件）前，必须先：
```
find_referencing_symbols / grep -r "<symbol>" packages/
```
列出所有引用点。改动日志记录这个清单。

### 7.2 禁用批量替换工具

- ❌ 禁止：`sed -i`、`find -exec`、IDE "rename in project"（除非已先按 7.1 列出所有引用并逐一确认）
- ✅ 允许：单点 Edit，每次改一个文件一个位置

### 7.3 Read 范围最小化

- ❌ 禁止：无目的地 `cat <整个文件>`，特别是大文件
- ✅ 允许：用 line range 读必要部分；用 symbol-level 工具（`get_symbols_overview`、`find_symbol`）按需展开

### 7.4 Edit 后主动验证

每个 Edit 完成后：
```
grep -r "<改动涉及的关键标识>" packages/  # 看有没有遗漏的引用点
bun run typecheck                          # 看类型有没有断
```

### 7.5 禁"顺手改"

看到无关代码的"明显小问题"（typo、格式、注释错别字）→ **不改**。记入待办，下次单独提 commit。本次改动严格只做计划内的事。

### 7.6 提交前自报清单

AI 在 commit 前必须输出：
- 本次实际触动的文件清单（与预清单对比）
- 是否有"顺手改"
- 是否有未理解但被改动的代码段
- 是否调用过批量替换

人工 review 看到任何一条异常 → 拒绝合入。

## 8. Commit 信息模板

```
<类型>: <一句话> [改动日志#N]

- <文件:行号> 改动概述
- <文件:行号> 改动概述

baseline: <pre-tag-name>
关联: 改动日志.md 第 N 条
回归点: R1, R3
影响范围: <列举或"无"，必须有判断>
```

**类型**：`feat` / `fix` / `refactor` / `chore` / `docs` / `test`

**关于"回归点"字段**：R 编号既可以是回归测试点（修复/重构 commit 用），也可以是新功能验证点（新功能首笔 commit 用，写"新增功能验证点 R1-Rx"即可）。任何想跑的测试都标 R 编号。

**特殊标记**：
- `[override-blacklist: 理由]` — 改了黑名单文件
- `[large-diff: 理由]` — 超过 200 行阈值
- `[no-test: 理由]` — 没跑冒烟测试（应极少出现）

> **关于多 override 标的配额计算**：一笔 commit 同时挂 `[override-blacklist] + [large-diff]` 等多个标，在 12 号规范的 override 配额里**算 1 笔**（标只是描述破例的不同维度，归属同一次决策）。详见 [`12-fork-跟随升级与协作规范.md`](12-fork-跟随升级与协作规范.md) R4。

## 9. Review 自检表（每个 commit / PR 必过）

- [ ] 仅触动白名单目录（除非显式 `[override-blacklist]` 且解释充分）
- [ ] git diff --stat 在改前预期内（差异 < 30%）
- [ ] 新增依赖：无 / 有（已在改动日志说明理由 + 体积 + 可信度）
- [ ] 是否动了 upstream 公用文件：是 → 评估 rebase 冲突风险
- [ ] 改动日志条目和 commit 1:1 对应
- [ ] 回归测试点（R 编号）已实跑或显式挂账
- [ ] baseline tag 已打且记录在 commit 信息
- [ ] 冒烟测试已跑且通过
- [ ] 无未记录的"顺手改"

---

## 10. 测试定位约定

```
改动日志 R<编号>  ↔  测试用例编号  ↔  Issue 编号
```

出 bug 时反查链路：
```
bug 报告 → 测试用例编号 → 改动日志条目 → commit hash → 改前/改后片段 → 回退 tag
```

每一环都是单跳查找，不需要全局搜索。

## 11. 回滚演练

**首次进入 Phase 1 时必做一次**：

1. 在 `upstream-baseline` 之后做一个无关紧要的小改动并 commit
2. 假装它崩了：`git reset --hard upstream-baseline`
3. 确认工作目录、index、log 都干净回到原状
4. 这一步走通后才开始真正的改动

不演练 = baseline tag 只是心理安慰，真出事不一定能用。
