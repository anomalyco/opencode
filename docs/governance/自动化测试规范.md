## 元原则(对齐 CLAUDE.md)

**稳定 > 简洁 > 一切**。测试纪律服务于三件事:
1. 跟随上游 opencode 升级时**不破坏 fork 自家的 feature**
2. 满足自有开发需要,**新 feat 不破老 feat**
3. **维护成本最低** — 测试本身要便宜,flaky 测试要立刻清除

**绝对单一**:一套测试纪律 / 一套金字塔比例 / 一种"测试通过"标准。**不分层、不双套、不双轨**。

---

## 五条核心决策(已固化)

### 决策 1:新 feat 必须含至少 1 个测试(R5 硬约束)

**规则**:任何引入用户可见行为或核心逻辑的 feat,**必须**至少含 1 个 e2e 或 unit 测试。pre-push hook 守门(后续接入)。

**例外清单**(以下不强制):
- **Tiny 改动 < 50 行**(纯 bug fix / 文案 / 配置 — 维度过窄,测试成本 > 收益)
- **docs / 规范文档 / 注释**(没法测)
- **品牌资源 / icon / 字体**(纯静态)
- **基础设施 / build 脚本 / CI workflow**(走"实跑通过"验证,不要求单元测试)
- **R3 配置 override**(`tauri-overrides/` JSON / CSS 变量)
- **上游 sync merge commits**(变更非 fork 自家,延用上游测试)

**判定权**:Claude 自判,边界模糊时主动问 user。

**规模分级 vs 测试要求**:

| 规模 | 行数 | 测试要求 |
|---|---|---|
| **Tiny** | < 50 | 不强制(但鼓励) |
| **Medium** | 50-500 | 至少 1 个 e2e **或** 3 个 unit |
| **Large** | > 500 / 触动 ≥ 5 上游文件 | 至少 2 个 e2e **+** 5 个 unit + spec 段写明测试覆盖范围 |

### 决策 2:关键模块覆盖率门槛 80%(R6 硬约束 — 渐进生效)

**规则**:列入"关键模块清单"的文件,单元测试覆盖率必须 ≥ 80%。覆盖率工具:`bun test --coverage`(后期接入)。

**关键模块清单(初版)**:

| 文件 | 理由 | 当前覆盖率 |
|---|---|---|
| `packages/app/src/utils/markdown-editor-extensions.ts` | 编辑器核心,改动频繁,11 项编辑增强主入口 | 待测 |
| `packages/app/src/components/dialog-settings.tsx` | 用户高频接触,版本牌 + i18n + 多平台 | 待测 |
| `packages/app/src/pages/session/file-tabs.tsx` | 文件查看器,选区 / 右键菜单 / 编辑态 / 渲染分发,多次出 bug | 待测 |
| `packages/app/src/utils/md-export-docx.ts` | Word 导出,引入新 dep,边界条件多 | 待测 |

**清单维护**:
- 加入清单 = 触发"该文件覆盖率必须 ≥ 80%"硬规则,**user 拍板**才能加
- 移出清单 = 该文件已退役 / 重构拆分,Claude 提议 + user 同意
- 每季度复核(2026 Q3 第一次复核)

**例外**:仅 import 第三方库的胶水代码(<20 行)不强制覆盖。

### 决策 3:测试数量比例 70 / 20 / 10(unit / integration / e2e)

**规则**:全仓测试数量分布按行业经验维持 70 / 20 / 10。**Claude 写新测试时优先写 unit,e2e 只用于"用户视角的端到端验证"**。

```
1000 个测试时:    700 unit + 200 integration + 100 e2e
今天起步阶段:     先扩 unit 到 800+,e2e 慢慢补,达成比例靠时间
```

**比例失衡处理**:
- 当 e2e 数量 > 总测试 15% → 触发警告,review 是否 e2e 过度堆叠(高维度问题向 unit 下沉)
- 当 unit 数量 < 总测试 60% → 触发警告,补 unit

**自动化测试 ≠ Playwright e2e** — 这条规则的核心是"**测试金字塔比例,而不是 e2e 数量本身**"。

### 决策 4:修 bug 必须先写复现测试(R7 硬约束)

**规则**:任何 bug fix 都**必须先写一个能复现该 bug 的测试**(测试此时 fail),然后修代码使测试 pass。fix commit 与测试代码必须**同一笔 commit**。

**为什么强制**:
- 防止同一 bug 几个月后又冒出来重修
- 自然增长测试覆盖率(不需要"为了写测试而写测试")
- review 时 "测试 + fix" 一起读,意图清晰

**例外**(以下情况测试可省):
- **bug 在外部依赖**(上游 / 第三方库)— 我们只能 workaround,不便测试上游行为
- **bug 仅在特殊环境复现**(某 user 特定 OS 配置 / 特殊文件锁状态)
- **修文案 / 翻译错误**

**操作流程**:

```
1. 收到 bug 报告
2. 写一个测试,能在当前代码下 fail(复现 bug)
3. 改代码使测试 pass
4. 同一 commit 提交测试 + fix
5. commit message 注明 [bug-repro: <一句话>]
```

**举例**(假想):今天的 `right-click-stale-selection-fix` 如果在新规范下做,流程会是:
```
step 1: 写 e2e 测试 "选 A → 点空白 → 别处右键不命中 A"(此时 fail)
step 2: 改 file-tabs.tsx 加 handleLightDomContextMenu
step 3: 测试 pass,commit 包含测试 + 修复
```

### 决策 5:测试代码 review 责任 — Claude 自审起步

**规则**:Claude 写完测试后,**用同一会话的另一轮调用做自审**,检查:
- 测试是否真的能抓出 bug(不是只 assert "字符串非空"之类的 trivial 检查)
- 测试是否有 race condition / time-dependent flakiness 风险
- 测试是否依赖外部资源(网络 / 文件系统状态 / 真实 LLM API)— 应当用 mock 替代

**自审形式**:
- 单测:Claude 提出"如果代码改成 X,这个测试还能 fail 吗?"逐条检查
- e2e:Claude 检查 selector 稳定性 / await 时机 / 失败诊断信息

**升级路径**(后期):
- **Phase A(现在)**:Claude 自审 + user 抽查
- **Phase B(未来)**:接入 mutation testing(故意改坏代码自动验证测试能不能抓到)
- **Phase C(可选)**:接入第三方人工 reviewer

## 操作流程

### 写新 feat 时

```
1. 写 feat spec(docs/features/<id>/1-spec.md)— spec 内必须有"测试覆盖范围"段
2. 写代码实现
3. 写测试(unit 优先 / e2e 仅用于用户级验证)
4. 跑全套测试 — 含旧测试(防回归)+ 新测试
5. 测试通过 → commit(代码 + 测试同一 commit)
6. push → pre-push hook 跑 typecheck + 单测
7. ff merge dev → push 双远端
8. feat 分支销毁
```

### 修 bug 时

```
1. 收到 bug → 复现
2. 写测试(能在当前代码下 fail)
3. 改代码 → 测试 pass
4. commit:测试 + fix 一起,message 注明 [bug-repro]
5. push → ff merge dev → push 双远端
```

### 测试 flaky(偶尔 fail)处理

**绝不能**用 `retries: 3` 一键掩盖。flaky 测试是规范的天敌 — 1 个不稳定测试会破坏整套信任。

**正确流程**:
1. 立即标记 `test.fixme()` 或 `test.skip()` 让 CI 不阻塞 —
2. **同一笔 commit** 加 TODO comment 写明 "为什么 flaky"
3. **48 小时内**修复或移除 — 不能让 skip 测试在仓里堆积
4. 修复方案不是 "retry" 而是定位 race / time-dependence 根因

## 测试基础设施(每期都要补)

| 设施 | 作用 | 何时建 |
|---|---|---|
| **测试 fixture 库** | 共享的 `.md` / 项目目录 / mock 用户配置 | 第 1 期起步 |
| **LLM mock 服务** | 不真调 Claude API(慢 + 贵 + 不稳),用回放固定对话 | 第 1 期起步 |
| **CI 加速** | 测试并行 / 缓存命中 / 失败快速反馈 | 第 1 期成熟后 |
| **flaky 监控** | CI 上记录 flaky 率,超阈值触发警报 | 第 2 期 |
| **覆盖率监控** | 每个 PR 显示覆盖率涨跌,review 必看 | 第 2 期 |
| **mutation testing** | 故意改坏代码看测试能不能抓到 | 第 4 期 |

## 失败处理 — "测试 fail 怎么办"

**绝对不允许**的处理方式:
- ❌ 注释掉 fail 测试
- ❌ 改 assert 让它 pass
- ❌ 加 retries 掩盖
- ❌ 用 `test.skip()` 但不修

**正确流程**:
1. 跑 fail 测试本地复现
2. **判断是 fix bug 还是 fix 测试**
   - 如果是代码出 bug → 走"修 bug"流程(决策 4)
   - 如果是测试本身写错(过严 / 过松 / 假阳性)→ 修测试,commit message 注明 `[fix-test]`
3. **绝不接受**"它有时 pass 有时 fail" — 这是 flaky,走上面 flaky 处理流程

## 与现有规范的边界

- **R1 三级跳决策**(新文件优先)— 不变。新增测试文件天然是新文件,不冲突
- **R2 FORK marker** — 测试文件全是 fork-only,不强制 marker
- **R3 hardcode 禁令** — 测试 fixture 数据可以 hardcode(测试场景需稳定)
- **R4 黑名单 override** — 测试文件不在黑名单,无配额消耗
- **改动规模分级**(Tiny / Medium / Large)— 不变,但本规范的"测试要求"叠加在原分级之上
