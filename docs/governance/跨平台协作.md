# 10 — 跨平台协作（Linux ↔ Windows ↔ macOS）

> **场景**：Linux 主开发 → push gitee → Windows 拉取做打包测试 → Windows 也可能改 → push gitee → Linux 拉取。
> 未来 macOS 同样路径。
>
> **核心矛盾**：三个 OS 的文件系统、行尾符、编码、shell、Tauri 依赖都不同。本文档把 14 个潜在坑列清楚，每个给出**机制级**解决方案（不是约定）。

---

## 1. 角色 / 仓库分工

| 端 | 角色 | 主要动作 |
|---|---|---|
| Linux（开发主机） | 主开发 | 写代码 / 提交 / push gitee |
| Windows | 打包 + 真机测试 | pull gitee / `bun install` / `tauri build` / 测 IME / 测 readonly attr |
| macOS（未来） | 打包 + 真机测试 | pull gitee / `bun install` / `tauri build` / 测 WKWebView 行为 |

**两个仓库**：

| 仓库 | gitee 地址 | 内容 | 三端是否都拉 |
|---|---|---|---|
| `opencode-plan` | `gitee.com/zoulukuang/opencode-plan` | 规划 + prototype 源码 | Linux 主拉，Win/Mac 看需要 |
| `opencode-fork`(本地目录名) | `gitee.com/zoulukuang/opencode-for-office`(gitee 2026-04-24 改名)+ `github.com/yuesoue/opencode-for-office`(PR 来源) | anomalyco/opencode 源码 + 我们的改动 | **三端都拉** |

`opencode-fork` 的 upstream 是 `github.com/anomalyco/opencode`（只读，仅 Linux 端拉 upstream 更新做 rebase）。

## 2. 14 个跨平台坑速查

| # | 坑 | 触发场景 | 解决方案 | 状态 |
|---|---|---|---|---|
| 1 | 行尾符 CRLF/LF 混乱 | Win 上 git 自动转 CRLF，commit 后 Linux 看到一堆 ^M | `.gitattributes` 强制 LF + 两端 `core.autocrlf=false` | ✅ 已加 .gitattributes |
| 2 | 大小写敏感差异 | Linux 区分 / Win 不区分 → Linux 写 `Foo.tsx` Win 上 import `foo.tsx` 不报错，反过来崩 | `.gitattributes` + pre-commit `git ls-files \| sort -fu \| uniq -di` 检查 | ✅ 进 09 第 8 道护栏 |
| 3 | 中文文件名乱码 | Win 上 `git status` 显示 `\346\262\237...` | Win 端 `git config --global core.quotepath false` | ⚠️ 用户配置 |
| 4 | 长路径 > 260 字符 | node_modules 嵌套深，Win 默认 MAX_PATH=260 报错 | Win 端 `git config --global core.longpaths true` + 注册表 `LongPathsEnabled=1` | ⚠️ 用户配置 |
| 5 | bun.lock 必须 commit | 不 commit → 两端依赖版本漂移 | 不进 .gitignore（已确认）+ 改 lock 必须显式说明 | ✅ 已确认 |
| 6 | Tauri 平台 dev 依赖差异 | Linux: webkit2gtk + libsoup3；Win: WebView2 + MSVC；Mac: Xcode CLT | 三端各自一次性环境准备（节 5） | 📝 写入文档 |
| 7 | Rust target | 不需要交叉编译，各端只装本平台 target | `rustup default stable` 即可 | 📝 写入文档 |
| 8 | npm/bun 镜像（国内速度） | Win 端拉依赖慢 | `bun config set registry https://registry.npmmirror.com` | ⚠️ 用户按需 |
| 9 | crates.io 镜像 | Rust 拉 crate 慢 | `~/.cargo/config.toml` 配 rsproxy 或字节镜像 | ⚠️ 用户按需 |
| 10 | 路径分隔符硬编码 | 代码里写 `/tmp/...` 或 `C:\...` 都会出问题 | 用 `path.join` (TS) / `PathBuf` (Rust) / Tauri `app_data_dir()` | 📝 写入 09 review checklist |
| 11 | shell 脚本不跨平台 | Linux 写 `*.sh`，Win 不能直接跑 | 优先用 `bun run xxx` 或 Rust binary；必要时同时维护 .sh + .ps1 | 📝 原则 |
| 12 | 编码 BOM | 中文 .md 带 BOM 在 Linux 工具上偶发问题 | `.editorconfig` `charset = utf-8`（无 BOM） | ✅ 已配 |
| 13 | Windows readonly attribute | 文件被设只读时 Tauri write 失败 | Rust 侧检查 `metadata.permissions().readonly()` 并提示 | 📝 Phase 2 必做 |
| 14 | gitee 容量 / 速度 | 单仓 1GB，单文件 100MB；国内速度比 GitHub 快但偶发抽风 | opencode-fork 当前 344MB OK；监控 `git count-objects -vH` | ✅ 当前安全 |

## 3. .gitattributes 已落地内容

见仓库根 `.gitattributes`。核心：

```
* text=auto eol=lf            # 默认 LF
*.bat / *.cmd / *.ps1 → CRLF  # Windows 脚本必须 CRLF
*.png/*.jpg/... binary        # 显式标二进制
bun.lock / Cargo.lock text eol=lf  # lock file 跟着 LF
```

`opencode-fork/` 也需要一份独立的 `.gitattributes`（fork 仓内单独维护）。

---

## 4. .editorconfig 已落地内容

见仓库根 `.editorconfig`。核心：

- 默认 utf-8 / LF / 2 空格
- Rust / TOML 4 空格
- Markdown 不 trim 行末空格（保留两空格强制换行）
- Windows 脚本 CRLF

## 5. 三端环境准备（一次性）

### 5.1 Linux（开发主机）

```bash
# Git 配置
git config --global core.autocrlf false
git config --global core.quotepath false
git config --global init.defaultBranch master
git config --global user.name "<你的名字>"
git config --global user.email "<你的邮箱>"

# Tauri 系统依赖（Ubuntu / Debian）
sudo apt update
sudo apt install -y libwebkit2gtk-4.1-dev libssl-dev libgtk-3-dev \
  libayatana-appindicator3-dev librsvg2-dev libsoup-3.0-dev \
  build-essential curl wget file pkg-config

# Rust
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source $HOME/.cargo/env

# bun
curl -fsSL https://bun.sh/install | bash
```

```powershell

# PowerShell: irm bun.sh/install.ps1 | iex
```

## 6. 提交流程（Linux 主开发端）

每次改完代码：

```bash
# 0. 改前已打 baseline tag（详见 09 节 3）
# 1. 验证大小写无冲突（防 Win 上崩）
git ls-files | sort -fu | uniq -di
# 期望输出：空

# 2. 验证行尾符（防 .gitattributes 失效）
git ls-files --eol | grep -E "^i/(crlf|mixed)" 
# 期望输出：仅 .bat/.cmd/.ps1 是 crlf；其他为空

# 3. 改动日志补全（事后比对）
# 见 09 节 5

# 4. 跑冒烟测试
cd packages/desktop && bun run tauri dev  # 30 秒手测主链路
# 失败 → git reset，不允许"先 commit 再修"

# 5. commit + push
git add <白名单内文件>
git commit -m "..."
git push origin <feature-branch>
```

## 7. 拉取流程（Windows 端）

```powershell
# 首次
git clone https://gitee.com/zoulukuang/opencode-fork.git
cd opencode-fork
git remote add upstream https://github.com/anomalyco/opencode.git  # 可选，Win 端一般不需要 fetch upstream

# 日常
git pull origin <feature-branch>     # 拉最新
bun install                           # 同步依赖（lock 文件已对齐）
cd packages\desktop
bun run tauri dev                     # 测试
# 或
bun run tauri build                   # 打包 .exe
```

**Windows 端检查清单**（每次 pull 后）：

- [ ] `bun install` 无 error（依赖能装）
- [ ] `tauri dev` 能起（基本链路通）
- [ ] 关键功能手测：加载文件 / 编辑 / 保存 / IME 输入
- [ ] 如改了什么本地特定的（如 git config），不要 commit 进仓

## 8. 双向修改的处理

如果 **Windows 端也改了代码**（比如修一个 Win 特定 bug），流程：

1. Windows 端 commit + push 到 feature 分支
2. Linux 端 `git pull --rebase origin <feature-branch>`
3. **冲突时**：Linux 端解决（Linux 工具链更稳），不要在 Win 端解决再 push
4. 解决后 push

**禁止**：Linux 和 Windows 同时改同一文件且都已 commit 但未 push（必出冲突）。规避方法：当天只一端改。

## 9. 出问题怎么办

### 9.1 Windows 拉下来跑不起来

| 症状 | 排查 |
|---|---|
| `bun install` 报某依赖找不到 | 看是不是配了 npm 镜像但镜像 outdated；`bun pm cache rm` 清缓存 |
| `tauri dev` 报 WebView2 找不到 | 装 WebView2 Runtime |
| `tauri dev` 报 MSVC 缺失 | 装 Build Tools 2022，确认 `cl.exe` 在 PATH |
| 编译 Rust crate 报路径太长 | 启用 longpath（节 5.2） |
| 文件名乱码 | `git config --global core.quotepath false` |
| import 报 `Cannot find module 'Foo'` | 大小写问题，Linux 上正确 Win 上不区分但解析不到 |

### 9.2 Linux 端发现 Windows commit 把 EOL 搞乱了

```bash
# 强制重新规范化 EOL
git rm --cached -r .
git reset --hard
```

如果是个别文件：
```bash
git add --renormalize <file>
git commit -m "fix: renormalize EOL for <file>"
```

### 9.3 大小写冲突（Linux 上有 Foo.tsx 和 foo.tsx 两个文件）

```bash
git ls-files | sort -fu | uniq -di
# 列出冲突，手动 git mv 改名
```

## 11. 与 09 改动规则的关系

- **09** 定义"改 fork 时怎么改"（白名单、commit 规则、护栏机制）
- **10** 定义"在不同 OS 间协作时怎么不踩坑"（EOL、编码、依赖、流程）
