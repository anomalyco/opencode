| **Google alpha track record** | Google kills alpha products. Period. | ↑ EXISTENTIAL |

### Risk Rating: **72/100** (High)

**Defensive patterns recommended:**

1. **Version-pin the API path** — hardcode `/v1alpha/` and validate response shapes at runtime. If Google ships `v1beta1`, the client should fail loudly, not silently.

2. **Response schema validation** — every Jules API response should be validated against a minimal expected shape before processing. Use Zod (already in the codebase via `model.ts` schemas). Don't trust the API to be stable.

3. **Raw JSON preservation** — the hybrid storage approach in ARCHITECTURE_DECISION_120 is correct. Store raw API responses verbatim. When Jules changes their schema, your stored data survives.

4. **Feature detection over assumption** — check for field existence (`response.plan?.steps`) rather than assuming structure. Jules added `requirePlanApproval` as an opt-in; more flags will come.

5. **Circuit breaker** — if Jules returns unexpected HTTP status codes or response shapes 3+ times in sequence, halt and surface the error. Don't retry into a changed API.

6. **Adapter isolation** — `JulesClient.ts` must be the ONLY file that touches Jules HTTP endpoints. Everything else talks through the interface. When Jules breaks, you fix ONE file.

## 2. STATE STORAGE WITHOUT MONGODB

### Critical Constraint Acknowledged
MongoDB is unavailable. Evaluating alternatives against the Jules session lifecycle requirements.

### What Needs Storing

| Data | Lifetime | Size | Access Pattern |
|------|----------|------|----------------|
| Session ID + status | Minutes to hours | ~1KB | Read/write per poll |
| Plan details | Session duration | ~5KB | Read once, approve/reject |
| Activity log | Session duration | ~10-50KB | Append-only reads |
| Artifacts/patches | Post-completion | ~1KB-1MB | Read once for delivery |
| Raw API responses | Archival | Variable | Write once, read rarely |

### Options Evaluated

#### A) File-based JSON storage (`.jules/` directory)
| Dimension | Assessment |
|-----------|-----------|
| **PR quality** | ❌ FATAL for OpenCode PR. OpenCode is a Cloudflare Workers + KV architecture. File I/O doesn't exist in Workers runtime. |
| **Portability** | ❌ Workers are stateless. No filesystem. |
| **Concurrency** | ❌ Race conditions on concurrent sessions |
| **Verdict** | **ELIMINATED** — architecturally incompatible with deployment target |

#### B) LocalStorage (browser context)
| Dimension | Assessment |
|-----------|-----------|
| **PR quality** | ❌ FATAL. Jules integration lives in `packages/console/app/` — server-side route handlers. No browser context. |
| **Scope** | ❌ Server-side Workers code has no `localStorage` |
| **Verdict** | **ELIMINATED** — wrong execution context |

#### C) In-memory with session persistence
| Dimension | Assessment |
|-----------|-----------|
| **PR quality** | ⚠️ RISKY. Workers can be evicted between requests. In-memory state vanishes. |
| **Viability** | ⚠️ Only works if polling is client-driven (Option C from architecture doc). The client holds state; the server is stateless pass-through. |
| **Pattern match** | ✅ Aligns with agent-driven polling — the CALLER maintains session ID and polls. Server is a proxy. |
| **Verdict** | **VIABLE IF** the server is a pure proxy (no server-side session tracking) |

#### D) No persistence (stateless per invocation)
| Dimension | Assessment |
|-----------|-----------|
| **PR quality** | ✅ CLEANEST for first PR. Server is a stateless proxy to Jules API. |
| **Architecture** | ✅ Matches existing OpenCode pattern — handler.ts is stateless per request |
| **State ownership** | ✅ Jules API itself holds all session state. Client polls Jules directly (through proxy). |
| **What's lost** | ⚠️ No server-side audit trail. No cost tracking between requests. No cross-session queries. |
| **Verdict** | **RECOMMENDED for Phase 1 PR** |

#### E) HIDDEN OPTION: Cloudflare KV (already in the architecture)
| Dimension | Assessment |
|-----------|-----------|
| **Evidence** | OpenCode already uses 30 KV resources for provider config (`model.ts:86-116`). KV is available. |
| **Fit** | ✅ Key-value with TTL. Perfect for session state with automatic expiry. |
| **PR quality** | ⚠️ MEDIUM RISK — adding KV bindings is a config change to `wrangler.toml` or SST config. First PR touching infra config may raise maintainer eyebrows. |
| **Verdict** | **VIABLE for Phase 2** — but too invasive for first PR |

### RECOMMENDED APPROACH

**Phase 1 (First PR): Option D — Stateless proxy**

The server provides authenticated proxy endpoints to Jules API. No server-side state. The client (OpenCode TUI/web) holds the session ID and drives the polling loop. This is:
- Zero new infrastructure
- Zero new storage dependencies
- Minimal diff (new route files only)
- Matches OpenCode's existing stateless request/response pattern
- Jules API itself is the state store

**Phase 2 (Follow-up PR): Option E — KV-backed session tracking**

Once the proxy pattern is established and trusted by maintainers, add KV-backed session metadata for cost tracking and audit trails.

### Storage Risk Score: **35/100** (Low) with Option D

**Red line**: Any approach requiring new database tables, file I/O, or persistent server-side state in the first PR. This would be rejected.
