---
title: "Compaction"
---

Compaction gives a long session more context space by replacing its older
conversation with a generated checkpoint. Earlier messages stay stored and
visible, but future model requests start from the latest checkpoint.

## Start

Automatic compaction is on by default. When a session approaches the model's
context limit, OpenCode summarizes the older conversation, keeps about 15,000
tokens of recent messages beside the summary, and continues the pending work.

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "compaction": {
    "auto": true,
    "keep": { "tokens": 15000 },
  },
}
```

Compaction is lossy. Increase `keep.tokens` when exact recent details matter,
or request a checkpoint yourself before the automatic one.

## Manual

Request a checkpoint at any time, even for a short history:

```sh
curl -X POST http://localhost:4096/api/session/ses_example/compact \
  -H 'content-type: application/json' \
  -d '{}'
```

The response confirms the request was accepted; it does not wait for the
summary. Follow `session.compaction.*` events to learn when it finishes. See the
[API reference](/api) for the full operation.

| Rule | Behavior |
| --- | --- |
| Timing | Runs at the next safe point, before prompts that are still waiting. |
| Repeats | Requests made while one is pending merge into it. |
| Automation | Works when `compaction.auto` is `false`. |

Pass an `id` to make an exact retry idempotent. Reusing that ID for a different
request returns a conflict.

```sh
curl -X POST http://localhost:4096/api/session/ses_example/compact \
  -H 'content-type: application/json' \
  -d '{"id":"msg_compact_once"}'
```

## Settings

Add `compaction` to any [OpenCode configuration file](/config):

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "compaction": {
    "auto": false,
    "keep": { "tokens": 24000 },
    "buffer": 16000,
  },
}
```

| Field | Default | Behavior |
| --- | ---: | --- |
| `auto` | `true` | Compact automatically near the context limit, and recover once when a provider rejects a request as too long. Manual compaction always works. |
| `keep.tokens` | `15000` | Approximate recent conversation kept beside the summary. Larger values preserve more detail but leave less room for new work. |
| `buffer` | `20000` | Tokens to reserve below the model's limit. Larger values start automatic compaction earlier. |

`keep.tokens` and `buffer` accept non-negative integers.

## Providers

By default OpenCode writes the summary itself with the session's model. Some
providers can produce a checkpoint natively; opt in per provider or model:

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "providers": {
    "openai": {
      "settings": { "compaction": { "type": "native" } },
      "models": {
        "gpt-4.1": { "settings": { "compaction": { "type": "summary" } } },
      },
    },
  },
}
```

A model setting overrides the provider setting.

| Topic | Behavior |
| --- | --- |
| Support | OpenAI Responses models support native compaction. Support varies by deployment and model. |
| Content | A native checkpoint is stored as the provider returns it. Recent user messages and attachments are kept up to `keep.tokens`. |
| Portability | A native checkpoint only works with the same provider, model, and endpoint. Switching models continues from the stored conversation instead. |
| Fallback | If the provider rejects an automatic native checkpoint as too long, OpenCode writes a local summary instead. |

## Checkpoints

A local checkpoint is a structured summary of the older conversation:

```md
## Objective
Finish the authentication migration.

## Next Move
- Update the callback handler.
- Verify the login flow.
```

It covers the objective and requirements, decisions, completed and active work,
blockers and next moves, and relevant files. The newest conversation up to
`keep.tokens` is kept alongside it, with long tool output shortened and
attachment data replaced by a descriptor.

Later checkpoints update the previous summary rather than starting over. The
model sees a completed checkpoint as past conversation, not as new instructions.
After a checkpoint, the current versions of your instruction files become the
baseline for the session; see [Instructions](/instructions).

## Limits

| Limit | Result |
| --- | --- |
| Model | Compaction uses the session's model. There is no separate compaction model. |
| History | Compaction needs older conversation to replace. It cannot create room when a request is mostly fixed instructions and tool schemas. |
| Recovery | A request rejected as too long is compacted and retried once. A second rejection is returned as an error. |
| Storage | Earlier messages remain stored even when they are no longer sent to the model. |

For example, compaction cannot help here:

```text
128k context = 120k fixed instructions and tools + 8k conversation
```

## Migration

V1 used tail-turn and pruning behavior. V2 uses checkpoints and
`compaction.keep.tokens`:

```jsonc
{
  "compaction": {
    "keep": { "tokens": 15000 }
  }
}
```

The settings and behavior on this page apply to V2.
