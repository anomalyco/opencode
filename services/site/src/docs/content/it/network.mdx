Imposta le variabili proxy standard ed escludi gli indirizzi di loopback. OpenCode usa connessioni HTTP locali tra la CLI e
il suo servizio in background, quindi l'esclusione del loopback è obbligatoria quando è configurato un proxy nell'ambiente della CLI.

```bash
export HTTP_PROXY=http://proxy.example.com:8080
export HTTPS_PROXY=http://proxy.example.com:8080
export NO_PROXY=localhost,127.0.0.1,::1

opencode
```

`HTTP_PROXY` gestisce le destinazioni HTTP e `HTTPS_PROXY` le destinazioni HTTPS. L'URL del proxy stesso può usare `http://`
per entrambe le variabili. `NO_PROXY` è un elenco separato da virgole di host e indirizzi che si collegano direttamente.

## Servizio

Le esportazioni della shell influiscono su un servizio in background solo quando quel servizio parte dalla shell. Salva le variabili nella configurazione gestita
del servizio, così le successive partenze usano le stesse impostazioni di rete.

```bash
opencode service set env HTTP_PROXY http://proxy.example.com:8080
opencode service set env HTTPS_PROXY http://proxy.example.com:8080
opencode service set env NO_PROXY localhost,127.0.0.1,::1
opencode service start
```

Cambiare una variabile d'ambiente gestita ferma il servizio in esecuzione. `service start` lo avvia di nuovo con il nuovo ambiente.
Mantieni `NO_PROXY` anche nella shell della CLI quando quella shell imposta un proxy, perché le variabili gestite del servizio si applicano al processo del server,
non a quello della CLI.

Rimuovi una variabile salvata con `service unset env`:

```bash
opencode service unset env HTTPS_PROXY
```

## Autenticazione

Per un proxy che accetta credenziali nell'URL, includi nome utente e password in ogni URL del proxy che richiede autenticazione.
Codifica in percentuale caratteri come `@`, `:` e `/` dentro entrambe le credenziali.

```bash
export HTTPS_PROXY='http://user:p%40ssword@proxy.example.com:8080'
```

Per il servizio in background, salva l'URL completo. Il valore viene memorizzato nella configurazione privata del servizio e
mostrato da `opencode service get env`, quindi non condividere quell'output.

```bash
opencode service set env HTTPS_PROXY 'http://user:p%40ssword@proxy.example.com:8080'
```

## Certificati

Imposta `NODE_EXTRA_CA_CERTS` su un file PEM quando il proxy o la destinazione usa un certificato firmato da un'autorità di certificazione
privata. All'avvio del processo, il runtime aggiunge queste autorità al proprio archivio dei certificati attendibili.

```bash
export NODE_EXTRA_CA_CERTS=/etc/company/ca.pem
opencode --standalone
```

Salva il percorso del file per il servizio in background, poi riavvialo:

```bash
opencode service set env NODE_EXTRA_CA_CERTS /etc/company/ca.pem
opencode service start
```

## Antivirus e ispezione HTTPS

L'«analisi HTTPS» o «analisi delle connessioni crittografate» degli antivirus (Kaspersky, Avast, ESET e altri) e i proxy aziendali
di ispezione SSL sostituiscono il certificato del server con il proprio. OpenCode lo rifiuta e le richieste falliscono con
errori come:

```text
self signed certificate in certificate chain
SELF_SIGNED_CERT_IN_CHAIN
CERT_NOT_YET_VALID
CERT_SIGNATURE_FAILURE
```

Risolvi in uno dei due modi:

- Escludi `opencode.ai` e `*.opencode.ai` dall'analisi HTTPS nelle impostazioni dell'antivirus. Aggiungi anche l'host API del tuo provider,
  ad esempio `api.anthropic.com`, se ti colleghi direttamente a un provider.
- Esporta l'autorità di certificazione dell'ispezione come file PEM e considerala attendibile con `NODE_EXTRA_CA_CERTS`, come mostrato in
  [Certificati](#certificates).

## Certificati client

Imposta `settings.tls` su un provider il cui gateway richiede mutual TLS. Le sue richieste ai modelli presentano il certificato, e
l'handshake TLS lo invia solo ai server che ne chiedono uno.

```jsonc title="opencode.jsonc"
{
  "providers": {
    "company": {
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "https://llm.company.example/v1",
        "tls": {
          "cert": "{file:/etc/company/client.pem}",
          "key": "{file:/etc/company/client.key}",
          "passphrase": "{env:CLIENT_KEY_PASSPHRASE}",
        },
      },
    },
  },
}
```

- `cert` e `key` sono testo PEM. Usa `{file:...}` per leggerli dai file. Un file che non può essere letto lascia `tls` non impostato.
- `passphrase` serve solo per una chiave crittografata.
- Funziona sulle build Bun e Node. Un server su Cloudflare Workers non può presentare un certificato client tramite `fetch`.
- Le richieste con un certificato client non seguono i reindirizzamenti, quindi il certificato non viene presentato a un altro host.

Ogni richiesta ai modelli di quel provider presenta il certificato: chat, compattazione, modelli di immagini e di decisione. Un provider
con `tls` usa HTTP invece dei WebSocket. Strumenti come webfetch, server MCP remoti e installazioni di plugin non lo presentano.

## Primo piano

`--standalone` e `serve` usano l'ambiente del proprio processo. `opencode service set env` non configura questi
processi.

```bash
HTTP_PROXY=http://proxy.example.com:8080 \
HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode --standalone
```

Applica lo stesso schema a un server in primo piano:

```bash
HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode serve
```

## Verifica

Controlla che la CLI riesca a raggiungere il servizio in background dopo aver applicato le impostazioni:

```bash
opencode api get /api/info
```

Una risposta di health riuscita verifica la connessione locale tra client e servizio. Esegui una normale richiesta a un provider per verificare il
proxy in uscita e il percorso dei certificati del servizio.
