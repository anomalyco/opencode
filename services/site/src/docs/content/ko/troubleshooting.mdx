<Callout type="tip">
  OpenCode에 스스로 디버깅을 요청할 수 있습니다. 문제를 설명하고 이 문제 해결 페이지를 사용해 달라고 하세요. 아래
  단계를 읽고 서비스와 로그를 검사해 원인을 찾는 데 도움을 줄 수 있습니다.
</Callout>

OpenCode는 클라이언트-서버 구조를 사용합니다. 백그라운드 서버가 세션, 플러그인, 권한 및 기타 애플리케이션 상태를
소유합니다. 먼저 문제가 클라이언트, 공유 서버, 특정 프로젝트 중 어디에 있는지 확인하세요.

## 백그라운드 서비스 확인

현재 서버 정보를 표시합니다.

```bash
opencode service status
```

API가 정상인지 확인합니다.

```bash
opencode api get /api/info
```

서비스가 멈췄거나 비정상이면 다시 시작하세요.

```bash
opencode service restart
```

명시적으로 중지하고 시작할 수도 있습니다.

```bash
opencode service stop
opencode service start
```

<Callout type="note">
  OpenCode는 보통 공유 백그라운드 서비스를 자동으로 찾거나 시작합니다. 서비스 명령은 수명 주기를 진단할 때만
  필요합니다.
</Callout>

## 브라우저 오리진 허용

다른 오리진의 브라우저 클라이언트가 CORS 때문에 연결할 수 없으면 서비스 구성에 해당 클라이언트의 오리진을 추가하세요.

```bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors
```

경로나 끝의 슬래시 없이, 필요하면 포트를 포함한 정확한 HTTP 또는 HTTPS 오리진을 사용하세요. 여러 오리진을
허용하려면 쉼표로 구분한 목록을 하나의 인수로 전달하세요. 각 오리진 주변의 공백은 제거됩니다.

```bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"
```

`service get cors`는 JSON 배열을 출력합니다. 구성된 목록은 다음과 같이 제거합니다.

```bash
opencode service unset cors
```

서비스 구성을 설정하거나 해제하면 백그라운드 서비스가 중지됩니다. 다음 시작 시 새 구성을 반영하며,
`opencode service start`로 직접 시작하세요.

포그라운드 서버에서는 허용할 오리진마다 `--cors`를 반복하세요.

```bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com
```

`serve --service`에서는 전달한 `--cors` 플래그가 해당 프로세스의 저장된 목록을 재정의합니다. 플래그가 없으면
서비스 모드는 저장된 목록을 사용합니다. CORS는 수신 주소를 바꾸거나 서버 인증을 우회하지 않습니다.

## API 검사

`api` 명령은 로컬 서비스 탐색과 인증 흐름을 사용합니다. HTTP 메서드와 경로 또는 OpenAPI 작업 ID를 받습니다.

모든 엔드포인트와 작업 ID는 [API 참조](/api)를 참고하세요.

JSON 요청 본문은 `--data`나 `-d`로 전달하고, 헤더는 `--header`나 `-H`로 추가하세요.

<Callout type="warning">
  `opencode api`를 실행하면 호환되는 정상 서비스가 없을 때 백그라운드 서비스가 시작될 수 있습니다.
</Callout>

## 로그 읽기

설치된 빌드는 다음 위치에 로그를 씁니다.

```text
~/.local/share/opencode/log/opencode.log
```

문제를 재현하면서 실시간으로 로그를 확인하세요.

```bash
tail -f ~/.local/share/opencode/log/opencode.log
```

각 줄에는 프로세스 `run` ID와 `role` 필드가 있습니다. 세션, 제공자, 플러그인, 권한, 도구 활동에는
`role=server`를 사용하세요.

```bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log
```

## 힙 스냅샷 캡처

모든 플랫폼에서 실행 중인 백그라운드 서버의 메모리(힙) 스냅샷을 작성합니다.

```bash
opencode debug heap-dump
```

이 명령은 스냅샷이 완료될 때까지 기다린 뒤 경로를 출력합니다.

```text
/home/me/.local/share/opencode/log/heap-48213-2026-10-23T013012345Z.heapsnapshot
```

`--directory`로 다른 위치에 작성할 수 있습니다. 디렉터리가 없으면 서버가 만듭니다.

```bash
opencode debug heap-dump --directory ./snapshots
```

- 이미 실행 중인 서버만 사용합니다. 서버를 시작, 교체, 재시작하지 않습니다.
- `--server <url>`로 `opencode serve`에서 시작한 서버를 캡처할 수 있습니다. 비밀번호가 있으면
  `OPENCODE_PASSWORD`를 설정하세요. 이때 `--directory`는 서버 머신의 경로입니다.
- 파일은 Chrome DevTools의 Memory 패널에서 여세요.

<Callout type="warning">
  스냅샷을 쓰는 동안 서버가 잠시 멈추고 메모리 사용량이 일시적으로 늘어날 수 있습니다. 스냅샷에는 프롬프트, 파일
  내용, 자격 증명이 들어갈 수 있으므로 공개적으로 공유하지 마세요.
</Callout>

### 데스크톱 앱에서

명령어 팔레트에서 **Capture heap snapshots**를 실행하세요. 다운로드 폴더 아래에 새 폴더를 만들고, 앱의 각 구성 요소를 캡처한 스냅샷과 스냅샷에 나타나지 않는 메모리 사용 내역을 함께 저장합니다.

```text
opencode-heap-2026-10-23T013012345Z/
  memory.json                  where the memory is, per process, in MiB: start here
  memory-infra.json            Chromium's memory dump trace; open it in https://ui.perfetto.dev
  heap-48213-….heapsnapshot    the desktop's own server
  window-1-48390.heapsnapshot  one per app window
  main-48102.heapsnapshot      the desktop main process
  gpu.json                     the GPU and driver
  manifest.json                processes, PIDs, and memory before and after; written last
```

- 힙 스냅샷에는 JavaScript 객체와 페이지만 담깁니다. 이미지, 레이아웃, 컴포지터 레이어, GPU 메모리는 대신
  `memory.json`과 `memory-infra.json`에 있습니다.
- 원격 서버는 캡처하지 않습니다. 해당 머신에서 `opencode debug heap-dump`를 사용하세요.
- 서버가 스냅샷을 폴더에 바로 쓰므로 큰 파일을 이동하거나 복사하지 않습니다.
- 방문한 페이지 내용이 스냅샷에 들어가므로 브라우저 탭은 포함하지 않습니다.

## CPU 및 메모리 프로파일 캡처

macOS와 Linux에서는 실행 중인 OpenCode 프로세스에 시그널을 보내 진단 데이터를 캡처할 수 있습니다. 상태
엔드포인트에서 백그라운드 서버 PID를 가져오세요.

```bash
opencode api get /api/info
```

응답의 `pid`를 다음 시그널 중 하나와 함께 사용하세요.

- `SIGPROF`는 10초 CPU 프로파일을 캡처합니다.

  ```bash
  kill -SIGPROF <pid>
  ```

  결과는 로그 디렉터리에 `cpu-<pid>-<timestamp>.cpuprofile`로 작성됩니다.

- `SIGUSR1`은 메모리(힙) 스냅샷을 캡처합니다.

  ```bash
  kill -SIGUSR1 <pid>
  ```

  결과는 로그 디렉터리에 `heap-<pid>-<timestamp>.heapsnapshot`로 작성됩니다.

파일을 열기 전에 `CPU profile written`이나 `heap snapshot written`이 `opencode.log`에 기록될 때까지 기다리세요. 해당 로그
항목에 전체 경로가 있습니다. 두 파일 형식 모두 Chrome DevTools에서 검사할 수 있습니다.

<Callout type="note">
  시그널로 트리거하는 프로파일은 Windows에서 사용할 수 없습니다. 힙 스냅샷에는 대신 `opencode debug heap-dump`를
  사용하세요. 힙 스냅샷을 쓰면 프로세스가 잠시 멈추고 메모리 사용량이 일시적으로 늘어날 수 있습니다.
</Callout>

## 서비스 파일

공유 서버는 다음 위치에 자신을 등록합니다.

```text
~/.local/state/opencode/service.json
```

비공개 서비스 구성은 다음 위치에 별도로 저장됩니다.

```text
~/.config/opencode/service.json
```

데이터베이스는 보통 다음 위치에 있습니다.

```text
~/.local/share/opencode/opencode.db
```

`OPENCODE_DB`로 데이터베이스 위치를 재정의할 수 있습니다.

<Callout type="warning">
  문제를 해결하는 동안 서비스 파일이나 데이터베이스를 삭제하거나 편집하지 마세요. 데몬은 서비스 명령으로
  관리하고, 외부 도구로 영구 데이터를 검사하기 전에 백업하세요.
</Callout>

## 문제 보고

재현 가능한 문제를 보고할 때 다음을 포함하세요.

- `opencode --version` 출력
- `opencode service status` 출력
- 문제를 재현하는 최소 단계
- 문제가 공유 서비스, 특정 클라이언트, 한 프로젝트 중 어디에 영향을 주는지
- 관련 로그 줄과 그 `run`, `role` 필드

로그를 공유하기 전에 API 키, 인증 헤더, 프롬프트, 파일 내용 및 기타 민감한 데이터를 제거하세요.

재현 가능한 문제는 [GitHub 이슈](https://github.com/anomalyco/opencode/issues)에 등록하세요.
