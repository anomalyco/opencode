description: "Configura proxies, autoridades de certificación personalizadas y certificados de cliente."

Define las variables de proxy estándar y excluye las direcciones de loopback. OpenCode usa conexiones HTTP locales entre la CLI y
su servicio en segundo plano, así que la exclusión de loopback es obligatoria cuando se configura un proxy en el entorno de la CLI.

```bash
export HTTP_PROXY=http://proxy.example.com:8080
export HTTPS_PROXY=http://proxy.example.com:8080
export NO_PROXY=localhost,127.0.0.1,::1

opencode
```

`HTTP_PROXY` gestiona los destinos HTTP y `HTTPS_PROXY` los destinos HTTPS. La URL del proxy puede usar `http://`
en ambas variables. `NO_PROXY` es una lista separada por comas de hosts y direcciones que se conectan directamente.

## Servicio

Las exportaciones del shell solo afectan a un servicio en segundo plano cuando ese servicio se inicia desde el shell. Guarda las variables en la configuración gestionada
del servicio para que los siguientes inicios usen los mismos ajustes de red.

```bash
opencode service set env HTTP_PROXY http://proxy.example.com:8080
opencode service set env HTTPS_PROXY http://proxy.example.com:8080
opencode service set env NO_PROXY localhost,127.0.0.1,::1
opencode service start
```

Cambiar una variable de entorno gestionada detiene el servicio en ejecución. `service start` lo inicia de nuevo con el nuevo entorno.
Mantén `NO_PROXY` también en el shell de la CLI cuando ese shell define un proxy, porque las variables gestionadas del servicio se aplican al proceso
del servidor, no al proceso de la CLI.

Elimina una variable guardada con `service unset env`:

```bash
opencode service unset env HTTPS_PROXY
```

## Autenticación

Para un proxy que acepta credenciales en la URL, incluye el nombre de usuario y la contraseña en cada URL de proxy que necesite autenticación.
Aplica la codificación porcentual a caracteres como `@`, `:` y `/` tanto en el usuario como en la contraseña.

```bash
export HTTPS_PROXY='http://user:p%40ssword@proxy.example.com:8080'
```

Para el servicio en segundo plano, guarda la URL completa. El valor se almacena en la configuración privada del servicio.
`opencode service get env` lo muestra, así que no compartas la salida del comando.

```bash
opencode service set env HTTPS_PROXY 'http://user:p%40ssword@proxy.example.com:8080'
```

## Certificados

Define `NODE_EXTRA_CA_CERTS` con un archivo PEM cuando el proxy o el destino use un certificado firmado por una autoridad de certificación privada.
Las autoridades adicionales se agregan al almacén de confianza en tiempo de ejecución cuando arranca el proceso.

```bash
export NODE_EXTRA_CA_CERTS=/etc/company/ca.pem
opencode --standalone
```

Guarda la ruta del archivo para el servicio en segundo plano y luego reinícialo:

```bash
opencode service set env NODE_EXTRA_CA_CERTS /etc/company/ca.pem
opencode service start
```

## Antivirus e inspección HTTPS

El «escaneo HTTPS» o «escaneo de conexiones cifradas» de los antivirus (Kaspersky, Avast, ESET y otros) y los proxies corporativos
de inspección SSL sustituyen el certificado del servidor por el suyo. OpenCode lo rechaza y las solicitudes fallan con
errores como:

```text
self signed certificate in certificate chain
SELF_SIGNED_CERT_IN_CHAIN
CERT_NOT_YET_VALID
CERT_SIGNATURE_FAILURE
```

Soluciónalo de una de estas dos formas:

- Excluye `opencode.ai` y `*.opencode.ai` del escaneo HTTPS en los ajustes del antivirus. Agrega también el host de la API de tu proveedor,
  como `api.anthropic.com`, si te conectas directamente a un proveedor.
- Exporta la autoridad de certificación de inspección como archivo PEM y confía en ella con `NODE_EXTRA_CA_CERTS`, como se muestra en
  [Certificados](#certificates).

## Certificados de cliente

Define `settings.tls` en un proveedor cuyo gateway requiera TLS mutuo. Sus solicitudes de modelos presentan el certificado, y el
handshake TLS solo lo envía a los servidores que lo piden.

```jsonc title="opencode.jsonc"
{
  "providers": {
    "company": {
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "https://llm.company.example/v1",
        "tls": {
          "cert": "{file:/etc/company/client.pem}",
          "key": "{file:/etc/company/client.key}",
          "passphrase": "{env:CLIENT_KEY_PASSPHRASE}",
        },
      },
    },
  },
}
```

- `cert` y `key` son texto PEM. Usa `{file:...}` para leerlos de archivos. Un archivo que no se puede leer deja `tls` sin definir.
- `passphrase` solo es necesaria para una clave cifrada.
- Funciona en las compilaciones de Bun y Node. Un servidor en Cloudflare Workers no puede presentar un certificado de cliente a través de `fetch`.
- Las solicitudes con un certificado de cliente no siguen redirecciones, así que el certificado no se presenta a otro host.

Todas las solicitudes de modelos de ese proveedor presentan el certificado: modelos de chat, compactación, imagen y decisión. Un proveedor
con `tls` usa HTTP en lugar de WebSockets. Herramientas como webfetch, los servidores MCP remotos y las instalaciones de plugins no lo presentan.

## Primer plano

`--standalone` y `serve` usan el entorno de su propio proceso. `opencode service set env` no configura estos
procesos.

```bash
HTTP_PROXY=http://proxy.example.com:8080 \
HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode --standalone
```

Aplica el mismo patrón a un servidor en primer plano:

```bash
HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode serve
```

## Verificar

Comprueba que la CLI puede llegar al servicio en segundo plano después de aplicar los ajustes:

```bash
opencode api get /api/info
```

Una respuesta de estado correcta verifica la conexión local del cliente al servicio. Ejecuta una solicitud normal a un proveedor para verificar el
proxy de salida y la ruta de certificados del servicio.
