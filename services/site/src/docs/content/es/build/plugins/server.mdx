La parte de servidor de un plugin se ejecuta en el servidor de OpenCode. Modifica el comportamiento de OpenCode y agrega funciones: herramientas,
hooks, integraciones, comandos y agentes. Consulta la [descripción general](/build/plugins) para ver cómo se estructura, carga
y publica un paquete de plugin.

```ts title=".opencode/plugins/example/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  async setup(ctx) {
    await ctx.storage.set("loaded", true)
  },
})
```

## Ciclo de vida

`setup` se ejecuta cuando se carga el plugin. Puede devolver una función de limpieza que se ejecuta cuando el plugin se descarga.

```ts
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  setup(ctx) {
    console.log(`loaded in OpenCode ${ctx.app.version}`)
    return () => console.log("unloaded")
  },
})
```

### Contexto

El contexto del plugin es esencialmente un [cliente del servidor de OpenCode](/build/client).
Sus métodos de lectura y acción usan las mismas entradas y respuestas que el cliente. Agrega métodos exclusivos del plugin para transformaciones,
hooks en tiempo de ejecución, recargas, registros y opciones del plugin.

```ts
setup(ctx) {
  console.log(ctx.app.version)
}
```

`ctx.location` describe la ubicación donde se carga esta instancia del plugin. Incluye `directory`, `workspaceID` opcional y metadatos de `project`
(`id`, `directory` y `canonical`). Está disponible tanto en plugins Promise como en plugins de Effect.
Es la ubicación de la instancia del plugin, no la de cada sesión a la que puede
acceder ni la de cada evento que recibe.

```ts
setup(ctx) {
  console.log(ctx.location.directory)
  console.log(ctx.location.project.canonical)
}
```

### Opciones

En `opencode.json(c)`, usa el formato de objeto para pasar las opciones del plugin.

```jsonc title="opencode.jsonc"
{
  "plugins": [
    {
      "package": "./plugins/company",
      "options": {
        "strict": true,
      },
    },
  ],
}
```

Lee esos valores de `ctx.options` durante `setup`.

```ts title="plugins/company/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company",
  setup(ctx) {
    const strict = ctx.options.strict === true
  },
})
```

## Transformaciones

Las transformaciones modifican de forma síncrona el estado de un dominio de OpenCode. Cada una parte de lo que ya se registró en ese dominio.
Las lecturas del registro, como `ctx.model.list()`, reflejan todo lo registrado hasta ese momento, incluso durante la inicialización del plugin.
Al arrancar solo se agrupan las notificaciones de actualización: las lecturas devuelven los cambios sin demora. Las API de estado de recursos
siguen informando del estado de los recursos en ejecución: que una definición esté registrada no significa que su conexión u otras operaciones
del recurso hayan terminado.

Las fuentes aportan proveedores y definiciones de modelo inmutables mediante `ctx.provider.transform`.

```ts title="plugins/models/index.ts"
import { Model, Plugin, Provider } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const providerID = Provider.ID.make("acme")
    const models = [{ ...Model.Info.default(providerID, Model.ID.make("reasoner")), name: "Acme Reasoner" }]
    await ctx.provider.transform((editor) => {
      editor.add({
        info: {
          ...Provider.Info.empty(providerID),
          name: "Acme",
          activation: "enabled",
          package: "@opencode/ai/providers/openai-compatible",
          settings: { baseURL: "http://127.0.0.1:8000/v1" },
        },
        models,
      })
    })

    const available = await ctx.model.list()
  },
})
```

Cualquier alta, eliminación o llamada a `reload()` marca el registro como modificado. En la siguiente lectura, OpenCode lo reconstruye
sobre un valor nuevo, aplicando de nuevo cada transformación activa en el orden en que se registró. Procura que las transformaciones
consuman pocos recursos y se puedan repetir. Las reconstrucciones posteriores no modifican los valores que ya hayas leído.

Después de resolver las transformaciones de proveedor y la disponibilidad, OpenCode materializa los modelos de los proveedores activos y repite
cada transformación de modelo en orden. Una política de modelo puede inspeccionar toda la colección de candidatos, incluidas las fuentes
recién actualizadas.

```ts title="plugins/model-budget/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.model-budget",
  async setup(ctx) {
    await ctx.model.transform((editor) => {
      editor
        .list()
        .filter((model) => model.cost.some((tier) => tier.output > 20))
        .forEach((model) => {
          editor.remove(model.providerID, model.id)
        })
    })
  },
})
```

Las entradas capturadas no se vigilan automáticamente. Carga los datos externos antes de la devolución de llamada síncrona y luego llama a
`reload()` cuando esas entradas cambien. Aquí, `loadFromSource()` devuelve
entradas `{ info: Provider.Info, models: readonly Model.Info[] }`.

```ts title="plugins/models/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const source = { providers: await loadFromSource() }

    await ctx.provider.transform((editor) => {
      source.providers.forEach((provider) => editor.add(provider))
    })

    const refresh = async () => {
      source.providers = await loadFromSource()
      await ctx.provider.reload()
    }

    const timer = setInterval(() => void refresh().catch(console.error), 60_000)
    return () => clearInterval(timer)
  },
})
```

Los cambios de proveedor invalidan todo el resultado de modelos activos, así que la política de precio de salida sigue filtrando los modelos actualizados.
Usa `ctx.model.reload()` cuando solo cambie una entrada capturada por una transformación de modelo.

## API

### Agentes

Lee todos los agentes u obtén uno por ID.

```ts
const agents = await ctx.agent.list()
const build = await ctx.agent.get({ agentID: "build" })
```

Registra una transformación para inspeccionar, actualizar, eliminar o seleccionar el agente predeterminado.

```ts
await ctx.agent.transform((editor) => {
  const agents = editor.list()
  const build = editor.get("build")

  editor.default("build")
  editor.update("build", (agent) => {
    agent.description = "Builds features and fixes bugs"
  })
  editor.remove("legacy")
})
```

Recarga los agentes cuando cambie el estado externo que usa una transformación.

```ts
await ctx.agent.reload()
```

### Proveedores

Lee los proveedores disponibles o inspecciona los metadatos de un proveedor por ID.

```ts
const providers = await ctx.provider.list()
const provider = await ctx.provider.get({ providerID: "anthropic" })
```

Las transformaciones de proveedor editan los ajustes del proveedor y las definiciones de origen. Las lecturas del editor incluyen proveedores inactivos y exponen
definiciones inmutables; `models.update` edita una copia propia de un modelo de origen.

```ts
await ctx.provider.transform((editor) => {
  editor.update("anthropic", (provider) => {
    provider.headers = { ...provider.headers, "x-company": "engineering" }
  })
  editor.models.update("anthropic", "claude-sonnet-5-5", (model) => {
    model.name = "Team Sonnet"
  })
  editor.models.remove("anthropic", "legacy-model")
  editor.remove("legacy-provider")
})
```

Sustituye el inventario de origen de un proveedor con `models.set` y luego recarga cuando cambien las definiciones capturadas.

```ts
const source = { models: await loadModels() }
await ctx.provider.transform((editor) => {
  editor.models.set("acme", source.models)
})

source.models = await loadModels()
await ctx.provider.reload()
```

Para descubrir los modelos de una cuenta concreta, pasa en `sourceConnection` la conexión que usaste para cargar el inventario. OpenCode excluye
ese proveedor mientras haya otra conexión seleccionada, hasta que tu plugin publique su inventario actualizado.

```ts
const connection = await ctx.integration.connection.active("acme")
if (!connection) return
const inventory = await loadInventory(connection)
await ctx.provider.transform((editor) => {
  editor.add({ info: inventory.provider, models: inventory.models, sourceConnection: connection })
})
```

### Modelos

Lee los modelos disponibles y la selección predeterminada.

```ts
const models = await ctx.model.list()
const selected = await ctx.model.default()
```

Las transformaciones de modelo editan toda la colección de candidatos de proveedores activos. Los candidatos deshabilitados siguen siendo editables hasta que terminan
todas las transformaciones; `update` puede agregar un modelo solo bajo un proveedor disponible.

```ts
await ctx.model.transform((editor) => {
  editor.list("anthropic").forEach((model) => {
    editor.update(model.providerID, model.id, (draft) => {
      draft.enabled = draft.capabilities.tools
    })
  })
  editor.default.set("anthropic", "claude-sonnet-5-5")
  editor.remove("anthropic", "legacy-model")
})
```

Los callbacks editan los valores sin procesar que sustituyen a los del modelo. Los valores predeterminados del proveedor se fusionan una sola vez, cuando OpenCode consolida el resultado;
las lecturas sin cambios reutilizan ese resultado. `editor.provider` expone definiciones de origen inmutables, incluidas plantillas inactivas, en lugar de
la salida de la transformación de modelos.

```ts
await ctx.model.transform((editor) => {
  const source = editor.provider.get("anthropic")?.models.get("claude-sonnet-5-5")
  if (!source) return
  editor.update("anthropic", source.id, (model) => {
    model.limit.context = Math.min(model.limit.context, source.limit.context)
  })
})

await ctx.model.reload()
```

### Integraciones

Lee las integraciones e inspecciona las credenciales activas.

```ts
const integrations = await ctx.integration.list()
const github = await ctx.integration.get({ integrationID: "github" })
const connection = await ctx.integration.connection.active("github")
const credential = connection ? await ctx.integration.connection.resolve(connection) : undefined
```

Conecta integraciones con una clave de API.

```ts
await ctx.integration.connect.key({
  integrationID: "github",
  key: process.env.GITHUB_TOKEN!,
})
```

Inicia, inspecciona, completa o cancela un intento de conexión OAuth.

```ts
const attempt = await ctx.integration.oauth.connect({ integrationID: "github", methodID: "oauth" })
const status = await ctx.integration.oauth.status({ integrationID: "github", attemptID: attempt.data.attemptID })
await ctx.integration.oauth.complete({ integrationID: "github", attemptID: attempt.data.attemptID, code })
await ctx.integration.oauth.cancel({ integrationID: "github", attemptID: attempt.data.attemptID })
```

Las conexiones basadas en comandos exponen el mismo flujo de inicio, estado y cancelación.

```ts
const attempt = await ctx.integration.command.connect({ integrationID: "acme", methodID: "cli" })
const status = await ctx.integration.command.status({ integrationID: "acme", attemptID: attempt.data.attemptID })
await ctx.integration.command.cancel({ integrationID: "acme", attemptID: attempt.data.attemptID })
```

Registra una transformación para inspeccionar integraciones y gestionar sus métodos de autenticación.

```ts
await ctx.integration.transform((editor) => {
  const integrations = editor.list()
  const acme = editor.get("acme")

  editor.update("acme", (integration) => {
    integration.name = "Acme"
  })
  editor.method.update({
    integrationID: "acme",
    method: { id: "cli", type: "command", label: "Sign in with Acme CLI", command: ["acme", "login"] },
  })

  const methods = editor.method.list("acme")
  const legacy = methods.find((method) => method.type === "command" && method.id === "legacy")
  if (legacy) editor.method.remove("acme", legacy)
  editor.remove("legacy")
})
```

Recarga las integraciones cuando cambie el estado externo que usa una transformación.

```ts
await ctx.integration.reload()
```

### MCP

Lista los servidores MCP y su estado de conexión actual.

```ts
const servers = await ctx.mcp.list()
```

Los plugins gestionan los servidores MCP solo mediante transformaciones. Usa `editor.set` para agregar o sustituir un servidor, `editor.update` para
cambiar su configuración y `editor.remove` para eliminarlo. Inspecciona la configuración con `editor.list` y `editor.get`.

```ts
await ctx.mcp.transform((editor) => {
  const servers = editor.list()
  const docs = editor.get("docs")
  editor.set("docs", { type: "remote", url: "https://mcp.example.com" })
  editor.update("docs", (server) => {
    server.disabled = false
  })
  editor.remove("legacy")
})
```

Define `disabled: true` en una transformación para deshabilitar un servidor y desconectarlo, o `disabled: false` para habilitarlo y permitir
que OpenCode se conecte. OpenCode ajusta el ciclo de vida del servidor a la configuración resultante.

Llama a `reload()` cuando cambie el estado externo que usa una transformación para volver a aplicar las transformaciones y ajustar el estado de los servidores.

```ts
await ctx.mcp.reload()
```

### Permisos

Pide permiso antes de realizar una acción. `assert` evalúa las [reglas de permisos](/permissions) de la sesión,
incluidas las aprobaciones guardadas, y pregunta al usuario cuando una regla se resuelve en `ask`. Se resuelve cuando se permite la acción.

```ts
execute: async (input, context) => {
  await ctx.permission.assert({
    sessionID: context.sessionID,
    agent: context.agent,
    source: { type: "tool", messageID: context.messageID, id: context.id },
    action: "deploy",
    resources: [input.environment],
    save: [input.environment],
  })
  return { content: await deploy(input.environment) }
}
```

- `action` y `resources` se comparan con las reglas. Cualquier `deny` bloquea la acción; si no, cualquier `ask` pregunta.
- `save` enumera los patrones que se guardan cuando el usuario elige permitir siempre.
- `agent` selecciona de quién son las reglas que se aplican y usa por defecto el agente de la sesión. `source` vincula el prompt a una llamada a herramienta.
- `metadata` pasa detalles adicionales a los prompts de permiso y a los hooks `evaluate`.

Si una regla deniega el permiso o el usuario lo rechaza con un comentario, la llamada falla con un `Tool.Error` que incluye el motivo. Así, el modelo puede leerlo y
continuar. Un rechazo sin comentarios termina el paso actual. Deja que estos errores se propaguen en lugar de devolverlos como salida de
herramienta.

Inspecciona o resuelve solicitudes de permiso pendientes.

```ts
const pending = await ctx.permission.list({ sessionID })
const request = await ctx.permission.get({ sessionID, requestID })
await ctx.permission.reply({ sessionID, requestID, decision: "once" })
```

Sustituye las reglas de permisos con ámbito de sesión. Se evalúan después de las reglas del agente, y gana la
última regla que coincide. Las sesiones hijas heredan las reglas vigentes cuando se crean.

```ts
await ctx.session.update({
  sessionID,
  permissions: [{ action: "edit", resource: "/path/to/original/checkout/**", effect: "deny" }],
})
```

### Sesiones

Crea o lee una sesión.

```ts
const created = await ctx.session.create({ title: "Review" })
const session = await ctx.session.get({ sessionID })
const messages = await ctx.session.context({ sessionID })
```

### Herramientas

Lee las herramientas registradas actualmente, después de todas las transformaciones, fuera de una devolución de llamada de transformación. Cada herramienta tiene un `id`
que contiene su nombre efectivo.

```ts
const tools = await ctx.tool.list()
const read = tools.find((tool) => tool.id === "read")
```

Registra, actualiza y elimina herramientas con una transformación síncrona, incluso en plugins Promise. Carga los datos externos
antes de registrar o recargar. Un registro válido posterior sobrescribe el mismo nombre efectivo de herramienta.

```ts
const registration = await ctx.tool.transform((editor) => {
  editor.namespace({
    name: "acme",
    description: "Customer account tools",
  })
  editor.add({
    name: "greeting",
    description: "Create a greeting",
    input: {
      type: "object",
      properties: { name: { type: "string" } },
      required: ["name"],
      additionalProperties: false,
    },
    options: { namespace: "acme", codemode: true },
    execute: async (input, context) => {
      await context.progress({ status: "greeting" })
      return { content: `Hello ${(input as { name: string }).name}!` }
    },
  })
})
```

Los ejecutores de herramientas Promise reciben `context.signal`. Pásalo al trabajo cancelable, como `fetch`, para que detener la Session
detenga también la operación subyacente.

```ts
execute: async ({ url }, context) => {
  const response = await fetch(url, { signal: context.signal })
  return { content: await response.text() }
}
```

#### Entrada de herramienta en formato libre

Si una herramienta directa tiene un único campo obligatorio de tipo cadena, puede dejar que el modelo escriba esa cadena sin envolverla en JSON. Define `freeform` como `{ type: "text" }`, `{ type: "regex", pattern }` o `{ type: "lark", grammar }`.

```ts
editor.add({
  name: "ticket",
  description: "Look up a ticket by ID",
  options: { codemode: false },
  input: Schema.Struct({ id: Schema.String }),
  freeform: { type: "regex", pattern: "OPS-[0-9]+" },
  execute: async ({ id }) => ({ content: await lookup(id) }),
})
```

Si la API del modelo seleccionado incluye `regex` en models.dev, el modelo puede escribir `OPS-42` directamente. De lo contrario, Core omite **solo** `freeform`: el modelo sigue teniendo la herramienta `ticket` y la llama con `{"id":"OPS-42"}`. Las listas de formatos ausentes o vacías significan que no hay compatibilidad con forma libre. El ejecutor recibe `{ id }` en cualquier caso.

Dentro de Code Mode (`codemode: true`), una herramienta de forma libre toma su cadena directamente, como en `await tools.ticket("OPS-42")`. `await tools.ticket({ id: "OPS-42" })` también funciona.

Llama a `reload()` cuando cambien los datos de origen que captura la devolución de llamada. La recarga repite las transformaciones activas sin
cambiar su orden; no vuelve a ejecutar la configuración del plugin.

```ts
await ctx.tool.reload()
```

Usa `list()` y `get()` para inspeccionar las herramientas que hay actualmente en el editor. Las herramientas tienen un `id` que contiene su nombre efectivo,
y `get()` devuelve `undefined` cuando ese ID no está presente. Usa `update` y `remove` con el nombre efectivo de la herramienta,
incluido su espacio de nombres (`acme_greeting` arriba). Los puntos en los
espacios de nombres y los caracteres no admitidos en los nombres de herramientas se convierten en `_`. Los nombres ausentes se ignoran; crear una herramienta requiere
`add` con una definición completa. Las actualizaciones conservan el nombre y el espacio de nombres. Asigna esquemas u opciones nuevas para sustituirlos
en lugar de mutar valores anidados. Las actualizaciones no válidas se registran y dejan intacta la definición anterior.

```ts
await ctx.tool.transform((editor) => {
  editor.update("acme_greeting", (tool) => {
    tool.description = "Greet the user by name"
  })
  editor.remove("acme_obsolete")
})
```

Las actualizaciones, eliminaciones y altas se vuelven a aplicar en orden, incluso tras actualizar el catálogo MCP. Al retirar un
registro se eliminan sus cambios y se reconstruye el resultado a partir de las transformaciones restantes.

Retira un registro para eliminar su transformación y reconstruir el resultado a partir de las restantes. Así vuelven a quedar disponibles
las definiciones anteriores que la transformación hubiera sustituido. Retirar un registro es una operación idempotente; al descargar el plugin también se retiran sus registros.

```ts
await registration.dispose()
```

Cada solicitud al modelo captura una instantánea de herramientas estable y ejecutable. Las transformaciones, recargas y desechos posteriores afectan a las instantáneas
futuras, no a las definiciones, las descripciones de espacios de nombres de Code Mode ni los ejecutores ya capturados. Los ejecutores que capturan
datos mutables del plugin siguen observando esos datos; captura un valor dentro de la transformación cuando deba permanecer ligado a
esa definición.

### Worktrees

Registra una estrategia de worktree local usando el ciclo de vida normal del plugin. El módulo de implementación de este ejemplo se encarga
de la validación de opciones y de las operaciones `create`, `remove` y `list` del backend.

```ts title="plugins/worktrees/index.ts"
import { Plugin } from "@opencode/plugin"
import { makeStrategy } from "./strategy"

export default Plugin.define({
  id: "company.worktrees",
  async setup(ctx) {
    const strategy = makeStrategy(ctx.options)
    await ctx.worktree.transform((editor) => {
      editor.add(strategy)
    })
  },
})
```

Carga el plugin a través de `plugins` y configura el destino común por separado:

```jsonc title="opencode.jsonc"
{
  "worktree": { "directory": "../worktrees" },
  "plugins": [{ "package": "./plugins/worktrees", "options": {} }],
}
```

- Agregar una estrategia la selecciona automáticamente. Gana el último registro activo; no se necesita ninguna configuración de selección de estrategia.
- Desechar su registro o descargar el plugin restaura la implementación anterior, en última instancia la estrategia Git incluida.
- `reload()` repite las transformaciones cuando cambian las entradas capturadas; no vuelve a ejecutar la configuración del plugin.
- Los fallos de creación no se reintentan con Git. Los worktrees existentes conservan su propietario registrado aunque cambie el valor predeterminado.
- Las estrategias gestionan directorios locales. El aprovisionamiento de espacios de trabajo remotos no forma parte de esta interfaz.

#### Operaciones

El contexto del plugin expone las mismas operaciones de worktree basadas en proyecto que el cliente. Cada operación requiere un
`projectID`. `list` solo lee el inventario guardado, incluidos los checkouts conocidos del mismo proyecto; no carga
configuración, no inicia plugins ni descubre cambios del sistema de archivos.

```ts
const projectID = ctx.location.project.id
const created = await ctx.worktree.create({ projectID, name: "task" })
const inventory = await ctx.worktree.list({ projectID })
await ctx.worktree.refresh({ projectID })
await ctx.worktree.remove({ projectID, directory: created.directory, force: false })
```

La operación de creación carga la configuración y los plugins desde el directorio `canonical` guardado del proyecto y aplica la estrategia seleccionada.
Acepta un directorio padre (`directory`), un origen (`from`), una rama inicial (`branch`) y un nombre (`name`), todos opcionales.
El origen predeterminado es el checkout canónico. Si indicas otro origen en `from`, debe pertenecer al mismo proyecto. Elegir un origen
no cambia la raíz de configuración.
Una referencia inicial proporcionada debe ser compatible con la estrategia seleccionada;
la operación de instantánea nativa de Rift, por ejemplo, no tiene opción de selección de referencia.

Las operaciones de creación y actualización esperan a que se activen los plugins del checkout canónico. Las llamadas hechas durante la inicialización
de esos plugins tienen acceso a lo registrado hasta ese momento, sin esperar a su propia activación.

La operación de eliminación carga la configuración canónica y activa sus plugins. Luego usa la estrategia registrada del worktree en lugar
de la estrategia predeterminada actual. Si la estrategia registrada no está disponible, se produce un error. El destino del worktree puede
estar en otro lugar:

```ts
await ctx.worktree.remove({
  directory: "/worktrees/task",
  projectID,
  force: false,
})
```

Si no está disponible la estrategia propietaria, la eliminación falla en lugar de recurrir a Git. Una estrategia puede lanzar `new Worktree.OperationError({
message: "Uncommitted changes", forceRequired: true })`, importando `Worktree` de `@opencode/plugin`, para solicitar
confirmación para forzar la operación sin depender de errores de Core ni de Git.

La operación de actualización carga la configuración canónica y pide a todas las estrategias disponibles que busquen worktrees en las raíces de checkout conocidas.
Combina los resultados, conserva la estrategia registrada de cada worktree y elimina del inventario los directorios que ya no existen. Si una fuente falla,
se registra el fallo y las demás siguen funcionando. Los directorios existentes se conservan en el inventario aunque ninguna estrategia disponible los indique.
Suscríbete a `worktree.updated` y vuelve a llamar a `list` para consultar el inventario actualizado.

```ts
await ctx.worktree.refresh({ projectID })
```

#### Referencia

Las implementaciones reciben un destino sugerido después de nombrar y gestionar las colisiones. Devuelve el directorio real desde
`create`; puede diferir cuando un backend requiere su propia estructura. OpenCode resuelve la ruta devuelta y la usa para
el inventario, los comandos de inicio y el resultado de la API. El directorio devuelto debe existir.

Las estrategias que eligen otro destino gestionan allí las colisiones de nombres. OpenCode sigue creando el directorio padre sugerido
antes de llamar a la estrategia. `list` debe informar solo de los directorios propiedad de la estrategia, además de las raíces de repositorio.

```ts
interface WorktreeDefinition {
  readonly id: string
  create(
    input: { sourceDirectory: string; directory: string; branch?: string },
    context: { signal: AbortSignal },
  ): Promise<{ directory: string }>
  remove(input: { directory: string; force: boolean }, context: { signal: AbortSignal }): Promise<void>
  list(
    sourceDirectory: string,
    context: { signal: AbortSignal },
  ): Promise<readonly { directory: string; type: "root" | "worktree" }[]>
}

interface WorktreeEditor {
  add(definition: WorktreeDefinition): void
}

  transform(callback: (editor: WorktreeEditor) => void): Promise<Registration>

}
```

Las devoluciones de llamada Promise deben cooperar con la cancelación de `signal`. Las devoluciones de llamada de Effect devuelven Effects y usan la interrupción de Effect
en su lugar. Los registros siguen con ámbito del entorno de ejecución del plugin; las operaciones de proyecto usan el registro del checkout canónico.
Los adaptadores de configuración de Core alimentan los ajustes de directorio en ese registro.

## Hooks

Los hooks interceptan operaciones en vivo. Registra un hook en su dominio y desecha el
registro devuelto cuando ya no sea necesario.

```ts
const registration = await ctx.session.hook("context", () => {})
await registration.dispose()
```

Varios plugins pueden registrar el mismo hook. OpenCode los ejecuta en orden de plugin,
así que los hooks posteriores ven los cambios hechos por los anteriores.

### Sesiones

Los hooks de sesión interceptan la admisión de prompts, las llamadas al modelo, el HTTP nativo y los reintentos.

#### Forks

El hook `fork` se ejecuta después de que OpenCode copia el historial y antes de que vuelva la llamada de bifurcación. `sessionID` identifica la sesión nueva.

```ts
await ctx.session.hook("fork", ({ sessionID }) => console.log(sessionID))
```

#### Admisión de prompts

Intercepta los prompts del usuario antes de resolver sus adjuntos y skills y de registrarlos de forma persistente en la bandeja de entrada:

```ts
await ctx.session.hook("prompt", (event) => {
  event.prompt.text = event.prompt.text.replaceAll("company-secret", "[redacted]")
  event.prompt.files ??= []
  event.prompt.files.push({ uri: "file:///project/policy.md" })
  event.metadata = { ...event.metadata, source: "company-policy" }
  event.delivery = "queue"
})
```

El hook recibe un borrador mutable propio:

- `prompt` contiene `text`, `files`, menciones de agentes en `agents` y `skills` seleccionadas.
- `metadata` contiene metadatos de admisión definidos por la aplicación.
- `delivery` es `"steer"` de forma predeterminada y se puede cambiar a `"queue"`.
- Los ID de sesión y mensaje son de solo lectura; un hook no puede redirigir la admisión.

Los archivos y las skills que agrega un hook se resuelven y validan como de costumbre.
Al reescribir texto, actualiza o elimina los desplazamientos `mention` de los adjuntos que ya
no coincidan. Las menciones de agentes no cambian el agente activo de la sesión.

Los hooks de prompt se ejecutan en estas condiciones:

- Los hooks se ejecutan en orden de registro después de que los plugins de ubicación de la sesión estén listos.
- Los comandos que envían a través de `session.prompt` ejecutan el hook.
- Los mensajes sintéticos, los mensajes de shell, los controles de compactación y los controles de movimiento no lo hacen.
- El hook se ejecuta una vez durante la admisión, no antes de cada llamada al modelo.
- El ámbito de proveedor no está disponible porque la resolución del modelo ocurre después de la admisión.

Las ediciones se convierten en la entrada de usuario canónica persistida. Si la preparación falla o se
interrumpe, OpenCode no admite el prompt.

Escribe los hooks de prompt de modo que se puedan reintentar sin problemas. No garantizan que los efectos secundarios ocurran una sola vez:

- Reintentar un ID ya pendiente o entregado devuelve la admisión original sin volver a ejecutar los hooks.
- Los envíos concurrentes pueden ejecutar los hooks más de una vez, pero solo gana la primera admisión correcta.
- Los hooks de prompt transforman la entrada y no exponen una API de rechazo tipada.

#### Solicitudes al modelo

Modifica las instrucciones del sistema, los mensajes, las herramientas o las opciones ya preparados justo antes de enviar la solicitud al modelo. Cada
tipo de solicitud que emite una sesión tiene su propio hook, así que un plugin puede tratar el bucle del agente y las solicitudes auxiliares de
forma distinta:

- `context` se ejecuta para el bucle del agente, incluidas las continuaciones impulsadas por herramientas.
- `compaction` se ejecuta para los resúmenes de puntos de control. `messages` es el historial que se resume; OpenCode agrega su
  prompt de resumen después de que se ejecutan los hooks. Define `result` para registrar tú mismo la compactación y omitir la llamada al modelo; toma los
  mismos campos que un mensaje de compactación completado.
- `generate` se ejecuta para las llamadas transitorias de `ctx.session.generate`.
- `title` se ejecuta para la generación de títulos. No tiene `agent` ni `tools`. Define `result` para proporcionar tú mismo el título.

```ts
await ctx.session.hook("context", (event) => {
  event.system.push({ type: "text", text: "Keep the review focused on correctness." })
  delete event.tools.write
  event.options.temperature = 0.2
  event.options.maxTokens = 8_000
})

await ctx.session.hook("compaction", async (event) => {
  event.result = { summary: await summarize(event.messages) }
})
```

Los cambios afectan solo a la llamada saliente al modelo, no al historial persistido ni a la configuración. Un hook que deba aplicarse a
todas las solicitudes debe registrarse para cada tipo.

Los mensajes de los hooks `context`, `compaction` y `generate` llevan los `metadata` de su mensaje almacenado, de solo lectura
(por ejemplo, lo que definió un hook `prompt`). No se envía al modelo.

La parte `system` que contiene las instrucciones de OpenCode también enumera cada fuente en `metadata.experimental.instructions` como
`{ key, text }`, como `core/date` o `core/environment`, para que un hook pueda distinguir las fuentes. La lista es una copia:
editar el `text` de la parte no la actualiza. Esto es experimental y puede cambiar.

Los valores que sustituyen a los de la solicitud siguen estas reglas:

- `options` empieza vacío en cada llamada al modelo; no contiene los ajustes de modelo resueltos.
- Las claves tipadas son ajustes de generación; cualquier otra clave se pasa al protocolo seleccionado como opción de proveedor.
- Los hooks se ejecutan en orden de registro y ven las sobrescrituras hechas por los anteriores.
- Las sobrescrituras de solicitud tienen prioridad sobre los valores predeterminados del modelo, que tienen prioridad sobre los valores predeterminados de la ruta.
- Los objetos de opciones de proveedor se fusionan de forma recursiva; los arrays y valores escalares sustituyen a los anteriores.
- Eliminar una sobrescritura o definirla como `undefined` recurre a los valores predeterminados configurados en lugar de eliminarlos.
- Los cambios directos en el cuerpo HTTP se aplican después de convertir la solicitud al formato del protocolo y pueden sustituir los campos resultantes.

#### Opciones de proveedor

Las opciones de proveedor usan los nombres semánticos de opción del protocolo seleccionado, no los campos del cuerpo HTTP sin procesar. Limita los ajustes específicos del
proveedor al proveedor correspondiente. Por ejemplo, OpenAI Responses usa `reasoningEffort`:

```ts
await ctx.session.hook(
  "context",
  (event) => {
    event.options.reasoningEffort = "high"
  },
  { providerID: "openai" },
)
```

Las opciones de generación dependen del protocolo y el modelo seleccionados:

- `maxTokens` es el límite semántico de tokens de salida.
- Gemini admite `topK`; OpenAI Responses no lo expone.

#### Resolución de modelo

Experimental. Se ejecuta cada vez que una Session resuelve el modelo para una solicitud, antes de construir nada para ella. `model` empieza
como el modelo seleccionado; cámbialo para atender esta solicitud con otro modelo del mismo proveedor, incluido uno oculto
en el selector de modelos. La Session conserva su modelo seleccionado; la solicitud y el mensaje del asistente usan el nuevo.
`kind` indica qué solicitud se está resolviendo, para que un enrutador pueda omitir títulos o enrutar de nuevo después de la compactación. Un modelo de
otro proveedor se considera no disponible y la solicitud falla.

```ts
await ctx.session.hook(
  "experimental.model.resolve",
  (event) => {
    if (event.model.id === "auto" && event.kind !== "title")
      event.model = { providerID: event.model.providerID, id: pick(event.sessionID) }
  },
  { providerID: "acme" },
)
```

#### Solicitud al modelo

Modifica los ajustes de solicitud al modelo y, opcionalmente, limita el hook a un proveedor. El evento lleva el mismo `kind`
que los hooks HTTP de abajo.

```ts
await ctx.session.hook(
  "model.request",
  (event) => {
    event.headers["x-plugin"] = "review"
  },
  { providerID: "anthropic" },
)
```

#### HTTP nativo

Modifica las solicitudes o respuestas nativas del proveedor. Sus cuerpos son streams de un solo uso; clona o sustituye un cuerpo antes de leerlo.

Ambos hooks se ejecutan para cada solicitud que emite una sesión. `event.kind` indica qué flujo la emitió: `"primary"` para el bucle
del agente, `"compaction"` para los resúmenes de puntos de control, `"title"` para la generación de títulos y `"generate"` para las llamadas transitorias
de `ctx.session.generate`. Úsalo en lugar del ID de agente para distinguir las solicitudes auxiliares.

```ts
await ctx.session.hook("http.request", (event) => {
  event.request.headers.set("x-session-id", event.sessionID)
  if (event.kind === "title") event.request.headers.set("x-priority", "background")
})

await ctx.session.hook("http.response", (event) => {
  event.response = new Response(event.response.body, {
    status: event.response.status,
    headers: { ...Object.fromEntries(event.response.headers), "x-plugin": "review" },
  })
})
```

#### WebSocket nativo (experimental)

Los proveedores que transmiten por WebSocket abren una conexión por sesión y la reutilizan entre solicitudes, así que
`http.request` y `http.response` nunca ven ese tráfico. El hook `experimental.ws.handshake` se ejecuta una vez por llamada al modelo
antes de seleccionar la conexión. Lleva el mismo `sessionID`, `agent`, `model` y `kind` que los hooks HTTP,
además de la `url` y los `headers` de la conexión. Cambiar `url` o `headers` cambia el socket que usa la solicitud, así que un
token Bearer rotado vuelve a abrir la conexión.

Los hooks HTTP siguen ejecutándose para cada solicitud HTTP, incluida la solicitud a la que recurre una ruta WebSocket.

```ts
await ctx.session.hook(
  "experimental.ws.handshake",
  async (event) => {
    event.headers.authorization = `Bearer ${await mintToken(event.url)}`
    delete event.headers["api-key"]
  },
  { providerID: "azure" },
)
```

`experimental.ws.send` y `experimental.ws.receive` exponen los propios frames, la contraparte WebSocket de
editar el cuerpo de una solicitud o respuesta HTTP. `send` se ejecuta después de que el controlador del proveedor construye un frame saliente y antes de que
se escriba; `receive` se ejecuta en cada frame entrante antes de que lo observe el controlador. Ambos llevan el frame como cadena y
envían lo que contenga `frame` cuando termine el hook.

OpenCode no valida los frames reescritos. El controlador rastrea el estado a partir de las respuestas del proveedor, así que una reescritura que
cambie el significado del protocolo es responsabilidad del plugin, igual que un cuerpo HTTP reescrito.

```ts
await ctx.session.hook(
  "experimental.ws.send",
  (event) => {
    const body = JSON.parse(event.frame)
    if (body.type === "response.create") body.metadata = { ...body.metadata, session: event.sessionID }
    event.frame = JSON.stringify(body)
  },
  { providerID: "openai" },
)

await ctx.session.hook("experimental.ws.receive", (event) => {
  if (event.frame.includes('"type":"error"')) console.error(event.frame)
})
```

Estos hooks son experimentales y sus nombres o formas pueden cambiar.

#### Política de reintentos

Sobrescribe la decisión de reintento de un fallo del proveedor o sustituye su retardo en milisegundos. El hook se ejecuta después de que OpenCode
clasifique el fallo y proponga su política, pero antes de programar ningún reintento. No expone cómo realiza OpenCode
internamente el siguiente intento.

```ts
await ctx.session.hook("retry", (event) => {
  if (event.error.status === 429) {
    event.decision = { retry: true, delay: 10_000 }
    return
  }
  if (event.error.type === "provider.invalid-request" && event.attempt === 2) {
    event.decision = { retry: true, delay: 0 }
    return
  }
  if (event.attempt >= 3) event.decision = { retry: false }
})
```

Los hooks de reintento pueden cambiar la `decision` inicial de OpenCode haciendo reintentable un fallo terminal
o vetando un reintento propuesto.

Las decisiones de reintento siguen estas reglas:

- Varios hooks se ejecutan en orden de registro, y los posteriores ven la decisión actual.
- El número máximo de intentos integrado sigue siendo un límite estricto.
- `attempt` identifica el intento real que se está evaluando. La solicitud inicial es `1`, así que el primer reintento es `2`.
- Los retardos no válidos como `NaN`, infinito o valores negativos recurren al retardo calculado.
- La recuperación de desbordamiento de contexto es independiente porque compacta la conversación en lugar de reintentar la misma solicitud.

### Permisos

Revisa las decisiones de permiso después de evaluar las reglas configuradas y antes de que se ejecute
una acción o se publique un prompt de permiso.

```ts
await ctx.permission.hook("evaluate", async (event) => {
  if (event.action === "read") return

  const messages = await ctx.session.context({ sessionID: event.sessionID })
  const review = await ctx.generate.text({
    model: { providerID: "anthropic", id: "claude-sonnet-5-5" },
    prompt: buildSafetyPrompt({ messages, action: event.action, resources: event.resources }),
  })
  const decision = parseDecision(review.text)

  event.effect = decision.effect
  event.message = decision.reason
})
```

Los hooks de permisos siguen estas reglas:

- Los hooks se ejecutan para las decisiones `allow` y `ask`.
- Un `deny` configurado explícitamente es definitivo y no invoca el hook.
- Un hook puede cambiar `effect` a `allow`, `ask` o `deny`.
- `message` aparece en una solicitud de permiso escalada o se convierte en el motivo de la denegación.

#### Referencia

```ts
  readonly metadata?: Record<string, unknown>
```

## Admitir V1

Un plugin puede admitir V1 y V2 desde el mismo punto de entrada del paquete. Exporta por defecto
un objeto con una función `server()` de V1 y una función `setup()` de V2:

```ts title="src/index.ts"
import { Plugin } from "@opencode/plugin"

export default {
  ...Plugin.define({
    id: "example",
    async setup(ctx) {
      await ctx.tool.hook("execute.before", () => {
        console.log("A tool is about to run")
      })
    },
  }),
  async server() {
    return {
      "tool.execute.before": async () => {
        console.log("A tool is about to run")
      },
    }
  },
}
```

- V1 llama a `server()` y usa los hooks devueltos.
- V2 lee el `id` y `setup()` de la exportación predeterminada (o `effect()` en los plugins de Effect), e ignora `server()`.
- Mantén cada implementación en su propia API; compartir una exportación no traduce los hooks de V1 a hooks de V2.
- Incorpora las propiedades de `Plugin.define(...)` al objeto exportado con el operador de propagación para comprobar los tipos de la definición de V2 por separado de `server()`.

La forma de objeto de V1 es compatible con OpenCode `1.18.29`. Las versiones de V1 anteriores pueden
esperar exportaciones de función; prueba el paquete instalado con la versión de V1 más antigua que
pretendas admitir y con V2.
