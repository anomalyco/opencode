Serverdelen kører i OpenCode-serveren. Den ændrer OpenCodes adfærd og tilføjer funktioner som værktøjer, hooks, integrationer, kommandoer og agenter. Se [oversigten](/build/plugins) for at læse, hvordan du strukturerer, indlæser og publicerer en pluginpakke.

```ts title=".opencode/plugins/example/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  async setup(ctx) {
    await ctx.storage.set("loaded", true)
  },
})
```

## Livscyklus

`setup` kører, når pluginet indlæses. Funktionen kan returnere en oprydningsfunktion, der kører, når pluginet afindlæses.

```ts
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  setup(ctx) {
    console.log(`loaded in OpenCode ${ctx.app.version}`)
    return () => console.log("unloaded")
  },
})
```

### Kontekst

Pluginkonteksten fungerer som en [OpenCode-serverklient](/build/client). Dens metoder til at læse data eller udføre handlinger bruger samme input og svar som klienten. Konteksten indeholder desuden metoder til transforms, hooks under kørsel, genindlæsning, registrering og pluginindstillinger, som kun er tilgængelige for plugins.

```ts
setup(ctx) {
  console.log(ctx.app.version)
}
```

`ctx.location` beskriver den location, hvor denne plugininstans indlæses. Den
indeholder `directory`, valgfri `workspaceID` og `project`-metadata (`id`,
`directory` og `canonical`). Den er tilgængelig i både Promise- og Effect-plugins.
Dette er plugininstansens location, ikke location for hver session, den kan
tilgå, eller hver hændelse, den modtager.

```ts
setup(ctx) {
  console.log(ctx.location.directory)
  console.log(ctx.location.project.canonical)
}
```

### Indstillinger

Send pluginindstillinger med objektformen i `opencode.json(c)`.

```jsonc title="opencode.jsonc"
{
  "plugins": [
    {
      "package": "./plugins/company",
      "options": {
        "strict": true,
      },
    },
  ],
}
```

Læs værdierne fra `ctx.options` under `setup`.

```ts title="plugins/company/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company",
  setup(ctx) {
    const strict = ctx.options.strict === true
  },
})
```

## Transforms

Transforms ændrer OpenCodes tilstand synkront inden for et domæne, og hver transform bygger på tidligere registreringer i domænet. Når du læser fra registeret, f.eks. med `ctx.model.list()`, får du alle hidtidige registreringer med, også mens pluginet sættes op. Under opstart grupperes kun notifikationer om opdateringer, uden at det forsinker resultatet af en læsning. API'er for ressourcestatus viser fortsat status for de ressourcer, der kører: En registreret definition betyder ikke, at forbindelsen er klar, eller at andet arbejde med ressourcen er færdigt.

Kilder bidrager med udbydere og uforanderlige modeldefinitioner gennem `ctx.provider.transform`.

```ts title="plugins/models/index.ts"
import { Model, Plugin, Provider } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const providerID = Provider.ID.make("acme")
    const models = [{ ...Model.Info.default(providerID, Model.ID.make("reasoner")), name: "Acme Reasoner" }]
    await ctx.provider.transform((editor) => {
      editor.add({
        info: {
          ...Provider.Info.empty(providerID),
          name: "Acme",
          activation: "enabled",
          package: "@opencode/ai/providers/openai-compatible",
          settings: { baseURL: "http://127.0.0.1:8000/v1" },
        },
        models,
      })
    })

    const available = await ctx.model.list()
  },
})
```

Hver registrering, fjernelse eller hvert kald til `reload()` markerer registeret som ændret. Ved næste læsning genopbygges det ved at anvende alle aktive transforms i registreringsrækkefølge på en ny værdi. Hold transforms hurtige, og sørg for, at de kan køres igen. En værdi, du allerede har læst, ændres ikke ved senere genopbygninger.

Når udbydernes transforms er anvendt, og deres tilgængelighed er afgjort, opretter OpenCode de aktive udbyderes modeller og anvender alle modeltransforms i rækkefølge. En modelpolitik kan undersøge alle modeller, der kan vælges, også dem fra kilder, der netop er opdateret.

```ts title="plugins/model-budget/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.model-budget",
  async setup(ctx) {
    await ctx.model.transform((editor) => {
      editor
        .list()
        .filter((model) => model.cost.some((tier) => tier.output > 20))
        .forEach((model) => {
          editor.remove(model.providerID, model.id)
        })
    })
  },
})
```

Fangede input overvåges ikke automatisk. Indlæs eksterne data før det synkrone callback, og kald derefter
`reload()`, når input ændres. Her returnerer `loadFromSource()`
`{ info: Provider.Info, models: readonly Model.Info[] }`-poster.

```ts title="plugins/models/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const source = { providers: await loadFromSource() }

    await ctx.provider.transform((editor) => {
      source.providers.forEach((provider) => editor.add(provider))
    })

    const refresh = async () => {
      source.providers = await loadFromSource()
      await ctx.provider.reload()
    }

    const timer = setInterval(() => void refresh().catch(console.error), 60_000)
    return () => clearInterval(timer)
  },
})
```

Udbyderændringer invaliderer hele det aktive modelresultat, så outputprispolitikken stadig filtrerer de opdaterede modeller.
Brug `ctx.model.reload()`, når kun et input fanget af en model-transform ændres.

## API

### Agent

Læs alle agenter, eller hent én efter ID.

```ts
const agents = await ctx.agent.list()
const build = await ctx.agent.get({ agentID: "build" })
```

Registrér en transform for at se, opdatere eller fjerne agenter eller vælge standardagenten.

```ts
await ctx.agent.transform((editor) => {
  const agents = editor.list()
  const build = editor.get("build")

  editor.default("build")
  editor.update("build", (agent) => {
    agent.description = "Builds features and fixes bugs"
  })
  editor.remove("legacy")
})
```

Genindlæs agenter, når ekstern tilstand brugt af en transform ændres.

```ts
await ctx.agent.reload()
```

### Udbydere

Læs tilgængelige udbydere, eller inspicér én udbyders metadata efter ID.

```ts
const providers = await ctx.provider.list()
const provider = await ctx.provider.get({ providerID: "anthropic" })
```

Udbyder-transforms redigerer udbyderindstillinger og kildedefinitioner. Editorlæsninger omfatter inaktive udbydere og eksponerer
uforanderlige definitioner; `models.update` redigerer en ejet kopi af en kildemodel.

```ts
await ctx.provider.transform((editor) => {
  editor.update("anthropic", (provider) => {
    provider.headers = { ...provider.headers, "x-company": "engineering" }
  })
  editor.models.update("anthropic", "claude-sonnet-5-5", (model) => {
    model.name = "Team Sonnet"
  })
  editor.models.remove("anthropic", "legacy-model")
  editor.remove("legacy-provider")
})
```

Erstat en udbyders kildefortegnelse med `models.set`, og genindlæs derefter, når de fangede definitioner ændres.

```ts
const source = { models: await loadModels() }
await ctx.provider.transform((editor) => {
  editor.models.set("acme", source.models)
})

source.models = await loadModels()
await ctx.provider.reload()
```

For kontospecifik søgning skal du sende den forbindelse, der bruges til at indlæse fortegnelsen, som `sourceConnection`. OpenCode udelukker
den udbyder, mens en anden forbindelse er valgt, indtil dit plugin publicerer sin opdaterede fortegnelse.

```ts
const connection = await ctx.integration.connection.active("acme")
if (!connection) return
const inventory = await loadInventory(connection)
await ctx.provider.transform((editor) => {
  editor.add({ info: inventory.provider, models: inventory.models, sourceConnection: connection })
})
```

### Modeller

Læs tilgængelige modeller og standardvalget.

```ts
const models = await ctx.model.list()
const selected = await ctx.model.default()
```

Model-transforms redigerer hele kandidatsamlingen for aktive udbydere. Deaktiverede kandidater forbliver redigerbare, indtil alle
transforms er færdige; `update` kan kun tilføje en model under en tilgængelig udbyder.

```ts
await ctx.model.transform((editor) => {
  editor.list("anthropic").forEach((model) => {
    editor.update(model.providerID, model.id, (draft) => {
      draft.enabled = draft.capabilities.tools
    })
  })
  editor.default.set("anthropic", "claude-sonnet-5-5")
  editor.remove("anthropic", "legacy-model")
})
```

Callbacks redigerer rå modeltilsidesættelser. Udbyderstandarder flettes én gang, når OpenCode gennemfører resultatet; uændrede læsninger
genbruger det resultat. `editor.provider` eksponerer uforanderlige kildedefinitioner, inklusive inaktive skabeloner, i stedet for
model-transform-output.

```ts
await ctx.model.transform((editor) => {
  const source = editor.provider.get("anthropic")?.models.get("claude-sonnet-5-5")
  if (!source) return
  editor.update("anthropic", source.id, (model) => {
    model.limit.context = Math.min(model.limit.context, source.limit.context)
  })
})

await ctx.model.reload()
```

Læs integrationer, og inspicér aktive legitimationsoplysninger.

```ts
const integrations = await ctx.integration.list()
```

```ts
await ctx.integration.connect.key({
  integrationID: "github",
  key: process.env.GITHUB_TOKEN!,

```

Start, inspicér, fuldfør eller annullér et OAuth-forbindelsesforsøg.

```ts
const attempt = await ctx.integration.oauth.connect({ integrationID: "github", methodID: "oauth" })
const status = await ctx.integration.oauth.status({ integrationID: "github", attemptID: attempt.data.attemptID })
await ctx.integration.oauth.complete({ integrationID: "github", attemptID: attempt.data.attemptID, code })
await ctx.integration.oauth.cancel({ integrationID: "github", attemptID: attempt.data.attemptID })
```

Kommandobaserede forbindelser eksponerer samme flow til start, status og annullering.

```ts
const attempt = await ctx.integration.command.connect({ integrationID: "acme", methodID: "cli" })
const status = await ctx.integration.command.status({ integrationID: "acme", attemptID: attempt.data.attemptID })
await ctx.integration.command.cancel({ integrationID: "acme", attemptID: attempt.data.attemptID })
```

Registrér en transform for at inspicere integrationer og administrere deres autentificeringsmetoder.

```ts
await ctx.integration.transform((editor) => {
  const integrations = editor.list()
  const acme = editor.get("acme")

  editor.update("acme", (integration) => {
    integration.name = "Acme"
  })
  editor.method.update({
    integrationID: "acme",
    method: { id: "cli", type: "command", label: "Sign in with Acme CLI", command: ["acme", "login"] },
  })

  const methods = editor.method.list("acme")
  const legacy = methods.find((method) => method.type === "command" && method.id === "legacy")
  if (legacy) editor.method.remove("acme", legacy)
  editor.remove("legacy")
})
```

### MCP

Vis MCP-servere og deres aktuelle forbindelsestilstand.

```ts
const servers = await ctx.mcp.list()
```

Plugins administrerer kun MCP-servere gennem transforms. Brug `editor.set` til at tilføje eller erstatte en server, `editor.update` til
at ændre dens konfiguration og `editor.remove` til at fjerne den. Inspicér konfigurationen med `editor.list` og `editor.get`.

```ts
await ctx.mcp.transform((editor) => {
  const servers = editor.list()
  const docs = editor.get("docs")
  editor.set("docs", { type: "remote", url: "https://mcp.example.com" })
  editor.update("docs", (server) => {
    server.disabled = false
  })
  editor.remove("legacy")
})
```

Sæt `disabled: true` i en transform for at deaktivere en server og afbryde den, eller `disabled: false` for at aktivere den og lade
OpenCode forbinde. OpenCode afstemmer serverlivscyklussen ud fra den transformerede konfiguration.

Kald `reload()`, når ekstern tilstand, som en transform bruger, ændres, for at genanvende transforms og afstemme serverne.

```ts
await ctx.mcp.reload()
```

### Tilladelser

Bed om tilladelse, før en handling udføres. `assert` evaluerer sessionens [tilladelsesregler](/permissions), herunder gemte godkendelser, og spørger brugeren, når en regel giver `ask`. Det returnerede promise fuldføres, når handlingen er tilladt.

```ts
execute: async (input, context) => {
  await ctx.permission.assert({
    sessionID: context.sessionID,
    agent: context.agent,
    source: { type: "tool", messageID: context.messageID, id: context.id },
    action: "deploy",
    resources: [input.environment],
    save: [input.environment],
  })
  return { content: await deploy(input.environment) }
}
```

- `action` og `resources` matches mod reglerne. Enhver `deny` blokerer handlingen; ellers spørger enhver `ask`.
- `save` angiver de mønstre, der gemmes, når brugeren vælger altid at tillade.
- `agent` vælger, hvis regler der gælder, og er som standard sessionens agent. `source` knytter prompten til et værktøjskald.
- `metadata` sender ekstra detaljer til tilladelsesprompts og `evaluate`-hooks.

Hvis en regel blokerer handlingen, eller brugeren afviser med en begrundelse, afvises kaldet med en `Tool.Error`, der indeholder årsagen, så modellen ser den og kan fortsætte. En afvisning uden begrundelse afslutter det aktuelle trin. Lad fejlene fortsætte op gennem kaldestakken i stedet for at returnere dem som værktøjsoutput.

Inspicér eller afgør ventende tilladelsesanmodninger.

```ts
const pending = await ctx.permission.list({ sessionID })
const request = await ctx.permission.get({ sessionID, requestID })
await ctx.permission.reply({ sessionID, requestID, decision: "once" })
```

Erstat de session-afgrænsede tilladelsesregler. De evalueres efter agentens regler, og den
sidste matchende regel vinder. Undersessioner arver de regler, der gælder, når de oprettes.

```ts
await ctx.session.update({
  sessionID,
  permissions: [{ action: "edit", resource: "/path/to/original/checkout/**", effect: "deny" }],
})
```

### Værktøjer

Læs de aktuelt registrerede værktøjer uden for en transforms callback. Du får resultatet, efter alle transforms er anvendt. Hvert værktøj har et `id`, der indeholder dets endelige navn.

```ts
const tools = await ctx.tool.list()
const read = tools.find((tool) => tool.id === "read")
```

Registrér, opdatér og fjern værktøjer med en synkron transform, også i Promise-plugins. Indlæs eksterne data
før registrering eller genindlæsning. En senere gyldig registrering tilsidesætter samme effektive værktøjsnavn.

```ts
const registration = await ctx.tool.transform((editor) => {
  editor.namespace({
    name: "acme",
    description: "Customer account tools",
  })
  editor.add({
    name: "greeting",
    description: "Create a greeting",
    input: {
      type: "object",
      properties: { name: { type: "string" } },
      required: ["name"],
      additionalProperties: false,
    },
    options: { namespace: "acme", codemode: true },
    execute: async (input, context) => {
      await context.progress({ status: "greeting" })
      return { content: `Hello ${(input as { name: string }).name}!` }
    },
  })
})
```

Kørselsfunktioner til Promise-værktøjer modtager `context.signal`. Send signalet med til operationer, der kan annulleres, f.eks. `fetch`, så den underliggende operation stopper, når du stopper sessionen.

```ts
execute: async ({ url }, context) => {
  const response = await fetch(url, { signal: context.signal })
  return { content: await response.text() }
}
```

#### Freeform-værktøjsinput

Et direkte værktøj med præcis ét påkrævet strengfelt kan lade modellen skrive strengen uden en JSON-wrapper. Sæt `freeform` til `{ type: "text" }`, `{ type: "regex", pattern }` eller `{ type: "lark", grammar }`.

```ts
editor.add({
  name: "ticket",
  description: "Look up a ticket by ID",
  options: { codemode: false },
  input: Schema.Struct({ id: Schema.String }),
  freeform: { type: "regex", pattern: "OPS-[0-9]+" },
  execute: async ({ id }) => ({ content: await lookup(id) }),
})
```

Hvis den valgte models API angiver `regex` i models.dev, kan modellen skrive `OPS-42` direkte. Ellers udelader Core **kun** `freeform`: modellen har stadig `ticket`-værktøjet og kalder det med `{"id":"OPS-42"}`. Manglende eller tomme formatlister betyder ingen freeform-understøttelse. Executoren modtager `{ id }` uanset hvad.

Inde i Code Mode (`codemode: true`) tager et freeform-værktøj sin streng direkte, som i `await tools.ticket("OPS-42")`. `await tools.ticket({ id: "OPS-42" })` virker også.

Kald `reload()` efter ændring af kildedata, som callbacket har fanget. Genindlæsning genafspiller de aktive transforms uden
at ændre deres rækkefølge; den kører ikke plugin-setup igen.

```ts
await ctx.tool.reload()
```

Brug `list()` og `get()` til at inspicere værktøjer, der aktuelt er i editoren. Værktøjer har et `id`, der indeholder deres effektive navn,
og `get()` returnerer `undefined`, når ID'et ikke findes. Brug `update` og `remove` med det effektive værktøjsnavn,
inklusive dets navnerum (`acme_greeting` ovenfor). Punktummer i
navnerum og ikke-understøttede tegn i værktøjsnavne bliver `_`. Manglende navne ignoreres; oprettelse af et værktøj kræver
`add` med en komplet definition. Opdateringer bevarer navn og navnerum. Tildel nye skemaer eller indstillinger for at erstatte
dem i stedet for at mutere indlejrede værdier. Ugyldige opdateringer logges og lader den tidligere definition være intakt.

```ts
await ctx.tool.transform((editor) => {
  editor.update("acme_greeting", (tool) => {
    tool.description = "Greet the user by name"
  })
  editor.remove("acme_obsolete")
})
```

Opdateringer og fjernelser genafspilles i rækkefølge sammen med tilføjelser, også efter MCP-katalogopdateringer. Afvikling af deres
registrering fjerner ændringerne og genopbygger ud fra de resterende transforms.

Afvikl en registrering for at fjerne dens transform og genopbygge ud fra de resterende transforms, så en tidligere
definition, den tilsidesatte, igen vises. Afvikling er idempotent, og afindlæsning af pluginet afvikler også dets registreringer.

```ts
await registration.dispose()
```

Hver modelanmodning fastholder et stabilt, eksekverbart snapshot af værktøjerne. Senere transforms, genindlæsning og afvikling påvirker fremtidige snapshots, ikke definitioner, navnerumsbeskrivelser til Code Mode eller kørselsfunktioner, der allerede er fastholdt. Kørselsfunktioner med en reference til plugindata, der kan ændres, ser stadig ændringer i dataene; bind værdien i transformen, hvis den skal forblive knyttet til definitionen.

### Worktrees

Registrér en lokal worktree-strategi med den normale pluginlivscyklus. Implementeringsmodulet i dette eksempel ejer
indstillingvalidering og backendens `create`-, `remove`- og `list`-operationer.

```ts title="plugins/worktrees/index.ts"
import { Plugin } from "@opencode/plugin"
import { makeStrategy } from "./strategy"

export default Plugin.define({
  id: "company.worktrees",
  async setup(ctx) {
    const strategy = makeStrategy(ctx.options)
    await ctx.worktree.transform((editor) => {
      editor.add(strategy)
    })
  },
})
```

Indlæs pluginet gennem `plugins`, og konfigurer den fælles destination separat:

```jsonc title="opencode.jsonc"
{
  "worktree": { "directory": "../worktrees" },
  "plugins": [{ "package": "./plugins/worktrees", "options": {} }],
}
```

- Tilføjelse af en strategi vælger den automatisk. Den sidste aktive registrering vinder; der er ingen konfiguration til strategivalg.
- Afvikling af dens registrering eller afindlæsning af pluginet gendanner den tidligere implementering, til sidst den medfølgende Git-strategi.
- `reload()` genafspiller transforms, når fangede input ændres; den kører ikke plugin-setup igen.
- Fejl ved oprettelse forsøges ikke igen gennem Git. Eksisterende worktrees beholder deres registrerede ejer, også når standarden ændres.
- Strategier administrerer lokale mapper. Fjernprovisionering af arbejdsområder er ikke en del af denne grænseflade.

#### Operationer

Plugin-konteksten eksponerer samme projektbaserede worktree-operationer som klienten. Hver operation kræver et
`projectID`. `list` læser kun den gemte fortegnelse, inklusive kendte checkouts af samme projekt; den indlæser ikke
konfiguration, starter ikke plugins og finder ikke filsystemændringer.

```ts
const projectID = ctx.location.project.id
const created = await ctx.worktree.create({ projectID, name: "task" })
const inventory = await ctx.worktree.list({ projectID })
await ctx.worktree.refresh({ projectID })
await ctx.worktree.remove({ projectID, directory: created.directory, force: false })
```

Create indlæser konfiguration og plugins fra projektets gemte `canonical`-mappe og bruger deres valgte strategi.
Den accepterer en valgfri overordnet `directory`, kilden `from`, start-`branch` og `name`.
Kilden er som standard det kanoniske checkout, og en `from`-tilsidesættelse skal tilhøre det projekt. Valg af en kilde
ændrer ikke konfigurationsroden.
En angivet startref skal understøttes af den valgte strategi;
Rifts native snapshot-operation har f.eks. ingen indstilling til ref-valg.

Create og refresh venter på, at det kanoniske checkouts plugins aktiveres. Kald, der foretages under det checkouts plugin-
setup, ser de hidtidige registreringer og venter ikke på deres egen aktivering.

Remove indlæser den kanoniske konfiguration og aktiverer dens plugins og bruger derefter worktreens registrerede strategi i stedet
for den aktuelt valgte standard. En utilgængelig registreret ejer giver en fejl. Worktreens destination kan
være et andet sted:

```ts
await ctx.worktree.remove({
  directory: "/worktrees/task",
  projectID,
  force: false,
})
```

Hvis den registrerede strategi mangler, mislykkes fjernelsen i stedet for at bruge Git som reserve. En strategi kan kaste `new Worktree.OperationError({
message: "Uncommitted changes", forceRequired: true })` med `Worktree` importeret fra `@opencode/plugin` for at bede om bekræftelse på tvungen fjernelse uden at være afhængig af Core- eller Git-fejl.

Refresh indlæser kanonisk konfiguration og beder alle tilgængelige strategier finde worktrees på tværs af kendte checkout-rødder.
Den kombinerer resultater, bevarer registreret ejerskab og fjerner manglende mapper. En mislykket søgekilde logges,
mens andre kilder fortsætter. Eksisterende mapper forbliver gemt, også når ingen tilgængelig strategi rapporterer dem. Lyt efter
`worktree.updated`, og kald `list` igen for at læse den ændrede fortegnelse.

```ts
await ctx.worktree.refresh({ projectID })
```

#### Reference

Implementeringer modtager en foreslået destination efter navngivning og kollisionshåndtering. Returnér den faktiske mappe fra
`create`; den kan afvige, når en backend kræver sit eget layout. OpenCode fortolker den returnerede sti og bruger den til
fortegnelse, startup-kommandoer og API-resultatet. Den returnerede mappe skal findes.

Strategier, der vælger en anden destination, håndterer navnkollisioner der. OpenCode opretter stadig den foreslåede overordnede
mappe, før strategien kaldes. `list` må kun rapportere mapper, som strategien ejer, samt eventuelle repositoryrødder.

```ts

    context: { signal: AbortSignal },

  remove(input: { directory: string; force: boolean }, context: { signal: AbortSignal }): Promise<void>
  list(
    sourceDirectory: string,
    context: { signal: AbortSignal },
  ): Promise<readonly { directory: string; type: "root" | "worktree" }[]>
}

  add(definition: WorktreeDefinition): void
}

```

Promise-callbacks skal samarbejde med `signal`-annullering. Effect-callbacks returnerer Effects og bruger i stedet Effect-afbrydelse.
Registreringer forbliver afgrænset til plugin-runtime; projektoperationer bruger det kanoniske checkouts register.
Core-konfigurationsadaptere fodrer mappeindstillinger ind i det register.

## Hooks

Hooks opsnapper live-operationer. Registrér en hook på dens domæne, og afvikl
den returnerede registrering, når den ikke længere er nødvendig.

```ts
const registration = await ctx.session.hook("context", () => {})
await registration.dispose()
```

Flere plugins kan registrere samme hook. OpenCode kører dem i pluginrækkefølge,
så senere hooks ser ændringer lavet af tidligere hooks.

### Sessioner

Sessionshooks griber ind, når prompts registreres, ved modelkald, i udbyderens HTTP-trafik og ved nye forsøg.

#### Forks

`fork`-hooken kører, efter at OpenCode har kopieret historikken, og før fork-kaldet returnerer. `sessionID` identificerer den nye session.

```ts
await ctx.session.hook("fork", ({ sessionID }) => console.log(sessionID))
```

#### Registrering af prompts

Grib ind, før OpenCode finder vedhæftninger og skills og gemmer den indgående brugerprompt i indbakken:

```ts
await ctx.session.hook("prompt", (event) => {
  event.prompt.text = event.prompt.text.replaceAll("company-secret", "[redacted]")
  event.prompt.files ??= []
  event.prompt.files.push({ uri: "file:///project/policy.md" })
  event.metadata = { ...event.metadata, source: "company-policy" }
  event.delivery = "queue"
})
```

Hooket får sit eget udkast, som det kan ændre:

- `prompt` indeholder `text`, `files`, agentomtaler i `agents` og valgte `skills`.
- `metadata` indeholder de metadata til registreringen, som appen har defineret.
- `delivery` er `"steer"` som standard og kan ændres til `"queue"`.
- Sessions- og besked-ID'er er skrivebeskyttede; et hook kan ikke omdirigere registreringen.

Filer og skills, som en hook tilføjer, findes og valideres på samme måde som ellers.
Når du omskriver tekst, skal du opdatere eller fjerne vedhæftnings-`mention`-forskydninger, der ikke
længere matcher. Agentomtaler skifter ikke sessionens aktive agent.

Prompt-hooks kører under disse betingelser:

- Hooks kører i registreringsrækkefølge, efter at sessionens location-plugins er klar.
- Kommandoer, der sender gennem `session.prompt`, kører hooken.
- Syntetiske beskeder, shell-beskeder, komprimeringskontroller og flyttekontroller gør ikke.
- Hooket kører én gang, når prompten registreres, ikke før hvert modelkald.
- Du kan ikke afgrænse hooket til en udbyder, fordi modelvalget først afgøres efter registreringen.

Det ændrede brugerinput gemmes som den autoritative version. Hvis forberedelsen mislykkes eller afbrydes, registrerer OpenCode ikke prompten.

Sørg for, at prompt-hooks kan tåle gentagne forsøg. De garanterer ikke, at sideeffekter kun sker én gang:

- Hvis du forsøger igen med et ID, der allerede venter eller er leveret, returneres den oprindelige registrering, uden at hooks køres igen.
- Samtidige indsendelser kan få hooks til at køre flere gange, men kun den første vellykkede registrering gælder.
- Prompt-hooks transformerer input og eksponerer ikke et typet afvisnings-API.

#### Modelanmodninger

Rediger sammensatte systeminstruktioner, beskeder, værktøjer eller indstillinger for anmodningen umiddelbart før modeldispatch. Hver
type anmodning, en session udsteder, har sin egen hook, så et plugin kan behandle agentløkken og hjælpeanmodninger
forskelligt:

- `context` kører for agentløkken, inklusive værktøjsdrevne fortsættelser.
- `compaction` kører for checkpointresuméer. `messages` er den samtalelog, der skal opsummeres; OpenCode tilføjer sin
  resuméprompt, efter hooks er kørt. Sæt `result` for selv at registrere komprimeringen og springe modelkaldet over; det tager de
  samme felter som en fuldført komprimeringsbesked.
- `generate` kører for forbigående `ctx.session.generate`-kald.
- `title` kører for titelgenerering. Den har ingen `agent` eller `tools`. Sæt `result` for selv at levere titlen.

```ts
await ctx.session.hook("context", (event) => {
  event.system.push({ type: "text", text: "Keep the review focused on correctness." })
  delete event.tools.write
  event.options.temperature = 0.2
  event.options.maxTokens = 8_000
})

await ctx.session.hook("compaction", async (event) => {
  event.result = { summary: await summarize(event.messages) }
})
```

Ændringer påvirker kun det udgående modelkald, ikke bevaret historik eller konfiguration. En hook, der skal gælde for
hver anmodning, skal registreres for hver type.

Beskeder i `context`-, `compaction`- og `generate`-hooks bærer deres gemte beskeds `metadata`, skrivebeskyttet
(f.eks. hvad en `prompt`-hook satte). Det sendes ikke til modellen.

Den `system`-del, der indeholder OpenCodes instruktioner, viser også hver kilde i `metadata.experimental.instructions` som
`{ key, text }`, f.eks. `core/date` eller `core/environment`, så en hook kan skelne kilderne. Listen er en kopi:
redigering af delens `text` opdaterer den ikke. Dette er eksperimentelt og kan ændre sig.

Tilsidesættelser i anmodningen følger disse regler:

- `options` starter tomt for hvert modelkald; det indeholder ikke de endelige modelindstillinger.
- Typede nøgler er genereringsindstillinger; enhver anden nøgle sendes til den valgte protokol som en udbyderindstilling.
- Hooks kører i registreringsrækkefølge og ser tilsidesættelser lavet af tidligere hooks.
- Tilsidesættelser i anmodningen har forrang over modelstandarder, som har forrang over rutestandarder.
- Udbyderindstillingsobjekter flettes rekursivt; arrays og skalarværdier erstatter tidligere værdier.
- Sletning af en tilsidesættelse eller sætning til `undefined` falder tilbage til konfigurerede standarder i stedet for at fjerne dem.
- Rå ændringer til HTTP-indholdet anvendes, efter at anmodningen er konverteret til protokollens format, og kan tilsidesætte felterne i resultatet.

#### Udbyderindstillinger

Udbyderindstillinger bruger den valgte protokols semantiske indstillingsnavne, ikke rå HTTP-body-felter. Afgræns udbyderspecifikke
indstillinger til den matchende udbyder. OpenAI Responses bruger f.eks. `reasoningEffort`:

```ts
await ctx.session.hook(
  "context",
  (event) => {
    event.options.reasoningEffort = "high"
  },
  { providerID: "openai" },
)
```

Genereringsindstillinger afhænger af den valgte protokol og model:

- `maxTokens` er den semantiske outputtokengrænse.
- Gemini understøtter `topK`; OpenAI Responses eksponerer det ikke.

#### Valg af model til anmodningen

Eksperimentelt. Kører, hver gang en session finder modellen til en anmodning, inden anmodningen bygges op. `model` er til at begynde med den valgte model. Skift værdien for at bruge en anden model fra samme udbyder til denne anmodning, også en model, der er skjult i modelvælgeren. Sessionen beholder den valgte model; anmodningen og assistentens besked bruger den nye. `kind` angiver, hvilken type anmodning der behandles, så en router kan springe titler over eller vælge model igen efter komprimering. En model fra en anden udbyder afvises som utilgængelig.

```ts
await ctx.session.hook(
  "experimental.model.resolve",
  (event) => {
    if (event.model.id === "auto" && event.kind !== "title")
      event.model = { providerID: event.model.providerID, id: pick(event.sessionID) }
  },
  { providerID: "acme" },
)
```

#### Modelanmodning

Rediger model-indstillinger for anmodningen, og afgræns eventuelt hooken til én udbyder. Hændelsen bærer samme `kind`
som HTTP-hookene nedenfor.

```ts
await ctx.session.hook(
  "model.request",
  (event) => {
    event.headers["x-plugin"] = "review"
  },
  { providerID: "anthropic" },
)
```

#### Native HTTP

Redigér udbyderens oprindelige HTTP-anmodninger eller -svar. Indholdet kan kun læses én gang som en stream. Klon eller erstat indholdet, før du læser det.

Begge hooks kører for hver anmodning, en session udsteder. `event.kind` angiver, hvilket flow der udstedte den: `"primary"` for agent-
løkken, `"compaction"` for checkpointresuméer, `"title"` for titelgenerering og `"generate"` for forbigående
`ctx.session.generate`-kald. Brug den i stedet for agent-ID'et til at skelne hjælpeanmodninger.

```ts
await ctx.session.hook("http.request", (event) => {
  event.request.headers.set("x-session-id", event.sessionID)
  if (event.kind === "title") event.request.headers.set("x-priority", "background")
})

await ctx.session.hook("http.response", (event) => {
  event.response = new Response(event.response.body, {
    status: event.response.status,
    headers: { ...Object.fromEntries(event.response.headers), "x-plugin": "review" },
  })
})
```

#### Native WebSocket (eksperimentelt)

Udbydere, der streamer over en WebSocket, åbner én forbindelse pr. session og genbruger den på tværs af anmodninger, så
`http.request` og `http.response` aldrig ser den trafik. Den eksperimentelle `experimental.ws.handshake`-hook kører én gang pr. model-
kald, før forbindelsen vælges. Den bærer samme `sessionID`, `agent`, `model` og `kind` som HTTP-
hookene samt forbindelsens `url` og `headers`. Ændring af `url` eller `headers` ændrer, hvilken socket anmodningen bruger, så et
roteret bearer-token genåbner forbindelsen.

HTTP-hooks kører stadig for hver HTTP-anmodning, inklusive den anmodning, som en WebSocket-rute falder tilbage til.

```ts
await ctx.session.hook(
  "experimental.ws.handshake",
  async (event) => {
    event.headers.authorization = `Bearer ${await mintToken(event.url)}`
    delete event.headers["api-key"]
  },
  { providerID: "azure" },
)
```

`experimental.ws.send` og `experimental.ws.receive` eksponerer selve frames, WebSocket-modstykket til
at redigere en HTTP-request- eller response-body. `send` kører, efter at udbyderdriveren har bygget en udgående frame, og før den
skrives; `receive` kører på hver indgående frame, før driveren observerer den. Begge bærer framen som en streng og
sender det, `frame` indeholder, når hooken returnerer.

OpenCode validerer ikke omskrevne frames. Driveren sporer tilstand ud fra udbyderens svar, så en omskrivning, der
ændrer protokolbetydning, er pluginets ansvar, ligesom en omskrevet HTTP-body er det.

```ts
await ctx.session.hook(
  "experimental.ws.send",
  (event) => {
    const body = JSON.parse(event.frame)
    if (body.type === "response.create") body.metadata = { ...body.metadata, session: event.sessionID }
    event.frame = JSON.stringify(body)
  },
  { providerID: "openai" },
)

await ctx.session.hook("experimental.ws.receive", (event) => {
  if (event.frame.includes('"type":"error"')) console.error(event.frame)
})
```

Disse hooks er eksperimentelle, og deres navne eller former kan ændre sig.

#### Genforsøgspolitik

Tilsidesæt genforsøgsbeslutningen for en udbyderfejl, eller erstat dens forsinkelse i millisekunder. Hooken kører, efter at OpenCode
klassificerer fejlen og foreslår sin politik, men før et genforsøg planlægges. Den eksponerer ikke, hvordan OpenCode
internt udfører det næste forsøg.

```ts
await ctx.session.hook("retry", (event) => {
  if (event.error.status === 429) {
    event.decision = { retry: true, delay: 10_000 }
    return
  }
  if (event.error.type === "provider.invalid-request" && event.attempt === 2) {
    event.decision = { retry: true, delay: 0 }
    return
  }
  if (event.attempt >= 3) event.decision = { retry: false }
})
```

Retry-hooks kan ændre OpenCodes indledende `decision` ved at gøre en terminal fejl
genforsøgsbar eller nedlægge veto mod et foreslået genforsøg.

Genforsøgsbeslutninger følger disse regler:

- Flere hooks kører i registreringsrækkefølge, og senere hooks ser den aktuelle beslutning.
- Det indbyggede maksimale forsøgsantal er stadig en hård grænse.
- `attempt` er det fysiske forsøg, der overvejes. Den indledende anmodning er `1`, så det første genforsøg er `2`.
- Ugyldige forsinkelser som `NaN`, uendelighed eller negative værdier falder tilbage til den beregnede forsinkelse.
- Gendannelse ved kontekstoverløb er separat, fordi den komprimerer samtalen i stedet for at prøve samme anmodning igen.

### Tilladelser

Gennemgå afgørelser om tilladelser, efter at de konfigurerede regler er evalueret, og før en handling udføres, eller en tilladelsesprompt vises.

```ts
await ctx.permission.hook("evaluate", async (event) => {
  if (event.action === "read") return

  const messages = await ctx.session.context({ sessionID: event.sessionID })
  const review = await ctx.generate.text({
    model: { providerID: "anthropic", id: "claude-sonnet-5-5" },
    prompt: buildSafetyPrompt({ messages, action: event.action, resources: event.resources }),
  })
  const decision = parseDecision(review.text)

  event.effect = decision.effect
  event.message = decision.reason
})
```

Tilladelseshooks følger disse regler:

- Hooks kører for `allow`- og `ask`-beslutninger.
- En eksplicit konfigureret `deny` er endelig og kalder ikke hooken.
- En hook kan ændre `effect` til `allow`, `ask` eller `deny`.
- `message` vises i en eskaleret tilladelsesanmodning eller bliver afvisningsårsagen.

## Understøt V1

Et plugin kan understøtte V1 og V2 fra samme indgangspunkt i pakken. Brug ét objekt med en V1-funktion `server()` og en V2-funktion `setup()` som standardeksport:

```ts title="src/index.ts"
import { Plugin } from "@opencode/plugin"

export default {
  ...Plugin.define({
    id: "example",
    async setup(ctx) {
      await ctx.tool.hook("execute.before", () => {
        console.log("A tool is about to run")
      })
    },
  }),
  async server() {
    return {
      "tool.execute.before": async () => {
        console.log("A tool is about to run")
      },
    }
  },
}
```

- V1 kalder `server()` og bruger de returnerede hooks.
- V2 læser standardeksportens `id` og `setup()` (eller `effect()` for Effect-plugins) og ignorerer `server()`.
- Hold hver implementering på sit eget API; deling af et export oversætter ikke V1-hooks til V2-hooks.
- Spread `Plugin.define(...)` ind i det eksporterede objekt, så det typechecker V2-definitionen separat fra `server()`.

V1-objektformen understøttes i OpenCode `1.18.29`. Ældre V1-releases kan
forvente funktionseksporter i stedet; test den installerede pakke med den ældste V1-
release, du vil understøtte, og med V2.
