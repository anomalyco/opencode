title: "Rozwiązywanie problemów"
description: "Diagnozuj problemy z OpenCode, sprawdzając usługę w tle, badając API, czytając logi i przechwytując profile."
---

<Callout type="tip">
  Możesz poprosić OpenCode o samodzielne debugowanie. Opisz problem i poproś o skorzystanie z tej strony; może odczytać
  poniższe kroki, sprawdzić swoją usługę i logi oraz pomóc zidentyfikować problem.
</Callout>

OpenCode korzysta z architektury klient-serwer. Serwer w tle zarządza sesjami, pluginami, uprawnieniami i innym stanem
aplikacji. Zacznij od ustalenia, czy problem dotyczy klienta, współdzielonego serwera czy konkretnego projektu.

## Sprawdzanie usługi w tle

Pokaż bieżące informacje o serwerze:

```bash
opencode service status
```

Sprawdź, czy jego API działa poprawnie:

```bash
opencode api get /api/info
```

Jeśli usługa zawiesiła się lub działa niepoprawnie, uruchom ją ponownie:

```bash
opencode service restart
```

Możesz też jawnie ją zatrzymać i uruchomić:

```bash
opencode service stop
opencode service start
```

<Callout type="note">
  OpenCode zwykle sam odnajduje lub uruchamia współdzieloną usługę w tle. Polecenia usługi są potrzebne tylko przy
  diagnozowaniu jej cyklu życia.
</Callout>

## Zezwalanie na źródło przeglądarki

Jeśli klient przeglądarkowy z innego źródła nie może się połączyć z powodu CORS, dodaj źródło klienta do konfiguracji
usługi:

```bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors
```

Użyj dokładnego źródła HTTP lub HTTPS, w razie potrzeby z portem, bez ścieżki ani końcowego ukośnika. Aby zezwolić na
wiele źródeł, przekaż listę rozdzielaną przecinkami jako jeden argument; odstępy wokół każdego źródła są usuwane:

```bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"
```

`service get cors` wypisuje tablicę JSON. Usuń skonfigurowaną listę przez:

```bash
opencode service unset cors
```

Ustawienie lub usunięcie konfiguracji usługi zatrzymuje usługę w tle. Przy następnym starcie przejmie nową konfigurację;
użyj `opencode service start`, aby uruchomić ją jawnie.

W przypadku serwera na pierwszym planie powtórz `--cors` dla każdego dodatkowego dozwolonego źródła:

```bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com
```

Przy `serve --service` podane flagi `--cors` zastępują zapisaną listę dla tego procesu. Bez tych flag tryb usługi używa
zapisanej listy. CORS nie zmienia adresu nasłuchiwania ani nie omija uwierzytelniania serwera.

## Badanie API

Polecenie `api` używa lokalnego wykrywania usługi i przepływu uwierzytelniania. Przyjmuje metodę HTTP i ścieżkę albo ID
operacji OpenAPI.

Wszystkie endpointy i ID operacji opisuje [dokumentacja API](/api).

Przekaż treść żądania JSON przez `--data` lub `-d`, a nagłówki dodaj przez `--header` lub `-H`.

<Callout type="warning">
  Uruchomienie `opencode api` może uruchomić usługę w tle, gdy nie ma dostępnej zgodnej, sprawnej usługi.
</Callout>

## Czytanie logów

Zainstalowane kompilacje zapisują logi w:

```text
~/.local/share/opencode/log/opencode.log
```

Śledź log podczas odtwarzania problemu:

```bash
tail -f ~/.local/share/opencode/log/opencode.log
```

Każda linia zawiera ID `run` procesu i pole `role`. Użyj `role=server` dla aktywności sesji, dostawców, pluginów,
uprawnień i narzędzi.

```bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log
```

## Przechwytywanie zrzutu sterty

Zapisz zrzut pamięci (sterty) działającego serwera w tle na dowolnej platformie:

```bash
opencode debug heap-dump
```

Polecenie czeka na ukończenie zrzutu, a następnie wypisuje jego ścieżkę:

```text
/home/me/.local/share/opencode/log/heap-48213-2026-10-23T013012345Z.heapsnapshot
```

Zapisz go gdzie indziej przez `--directory`. Serwer tworzy katalog, jeśli go nie ma:

```bash
opencode debug heap-dump --directory ./snapshots
```

- Używa tylko już działającego serwera. Nigdy go nie uruchamia, nie zastępuje ani nie restartuje.
- Użyj `--server <url>`, aby przechwycić serwer uruchomiony przez `opencode serve`. Ustaw `OPENCODE_PASSWORD`, jeśli go
  ma. `--directory` jest wtedy ścieżką na maszynie serwera.
- Otwórz plik w panelu Memory narzędzi Chrome DevTools.

<Callout type="warning">
  Serwer wstrzymuje się na czas zapisu zrzutu, a jego użycie pamięci może na krótko wzrosnąć. Zrzut może zawierać
  prompty, treści plików i poświadczenia. Nie udostępniaj go publicznie.
</Callout>

### W aplikacji desktopowej

Uruchom **Capture heap snapshots** z palety poleceń. W katalogu Pobrane powstanie jeden folder ze zrzutami wszystkich
części aplikacji i zestawieniem użycia pamięci, którego same zrzuty nie pokazują:

```text
opencode-heap-2026-10-23T013012345Z/
  memory.json                  where the memory is, per process, in MiB: start here
  memory-infra.json            Chromium's memory dump trace; open it in https://ui.perfetto.dev
  heap-48213-….heapsnapshot    the desktop's own server
  window-1-48390.heapsnapshot  one per app window
  main-48102.heapsnapshot      the desktop main process
  gpu.json                     the GPU and driver
  manifest.json                processes, PIDs, and memory before and after; written last
```

- Zrzut sterty zawiera tylko obiekty JavaScript i stronę. Obrazy, układ, warstwy kompozytora i pamięć GPU są
  w `memory.json` i `memory-infra.json`.
- Zdalne serwery nie są przechwytywane. Użyj na tej maszynie `opencode debug heap-dump`.
- Serwer zapisuje zrzut bezpośrednio w folderze, więc nic dużego nie jest przenoszone ani kopiowane.
- Karty przeglądarki nie są uwzględniane, ponieważ ich zrzuty zawierają treść odwiedzonych stron.

## Przechwytywanie profili CPU i pamięci

W macOS i Linuksie możesz wysłać sygnał do działającego procesu OpenCode, aby przechwycić dane diagnostyczne. Pobierz PID
serwera w tle z endpointu health:

```bash
opencode api get /api/info
```

Użyj `pid` z odpowiedzi z jednym z tych sygnałów:

- `SIGPROF` przechwytuje dziesięciosekundowy profil CPU:

  ```bash
  kill -SIGPROF <pid>
  ```

  Wynik jest zapisywany w katalogu logów jako `cpu-<pid>-<timestamp>.cpuprofile`.

- `SIGUSR1` przechwytuje zrzut pamięci (sterty):

  ```bash
  kill -SIGUSR1 <pid>
  ```

  Wynik jest zapisywany w katalogu logów jako `heap-<pid>-<timestamp>.heapsnapshot`.

Przed otwarciem pliku poczekaj na `CPU profile written` lub `heap snapshot written` w `opencode.log`. Odpowiedni wpis
w logu zawiera pełną ścieżkę. Oba typy plików możesz sprawdzić w Chrome DevTools.

<Callout type="note">
  Profile wywoływane sygnałem nie są dostępne w Windows. Zamiast tego użyj `opencode debug heap-dump` do zrzutów sterty.
  Zapisywanie zrzutu sterty może wstrzymać proces i tymczasowo zwiększyć jego użycie pamięci.
</Callout>

## Pliki usługi

Współdzielony serwer rejestruje się w:

```text
~/.local/state/opencode/service.json
```

Jego prywatna konfiguracja usługi jest przechowywana osobno w:

```text
~/.config/opencode/service.json
```

Baza danych zwykle znajduje się w:

```text
~/.local/share/opencode/opencode.db
```

`OPENCODE_DB` może nadpisać lokalizację bazy danych.

<Callout type="warning">
  Nie usuwaj ani nie edytuj plików usługi ani bazy danych podczas rozwiązywania problemów. Zarządzaj demonem poleceniami
  usługi, a przed sprawdzaniem trwałych danych zewnętrznymi narzędziami zrób kopię zapasową.
</Callout>

## Zgłaszanie problemu

Zgłaszając powtarzalny problem, dołącz:

- Dane wyjściowe `opencode --version`
- Dane wyjściowe `opencode service status`
- Najkrótszą sekwencję kroków odtwarzającą problem
- Informację, czy problem dotyczy współdzielonej usługi, konkretnego klienta czy jednego projektu
- Istotne linie logu, wraz z ich polami `run` i `role`

Usuń klucze API, nagłówki autoryzacji, prompty, treści plików i inne poufne dane przed udostępnieniem logów.

Zgłaszaj powtarzalne problemy w [GitHub Issues](https://github.com/anomalyco/opencode/issues).
