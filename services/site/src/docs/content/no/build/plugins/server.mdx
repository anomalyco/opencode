Serverdelen av en plugin kjører i OpenCode-serveren. Den endrer OpenCodes atferd og legger til funksjoner: verktøy,
hooks, integrasjoner, kommandoer og agenter. Se [Oversikten](/build/plugins) for hvordan en pluginpakke er bygget opp,
lastet og publisert.

```ts title=".opencode/plugins/example/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  async setup(ctx) {
    await ctx.storage.set("loaded", true)
  },
})
```

## Livssyklus

`setup` kjører når pluginen lastes inn. Funksjonen kan returnere en oppryddingsfunksjon som kjøres når pluginen lastes ut.

```ts
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  setup(ctx) {
    console.log(`loaded in OpenCode ${ctx.app.version}`)
    return () => console.log("unloaded")
  },
})
```

### Kontekst

Plugin-konteksten er i praksis en [OpenCode-serverklient](/build/client).
Metodene for lesing og handling bruker samme inndata og svar som klienten. I tillegg har konteksten metoder som
bare plugins kan bruke, for transforms, hooks under kjøring, innlasting på nytt, registreringer
og pluginalternativer.

```ts
setup(ctx) {
  console.log(ctx.app.version)
}
```

`ctx.location` beskriver plasseringen der denne plugin-forekomsten lastes. Den
inkluderer `directory`, valgfri `workspaceID` og `project`-metadata (`id`,
`directory` og `canonical`). Den er tilgjengelig i både Promise- og Effect-plugins.
Dette er plugin-forekomstens plassering, ikke plasseringen til hver økt den kan
nå eller hver hendelse den mottar.

```ts
setup(ctx) {
  console.log(ctx.location.directory)
  console.log(ctx.location.project.canonical)
}
```

### Alternativer

Send pluginalternativer med objektformen i `opencode.json(c)`.

```jsonc title="opencode.jsonc"
{
  "plugins": [
    {
      "package": "./plugins/company",
      "options": {
        "strict": true,
      },
    },
  ],
}
```

Les verdiene fra `ctx.options` under `setup`.

```ts title="plugins/company/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company",
  setup(ctx) {
    const strict = ctx.options.strict === true
  },
})
```

## Transforms

Transforms er synkrone endringer i OpenCodes domenetilstand, og hver bygger på tidligere registreringer i domenet sitt.
Registerlesinger som `ctx.model.list()` gjenspeiler hver registrering så langt, også under plugin-oppsett;
oppstartsbatching slår bare sammen oppdateringsvarsler og forsinker aldri det en lesing returnerer. Ressursstatus-API-er
rapporterer fortsatt tilstanden til kjørende ressurser: en registrert definisjon betyr ikke at tilkoblingen eller annet ressursarbeid er
fullført.

Kilder bidrar med leverandører og uforanderlige modelldefinisjoner gjennom `ctx.provider.transform`.

```ts title="plugins/models/index.ts"
import { Model, Plugin, Provider } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const providerID = Provider.ID.make("acme")
    const models = [{ ...Model.Info.default(providerID, Model.ID.make("reasoner")), name: "Acme Reasoner" }]
    await ctx.provider.transform((editor) => {
      editor.add({
        info: {
          ...Provider.Info.empty(providerID),
          name: "Acme",
          activation: "enabled",
          package: "@opencode/ai/providers/openai-compatible",
          settings: { baseURL: "http://127.0.0.1:8000/v1" },
        },
        models,
      })
    })

    const available = await ctx.model.list()
  },
})
```

Registrering, fjerning og `reload()` markerer registeret som endret. Ved neste lesing bygges registeret opp på nytt:
Alle aktive transforms kjøres på en ny verdi i registreringsrekkefølge. Sørg for at de krever lite arbeid og kan kjøres flere ganger.
Senere gjenoppbygging endrer aldri en verdi du allerede har lest.

Etter at leverandørtransforms og tilgjengelighet er løst, materialiserer OpenCode modellene til de aktive leverandørene og spiller av
hver modelltransform i rekkefølge. En modellpolicy kan inspisere hele kandidatsamlingen, inkludert nylig oppdaterte
kilder.

```ts title="plugins/model-budget/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.model-budget",
  async setup(ctx) {
    await ctx.model.transform((editor) => {
      editor
        .list()
        .filter((model) => model.cost.some((tier) => tier.output > 20))
        .forEach((model) => {
          editor.remove(model.providerID, model.id)
        })
    })
  },
})
```

Fangede inndata overvåkes ikke automatisk. Last eksterne data før den synkrone tilbakeringingen, og kall deretter
`reload()` etter at disse inndataene endres. Her returnerer `loadFromSource()`
oppføringene `{ info: Provider.Info, models: readonly Model.Info[] }`.

```ts title="plugins/models/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const source = { providers: await loadFromSource() }

    await ctx.provider.transform((editor) => {
      source.providers.forEach((provider) => editor.add(provider))
    })

    const refresh = async () => {
      source.providers = await loadFromSource()
      await ctx.provider.reload()
    }

    const timer = setInterval(() => void refresh().catch(console.error), 60_000)
    return () => clearInterval(timer)
  },
})
```

Leverandørendringer invaliderer hele det aktive modellresultatet, så utdataprispolicyen filtrerer fortsatt de oppdaterte modellene.
Bruk `ctx.model.reload()` når bare en inndata fanget av en modelltransform endres.

## API

### Agent

Les alle agenter eller hent én etter ID.

```ts
const agents = await ctx.agent.list()
const build = await ctx.agent.get({ agentID: "build" })
```

Registrer en transform for å inspisere, opprette, oppdatere eller fjerne agenter, eller for å velge standardagenten.

```ts
await ctx.agent.transform((editor) => {
  const agents = editor.list()
  const build = editor.get("build")

  editor.default("build")
  editor.update("build", (agent) => {
    agent.description = "Builds features and fixes bugs"
  })
  editor.remove("legacy")
})
```

Registrer en ny agent med `editor.update`. Hvis ID-en allerede finnes, redigeres den agenten. Ellers opprettes en ny
agent med `Agent.Info.default(id)` før callback-funksjonen kjøres.

```ts
await ctx.agent.transform((editor) => {
  editor.update("reviewer", (agent) => {
    agent.description = "Reviews code for correctness and maintainability"
    agent.mode = "subagent"
    agent.system = "Review the proposed changes and report actionable findings."
  })
})
```

Last agenter på nytt etter at ekstern tilstand brukt av en transform er endret.

```ts
await ctx.agent.reload()
```

### Leverandører

Les tilgjengelige leverandører eller inspiser én leverandørs metadata etter ID.

```ts
const providers = await ctx.provider.list()
const provider = await ctx.provider.get({ providerID: "anthropic" })
```

Leverandørtransforms redigerer leverandørinnstillinger og kildedefinisjoner. Redigererlesinger inkluderer inaktive leverandører og eksponerer
uforanderlige definisjoner; `models.update` redigerer en eid kopi av en kildemodell.

```ts
await ctx.provider.transform((editor) => {
  editor.update("anthropic", (provider) => {
    provider.headers = { ...provider.headers, "x-company": "engineering" }
  })
  editor.models.update("anthropic", "claude-sonnet-5-5", (model) => {
    model.name = "Team Sonnet"
  })
  editor.models.remove("anthropic", "legacy-model")
  editor.remove("legacy-provider")
})
```

Erstatt en leverandørs kildebeholdning med `models.set`, og last deretter på nytt etter at de fangede definisjonene endres.

```ts
const source = { models: await loadModels() }
await ctx.provider.transform((editor) => {
  editor.models.set("acme", source.models)
})

source.models = await loadModels()
await ctx.provider.reload()
```

For kontospesifikk oppdagelse, send tilkoblingen som ble brukt til å laste beholdningen, som `sourceConnection`. OpenCode utelater
den leverandøren mens en annen tilkobling er valgt, til plugin'en din publiserer sin oppdaterte beholdning.

```ts
const connection = await ctx.integration.connection.active("acme")
if (!connection) return
const inventory = await loadInventory(connection)
await ctx.provider.transform((editor) => {
  editor.add({ info: inventory.provider, models: inventory.models, sourceConnection: connection })
})
```

### Modeller

Les tilgjengelige modeller og standardvalget.

```ts
const models = await ctx.model.list()
const selected = await ctx.model.default()
```

Modelltransforms redigerer hele kandidatsamlingen for aktive leverandører. Deaktiverte kandidater forblir redigerbare til alle
transforms er ferdige; `update` kan legge til en modell bare under en tilgjengelig leverandør.

```ts
await ctx.model.transform((editor) => {
  editor.list("anthropic").forEach((model) => {
    editor.update(model.providerID, model.id, (draft) => {
      draft.enabled = draft.capabilities.tools
    })
  })
  editor.default.set("anthropic", "claude-sonnet-5-5")
  editor.remove("anthropic", "legacy-model")
})
```

Tilbakeringinger redigerer rå modelloverstyringer. Leverandørstandarder flettes én gang når OpenCode fullfører resultatet; uendrede lesinger
gjenbruker det resultatet. `editor.provider` eksponerer uforanderlige kildedefinisjoner, inkludert inaktive maler, i stedet for
modelltransformutdata.

```ts
await ctx.model.transform((editor) => {
  const source = editor.provider.get("anthropic")?.models.get("claude-sonnet-5-5")
  if (!source) return
  editor.update("anthropic", source.id, (model) => {
    model.limit.context = Math.min(model.limit.context, source.limit.context)
  })
})

await ctx.model.reload()
```

### Integrasjoner

Les integrasjoner og se hvilke tilgangsopplysninger som er aktive.

```ts
const integrations = await ctx.integration.list()
const github = await ctx.integration.get({ integrationID: "github" })
const connection = await ctx.integration.connection.active("github")
const credential = connection ? await ctx.integration.connection.resolve(connection) : undefined
```

Koble integrasjoner til med en API-nøkkel.

```ts
await ctx.integration.connect.key({
  integrationID: "github",
  key: process.env.GITHUB_TOKEN!,
})
```

Start, inspiser, fullfør eller avbryt et OAuth-tilkoblingsforsøk.

```ts
const attempt = await ctx.integration.oauth.connect({ integrationID: "github", methodID: "oauth" })
const status = await ctx.integration.oauth.status({ integrationID: "github", attemptID: attempt.data.attemptID })
await ctx.integration.oauth.complete({ integrationID: "github", attemptID: attempt.data.attemptID, code })
await ctx.integration.oauth.cancel({ integrationID: "github", attemptID: attempt.data.attemptID })
```

Kommandobaserte tilkoblinger eksponerer samme flyt for start, status og avbrytelse.

```ts
const attempt = await ctx.integration.command.connect({ integrationID: "acme", methodID: "cli" })
const status = await ctx.integration.command.status({ integrationID: "acme", attemptID: attempt.data.attemptID })
await ctx.integration.command.cancel({ integrationID: "acme", attemptID: attempt.data.attemptID })
```

Registrer en transform for å inspisere integrasjoner og administrere autentiseringsmetodene deres.

```ts
await ctx.integration.transform((editor) => {
  const integrations = editor.list()
  const acme = editor.get("acme")

  editor.update("acme", (integration) => {
    integration.name = "Acme"
  })
  editor.method.update({
    integrationID: "acme",
    method: { id: "cli", type: "command", label: "Sign in with Acme CLI", command: ["acme", "login"] },
  })

  const methods = editor.method.list("acme")
  const legacy = methods.find((method) => method.type === "command" && method.id === "legacy")
  if (legacy) editor.method.remove("acme", legacy)
  editor.remove("legacy")
})
```

Last integrasjoner på nytt etter at ekstern tilstand brukt av en transform er endret.

```ts
await ctx.integration.reload()
```

### MCP

List MCP-servere og deres gjeldende tilkoblingstilstand.

```ts
const servers = await ctx.mcp.list()
```

Plugins administrerer MCP-servere bare gjennom transforms. Bruk `editor.set` for å legge til eller erstatte en server, `editor.update` for å
endre konfigurasjonen og `editor.remove` for å fjerne den. Inspiser konfigurasjonen med `editor.list` og `editor.get`.

```ts
await ctx.mcp.transform((editor) => {
  const servers = editor.list()
  const docs = editor.get("docs")
  editor.set("docs", { type: "remote", url: "https://mcp.example.com" })
  editor.update("docs", (server) => {
    server.disabled = false
  })
  editor.remove("legacy")
})
```

Angi `disabled: true` i en transform for å deaktivere og koble fra en server, eller `disabled: false` for å aktivere den og la
OpenCode koble til. OpenCode tilpasser servernes livssyklus til den transformerte konfigurasjonen.

Kall `reload()` når ekstern tilstand som en transform bruker, endres. Da brukes transformene på nytt, og serverne tilpasses resultatet.

```ts
await ctx.mcp.reload()
```

### Tillatelser

Be om tillatelse før du utfører en handling. `assert` vurderer øktens [tillatelsesregler](/permissions),
inkludert lagrede godkjenninger, og spør brukeren når en regel gir `ask`. Den fullføres når handlingen er tillatt.

```ts
execute: async (input, context) => {
  await ctx.permission.assert({
    sessionID: context.sessionID,
    agent: context.agent,
    source: { type: "tool", messageID: context.messageID, id: context.id },
    action: "deploy",
    resources: [input.environment],
    save: [input.environment],
  })
  return { content: await deploy(input.environment) }
}
```

- `action` og `resources` samsvares med reglene. En `deny` blokkerer handlingen; ellers spør en `ask`.
- `save` lister mønstrene som lagres når brukeren velger å alltid tillate.
- `agent` velger hvilke regler som gjelder, og er som standard øktens agent. `source` knytter prompten til et verktøykall.
- `metadata` sender ekstra detaljer til tillatelsesforespørsler og `evaluate`-hooks.

En deny-regel eller en avvisning med tilbakemelding avvises med en `Tool.Error` som bærer årsaken, slik at modellen ser den og
fortsetter. En ren avvisning avslutter gjeldende trinn. La disse feilene forplante seg i stedet for å returnere dem som verktøy-
utdata.

Inspiser eller løs ventende tillatelsesforespørsler.

```ts
const pending = await ctx.permission.list({ sessionID })
const request = await ctx.permission.get({ sessionID, requestID })
```

### Verktøy

Les verktøyene som er registrert nå, etter alle transforms, utenfor en transformtilbakeringing. Hvert verktøy har en `id`
som inneholder dets effektive navn.

```ts
const tools = await ctx.tool.list()
const read = tools.find((tool) => tool.id === "read")
```

Registrer, oppdater og fjern verktøy med en synkron transform, også i Promise-plugins. Last eksterne data
før du registrerer eller laster på nytt. En senere gyldig registrering overstyrer samme effektive verktøynavn.

```ts
const registration = await ctx.tool.transform((editor) => {
  editor.namespace({
    name: "acme",
    description: "Customer account tools",
  })
  editor.add({
    name: "greeting",
    description: "Create a greeting",
    input: {
      type: "object",
      properties: { name: { type: "string" } },
      required: ["name"],
      additionalProperties: false,
    },
    options: { namespace: "acme", codemode: true },
    execute: async (input, context) => {
      await context.progress({ status: "greeting" })
      return { content: `Hello ${(input as { name: string }).name}!` }
    },
  })
})
```

Funksjoner som kjører Promise-verktøy, mottar `context.signal`. Send signalet videre til operasjoner som kan avbrytes, for eksempel `fetch`.
Da stopper også den underliggende operasjonen når økten stoppes.

```ts
execute: async ({ url }, context) => {
  const response = await fetch(url, { signal: context.signal })
  return { content: await response.text() }
}
```

#### Fri form for verktøyinndata

Et direkte verktøy med nøyaktig ett påkrevd strengfelt kan la modellen skrive den strengen uten JSON-innpakning. Angi `freeform` til `{ type: "text" }`, `{ type: "regex", pattern }` eller `{ type: "lark", grammar }`.

```ts
editor.add({
  name: "ticket",
  description: "Look up a ticket by ID",
  options: { codemode: false },
  input: Schema.Struct({ id: Schema.String }),
  freeform: { type: "regex", pattern: "OPS-[0-9]+" },
  execute: async ({ id }) => ({ content: await lookup(id) }),
})
```

Hvis den valgte modellens API lister `regex` i models.dev, kan modellen skrive `OPS-42` direkte. Ellers utelater Core **bare** `freeform`: modellen har fortsatt `ticket`-verktøyet og kaller det med `{"id":"OPS-42"}`. Manglende eller tomme formatlister betyr ingen fri form-støtte. Utføreren mottar `{ id }` uansett.

Inne i Code Mode (`codemode: true`) tar et fri form-verktøy strengen direkte, som i `await tools.ticket("OPS-42")`. `await tools.ticket({ id: "OPS-42" })` virker også.

Kall `reload()` etter at kildedata fanget av tilbakeringingen er endret. Omlasting spiller av de aktive transformene uten
å endre rekkefølgen; den kjører ikke plugin-oppsettet på nytt.

```ts
await ctx.tool.reload()
```

Bruk `list()` og `get()` for å inspisere verktøyene som er i redigereren nå. Verktøy har en `id` som inneholder det effektive navnet,
og `get()` returnerer `undefined` når den ID-en ikke finnes. Bruk `update` og `remove` med det effektive verktøynavnet,
inkludert navnerommet (`acme_greeting` ovenfor). Punktum i navnerom blir `_`. I verktøynavn beholdes bokstaver, sifre,
`_` og `-`. Alle andre tegn blir `_`. Navn som ikke finnes, ignoreres. Bruk `add` med en fullstendig definisjon for å
opprette et verktøy. Oppdateringer bevarer navn og navnerom. Tilordne nye skjemaer eller alternativer for å erstatte
dem i stedet for å mutere nestede verdier. Ugyldige oppdateringer logges og lar den forrige definisjonen være intakt.

```ts
await ctx.tool.transform((editor) => {
  editor.update("acme_greeting", (tool) => {
    tool.description = "Greet the user by name"
  })
  editor.remove("acme_obsolete")
})
```

Oppdateringer og fjerninger spilles av i rekkefølge med tillegg, også etter oppdateringer av MCP-katalogen. Avhending av
registreringen fjerner disse endringene og bygger på nytt fra de gjenværende transformene.

Avhend en registrering for å fjerne transformen og bygge på nytt fra de gjenværende transformene, slik at en tidligere
definisjon den overstyrte, avdekkes. Avhending er idempotent, og avlasting av plugin'en avhender også registreringene.

```ts
await registration.dispose()
```

Hver modellforespørsel fanger et stabilt, kjørbart verktøysnapshot. Senere transforms, omlastinger og avhending påvirker fremtidige
snapshots, ikke definisjonene, Code Mode-navneromsbeskrivelsene eller utførerne som allerede er fanget. Utførere som lukker
over muterbare plugin-data, observerer fortsatt disse dataene; fang en verdi inne i transformen når den må forbli knyttet til
den definisjonen.

### Worktrees

Registrer en lokal worktree-strategi med normal plugin-livssyklus. Implementasjonsmodulen i dette eksempelet eier
validering av alternativer og backendens `create`-, `remove`- og `list`-operasjoner.

```ts title="plugins/worktrees/index.ts"
import { Plugin } from "@opencode/plugin"
import { makeStrategy } from "./strategy"

export default Plugin.define({
  id: "company.worktrees",
  async setup(ctx) {
    const strategy = makeStrategy(ctx.options)
    await ctx.worktree.transform((editor) => {
      editor.add(strategy)
    })
  },
})
```

Last plugin'en gjennom `plugins` og konfigurer fellesdestinasjonen separat:

```jsonc title="opencode.jsonc"
{
  "worktree": { "directory": "../worktrees" },
  "plugins": [{ "package": "./plugins/worktrees", "options": {} }],
}
```

- Tillegg av en strategi velger den automatisk. Den siste aktive registreringen vinner; ingen konfigurasjon for strategivalg trengs.
- Avhending av registreringen eller avlasting av plugin'en gjenoppretter forrige implementasjon, til slutt den medfølgende Git-strategien.
- `reload()` spiller av transforms etter at fangede inndata er endret; den kjører ikke plugin-oppsettet på nytt.
- Opprettingsfeil prøves ikke på nytt gjennom Git. Eksisterende worktrees beholder sin registrerte eier selv når standarden endres.
- Strategier administrerer lokale kataloger. Provisjonering av eksterne arbeidsområder er ikke en del av dette grensesnittet.

#### Operasjoner

Plugin-konteksten eksponerer de samme prosjektbaserte worktree-operasjonene som klienten. Hver operasjon krever en
`projectID`. `list` leser bare lagret beholdning, inkludert kjente utsjekker av samme prosjekt; den laster ikke
konfigurasjon, starter ikke plugins og oppdager ikke filsystemendringer.

```ts
const projectID = ctx.location.project.id
const created = await ctx.worktree.create({ projectID, name: "task" })
const inventory = await ctx.worktree.list({ projectID })
await ctx.worktree.refresh({ projectID })
await ctx.worktree.remove({ projectID, directory: created.directory, force: false })
```

Oppretting laster konfigurasjon og plugins fra prosjektets lagrede `canonical`-katalog og bruker deres valgte strategi.
Den godtar en valgfri overordnet `directory`, kilde `from`, start `branch` og `name`.
Kilden er som standard den kanoniske utsjekken, og en `from`-overstyring må tilhøre det prosjektet. Valg av kilde
endrer ikke konfigurasjonsroten.
En oppgitt startreferanse må støttes av den valgte strategien;
Rifts native snapshot-operasjon har for eksempel ingen valg av referanse.

Oppretting og oppdatering venter på at den kanoniske utsjekkens plugins aktiveres. Kall som gjøres under den utsjekkens plugin-
oppsett, ser registreringene så langt og venter ikke på egen aktivering.

Fjerning laster den kanoniske konfigurasjonen og aktiverer pluginene, og bruker deretter worktreens registrerte strategi i stedet
for gjeldende valgte standard. En utilgjengelig registrert eier gir en feil. Worktreens destinasjon kan
ligge et annet sted:

```ts
await ctx.worktree.remove({
  directory: "/worktrees/task",
  projectID,
  force: false,
})
```

Manglende eiere gjør at fjerning mislykkes i stedet for å falle tilbake til Git. En strategi kan kaste `new Worktree.OperationError({
message: "Uncommitted changes", forceRequired: true })`, med `Worktree` importert fra `@opencode/plugin`, for å be om bekreftelse
før en tvungen fjerning, uten å være avhengig av feil fra Core eller Git.

Oppdatering laster kanonisk konfigurasjon og ber alle tilgjengelige strategier finne worktrees på tvers av kjente utsjekkrøtter.
Den kombinerer resultater, bevarer registrert eierskap og rydder bort manglende kataloger. En mislykket oppdagelseskilde logges
mens andre kilder fortsetter. Eksisterende kataloger forblir lagret selv om ingen tilgjengelig strategi rapporterer dem. Observer
`worktree.updated` og kall `list` igjen for å lese endret beholdning.

```ts
await ctx.worktree.refresh({ projectID })
```

#### Referanse

Implementasjoner mottar en foreslått destinasjon etter navngiving og kollisjonshåndtering. Returner den faktiske katalogen fra
`create`; den kan avvike når en backend krever eget oppsett. OpenCode slår opp stien som returneres, og bruker den til
beholdning, oppstartskommandoer og API-resultatet. Den returnerte katalogen må finnes.

Strategier som velger en annen destinasjon, håndterer navnekollisjoner der. OpenCode oppretter fortsatt den foreslåtte overordnede
katalogen før den kaller strategien. `list` må bare rapportere kataloger strategien eier, pluss eventuelle repositoriumsrøtter.

```ts
interface WorktreeDefinition {
  readonly id: string
  create(
    input: { sourceDirectory: string; directory: string; branch?: string },
    context: { signal: AbortSignal },
  ): Promise<{ directory: string }>
  remove(input: { directory: string; force: boolean }, context: { signal: AbortSignal }): Promise<void>
  list(
    sourceDirectory: string,
    context: { signal: AbortSignal },
  ): Promise<readonly { directory: string; type: "root" | "worktree" }[]>
}

interface WorktreeEditor {
  add(definition: WorktreeDefinition): void
}

interface WorktreeDomain extends WorktreeApi {
  transform(callback: (editor: WorktreeEditor) => void): Promise<Registration>
  reload(): Promise<void>
}
```

Promise-tilbakeringinger må samarbeide med `signal`-avbrytelse. Effect-tilbakeringinger returnerer Effects og bruker Effect-avbrytelse
i stedet. Registreringer forblir avgrenset til plugin-kjøretiden; prosjektoperasjoner bruker den kanoniske utsjekkens register.
Core-konfigurasjonsadaptere mater kataloginnstillinger inn i det registeret.

## Hooks

Hooks griper inn i operasjoner mens de pågår. Registrer en hook på domenet den tilhører, og fjern registreringen du får tilbake,
når du ikke lenger trenger den.

```ts
const registration = await ctx.session.hook("context", () => {})
await registration.dispose()
```

Flere plugins kan registrere samme hook. OpenCode kjører dem i pluginrekkefølge,
så senere hooks ser endringer gjort av tidligere hooks.

### Økter

Økthooks fanger promptgodtakelse, modellkall, native HTTP og nye forsøk.

#### Forgreninger

`fork`-hooken kjører etter at OpenCode har kopiert historikken og før forgreningskallet returnerer. `sessionID` identifiserer den nye økten.

```ts
await ctx.session.hook("fork", ({ sessionID }) => console.log(sessionID))
```

#### Mottak av prompter

Fang opp innkommende brukerprompter før OpenCode finner vedlegg og skills og lagrer prompten i innboksen:

```ts
await ctx.session.hook("prompt", (event) => {
  event.prompt.text = event.prompt.text.replaceAll("company-secret", "[redacted]")
  event.prompt.files ??= []
  event.prompt.files.push({ uri: "file:///project/policy.md" })
  event.metadata = { ...event.metadata, source: "company-policy" }
  event.delivery = "queue"
})
```

Hooken mottar et eid, muterbart utkast:

- `prompt` inneholder `text`, `files`, agentomtaler i `agents` og valgte `skills`.
- `metadata` inneholder applikasjonsdefinert godtakelsesmetadata.
- `delivery` er `"steer"` som standard og kan endres til `"queue"`.
- Økt- og meldings-ID-er er skrivebeskyttet; en hook kan ikke omdirigere godtakelsen.

OpenCode finner og validerer filer og skills som en hook legger til, på vanlig måte.
Når du skriver om tekst, oppdater eller fjern vedleggs-`mention`-forskyvninger som ikke
lenger samsvarer. Agentomtaler bytter ikke øktens aktive agent.

Prompt-hooks kjører under disse forholdene:

- Hooks kjører i registreringsrekkefølge etter at øktens plasseringsplugins er klare.
- Kommandoer som sender gjennom `session.prompt`, kjører hooken.
- Syntetiske meldinger, terminalmeldinger, komprimeringskontroller og flyttekontroller utløser den ikke.
- Hooken kjører én gang under godtakelsen, ikke før hvert modellkall.
- Leverandøravgrensning er utilgjengelig fordi modelloppløsningen skjer etter godtakelsen.

Endringene blir den kanoniske, varige brukerinndataen. Hvis forberedelsen mislykkes eller
avbrytes, godtar ikke OpenCode prompten.

Skriv prompt-hooks som tåler å bli kjørt på nytt. Det er ingen garanti for at sideeffekter skjer nøyaktig én gang:

- Nytt forsøk på en ID som allerede venter eller er levert, returnerer den opprinnelige godtakelsen uten å kjøre hooks på nytt.
- Samtidige innsendinger kan kjøre hooks mer enn én gang, men bare den første vellykkede godtakelsen vinner.
- Prompt-hooks transformerer inndata og eksponerer ikke et typet avvisnings-API.

#### Modellforespørsler

Endre sammensatte systeminstruksjoner, meldinger, verktøy eller forespørselsalternativer rett før modelutsending. Hver
type forespørsel en økt sender, har sin egen hook, så en plugin kan behandle agentløkken og hjelpeforespørsler
ulikt:

- `context` kjører for agentløkken, inkludert verktøydrevne fortsettelser.
- `compaction` kjører for sjekkpunktsammendrag. `messages` er transkripsjonen som oppsummeres; OpenCode legger til
  sammendragsprompten etter at hooks har kjørt. Angi `result` for å registrere komprimeringen selv og hoppe over modellkallet; det tar
  samme felt som en fullført komprimeringsmelding.
- `generate` kjører for midlertidige `ctx.session.generate`-kall.
- `title` kjører for tittelgenerering. Det har ingen `agent` eller `tools`. Angi `result` for å levere tittelen selv.

```ts
await ctx.session.hook("context", (event) => {
  event.system.push({ type: "text", text: "Keep the review focused on correctness." })
  delete event.tools.write
  event.options.temperature = 0.2
  event.options.maxTokens = 8_000
})

await ctx.session.hook("compaction", async (event) => {
  event.result = { summary: await summarize(event.messages) }
})
```

Endringer påvirker bare det utgående modellkallet, ikke lagret historikk eller konfigurasjon. En hook som skal gjelde
hver forespørsel, må registreres for hver type.

Meldinger i `context`-, `compaction`- og `generate`-hookene bærer `metadata` fra sin lagrede melding, skrivebeskyttet
(for eksempel det en `prompt`-hook satte). Det sendes ikke til modellen.

`system`-delen som inneholder OpenCodes instruksjoner, lister også hver kilde i `metadata.experimental.instructions` som
`{ key, text }`, for eksempel `core/date` eller `core/environment`, slik at en hook kan skille kildene. Listen er en kopi:
redigering av delens `text` oppdaterer den ikke. Dette er eksperimentelt og kan endres.

Forespørselsoverstyringer følger disse reglene:

- `options` starter tomt for hvert modellkall; det inneholder ikke løste modellinnstillinger.
- Typede nøkler er genereringsinnstillinger; enhver annen nøkkel sendes til den valgte protokollen som et leverandøralternativ.
- Hooks kjører i registreringsrekkefølge og ser overstyringer gjort av tidligere hooks.
- Forespørselsoverstyringer har forrang over modellstandarder, som har forrang over rutestandarder.
- Leverandøralternativobjekter flettes rekursivt; matriser og skalarverdier erstatter tidligere verdier.
- Sletting av en overstyring eller angivelse av `undefined` faller tilbake til konfigurerte standarder i stedet for å fjerne dem.
- Rå HTTP-bodyoverlegg brukes etter protokollsenking og kan overstyre de resulterende feltene.

#### Leverandøralternativer

Leverandøralternativer bruker den valgte protokollens semantiske alternativnavn, ikke rå HTTP-bodyfelt. Avgrens leverandørspesifikke
innstillinger til den samsvarende leverandøren. For eksempel bruker OpenAI Responses `reasoningEffort`:

```ts
await ctx.session.hook(
  "context",
  (event) => {
    event.options.reasoningEffort = "high"
  },
  { providerID: "openai" },
)
```

Genereringsalternativer avhenger av valgt protokoll og modell:

- `maxTokens` er den semantiske grensen for utdatatokens.
- Gemini støtter `topK`; OpenAI Responses eksponerer det ikke.

#### Modelloppløsning

Eksperimentelt. Kjører hver gang en Session løser modellen for en forespørsel, før noe bygges for den. `model` starter
som den valgte modellen; endre den for å betjene denne forespørselen med en annen modell fra samme leverandør, inkludert en som er skjult
fra modellvelgeren. Session beholder sin valgte modell; forespørselen og assistentmeldingen bruker den nye.
`kind` sier hvilken forespørsel som løses, slik at en ruter kan hoppe over titler eller rute på nytt etter komprimering. En modell fra
en annen leverandør mislykkes som utilgjengelig.

```ts
await ctx.session.hook(
  "experimental.model.resolve",
  (event) => {
    if (event.model.id === "auto" && event.kind !== "title")
      event.model = { providerID: event.model.providerID, id: pick(event.sessionID) }
  },
  { providerID: "acme" },
)
```

#### Modellforespørsel

Endre modellforespørselsinnstillinger og eventuelt avgrens hooken til én leverandør. Hendelsen bærer samme `kind`
som HTTP-hookene nedenfor.

```ts
await ctx.session.hook(
  "model.request",
  (event) => {
    event.headers["x-plugin"] = "review"
  },
  { providerID: "anthropic" },
)
```

#### Native HTTP

Endre native leverandørforespørsler eller -svar. Bodyene deres er engangsstrømmer; klon eller erstatt en body før du leser
den.

Begge hookene kjører for hver forespørsel en økt sender. `event.kind` sier hvilken flyt som sendte den: `"primary"` for agent-
løkken, `"compaction"` for sjekkpunktsammendrag, `"title"` for tittelgenerering og `"generate"` for midlertidige
`ctx.session.generate`-kall. Bruk den i stedet for agent-ID-en for å skille hjelpeforespørsler.

```ts
await ctx.session.hook("http.request", (event) => {
  event.request.headers.set("x-session-id", event.sessionID)
  if (event.kind === "title") event.request.headers.set("x-priority", "background")
})

await ctx.session.hook("http.response", (event) => {
  event.response = new Response(event.response.body, {
    status: event.response.status,
    headers: { ...Object.fromEntries(event.response.headers), "x-plugin": "review" },
  })
})
```

#### Native WebSocket (eksperimentelt)

Leverandører som strømmer over en WebSocket, åpner én tilkobling per økt og gjenbruker den på tvers av forespørsler, så
`http.request` og `http.response` ser aldri den trafikken. `experimental.ws.handshake`-hooken kjører én gang per modell-
kall før tilkoblingen velges. Den bærer samme `sessionID`, `agent`, `model` og `kind` som HTTP-
hookene, pluss tilkoblingens `url` og `headers`. Endring av `url` eller `headers` endrer hvilken socket forespørselen bruker, så en
rotert bearer-token åpner tilkoblingen på nytt.

HTTP-hooks kjører fortsatt for hver HTTP-forespørsel, inkludert forespørselen en WebSocket-rute faller tilbake til.

```ts
await ctx.session.hook(
  "experimental.ws.handshake",
  async (event) => {
    event.headers.authorization = `Bearer ${await mintToken(event.url)}`
    delete event.headers["api-key"]
  },
  { providerID: "azure" },
)
```

`experimental.ws.send` og `experimental.ws.receive` eksponerer rammene selv, WebSocket-motstykket til
redigering av en HTTP-forespørsels- eller -svarbody. `send` kjører etter at leverandørdriveren har bygget en utgående ramme og før den
skrives; `receive` kjører på hver innkommende ramme før driveren observerer den. Begge bærer rammen som en streng og
sender det `frame` inneholder når hooken returnerer.

OpenCode validerer ikke omskrevne rammer. Driveren sporer tilstand fra leverandørens svar, så en omskriving som
endrer protokollbetydning, er pluginens ansvar, akkurat som en omskrevet HTTP-body er det.

```ts
await ctx.session.hook(
  "experimental.ws.send",
  (event) => {
    const body = JSON.parse(event.frame)
    if (body.type === "response.create") body.metadata = { ...body.metadata, session: event.sessionID }
    event.frame = JSON.stringify(body)
  },
  { providerID: "openai" },
)

await ctx.session.hook("experimental.ws.receive", (event) => {
  if (event.frame.includes('"type":"error"')) console.error(event.frame)
})
```

Disse hookene er eksperimentelle, og navnene eller formene kan endres.

#### Policy for nye forsøk

Overstyr beslutningen om nytt forsøk for en leverandørfeil eller erstatt forsinkelsen i millisekunder. Hooken kjører etter at OpenCode
klassifiserer feilen og foreslår policyen sin, men før noe nytt forsøk planlegges. Den eksponerer ikke hvordan OpenCode
internt utfører neste forsøk.

```ts
await ctx.session.hook("retry", (event) => {
  if (event.error.status === 429) {
    event.decision = { retry: true, delay: 10_000 }
    return
  }
  if (event.error.type === "provider.invalid-request" && event.attempt === 2) {
    event.decision = { retry: true, delay: 0 }
    return
  }
  if (event.attempt >= 3) event.decision = { retry: false }
})
```

Hooks for nye forsøk kan endre OpenCodes første `decision`. De kan tillate et nytt forsøk etter en feil som normalt ville stoppet
forespørselen, eller stoppe et foreslått nytt forsøk.

Beslutninger om nye forsøk følger disse reglene:

- Flere hooks kjører i registreringsrekkefølge, og senere hooks ser gjeldende beslutning.
- Det innebygde maksimale antallet forsøk er fortsatt en hard grense.
- `attempt` er det fysiske forsøket som vurderes. Den innledende forespørselen er `1`, så det første nye forsøket er `2`.
- Ugyldige forsinkelser som `NaN`, uendelighet eller negative verdier faller tilbake til den beregnede forsinkelsen.
- Gjenoppretting ved kontekstoverflyt er separat, fordi den komprimerer samtalen i stedet for å prøve samme forespørsel på nytt.

#### Øktreferanse

```ts
import type { SessionPrompt } from "@opencode/plugin/promise/session"

interface SessionHooks {
  prompt: SessionPrompt
  context: SessionContextHook
  compaction: SessionContextHook & { result?: SessionCompactionResult }
  generate: SessionContextHook
  title: SessionRequestHook & { result?: string }
  "experimental.model.resolve": SessionModelResolveHook
  "model.request": SessionModelRequestHook
  "http.request": SessionHttpRequestHook
  "http.response": SessionHttpResponseHook
  "experimental.ws.handshake": SessionWebSocketHandshakeHook
  "experimental.ws.send": SessionWebSocketSendHook
  "experimental.ws.receive": SessionWebSocketReceiveHook
  retry: SessionRetryHook
}

interface SessionModelResolveHook {
  readonly sessionID: string
  readonly agent: string
  readonly kind: "primary" | "compaction" | "title" | "generate"
  model: { providerID: string; id: string; variant?: string }
}

interface SessionWebSocketHandshakeHook {
  readonly sessionID: string
  readonly agent: string
  readonly model: { providerID: string; id: string; variant?: string }
  readonly kind: "primary" | "compaction" | "title" | "generate"

  headers: Record<string, string>
}

interface SessionWebSocketSendHook {
  readonly sessionID: string
  readonly agent: string

  frame: string
}

interface SessionWebSocketReceiveHook {
  readonly sessionID: string
  readonly agent: string
  readonly model: { providerID: string; id: string; variant?: string }
  readonly kind: "primary" | "compaction" | "title" | "generate"
  frame: string
}

type RetryDecision = { retry: false } | { retry: true; delay: number }

interface SessionRetryHook {
  readonly sessionID: string
  readonly agent: string
  readonly model: { providerID: string; id: string; variant?: string }
  readonly error: { type: string; message: string; status?: number }
  readonly attempt: number
  decision: RetryDecision
}

interface SessionRequestHook {
  readonly sessionID: string
  readonly model: { providerID: string; id: string; variant?: string }
  system: SystemPart[]
  messages: Message[]
  options: {
    maxTokens?: number
    temperature?: number
    topP?: number
    topK?: number
    frequencyPenalty?: number
    presencePenalty?: number
    seed?: number
    stop?: string[]
  } & Record<string, unknown>
}

interface SessionContextHook extends SessionRequestHook {
  readonly agent: string
  tools: Record<string, { description: string; input: JsonSchema }>
}

interface SessionCompactionResult {
  summary: string
  native?: Record<string, unknown>
  metadata?: Record<string, unknown>
  tokens?: TokenUsage
}
```

### Tillatelser

Se gjennom tillatelsesbeslutninger etter at konfigurerte regler er evaluert og før en
handling kjøres eller en tillatelsesprompt publiseres.

```ts
await ctx.permission.hook("evaluate", async (event) => {
  if (event.action === "read") return

  const messages = await ctx.session.context({ sessionID: event.sessionID })
  const review = await ctx.generate.text({
    model: { providerID: "anthropic", id: "claude-sonnet-5-5" },
    prompt: buildSafetyPrompt({ messages, action: event.action, resources: event.resources }),
  })
  const decision = parseDecision(review.text)

  event.effect = decision.effect
  event.message = decision.reason
})
```

Tillatelseshooks følger disse reglene:

- Hooks kjører for `allow`- og `ask`-beslutninger.
- En eksplisitt konfigurert `deny` er endelig og påkaller ikke hooken.
- En hook kan endre `effect` til `allow`, `ask` eller `deny`.
- `message` vises i en eskalert tillatelsesforespørsel eller blir avvisningsårsaken.

#### Referanse

```ts
interface PermissionEvaluation {
  readonly sessionID: string
  readonly agent?: string
  readonly action: string
  readonly resources: readonly string[]
  readonly metadata?: Record<string, unknown>
  readonly source?: { type: "tool"; messageID: string; id: string }
  effect: "allow" | "ask" | "deny"
  message?: string
}
```

## Støtt V1

En plugin kan støtte V1 og V2 fra samme pakkeinngangspunkt. Standardeksporter
ett objekt med en V1-`server()`-funksjon og en V2-`setup()`-funksjon:

```ts title="src/index.ts"
import { Plugin } from "@opencode/plugin"

export default {
  ...Plugin.define({
    id: "example",
    async setup(ctx) {
      await ctx.tool.hook("execute.before", () => {
        console.log("A tool is about to run")
      })
    },
  }),
  async server() {
    return {
      "tool.execute.before": async () => {
        console.log("A tool is about to run")
      },
    }
  },
}
```

- V1 kaller `server()` og bruker de returnerte hookene.
- V2 leser standardeksportens `id` og `setup()` (eller `effect()` for Effect-plugins), og ignorerer `server()`.
- Hold hver implementasjon på sitt eget API; deling av en eksport oversetter ikke V1-hooks til V2-hooks.
- Spred `Plugin.define(...)` inn i det eksporterte objektet, slik at det typesjekker V2-definisjonen separat fra `server()`.

V1-objektformen støttes i OpenCode `1.18.29`. Eldre V1-utgivelser kan
forvente funksjonseksporter i stedet; test den installerte pakken med den eldste V1-
utgivelsen du vil støtte, og med V2.
