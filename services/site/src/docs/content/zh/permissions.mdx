---
title: "权限"
description: "按顺序匹配操作和资源（如路径、命令），通过允许、拒绝或询问规则，控制 OpenCode agent 能做什么。"
---

权限决定 agent 能否对某个资源执行某项操作。

## 配置

常见做法是让 OpenCode 在运行 shell 命令前先询问，直接放行常规的 Git 查看操作，并始终禁止推送。按以下顺序将规则添加到 `opencode.jsonc`：

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" },
  ],
}
```

最后一条匹配的规则生效，因此具体的例外规则要放在宽泛规则之后。

<Callout type="warning">
  V1 使用的字段名和操作名与 V2 不同。在 V2 中，请使用 `permissions`、`shell` 和 `subagent`，而不是 `permission`、`bash` 和 `task`。
</Callout>

## 规则

每条规则都需要三个字符串字段：

| 字段 | 含义 |
| ---------- | -------------------------------------------------------------------------- |
| `action` | 工具的权限操作 |
| `resource` | 操作涉及的值，例如路径、命令、URL、搜索词、技能 ID 或 agent ID |
| `effect` | `allow`、`deny` 或 `ask` |

```jsonc
{
  "permissions": [
    { "action": "read", "resource": "*", "effect": "allow" },
    { "action": "read", "resource": "*.env", "effect": "deny" },
  ],
}
```

| 效果 | 结果 |
| ------- | ----------------------------------- |
| `allow` | 直接继续，不提示 |
| `deny` | 阻止该操作 |
| `ask` | 等待客户端做出决定 |

如果没有匹配的规则，OpenCode 使用 `ask`。

## 匹配规则

操作和资源都支持简单的通配符，匹配时会检查完整值：

| 模式 | 匹配 |
| ------- | ------------------------------------------ |
| `*` | 零个或多个字符，包括 `/` |
| `?` | 恰好一个字符 |
| 其他 | 字符本身 |

```jsonc
{
  "permissions": [
    { "action": "edit", "resource": "packages/docs/*.mdx", "effect": "allow" },
  ],
}
```

该模式会匹配完整的规范化路径。反斜杠会被规范化为正斜杠；在 Windows 上，匹配不区分大小写。

以 ` *` 结尾的 shell 模式也会匹配不带参数的命令：

```jsonc
{ "action": "shell", "resource": "git status *", "effect": "allow" }
```

它同时匹配 `git status` 和 `git status --short`。

OpenCode 按顺序合并规则，并采用最后一条匹配的规则。优先级较低的配置最先加载，然后追加全局规则，最后追加 agent 规则。

```jsonc
{
  "permissions": [
    { "action": "read", "resource": "*", "effect": "allow" },
    { "action": "read", "resource": "secrets/*", "effect": "deny" },
  ],
}
```

一次操作可能涉及多个资源，例如一个补丁修改了多个文件。只要有一个资源的结果是 `deny`，就拒绝整个操作；否则，只要有一个结果是 `ask`，就先询问；其余情况直接允许。

## 操作

V2 的操作名是字符串，因此插件可以定义更多操作。内置工具目前使用以下操作和资源：

| 操作 | 资源 |
| -------------------- | --------------------------------------------------------------------------- |
| `read` | 内部路径为相对于 Location 的路径，外部路径为规范化的绝对路径 |
| `edit` | `edit`、`write` 和 `patch` 的目标路径 |
| `glob` | 请求的 glob 模式 |
| `grep` | 请求的正则表达式，而不是搜索路径 |
| `shell` | 扫描器提取的命令字符串；复合命令可能提取出多个字符串 |
| `subagent` | 目标 agent ID |
| `skill` | 技能 ID |
| `question` | `*` |
| `webfetch` | 请求的 URL |
| `websearch` | 搜索词 |
| `generate_image` | 所选图像模型，格式为 `providerID/modelID`；如果指定了变体，则附加 `#variant` |
| `external_directory` | 规范化的外部目录边界，通常以 `/*` 结尾 |
| `<server>_<tool>` | MCP 工具的资源为 `*`；两个名称中的字母、数字、`_` 和 `-` 会原样保留，其他字符一律替换为 `_` |
| `opencode_list_mcp_resources` | MCP 服务器名称 |
| `opencode_read_mcp_resource` | `<server>:<uri>` |
| `execute` | `*`；拒绝此操作时不提供 Code Mode，而是直接列出它包含的工具；嵌套调用的工具仍遵循各自的规则 |

MCP 操作名保留连字符，因此名为 `mcp-atlassian` 的服务器所提供的工具匹配 `mcp-atlassian_*`，而不是 `mcp_atlassian_*`。

例如，只允许一个技能，拒绝其他所有技能：

```jsonc
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "deny" },
    { "action": "skill", "resource": "effect", "effect": "allow" },
  ],
}
```

`doom_loop` 和 `lsp` 目前不是 V2 Core 的权限操作。

## 目录

如果路径既不在当前 Location 内，也不在该项目的工作树内（文件系统根目录不计入），OpenCode 会在应用 `read` 或 `edit` 规则之前，先检查 `external_directory`。默认策略允许 `external_directory`，所以外部路径不会触发询问，除非你添加规则。若要在访问项目之外的任何路径前先询问，可添加：

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "external_directory", "resource": "*", "effect": "ask" },
  ],
}
```

在它后面添加范围更小的规则，就可以允许或拒绝访问特定目录：

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "external_directory", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "read", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "edit", "resource": "~/projects/reference/*", "effect": "deny" },
  ],
}
```

这适用于 `read`、`edit`、`write` 和 `patch` 使用的外部路径。Shell 在检查 `shell` 资源之前，会先检查其外部工作目录以及扫描器推断出的目录。

对于 `external_directory`、`read` 和 `edit`，开头的 `~`、`~/`、`$HOME` 或 `$HOME/` 会在加载配置时展开：

```jsonc
{ "action": "read", "resource": "$HOME/reference/*", "effect": "allow" }
```

Shell 资源保留原始命令文本，不会将上述前缀展开为主目录。

<Callout type="warning">
  `shell` 以主机用户的身份运行，拥有其在文件系统、进程和网络方面的全部权限。从命令文本推断目录只能尽力而为，因此请优先使用范围较窄的 shell 允许列表，而不是试图用模式识别所有危险命令。
</Callout>

通过相对路径修改文件时，目标可能在当前 Location 之外，但仍在项目的工作树内。显式指定的外部路径会先规范化，再匹配规则，因此请只放行你信任的目录范围。

## 扫描器

对于 Bash、Zsh、POSIX `sh` 和 PowerShell，OpenCode 都使用内置的 shell 扫描器来检查权限。语法有误或涉及 `eval` 等动态求值的命令无法安全分析。如果存在适用的 `shell` 拒绝规则，扫描器会报错并阻止执行，因为它无法用拒绝规则检查子命令。否则，整条命令需要作为一个 `shell` 资源获得批准，此外还须批准 `external_directory` 的 `*` 资源。后者只能由允许访问所有目录的规则或用户本人批准。这两项批准都不会保存为模式。

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "policies": [
    {
      "permissions": [
        { "action": "shell", "resource": "git status *", "effect": "allow" },
        { "action": "shell", "resource": "rm *", "effect": "deny" },
      ],
    },
  ],
}
```

OpenCode 会对提取出的每条子命令和每个 `cd` 目标应用权限规则、已保存的批准模式，并尽可能推断目录。对于未知目录，不会启用额外的批准模式，也不会一律禁止访问。

## 默认值

每个 agent（包括自定义 agent）都从以下有序的基础策略开始：

```jsonc
[
  { "action": "*", "resource": "*", "effect": "allow" },
  { "action": "read", "resource": "*.env", "effect": "ask" },
  { "action": "read", "resource": "*.env.*", "effect": "ask" },
  { "action": "read", "resource": "*.env.example", "effect": "allow" },
]
```

内置 agent 会在此基础上追加以下策略：

| Agent | 追加的策略 |
| ------------ | ------------------------------------------------------------------------------ |
| `build` | 允许提问 |
| `plan` | 允许提问；拒绝编辑，`~/.opencode/plan` 下的文件除外 |
| `general` | 拒绝提问和启动 subagent |
| `explore` | 除 shell、读取、glob、grep、网页获取、网页搜索和外部目录外，拒绝所有操作；读取 `.env` 时询问 |
| `title` | 拒绝所有操作 |
| `summary` | 拒绝所有操作 |
| `compaction` | 保持基础策略 |

默认规则不会针对 `external_directory` 询问，因此读取或编辑 Location 和工作树之外的文件时，不会弹出权限提示。要先询问或禁止外部访问，请按[目录](#directories)一节所示，为 `external_directory` 添加 `ask` 或 `deny` 规则。后加载的全局规则和 agent 规则可以覆盖这些默认规则。

## Agents

将共享规则放在顶层，将范围更窄的规则放在 `agents.<id>.permissions` 下：

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
  ],
  "agents": {
    "reviewer": {
      "description": "Review code without changing it",
      "mode": "subagent",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" },
      ],
    },
  },
}
```

agent 规则会追加到全局规则之后，不会替换全局规则数组。自定义 subagent 使用自己的权限规则，其权限不必是父 agent 权限的子集。

## 批准

当规则的结果为 `ask` 时，客户端可以这样回复：

| 选项 | 回复 | 结果 |
| ------------ | ---------- | -------------------------------------------------------------------- |
| Allow once | `once` | 仅允许当前待处理的请求 |
| Allow always | `always` | 允许该请求，并为项目保存工具建议的模式 |
| Reject | `reject` | 拒绝该请求，以及该会话中所有其他待处理的权限请求 |

例如，对 `git status --short` 选择 **Allow always**，可能会保存一个 shell 前缀，覆盖之后的 `git status` 命令：

```text
shell: git status * → allow
```

批准保存后会成为项目级的持久 `allow` 规则，但不会覆盖已配置的 `deny`。由工具决定建议保存什么模式：有些工具建议 `*`，shell 建议命令前缀，网页获取建议 URL 对应的站点（例如 `https://opencode.ai/*`），技能和 subagent 则建议保存各自的 ID。请检查范围过宽的批准，删除不再需要的规则。

客户端在拒绝时可以附带反馈。非交互式客户端必须自行决定如何处理批准请求；已配置的 `deny` 规则始终会被执行。

## 策略

应用上述规则和已保存的批准后，[策略](/policies)仍可强制拒绝操作。它会把 `allow` 或 `ask` 改为 `deny`，但绝不会授予访问权限。

```jsonc
{
  "policies": [{ "action": "tool.use", "resource": "shell:sudo *", "effect": "deny" }],
}
```

全局策略和控制台管理的策略会覆盖项目配置，组织可以借此禁止某个仓库原本允许的命令。
