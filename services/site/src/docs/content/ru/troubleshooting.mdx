<Callout type="tip">
  Вы можете попросить OpenCode отладить себя. Опишите проблему и попросите использовать эту страницу: он прочитает шаги
  ниже, проверит свой сервис и журналы и поможет найти причину.
</Callout>

OpenCode использует архитектуру клиент-сервер. Фоновый сервер хранит сессии, плагины, разрешения и другое состояние приложения. Начните с определения того, в чём проблема: в клиенте, общем сервере или конкретном проекте.

## Проверка фонового сервиса

Покажите текущую информацию о сервере:

```bash
opencode service status
```

Убедитесь, что его API работает:

```bash
opencode api get /api/info
```

Если сервис завис или работает некорректно, перезапустите его:

```bash
opencode service restart
```

Можно также явно остановить и запустить его:

```bash
opencode service stop
opencode service start
```

<Callout type="note">
  OpenCode обычно сам находит или запускает общий фоновый сервис. Команды сервиса нужны только при диагностике его
  жизненного цикла.
</Callout>

## Доступ из браузера с другого источника

Если CORS блокирует подключение браузерного клиента с другого источника, добавьте источник клиента в конфигурацию сервиса:

```bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors
```

Укажите источник HTTP или HTTPS в точности, при необходимости с портом, но без пути и завершающего слеша. Чтобы разрешить несколько источников, перечислите их через запятую в одном аргументе. Пробелы вокруг каждого значения будут удалены:

```bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"
```

`service get cors` выводит массив JSON. Удалите настроенный список командой:

```bash
opencode service unset cors
```

Установка или снятие конфигурации сервиса останавливает фоновый сервис. При следующем запуске он подхватит новую конфигурацию; используйте `opencode service start`, чтобы запустить его явно.

Если сервер запущен не в фоновом режиме, укажите `--cors` отдельно для каждого дополнительного разрешённого источника:

```bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com
```

При `serve --service` переданные флаги `--cors` переопределяют сохранённый список для этого процесса. Без этих флагов режим сервиса использует сохранённый список. CORS не меняет адрес прослушивания и не обходит аутентификацию сервера.

## Проверка API

Команда `api` использует локальный механизм обнаружения и аутентификации сервиса. Она принимает метод HTTP и путь или ID операции OpenAPI.

О всех эндпоинтах и ID операций см. [справочник API](/api).

Передайте тело запроса JSON через `--data` или `-d`, а заголовки — через `--header` или `-H`.

<Callout type="warning">
  Выполнение `opencode api` может запустить фоновый сервис, если нет совместимого рабочего сервиса.
</Callout>

## Чтение журналов

Установленные сборки пишут журналы в:

```text
~/.local/share/opencode/log/opencode.log
```

Следите за журналом, воспроизводя проблему:

```bash
tail -f ~/.local/share/opencode/log/opencode.log
```

Каждая строка содержит ID процесса `run` и поле `role`. Используйте `role=server` для активности сессий, провайдеров, плагинов, разрешений и инструментов.

```bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log
```

## Снимок кучи

Сделайте снимок памяти (кучи) работающего фонового сервера на любой платформе:

```bash
opencode debug heap-dump
```

Команда ждёт завершения снимка, затем выводит его путь:

```text
/home/me/.local/share/opencode/log/heap-48213-2026-10-23T013012345Z.heapsnapshot
```

Запишите его в другое место с помощью `--directory`. Сервер создаёт каталог, если его нет:

```bash
opencode debug heap-dump --directory ./snapshots
```

- Используется только уже работающий сервер. Команда никогда не запускает, не заменяет и не перезапускает его.
- Используйте `--server <url>`, чтобы снять снимок сервера, запущенного через `opencode serve`. Задайте `OPENCODE_PASSWORD`, если он есть. Тогда `--directory` — путь на машине сервера.
- Откройте файл на панели Memory в Chrome DevTools.

<Callout type="warning">
  Сервер приостанавливается, пока пишет снимок, и его потребление памяти на короткое время может вырасти. Снимок может
  содержать промпты, содержимое файлов и учётные данные. Не публикуйте его.
</Callout>

### В десктопном приложении

Выберите **Capture heap snapshots** в палитре команд. Команда создаёт в папке загрузок каталог со снимками каждой части приложения и данными о расходе памяти, которые не попадают в снимки:

```text
opencode-heap-2026-10-23T013012345Z/
  memory.json                  where the memory is, per process, in MiB: start here
  memory-infra.json            Chromium's memory dump trace; open it in https://ui.perfetto.dev
  heap-48213-….heapsnapshot    the desktop's own server
  window-1-48390.heapsnapshot  one per app window
  main-48102.heapsnapshot      the desktop main process
  gpu.json                     the GPU and driver
  manifest.json                processes, PIDs, and memory before and after; written last
```

- Снимок кучи содержит только объекты JavaScript и страницу. Изображения, вёрстка, слои композитора и память GPU находятся в `memory.json` и `memory-infra.json`.
- Удалённые серверы не снимаются. Используйте `opencode debug heap-dump` на той машине.
- Сервер пишет снимок прямо в папку, поэтому ничего большого не перемещается и не копируется.
- Вкладки браузера не включаются, потому что их снимки содержат содержимое посещённых страниц.

## Профили CPU и памяти

В macOS и Linux можно отправить работающему процессу OpenCode сигнал для сбора диагностических данных. Получите PID фонового сервера через эндпоинт проверки состояния:

```bash
opencode api get /api/info
```

Используйте `pid` из ответа с одним из этих сигналов:

- `SIGPROF` снимает десятисекундный профиль CPU:

  ```bash
  kill -SIGPROF <pid>
  ```

  Результат записывается в каталог журналов как `cpu-<pid>-<timestamp>.cpuprofile`.

- `SIGUSR1` снимает снимок памяти (кучи):

  ```bash
  kill -SIGUSR1 <pid>
  ```

  Результат записывается в каталог журналов как `heap-<pid>-<timestamp>.heapsnapshot`.

Дождитесь `CPU profile written` или `heap snapshot written` в `opencode.log`, прежде чем открывать файл. Соответствующая запись журнала содержит полный путь. Оба типа файлов можно открыть в Chrome DevTools.

<Callout type="note">
  Профили по сигналу недоступны в Windows. Для снимков кучи используйте `opencode debug heap-dump`. Запись снимка кучи
  может приостановить процесс и временно увеличить потребление памяти.
</Callout>

## Файлы сервиса

Общий сервер регистрируется в:

```text
~/.local/state/opencode/service.json
```

Его приватная конфигурация сервиса хранится отдельно в:

```text
~/.config/opencode/service.json
```

База данных обычно находится в:

```text
~/.local/share/opencode/opencode.db
```

`OPENCODE_DB` может переопределить расположение базы данных.

<Callout type="warning">
  Не удаляйте и не редактируйте файлы сервиса или базу данных во время диагностики. Управляйте демоном командами
  сервиса, а перед просмотром постоянных данных внешними инструментами сделайте резервную копию.
</Callout>

## Сообщение о проблеме

При сообщении о воспроизводимой проблеме приложите следующее:

- вывод `opencode --version`;
- вывод `opencode service status`;
- минимальную последовательность шагов, воспроизводящую проблему;
- информацию о том, затрагивает ли проблема общий сервис, конкретный клиент или один проект;
- соответствующие строки журнала, включая их поля `run` и `role`.

Удалите API-ключи, заголовки авторизации, промпты, содержимое файлов и другие конфиденциальные данные перед публикацией журналов.

Сообщайте о воспроизводимых проблемах в [GitHub Issues](https://github.com/anomalyco/opencode/issues).
