description: "Обновитесь с OpenCode 1 до OpenCode 2, в котором есть несовместимые изменения плагинов, API сервера и конфигурации терминального клиента."
---

OpenCode 1 и OpenCode 2 используют команду `opencode` и по умолчанию больше не устанавливаются рядом. Удалите V1, установленную менеджером пакетов, перед установкой V2; установщик V2 через curl заменяет бинарник V1.

## Несовместимые изменения

В V2 есть три намеренных несовместимых изменения:

- [Плагины](/build/plugins/migrate-v1) используют новый API плагинов.
- У [API сервера и клиентов](#server-api-and-clients) новые контракты.
- Вместо файлов `tui.json(c)` на разных уровнях [конфигурация терминального клиента](/cli/config) использует один глобальный файл `cli.json`. Настройки переносятся автоматически.

Поддерживаемая функциональность V1 за пределами этих областей должна оставаться совместимой с V1. Некоторые поля,
принимавшиеся схемой V1, никогда не имели аналога в V2 и намеренно игнорируются; они перечислены в разделе
[Принимаемые, но неподдерживаемые поля](#accepted-but-unsupported-fields).

Существующие поддерживаемые поля конфигурации сервера, определения агентов, определения команд, навыки и другие файлы
в `.opencode/` должны продолжать работать без изменений. Если поддерживаемое поведение, описанное в этом руководстве,
перестаёт работать в V2, считайте это ошибкой совместимости, а не ожидаемым требованием миграции.

<Callout type="tip">
  Если поддерживаемая функциональность V1 не работает в V2, следуйте указаниям по сообщению о проблемах в разделе
  [Устранение неполадок](/troubleshooting) и создайте задачу о совместимости.
</Callout>

## Установка V2

Установите терминальный клиент V2 по [инструкциям по установке](/#cli).

Вам не нужно переписывать всё перед запуском V2. Практичный путь миграции:

1. Сохраните существующую конфигурацию и файловые определения.
2. Запустите V2 и проверьте модели, учётные данные, агентов, разрешения и MCP-серверы.
3. Перенесите плагины, потому что реализации плагинов V1 не работают в V2.
4. Перенесите интеграции, которые вызывают API сервера.
5. При желании преобразуйте конфигурацию в нативную форму V2. Этот шаг необязателен.

Сохраните копию настройки V1, пока проверяете миграцию. V1 и V2 используют одни и те же расположения конфигурации,
поэтому не направляйте V1 на файлы после преобразования их в нативную форму, понятную только V2.

## Конфигурация

Этот раздел охватывает и конфигурацию JSON/JSONC, и файловые определения в `.opencode/`.

### Используйте существующую конфигурацию

V2 читает существующую системную, глобальную и проектную конфигурацию из тех же мест, что и V1:

```text
/Library/Application Support/opencode/opencode.json(c)
/etc/opencode/opencode.json(c)
%ProgramData%\opencode\opencode.json(c)
/Library/Managed Preferences/<user>/ai.opencode.managed.plist
/Library/Managed Preferences/ai.opencode.managed.plist
~/.config/opencode/opencode.json(c)
<project>/opencode.json(c)
<project>/.opencode/opencode.json(c)
```

V2 нормализует поддерживаемые поля V1 и нативные поля V2 в памяти, не переписывая исходный файл. Существующая
поддерживаемая конфигурация V1 должна продолжать работать, поэтому преобразовывать её, чтобы попробовать или принять
V2, не нужно.

Как и в V1, системная конфигурация и управляемые настройки macOS имеют наивысший приоритет, поэтому их значения
переопределяют глобальные и проектные файлы. Их [политики](/policies#precedence), включая перенесённые
`enabled_providers` и `disabled_providers`, тоже превосходят глобальные и проектные политики. Переопределение настройки
не мешает пользователям добавлять провайдеров, MCP-серверы, агентов или плагины, поэтому выражайте ограничения
администратора через `policies`, а не через обычные настройки вроде `permissions`.

### Попросите OpenCode мигрировать

Формат конфигурации V1 остаётся поддерживаемым. Нативный формат V2 необязателен и делает некоторые настройки более
явными и удобными.

Рекомендуемый путь миграции — попросить OpenCode обновить конфигурацию за вас:

```text
Migrate my OpenCode configuration, including file-based definitions, from the V1 format to the native V2 format.
Preserve its behavior and all unrelated settings.
```

OpenCode может просмотреть весь файл, применить описанные ниже изменения и не переписывать настройки, которым не нужны
изменения. Преобразование не обязано происходить сразу: поддерживаемые поля V1 и нативные поля V2 могут соседствовать
на верхнем уровне. Когда обе формы задают одно каноническое значение, допустимое нативное значение V2 имеет приоритет
независимо от порядка ключей JSON.

Смешивание на вложенных уровнях намеренно ограничено. OpenCode распознаёт смешанные элементы V1 и V2 внутри `mcp`,
`compaction` и `experimental`, но не выводит рекурсивно форматы внутри отдельных агентов, провайдеров, команд или
моделей. Держите каждую такую вложенную запись целиком в одном формате. Поддерживаемый синтаксис V1 сам по себе не
выдаёт предупреждений; некорректные значения, неподдерживаемые устаревшие поля и конфликтующие значения V1/V2 вызывают
предупреждения, а остальные допустимые настройки продолжают загружаться.

### Разрешения и инструменты

V1 группирует эффекты разрешений по инструментам. V2 использует один упорядоченный массив `permissions`, делая
приоритет и исключения явными:

```jsonc
// V1
{
  "permission": {
    "bash": {
      "git push *": "ask"
    },
    "edit": "allow"
  },
  "tools": {
    "websearch": false
  }
}

// V2
{
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "edit", "resource": "*", "effect": "allow" },
    { "action": "websearch", "resource": "*", "effect": "deny" }
  ]
}
```

Действия разрешений тоже изменились: `bash` теперь `shell`, `task` теперь `subagent`, а `write` и `patch` теперь `edit`.
Об упорядоченном формате правил V2 см. [Разрешения](/permissions).

В V2 задачи выключены по умолчанию. Чтобы включить их, используйте экспериментальный флаг. Он может измениться или
исчезнуть в будущем релизе; см. [Экспериментальные настройки](/config#experimental).

```jsonc
{
  "experimental": {
    "todo": true,
  },
}
```

<Callout type="warning">
  V1 спрашивает перед доступом к путям за пределами проекта. V2 — нет: `external_directory` разрешён по умолчанию.
  Чтобы сохранить поведение V1, добавьте `{ "action": "external_directory", "resource": "*", "effect": "ask" }`
  в `permissions`.
</Callout>

### Агенты и режимы

Карты `agent` в единственном числе и устаревшая `mode` становятся `agents`. Поля агентов становятся согласованнее с
остальной конфигурацией V2:

```jsonc
// V1
{
  "agent": {
    "reviewer": {
      "prompt": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-5-5",
      "variant": "high",
      "disable": false,
      "permission": {
        "edit": "deny"
      }
    }
  }
}

// V2
{
  "agents": {
    "reviewer": {
      "system": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-5-5#high",
      "disabled": false,
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
```

`prompt` становится `system`, `disable` — `disabled`, а отдельный `variant` присоединяется к ссылке на модель после `#`.
`maxSteps` становится `steps`. Записи из старой карты `mode` становятся основными агентами.

[`request.body`](/agents#request) агента сохраняется, но не отправляется модели, поэтому `temperature`, `top_p` и
`options` из V1 там не действуют. Задайте их на варианте модели. DeepSeek применяет `temperature` только с выключенным
размышлением, поэтому этот вариант также выключает размышление:

```jsonc title="opencode.jsonc"
{
  "providers": {
    "opencode": {
      "models": {
        "deepseek-v4.1-flash": {
          "variants": [{ "id": "review", "body": { "thinking": { "type": "disabled" }, "temperature": 0.2 } }],
        },
      },
    },
  },
  "agents": {
    "reviewer": { "model": "opencode/deepseek-v4.1-flash#review" },
  },
}
```

Используйте `body` для полей JSON провайдера и `settings` для параметров пакета провайдера. См. [Параметры модели](/models#options).

### Снимки

Переименуйте поле `snapshot` в единственном числе в `snapshots`. Его булево значение не меняется:

```jsonc
// V1
{ "snapshot": false }

// V2
{ "snapshots": false }
```

### Медиа

Переименуйте объект `attachment` в единственном числе в `media`. Вложенные настройки изображений сохраняют те же имена:

```jsonc
// V1
{ "attachment": { "image": { "auto_resize": true } } }

// V2
{ "media": { "image": { "auto_resize": true } } }
```

### MCP-серверы

V2 группирует серверы в `mcp.servers`, заменяет `enabled` обратным `disabled` и разделяет назначения тайм-аутов:

```jsonc
// V1
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "@playwright/mcp"],
      "enabled": true,
      "timeout": 30000
    }
  }
}

// V2
{
  "mcp": {
    "servers": {
      "playwright": {
        "type": "local",
        "command": ["npx", "@playwright/mcp"],
        "disabled": false,
        "timeout": {
          "catalog": 30000,
          "execution": 30000
        }
      }
    }
  }
}
```

Поля удалённого OAuth используют snake_case: `clientId` становится `client_id`, `clientSecret` — `client_secret`,
`callbackPort` — `callback_port`, а `redirectUri` — `redirect_uri`. Значение `experimental.mcp_timeout` из V1 также
становится значениями по умолчанию `mcp.timeout.catalog` и `mcp.timeout.execution`. См. [MCP-серверы](/mcp-servers).

### Сжатие контекста

V2 группирует бюджет токенов сохраняемого контекста в `keep` и даёт резерву более понятное имя:

```jsonc
// V1
{
  "compaction": {
    "preserve_recent_tokens": 8000,
    "reserved": 20000
  }
}

// V2
{
  "compaction": {
    "keep": {
      "tokens": 8000
    },
    "buffer": 20000
  }
}
```

Число токенов V1 переносится как есть. V2 также принимает процент от окна модели, например `"buffer": "15%"`, что
подходит моделям с разными размерами окон.

`auto` сохраняет имя. В V2 нет нативных полей `tail_turns` или `prune`; оба устаревших поля игнорируются с
предупреждением. Объём сохраняемого контекста теперь задаётся в токенах. См. раздел [Сжатие контекста](/compaction).

### Навыки

V1 разделяет дополнительные пути и URL навыков. V2 объединяет оба в один упорядоченный массив:

```jsonc
// V1
{
  "skills": {
    "paths": ["./team-skills"],
    "urls": ["https://example.com/skills/"]
  }
}

// V2
{
  "skills": ["./team-skills", "https://example.com/skills/"]
}
```

Существующие файлы навыков и автоматическое обнаружение в `.opencode/skills/` не меняются. См. [Навыки](/skills).

### Команды

Переименуйте карту `command` в единственном числе в `commands`, а `subtask` — в `subagent`. Присоедините отдельный
`variant` модели к ссылке на модель:

```jsonc
// V1
{
  "command": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-5-5",
      "variant": "high",
      "subtask": true
    }
  }
}

// V2
{
  "commands": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-5-5#high",
      "subagent": true
    }
  }
}
```

`template`, `description` и `agent` сохраняют имена. Устаревший `subtask` по-прежнему принимается; делегированные
команды теперь автоматически выполняются в фоне и сообщают результаты родительской сессии. Существующие определения
команд Markdown остаются поддерживаемыми. См. [Команды](/commands).

### Референсы

Переименуйте устаревшую карту `reference` в единственном числе в `references`:

```jsonc
// V1
{ "reference": { "docs": "../docs" } }

// V2
{ "references": { "docs": "../docs" } }
```

V1 уже принимает `references`, поэтому при использовании этого имени изменения не нужны. Записи референсов сохраняют
те же формы. См. [Референсы](/references).

### Провайдеры

Переименуйте карту `provider` в единственном числе в `providers`. V2 разделяет пакет среды выполнения, эндпоинт и
параметры запросов:

```jsonc
// V1
{
  "provider": {
    "acme": {
      "npm": "@ai-sdk/openai-compatible",
      "api": "https://llm.example.com/v1",
      "options": {
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}

// V2
{
  "providers": {
    "acme": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": {
        "baseURL": "https://llm.example.com/v1",
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}
```

`npm` из V1 становится `package`, а пакеты AI SDK получают префикс `aisdk:`. `api` становится `settings.baseURL`.
Провайдерские `options` разделяются на `settings`, `headers` и `body` в соответствии с их ролью в запросе.
`options.setCacheKey` становится `compatibility.supportsPromptCacheKey` у провайдера. См. [Провайдеры](/providers).

V2 объединил два устаревших пространства имён провайдеров:

| ID провайдера V1           | Канонический ID провайдера V2 |
| -------------------------- | ----------------------------- |
| `azure-cognitive-services` | `azure`                       |
| `google-vertex-anthropic`  | `google-vertex`               |

Миграция однозначных полей провайдера, агента, команды и фильтра провайдеров V1 использует эти канонические ID. Общее
поле верхнего уровня `model` сохраняет точный ID провайдера, потому что тот же синтаксис допустим в нативной
конфигурации V2; обновите это поле до канонического ID при миграции устаревшего встроенного провайдера.

### Модели и варианты

Модели остаются вложенными в своего провайдера, но несколько полей модели становятся явнее:

- `id` становится `modelID`.
- `tool_call` и `modalities` становятся `capabilities.tools`, `capabilities.input` и `capabilities.output`.
- `status` со значением `"deprecated"` становится `disabled: true`.
- Стоимость кэша переходит из `cache_read` и `cache_write` в `cache.read` и `cache.write`.
- Провайдерские `options` становятся `settings`.
- Объект вариантов V1 становится массивом V2 с `id` в каждой записи.

```jsonc
// V1
{
  "variants": {
    "high": {
      "reasoningEffort": "high"
    }
  }
}

// V2
{
  "variants": [
    {
      "id": "high",
      "settings": {
        "reasoningEffort": "high"
      }
    }
  ]
}
```

О полной нативной форме модели см. [Модели](/models).

### Поддерживаемые поля без прямых нативных аналогов

Большинство полей, сохраняющих форму, включая `shell`, `model`, `default_agent`, `watcher`, `formatter`, `instructions`,
`enterprise` и `tool_output`, не требуют миграции.

V2 принимает и сохраняет конфигурацию `lsp`, но не запускает языковые серверы, не предоставляет инструменты LSP и не
выдаёт диагностику LSP. Замените рабочие процессы, зависящие от этих возможностей, командами линтинга, проверки типов
или компиляции проекта.

Фильтры провайдеров V1 не имеют однозначных нативных полей V2, но их поведение остаётся поддерживаемым через
[политики](/policies):

- `enabled_providers` становится внутренней политикой провайдеров с запретом по умолчанию, за которой следуют
  разрешения для перечисленных провайдеров.
- `disabled_providers` становится внутренними политиками запрета для перечисленных провайдеров.
- `autoupdate` становится `update`: `false` соответствует `"disable"`, `"notify"` — `"notify"`, а `true` — `"auto"`.
- `small_model` становится выбором `model` для встроенного агента `title`. Нативная конфигурация V2 должна использовать
  `agents.title.model`.

Эти поля можно оставить в синтаксисе V1. OpenCode нормализует их без предупреждения.

### Принимаемые, но неподдерживаемые поля

Схема V1 также принимала поля, у которых нет поддерживаемого поведения в V2. V2 игнорирует эти значения и выдаёт
предупреждение, чтобы их не приняли за активную конфигурацию:

- `logLevel`: используйте `OPENCODE_LOG_LEVEL` при запуске OpenCode.
- `server`: используйте сервис V2 и явные параметры сервера; API сервера намеренно несовместимо изменён.
- `subagent_depth` верхнего уровня: используйте `experimental.subagent_depth`.
- `compaction.tail_turns` и `compaction.prune`: в V2 используется `compaction.keep.tokens` и сжатие контекста на основе чекпоинтов.
- `name` агента внутри JSON-конфигурации V1.
- Запись MCP V1 только с включением и без `type`.
- Экспериментальные поля V1 `batch_tool`, `openTelemetry`, `primary_tools` и `continue_loop_on_deny`.
- Поля провайдера V1 `id`, `whitelist` и `blacklist`.
- Поля модели провайдера V1 `release_date`, `attachment`, `reasoning`, `temperature`, `experimental`, `status` со
  значением не `deprecated` и булево `interleaved`.

Игнорирование этих полей намеренно и не является регрессией совместимости. Если V2 не сохраняет поведение, названное
поддерживаемым в другом месте этого руководства, следуйте указаниям по сообщению о проблемах в разделе
[Устранение неполадок](/troubleshooting).

### Файлы агентов

Файлы агентов V1 могут использовать `agent/`, `agents/`, `mode/` или `modes/`. V2 по-прежнему обнаруживает все четыре
каталога. Предпочтительное расположение в V2:

```text
.opencode/agents/<name>.md
```

Файлы в каталоге `mode/` или `modes/` из V1 представляют основных агентов. При переносе в `agents/` добавьте
`mode: primary` в их frontmatter. Файлы из `agent/` можно перенести в `agents/`, не меняя ID, производный от пути.

При преобразовании frontmatter в нативные поля V2:

- Оставьте тело Markdown системными инструкциями агента.
- Переименуйте `prompt` в `system`, когда он встречается в JSON-конфигурации; тела файлов не нуждаются в поле `system`.
- Переименуйте `disable` в `disabled`, а `permission` — в `permissions`.
- Соедините `model` и `variant` как `provider/model#variant`.
- Задайте параметры сэмплирования и провайдера на варианте модели, как показано [выше](#agents-and-modes).

Frontmatter агентов V1 устарел, но всё ещё переводится автоматически. Каждый файл читается как один формат. Файл,
использующий любой из `permissions`, `request`, `system` или `disabled`, читается как V2, а поля V1 в нём, например
`name`, `tools`, `permission` или `temperature`, игнорируются с предупреждением в журнале. Другие файлы с полями V1
читаются как V1. Преобразуйте frontmatter файла целиком, а не смешивайте два формата. См. [Агенты](/agents).

### Файлы команд

Файлы команд V1 могут использовать `command/` или `commands/`. V2 обнаруживает оба. Предпочтительное расположение:

```text
.opencode/commands/<name>.md
```

Переносите файлы из `command/` в тот же относительный путь в `commands/`, чтобы сохранить имена команд. Тело Markdown
остаётся шаблоном команды, а `description` и `agent` во frontmatter сохраняют имена. Переименуйте `subtask` в
`subagent`, чтобы использовать нативное имя фонового делегирования. Если во frontmatter есть отдельные поля `model` и
`variant`, добавьте вариант к модели и удалите `variant`:

```yaml
# V1
model: anthropic/claude-sonnet-5-5
variant: high
subtask: true

# V2
model: anthropic/claude-sonnet-5-5#high
subagent: true
```

См. [Команды](/commands).

### Файлы навыков

V2 обнаруживает навыки и в `.opencode/skill/`, и в `.opencode/skills/`. Предпочтительная структура:

```text
.opencode/skills/<skill-id>/SKILL.md
```

Перемещайте весь каталог навыка, а не только `SKILL.md`, чтобы относительные скрипты, референсы и другие вспомогательные
файлы оставались доступными. Сохраняйте имя каталога, чтобы сохранить ID навыка. Существующий frontmatter навыков и
тела Markdown не требуют переписывания под V2. См. [Навыки](/skills).

### Файлы инструкций

Существующие файлы `AGENTS.md` остаются на месте. V2 обнаруживает глобальный `~/.config/opencode/AGENTS.md` и
окружающие файлы `AGENTS.md` от текущего каталога до домашнего. Для проектов за пределами домашнего каталога поиск
останавливается на корне проекта.

V2 сохраняет запасной вариант `CLAUDE.md` из V1: каталог без `AGENTS.md` использует свой `CLAUDE.md`, а
`~/.claude/CLAUDE.md` заменяет отсутствующий глобальный `AGENTS.md`. `OPENCODE_DISABLE_CLAUDE_CODE` пропускает все
`CLAUDE.md`, как и `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT`, который в V1 пропускал только `~/.claude/CLAUDE.md`. В
отличие от V1, останавливавшегося на первом найденном имени файла в дереве, V2 выбирает для каждого каталога, поэтому
`AGENTS.md` в корне больше не скрывает вложенный `CLAUDE.md`. См. [Инструкции](/instructions).

## Конфигурация терминального клиента

Вместо нескольких уровней файлов `tui.json(c)`, как в V1, в V2 используется один глобальный файл конфигурации терминального клиента:

```text
~/.config/opencode/cli.json
```

Этим файлом владеет терминальный клиент; фоновый сервис его не загружает. Когда `cli.json` отсутствует, первый запуск
терминального клиента V2 переносит поддерживаемые глобальные настройки `tui.json` и сохранённые предпочтения, оставляя
файлы V1 без изменений. Локальная конфигурация клиента проекта не переносится, потому что конфигурация клиента V2
глобальна. О текущем справочнике настроек клиента см. [Настройки CLI](/cli/config).

После создания `cli.json` изменения в `tui.json` игнорируются. См. раздел [Устаревший файл `tui.json`](/cli/config#legacy-tuijson).

## Плагины

Переименуйте `plugin` в `plugins`. Замените кортеж пакета и параметров объектом:

```jsonc
// V1
{
  "plugin": ["opencode-example-plugin", ["./plugin/local.ts", { "enabled": true }]]
}

// V2
{
  "plugins": [
    "opencode-example-plugin",
    {
      "package": "./plugin/local",
      "options": { "enabled": true }
    }
  ]
}
```

V2 обнаруживает локальные плагины и в `.opencode/plugin/`, и в `.opencode/plugins/`; для файлов V2 используйте
`.opencode/plugins/`. Настроенные локальные пути должны быть каталогами, поэтому перенесите портированный плагин в
`./plugin/local/index.ts`.

<Callout type="warning">
  Реализации плагинов V1 не работают в V2. Переместить файл или переименовать запись конфигурации недостаточно.
</Callout>

Переносите точки входа, хуки, инструменты, события и экспорты пакета по специальному
[руководству по миграции плагинов](/build/plugins/migrate-v1).

## API сервера и клиенты

В OpenCode 2 переработанный, более удобный API сервера и новый набор клиентов. Интеграции, вызывающие API сервера V1,
должны перейти на API V2.

Используйте пакет `@opencode/client` для доступа к выпущенному API V2. О его эндпоинтах, типах запросов и ответах см.
сгенерированный [справочник API](/api).

### Аутентификация сервера

Серверы V2 по-прежнему используют HTTP Basic auth со следующими изменениями:

- `OPENCODE_PASSWORD` задаёт пароль. `OPENCODE_SERVER_PASSWORD` всё ещё работает.
- `OPENCODE_SERVER_USERNAME` больше не поддерживается. Имя пользователя всегда `opencode`.

```bash
# V1
OPENCODE_SERVER_USERNAME=alice OPENCODE_SERVER_PASSWORD=secret opencode serve

# V2
OPENCODE_PASSWORD=secret opencode serve
```

См. [Веб-интерфейс](/cli/web#authentication).

## Проверка настройки

Проверьте модель, учётные данные провайдеров, агентов, разрешения, MCP-серверы и плагины в проекте, прежде чем полагаться
на V2 в обычной работе. Сохраняйте настройку V1, пока не убедитесь, что нужное поведение V2 работает, и не направляйте
V1 на конфигурацию, преобразованную в нативную форму V2.
