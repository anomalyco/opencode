Задайте стандартные переменные прокси и исключите loopback-адреса. OpenCode использует локальные HTTP-соединения между CLI и фоновым сервисом, поэтому при настроенном прокси в окружении CLI исключение loopback обязательно.

```bash
export HTTP_PROXY=http://proxy.example.com:8080
export HTTPS_PROXY=http://proxy.example.com:8080
export NO_PROXY=localhost,127.0.0.1,::1

opencode
```

`HTTP_PROXY` обрабатывает адреса HTTP, а `HTTPS_PROXY` — адреса HTTPS. Сам URL прокси может использовать `http://` для обеих переменных. `NO_PROXY` — разделённый запятыми список хостов и адресов, которые подключаются напрямую.

## Сервис

Переменные, экспортированные в командной оболочке, действуют на фоновый сервис только при запуске из этой оболочки. Сохраните переменные в конфигурации управляемого сервиса, чтобы при следующих запусках сохранялись те же сетевые настройки.

```bash
opencode service set env HTTP_PROXY http://proxy.example.com:8080
opencode service set env HTTPS_PROXY http://proxy.example.com:8080
opencode service set env NO_PROXY localhost,127.0.0.1,::1
opencode service start
```

Изменение управляемой переменной окружения останавливает работающий сервис. `service start` запускает его снова с новым окружением. Держите `NO_PROXY` и в shell CLI, если этот shell задаёт прокси: управляемые переменные сервиса применяются к процессу сервера, а не к процессу CLI.

Удалите сохранённую переменную с помощью `service unset env`:

```bash
opencode service unset env HTTPS_PROXY
```

## Аутентификация

Если прокси принимает учётные данные в URL, включите имя пользователя и пароль в каждый URL прокси, для которого нужна аутентификация. В имени и пароле используйте процентное кодирование для символов вроде `@`, `:` и `/`.

```bash
export HTTPS_PROXY='http://user:p%40ssword@proxy.example.com:8080'
```

Для фонового сервиса сохраните полный URL. Значение хранится в приватной конфигурации сервиса и выводится командой `opencode service get env`, поэтому не делитесь этим выводом.

```bash
opencode service set env HTTPS_PROXY 'http://user:p%40ssword@proxy.example.com:8080'
```

## Сертификаты

Укажите PEM-файл в `NODE_EXTRA_CA_CERTS`, если прокси или адрес назначения использует сертификат, подписанный частным удостоверяющим центром. Дополнительные центры добавляются в хранилище доверия среды выполнения при запуске процесса.

```bash
export NODE_EXTRA_CA_CERTS=/etc/company/ca.pem
opencode --standalone
```

Сохраните путь к файлу для фонового сервиса, затем перезапустите его:

```bash
opencode service set env NODE_EXTRA_CA_CERTS /etc/company/ca.pem
opencode service start
```

## Антивирус и проверка HTTPS

При включённом «сканировании HTTPS» или «сканировании зашифрованных соединений» антивирусы (Kaspersky, Avast, ESET и другие) подменяют сертификат сервера своим. Корпоративные прокси с проверкой SSL действуют так же. OpenCode отклоняет такой сертификат, и запросы завершаются ошибками, например:

```text
self signed certificate in certificate chain
SELF_SIGNED_CERT_IN_CHAIN
CERT_NOT_YET_VALID
CERT_SIGNATURE_FAILURE
```

Исправьте это одним из двух способов:

- Исключите `opencode.ai` и `*.opencode.ai` из сканирования HTTPS в настройках антивируса. Добавьте и хост API вашего провайдера, например `api.anthropic.com`, если подключаетесь к провайдеру напрямую.
- Экспортируйте сертификат удостоверяющего центра, который используется для проверки трафика, в PEM-файл и добавьте его в доверенные через `NODE_EXTRA_CA_CERTS`, как описано в разделе [Сертификаты](#certificates).

## Клиентские сертификаты

Задайте `settings.tls` у провайдера, чей шлюз требует взаимного TLS. Его запросы к моделям предъявляют сертификат, и рукопожатие TLS отправляет его только серверам, которые его запрашивают.

```jsonc title="opencode.jsonc"
{
  "providers": {
    "company": {
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "https://llm.company.example/v1",
        "tls": {
          "cert": "{file:/etc/company/client.pem}",
          "key": "{file:/etc/company/client.key}",
          "passphrase": "{env:CLIENT_KEY_PASSPHRASE}",
        },
      },
    },
  },
}
```

- `cert` и `key` — текст PEM. Используйте `{file:...}`, чтобы прочитать их из файлов. Если файл не читается, `tls` остаётся незаданным.
- `passphrase` нужен только для зашифрованного ключа.
- Работает в сборках для Bun и Node. Сервер на Cloudflare Workers не может предъявить клиентский сертификат через `fetch`.
- Запросы с клиентским сертификатом не следуют перенаправлениям, поэтому сертификат не предъявляется другому хосту.

Сертификат предъявляется при каждом запросе к моделям этого провайдера: в чате, при сжатии контекста, при работе с моделями для изображений и принятия решений. Провайдер с `tls` использует HTTP вместо WebSockets. Инструменты вроде webfetch, удалённые MCP-серверы и установка плагинов сертификат не используют.

## Запуск не в фоновом режиме

`--standalone` и `serve` используют окружение собственного процесса. `opencode service set env` не настраивает эти процессы.

```bash
HTTP_PROXY=http://proxy.example.com:8080 \
HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode --standalone
```

Аналогично для сервера, запущенного не в фоновом режиме:

```bash
HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode serve
```

## Проверка

Убедитесь, что CLI может достучаться до фонового сервиса после применения настроек:

```bash
opencode api get /api/info
```

Успешная проверка состояния подтверждает, что локальное соединение клиента с сервисом работает. Чтобы проверить исходящий прокси и путь к сертификату сервиса, выполните обычный запрос к провайдеру.
