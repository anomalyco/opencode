Задайте стандартні змінні проксі. CLI OpenCode з'єднується з фоновою службою локально через HTTP й автоматично
спрямовує з'єднання з loopback-адресами в обхід проксі.

```bash
export HTTP_PROXY=http://proxy.example.com:8080
export HTTPS_PROXY=http://proxy.example.com:8080

opencode
```

`HTTP_PROXY` задає проксі для HTTP-запитів, а `HTTPS_PROXY` — для HTTPS-запитів. URL-адреса самого проксі може починатися
з `http://` в обох змінних. Під час запуску CLI додає `127.0.0.1`, `localhost` і `::1` до `NO_PROXY` і `no_proxy`.
Інші хости, до яких слід підключатися напряму, перелічіть через кому в `NO_PROXY`.

## Служба

Експортовані змінні оболонки діють для фонової служби, лише якщо її запущено з цієї оболонки. Збережіть змінні
в конфігурації керованої служби, щоб під час наступних запусків діяли ті самі мережеві налаштування.

```bash
opencode service set env HTTP_PROXY http://proxy.example.com:8080
opencode service set env HTTPS_PROXY http://proxy.example.com:8080
opencode service set env NO_PROXY llm.company.example
opencode service start
```

Зміна керованої змінної середовища зупиняє запущену службу. `service start` запускає її знову з новим середовищем.
Задайте змінні проксі окремо в оболонці, з якої запускаєте CLI: змінні керованої служби діють у процесі сервера,
а не CLI. В обох процесах з'єднання з loopback-адресами автоматично йдуть в обхід проксі.

Видаліть збережену змінну за допомогою `service unset env`:

```bash
opencode service unset env HTTPS_PROXY
```

## Автентифікація

Для проксі, що приймає облікові дані в URL, додайте ім'я користувача й пароль до кожного URL проксі, який потребує
автентифікації. У назві користувача й паролі застосуйте відсоткове кодування до символів на кшталт `@`, `:` і `/`.

```bash
export HTTPS_PROXY='http://user:p%40ssword@proxy.example.com:8080'
```

Для фонової служби збережіть повний URL. Значення зберігається в приватній конфігурації служби й показується
командою `opencode service get env`, тому не діліться цим виводом.

```bash
opencode service set env HTTPS_PROXY 'http://user:p%40ssword@proxy.example.com:8080'
```

## Сертифікати

Задайте `NODE_EXTRA_CA_CERTS` як PEM-файл, коли проксі або призначення використовує сертифікат, підписаний приватним
центром сертифікації. Додаткові центри додаються до сховища довіри середовища виконання під час запуску процесу.

```bash
export NODE_EXTRA_CA_CERTS=/etc/company/ca.pem
opencode --standalone
```

Збережіть шлях до файлу для фонової служби, а потім перезапустіть її:

```bash
opencode service set env NODE_EXTRA_CA_CERTS /etc/company/ca.pem
opencode service start
```

## Антивірус і перевірка HTTPS

Антивірусне «сканування HTTPS» або «сканування зашифрованих з'єднань» (Kaspersky, Avast, ESET та інші) і корпоративні
проксі SSL-інспекції підміняють сертифікат сервера своїм. OpenCode відхиляє його, і запити завершуються помилками на
кшталт:

```text
self signed certificate in certificate chain
SELF_SIGNED_CERT_IN_CHAIN
CERT_NOT_YET_VALID
CERT_SIGNATURE_FAILURE
```

Виправте це одним із двох способів:

- Виключіть `opencode.ai` і `*.opencode.ai` зі сканування HTTPS у налаштуваннях антивірусу. Додайте також хост API
  вашого провайдера, наприклад `api.anthropic.com`, якщо підключаєтеся до провайдера напряму.
- Експортуйте центр сертифікації інспекції як PEM-файл і довірте йому через `NODE_EXTRA_CA_CERTS`, як показано в
  [Сертифікатах](#certificates).

## Клієнтські сертифікати

Задайте `settings.tls` для провайдера, чий шлюз потребує взаємного TLS. Його запити до моделей подають сертифікат, а
TLS-рукостискання надсилає його лише серверам, які його запитують.

```jsonc title="opencode.jsonc"
{
  "providers": {
    "company": {
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "https://llm.company.example/v1",
        "tls": {
          "cert": "{file:/etc/company/client.pem}",
          "key": "{file:/etc/company/client.key}",
          "passphrase": "{env:CLIENT_KEY_PASSPHRASE}",
        },
      },
    },
  },
}
```

- `cert` і `key` — це текст PEM. Використовуйте `{file:...}`, щоб прочитати їх із файлів. Файл, який не вдається
  прочитати, залишає `tls` незаданим.
- `passphrase` потрібен лише для зашифрованого ключа.
- Працює в збірках Bun і Node. Сервер на Cloudflare Workers не може подати клієнтський сертифікат через `fetch`.
- Запити з клієнтським сертифікатом не переходять за перенаправленнями, тому сертифікат не подається іншому хосту.

Кожен запит до моделі цього провайдера подає сертифікат: чат, ущільнення, зображення й модель рішень. Провайдер із
`tls` використовує HTTP замість WebSockets. Інструменти на кшталт webfetch, віддалених MCP-серверів і встановлення
плагінів його не подають.

## Процеси переднього плану

`--standalone` і `serve` використовують середовище власного процесу. `opencode service set env` не налаштовує ці
процеси.

```bash
HTTP_PROXY=http://proxy.example.com:8080 \
HTTPS_PROXY=http://proxy.example.com:8080 \
opencode --standalone
```

Застосуйте той самий підхід до сервера на передньому плані:

```bash
HTTPS_PROXY=http://proxy.example.com:8080 \
opencode serve
```

## Перевірка

Перевірте, чи CLI може досягти фонової служби після застосування налаштувань:

```bash
opencode api get /api/info
```

Успішна відповідь перевірки стану підтверджує локальне з'єднання клієнта зі службою. Виконайте звичайний запит до
провайдера, щоб перевірити вихідний проксі служби та шлях сертифіката.
