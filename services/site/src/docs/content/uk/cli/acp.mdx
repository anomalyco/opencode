`opencode acp` запускає OpenCode як агент [Agent Client Protocol](https://agentclientprotocol.com), тож його можна
використовувати з ACP-клієнта, наприклад Zed. Цей приклад додає OpenCode до Zed:

```json title="~/.config/zed/settings.json"
{
  "agent_servers": {
    "OpenCode": {
      "command": "opencode",
      "args": ["acp"]
    }
  }
}
```

Інші ACP-клієнти використовують ту саму команду й аргумент `acp`, але їхні файли конфігурації та назви полів можуть
відрізнятися. Якщо графічний клієнт не може знайти `opencode`, задайте в `command` абсолютний шлях, який виводить
`which opencode`.

## Автентифікація

OpenCode використовує облікові дані провайдера, які вже має. Увійдіть у терміналі перед запуском ACP-клієнта:

```bash
opencode auth login
```

OpenCode пропонує один метод автентифікації — `opencode-login`. Типово це метод автентифікації агента. Запит
`authenticate` приймає лише цей метод і не збирає облікові дані. Якщо промпт завершується помилкою, бо провайдер
потребує автентифікації, OpenCode повертає помилку ACP `auth_required`.

Якщо клієнт задає `clientCapabilities.auth.terminal` як `true`, метод автентифікації стає термінальним методом:

```json
{
  "id": "opencode-login",
  "name": "Login with opencode",
  "description": "Run `opencode auth login` in the terminal",
  "type": "terminal",
  "args": ["--login"]
}
```

Клієнт не має надсилати цей метод у `authenticate`. Натомість він додає `--login` до команди, що запускає
OpenCode, наприклад `opencode acp --login`, і виконує її в терміналі. OpenCode проходить процес `opencode auth login` і
завершується. Код виходу 0 означає успішний вхід. Після цього клієнт перепідключається й знову надсилає
`initialize`.

Якщо клієнт задає `clientCapabilities._meta["terminal-auth"]` як `true`, метод автентифікації містить команду входу:

```json
{
  "id": "opencode-login",
  "name": "Login with opencode",
  "description": "Run `opencode auth login` in the terminal",
  "_meta": { "terminal-auth": { "command": "opencode", "args": ["auth", "login"], "label": "OpenCode Login" } }
}
```

## Усунення проблем

`opencode acp` чекає на повідомлення ACP зі stdin, тож у терміналі здається, ніби він завис. Запускайте його з
ACP-клієнта.

Якщо клієнт повідомляє, що процес завершився або вивів некоректний протокольний вивід, додайте `--print-logs` перед
`acp` в аргументах клієнта. Тоді OpenCode записує журнали ACP і приватного сервера в stderr. Stdout містить лише
повідомлення ACP.

```bash
opencode --print-logs acp
```

## Довідник протоколу

Цей розділ для авторів ACP-клієнтів. Він перелічує частини ACP, які підтримує OpenCode, і ключі `_meta`, які додає
OpenCode. Клієнти, що не розпізнають ці ключі, можуть їх ігнорувати. Повідомлення визначає
[документація ACP](https://agentclientprotocol.com).

### Транспорт

Клієнт запускає `opencode acp` як дочірній процес. Вони обмінюються JSON-RPC-повідомленнями, розділеними новими
рядками, через stdin і stdout, використовуючи протокол ACP версії 1.

`opencode acp` запускає приватний сервер OpenCode для власного використання. Він не підключається до спільного фонового
сервісу й не відкриває мережевого порту для ACP. Один процес може обслуговувати багато ACP-сесій. Він завершується,
коли клієнт закриває stdin.

### Можливості

Відповідь `initialize` від OpenCode містить ці можливості агента:

```json
{
  "loadSession": true,
  "mcpCapabilities": { "http": true, "sse": false },
  "promptCapabilities": { "embeddedContext": true, "image": true },
  "sessionCapabilities": {
    "additionalDirectories": {},
    "close": {},
    "delete": {},
    "fork": {},
    "list": {},
    "resume": {}
  }
}
```

OpenCode читає ці можливості клієнта:

| Можливість                                | Дія                                                               |
| ----------------------------------------- | ------------------------------------------------------------------ |
| `auth.terminal` зі значенням `true`       | Метод автентифікації стає [термінальним методом](#authentication). |
| `elicitation.form`                        | OpenCode ставить [запитання](#questions) у вигляді форм.           |
| `session.compaction`                      | OpenCode повідомляє про [ущільнення](#compaction) через оновлення ACP. |
| `_meta["terminal-auth"]` зі значенням `true` | Метод автентифікації містить [команду входу](#authentication).  |

### Сесії

Клієнт задає робочий каталог, коли створює сесію. OpenCode використовує конфігурацію цього каталогу, зокрема його
моделі, агентів, команди, навички, інструкції, плагіни й MCP-сервери.

- `cwd` має бути абсолютним шляхом. OpenCode відхиляє відносний `cwd` з помилкою недійсних параметрів.
- `session/load` відтворює збережені повідомлення. `session/resume` і `session/fork` їх не відтворюють.
- Щоб завантажити, відновити або розгалужити сесію, клієнт має передати каталог цієї сесії як `cwd`, або інший каталог
  того самого проєкту, наприклад основний каталог сесії, що перейшла в worktree. OpenCode відхиляє будь-який інший
  `cwd` з помилкою недійсних параметрів, де `data.directory` — каталог сесії.
- `session/list` повертає до 100 сесій на сторінку. Він приймає фільтр `cwd` і `cursor`. Кожна сесія субагента
  містить `_meta["opencode/child-session"]` з її `id`, `parentID` і `title`.
- Коли OpenCode перейменовує сесію, наприклад після генерації заголовка, він надсилає `session_info_update` з новим
  `title`.
- `session/close` перериває активну роботу й від'єднує сесію від процесу ACP. OpenCode зберігає сесію.
- `session/delete` завершує активний промпт так само, як `session/cancel`, а потім видаляє сесію. Видалення
  неіснуючої сесії завершується успішно.
- Сесія виконує один промпт за раз. OpenCode повертає помилку на другий `session/prompt`, поки перший активний.
- Якщо промпт завершується помилкою, `data` помилки містить `errorName` збою. Вона також містить `status` і
  `retryAfterMs`, якщо провайдер їх надіслав.

### Скасування

`session/cancel` завершує активний промпт зі `stopReason: "cancelled"`. `$/cancel_request` для запиту промпту робить те
саме. OpenCode відхиляє очікувані запити дозволів. Виклики інструментів, які не завершуються після скасування, він
позначає як `failed`.

### Додаткові каталоги

Клієнт може передати `additionalDirectories` у `session/new`, `session/load`, `session/resume` і `session/fork`:

```json
{ "cwd": "/work/app", "additionalDirectories": ["/work/shared"], "mcpServers": [] }
```

- Кожен запис має бути абсолютним шляхом без `*` і `?`.
- OpenCode дозволяє доступ до зовнішніх каталогів усередині кожного кореня. Правила дозволів для читання, редагування
  й shell усе ще діють.
- Список кожного запиту замінює попередній список сесії, як визначає
  [RFD про додаткові каталоги](https://agentclientprotocol.com/rfds/additional-directories).
- OpenCode зберігає надані дозволи в сесії, тож вони діють, коли сесію використовує інший клієнт OpenCode. Дочірні
  сесії копіюють ці дозволи під час створення.

`session/list` повертає збережений список кожної сесії в `additionalDirectories`.

### Параметри конфігурації

Нові сесії використовують типову модель і основний агент каталогу. Відповіді на `session/new`, `session/load`,
`session/resume` і `session/fork` містять ці параметри конфігурації:

| ID       | Категорія       | Значення                                                                         |
| -------- | --------------- | -------------------------------------------------------------------------------- |
| `model`  | `model`         | Увімкнені моделі у форматі `provider/model`. Суфікс `/variant` також задає зусилля. |
| `effort` | `thought_level` | Варіанти моделі та `default`. Присутній лише для моделей з варіантами.           |
| `mode`   | `mode`          | Видимі основні агенти.                                                           |

Кожен параметр `model` названо за показуваною назвою його провайдера та назвою моделі, наприклад
`Anthropic / Claude Sonnet 5.5`. `session/set_config_option` приймає рядкові значення:

```json
{ "sessionId": "ses_123", "configId": "model", "value": "anthropic/claude-sonnet-5-5" }
```

`session/set_mode` також задає агента. OpenCode надсилає `config_option_update`, коли змінюються доступні моделі або
агенти. Він також надсилає його, коли інший клієнт змінює модель або агента сесії.

### Вміст промпту

Промпти можуть містити текст, зображення, вбудовані ресурси й посилання на ресурси. OpenCode ігнорує аудіоблоки. Інші
блоки він обробляє так:

| Блок                                                  | Що робить OpenCode                                                                     |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `text`                                                | Надсилає його моделі.                                                                  |
| `text` лише з аудиторією `assistant`                  | Надсилає його моделі як окремий контекст, поза повідомленням користувача.               |
| `text` лише з аудиторією `user`                       | Не додає його до вхідних даних моделі.                                                 |
| `image` з `data`                                      | Прикріплює його до промпту.                                                            |
| `image` лише з `uri`                                  | Обробляє його як посилання на ресурс.                                                  |
| `resource` з `text`                                   | Вбудовує текст після шляху або URI ресурсу.                                            |
| `resource` з `blob`                                   | Прикріплює його. Без `mimeType` визначає його за назвою файлу в URI.                    |
| `resource_link` на URI `file:`                        | Прикріплює файл. Натомість надсилає Markdown-посилання, якщо файл відсутній або недоступний для читання. |
| `resource_link` на URI `zed://` із запитом `path`     | Прикріплює файл за `path`.                                                             |
| `resource_link` на інший URI                          | Надсилає Markdown-посилання, наприклад `[spec](https://example.com/spec.md)`.          |

Аудиторія береться з `annotations` блоку. OpenCode відхиляє блок `image`, у якому немає ні `data`, ні `uri`. Цей блок є
контекстом лише для моделі:

```json
{ "type": "text", "text": "Open file: src/app.ts", "annotations": { "audience": ["assistant"] } }
```

### Команди

Після `session/new`, `session/load`, `session/resume` або `session/fork` OpenCode надсилає `available_commands_update` з
командами каталогу, вбудованою командою `compact` і навичками каталогу. Він надсилає ще одне оновлення, коли команди
або навички змінюються.

```json
{
  "sessionUpdate": "available_commands_update",
  "availableCommands": [{ "name": "compact", "description": "Compact the session" }]
}
```

Якщо промпт починається з `/` і назви доступної команди, OpenCode виконує цю команду, а решту тексту передає як
аргументи. Якщо він починається з `/` та ID навички, OpenCode надсилає промпт із прикріпленою навичкою. Інший текст,
що починається з `/`, OpenCode надсилає як звичайний промпт. `/compact` запускає [ущільнення](/compaction). Навичка,
чий ID збігається з командою, не показується у списку.

Якщо команда завершується помилкою, промпт завершується з власним повідомленням команди, наприклад підказкою щодо
використання, і `data.service` зі значенням `command`.

### MCP-сервери

Клієнт може передати stdio- та HTTP MCP-сервери в `session/new`, `session/load`, `session/resume` і `session/fork`.
OpenCode додає їх до каталогу сесії на весь час роботи процесу `opencode acp`, тож інші сесії в цьому каталозі можуть
ними користуватися. Якщо OpenCode вивантажує неактивний каталог, він додає їх знову перед наступним промптом сесії.
OpenCode передає HTTP-заголовки й не використовує OAuth для цих серверів. Він не оголошує MCP через SSE і не підтримує
MCP через ACP.

| Випадок                              | Поведінка                                                          |
| ------------------------------------ | ------------------------------------------------------------------ |
| Те саме ім'я, що й у налаштованого сервера | Сервер клієнта замінює налаштований у цьому каталозі.        |
| [Політики](/policies)                | Правила `integration.use` усе ще діють.                            |

```json
{ "type": "http", "name": "docs", "url": "https://mcp.example.com", "headers": [] }
```

### Дозволи

Запити дозволів пропонують три варіанти:

```json
[
  { "optionId": "once", "kind": "allow_once", "name": "Allow once" },
  { "optionId": "always", "kind": "allow_always", "name": "Always allow" },
  { "optionId": "reject", "kind": "reject_once", "name": "Reject" }
]
```

Коли запит змінює файли, OpenCode додає вміст `diff`, якщо може побудувати попередній перегляд зміни.

### Запитання

Якщо клієнт оголошує `elicitation.form`, OpenCode ставить запитання через `elicitation/create` у режимі форми. Запит
містить `toolCallId`, коли OpenCode надіслав цей виклик інструмента як `session/update` для цієї сесії.

```json
{
  "mode": "form",
  "sessionId": "ses_123",
  "toolCallId": "call_1",
  "message": "Which package manager?",
  "requestedSchema": {
    "type": "object",
    "properties": { "pm": { "type": "string", "oneOf": [{ "const": "bun", "title": "Bun" }] } },
    "required": ["pm"]
  }
}
```

- OpenCode ніколи не надсилає форм, які можуть збирати секрети. Вибір, сформульований як збирання секрету, наприклад
  «Який API-токен мені використовувати?», усе одно надсилається без введеної відповіді.
- Якщо поле приймає введену відповідь поруч зі своїми варіантами, схема додає необов'язкову рядкову властивість
  `<key>_custom`. Для одного варіанта непорожня власна відповідь замінює вибраний варіант. Для кількох варіантів
  OpenCode додає її до вибраних.
- Якщо користувач відхиляє або скасовує форму, OpenCode скасовує запитання.

Якщо OpenCode не може показати запитання, він скасовує його й повідомляє моделі продовжити без відповіді.

### Ущільнення

Якщо клієнт заявляє про підтримку `session.compaction`, OpenCode повідомляє про ущільнення через `compaction_update` і
`compaction_summary_chunk`. Ці оновлення описано в RFD ACP про [ущільнення сесії](https://agentclientprotocol.com/rfds/session-compaction), який
має статус Preview. Коли клієнт завантажує сесію, OpenCode відтворює кожне успішне або невдале ущільнення як одне
оновлення.

```json
{
  "sessionUpdate": "compaction_update",
  "compactionId": "msg_123",
  "status": "completed",
  "summary": [{ "type": "text", "text": "..." }]
}
```

Інші клієнти натомість отримують [маркер ущільнення](#compaction-marker). Цей маркер також використовується під час ущільнення дочірніх сесій.

### Використання

Відповідь на промпт містить `usage` з RFD [використання наприкінці ходу](https://agentclientprotocol.com/rfds/end-turn-token-usage),
який є чернеткою. `usage` підсумовує виклики моделі цього промпту в цій сесії. Він не включає дочірні сесії.

```json
{ "stopReason": "end_turn", "usage": { "inputTokens": 1200, "outputTokens": 340, "totalTokens": 1540 }, "_meta": {} }
```

Перед відповіддю OpenCode надсилає `usage_update` з
[RFD використання сесії](https://agentclientprotocol.com/rfds/session-usage). Він надсилає його, лише якщо промпт
використав токени й OpenCode знає розмір контексту моделі. `cost` — загальна вартість сесії та її дочірніх сесій у USD.

```json
{ "sessionUpdate": "usage_update", "used": 1540, "size": 200000, "cost": { "amount": 0.012, "currency": "USD" } }
```

### Дочірні сесії

Поки виконується промпт, OpenCode надсилає оновлення з дочірніх сесій як сповіщення `session/update` у сесії промпту.
Кожне оновлення містить `_meta["opencode/child-session"]`. OpenCode додає префікс `<childSessionId>:` до ID викликів
інструментів. Він додає префікс із заголовком дочірньої сесії до заголовків викликів інструментів, якщо в дочірньої
сесії є заголовок.

```json
{
  "sessionUpdate": "tool_call",
  "toolCallId": "ses_child:call_1",
  "title": "Explore the codebase: src/app.ts",
  "_meta": {
    "opencode/child-session": { "id": "ses_child", "parentID": "ses_123", "depth": 1, "title": "Explore the codebase" }
  }
}
```

| Поле       | Тип      | Опис                                                                                   |
| ---------- | -------- | -------------------------------------------------------------------------------------- |
| `id`       | `string` | ID дочірньої сесії.                                                                    |
| `parentID` | `string` | ID батьківської сесії дочірньої сесії.                                                 |
| `depth`    | `number` | 1 для дочірньої сесії промпту, 2 для дочірньої сесії цієї дочірньої сесії тощо.         |
| `title`    | `string` | Заголовок дочірньої сесії. OpenCode пропускає його, якщо в дочірньої сесії немає заголовка. |

Запити дозволів із дочірньої сесії містять той самий ключ у `toolCall._meta`. Після завершення промпту OpenCode
припиняє надсилати оновлення дочірніх сесій. Запити дозволів і запитання з дочірніх сесій усе ще доходять до клієнта.

### Статус повторної спроби

Коли виклик моделі завершується помилкою й OpenCode планує повторну спробу, він надсилає `session_info_update` з
`_meta["opencode/retry"]`. Коли повторна спроба починається, OpenCode надсилає `"opencode/retry": null`. Очищайте
будь-який статус повторної спроби, коли надходить відповідь на промпт.

```json
{
  "sessionUpdate": "session_info_update",
  "_meta": {
    "opencode/retry": {
      "attempt": 1,
      "nextRetryAt": "2026-10-02T12:00:05.000Z",
      "error": { "type": "provider.rate-limit", "message": "Rate limit exceeded", "status": 429 }
    }
  }
}
```

| Поле          | Тип      | Опис                                                                                       |
| ------------- | -------- | ------------------------------------------------------------------------------------------ |
| `attempt`     | `number` | Номер повторної спроби.                                                                    |
| `nextRetryAt` | `string` | Час наступної спроби у форматі ISO 8601.                                                   |
| `error`       | `object` | Містить `type` і `message`. Також містить `status` і `response.body`, якщо провайдер їх надіслав. |

### Маркер ущільнення

Якщо клієнт не заявляє про підтримку `session.compaction`, OpenCode повідомляє про перебіг ущільнення через `session_info_update` з
`_meta["opencode/compaction"]`. Для ущільнення дочірніх сесій OpenCode завжди використовує маркер.

```json
{
  "sessionUpdate": "session_info_update",
  "_meta": { "opencode/compaction": { "status": "started", "messageId": "msg_123", "reason": "auto" } }
}
```

| Поле        | Тип      | Опис                                                                                 |
| ----------- | -------- | ------------------------------------------------------------------------------------ |
| `status`    | `string` | `started`, `completed` або `failed`. Скасоване ущільнення має статус `failed`. |
| `messageId` | `string` | Пов'язує початок ущільнення з його завершенням. Використовуйте його як ключ, не інтерпретуючи його вміст. |
| `reason`    | `string` | `auto` або `manual`.                                                                 |
| `error`     | `object` | Присутній, коли `status` — `failed`. Такої самої форми, як `error` у [повторній спробі](#retry-status). |

Маркер не містить підсумку. Автоматичне ущільнення може завершитися невдало без маркера `started`. Коли клієнт
завантажує сесію, OpenCode відтворює кожне успішне або невдале ущільнення як один маркер.
