<Callout type="tip">
  Ви можете попросити OpenCode діагностувати проблему в його роботі. Опишіть її та вкажіть на цю сторінку.
  OpenCode може прочитати інструкції нижче, перевірити свою службу й журнали та допомогти знайти причину.
</Callout>

OpenCode використовує клієнт-серверну архітектуру. Фонова служба володіє сесіями, плагінами, дозволами та іншим
станом застосунку. Почніть із визначення, чи проблема в клієнті, спільній службі чи конкретному проєкті.

## Перевірка фонової служби

Покажіть поточну інформацію про сервер:

```bash
opencode service status
```

Переконайтеся, що його API працює належно:

```bash
opencode api get /api/info
```

Якщо служба зависла або несправна, перезапустіть її:

```bash
opencode service restart
```

Також можна явно зупинити й запустити її:

```bash
opencode service stop
opencode service start
```

<Callout type="note">
  OpenCode зазвичай сам знаходить або запускає спільну фонову службу. Команди служби потрібні лише для діагностики її
  життєвого циклу.
</Callout>

## Дозвіл джерела браузера

Якщо браузерний клієнт з іншого джерела не може підключитися через CORS, додайте джерело клієнта до конфігурації служби:

```bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors
```

Використовуйте точне джерело HTTP або HTTPS, за потреби з портом, без шляху й без скісної риски в кінці. Щоб дозволити
кілька джерел, передайте список через кому одним аргументом; пробіли навколо кожного джерела обрізаються:

```bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"
```

`service get cors` виводить масив JSON. Видаліть налаштований список так:

```bash
opencode service unset cors
```

Встановлення або скасування конфігурації служби зупиняє фонову службу. Наступний запуск підхопить нову конфігурацію;
щоб запустити її явно, використайте `opencode service start`.

Для сервера на передньому плані повторіть `--cors` для кожного додаткового дозволеного джерела:

```bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com
```

З `serve --service` передані прапорці `--cors` перекривають збережений список для цього процесу. Без цих прапорців
режим служби використовує збережений список. CORS не змінює адресу прослуховування й не обходить автентифікацію сервера.

## Дослідження API

Команда `api` використовує локальне виявлення служби й потік автентифікації. Вона приймає або HTTP-метод і шлях, або
ID операції OpenAPI.

Усі ендпоінти й ID операцій наведено в [довіднику API](/api).

Передайте тіло запиту JSON через `--data` або `-d`, а заголовки додайте через `--header` або `-H`.

<Callout type="warning">
  Запуск `opencode api` може запустити фонову службу, якщо немає сумісної справної служби.
</Callout>

## Читання логів

Встановлені збірки пишуть логи до:

```text
~/.local/share/opencode/log/opencode.log
```

Стежте за логом, відтворюючи проблему:

```bash
tail -f ~/.local/share/opencode/log/opencode.log
```

Кожен рядок містить ID `run` процесу й поле `role`. Використовуйте `role=server` для активності сесій, провайдерів,
плагінів, дозволів та інструментів.

```bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log
```

## Експорт телеметрії

OpenCode може надсилати журнали й дані трасування до колектора OpenTelemetry або до бекенду APM, який приймає дані OTLP через HTTP.
Задайте базову URL-адресу колектора без шляху:

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer example-token"
export OTEL_RESOURCE_ATTRIBUTES="team=platform,host.name=dev-laptop"
opencode
```

| Змінна | Поведінка |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Базова URL-адреса. Журнали надсилаються до `<endpoint>/v1/logs`, а дані трасування — до `<endpoint>/v1/traces`. Якщо змінну не задано, експорт вимкнено. |
| `OTEL_EXPORTER_OTLP_HEADERS` | Розділені комами заголовки у форматі `key=value`. Надсилаються з кожним експортом; наприклад, тут можна вказати API-ключ. |
| `OTEL_RESOURCE_ATTRIBUTES` | Розділені комами атрибути у форматі `key=value` з URL-кодуванням. Додаються до кожного запису. Якщо хоча б один атрибут має хибний формат, OpenCode відкидає всі. |

Кожен запис також містить `service.name` (`opencode`), `service.version`, `deployment.environment.name` (канал
випуску), `opencode.client` і `opencode.run` — той самий ID запуску, що й у файлі журналу.

Фонова служба працює в окремому процесі й не успадковує середовище вашої оболонки. Задайте змінні й для служби,
щоб трасувати виклики моделей і виконання інструментів:

```bash
opencode service set env OTEL_EXPORTER_OTLP_ENDPOINT http://localhost:4318
opencode service set env OTEL_EXPORTER_OTLP_HEADERS "authorization=Bearer example-token"
opencode service start
```

## Знімок купи пам'яті

Запишіть знімок пам'яті (купи) запущеної фонової служби на будь-якій платформі:

```bash
opencode debug heap-dump
```

Команда чекає, доки знімок завершиться, а потім виводить його шлях:

```text
/home/me/.local/share/opencode/log/heap-48213-2026-10-23T013012345Z.heapsnapshot
```

Запишіть його в інше місце через `--directory`. Сервер створює каталог, якщо його немає:

```bash
opencode debug heap-dump --directory ./snapshots
```

- Він використовує лише сервер, який уже запущено. Він ніколи не запускає, не замінює й не перезапускає сервер.
- Використайте `--server <url>`, щоб зняти сервер, який ви запустили через `opencode serve`. Встановіть
  `OPENCODE_PASSWORD`, якщо він є. Тоді `--directory` — це шлях на машині сервера.
- Відкрийте файл на панелі Memory у Chrome DevTools.

<Callout type="warning">
  Сервер призупиняється, поки пише знімок, і його використання пам'яті може на короткий час зрости. Знімок може
  містити промпти, вміст файлів і облікові дані. Не діліться ним публічно.
</Callout>

### У десктопному застосунку

Запустіть **Capture heap snapshots** з палітри команд. Він записує одну теку в каталозі Downloads зі знімком
кожної частини застосунку, а також розподіл пам'яті, який знімок показати не може:

```text
opencode-heap-2026-10-23T013012345Z/
  memory.json                  where the memory is, per process, in MiB: start here
  memory-infra.json            Chromium's memory dump trace; open it in https://ui.perfetto.dev
  heap-48213-….heapsnapshot    the desktop's own server
  window-1-48390.heapsnapshot  one per app window
  main-48102.heapsnapshot      the desktop main process
  gpu.json                     the GPU and driver
  manifest.json                processes, PIDs, and memory before and after; written last
```

- Знімок купи містить лише об'єкти JavaScript і сторінку. Зображення, верстка, шари композитора й пам'ять GPU
  натомість у `memory.json` і `memory-infra.json`.
- Віддалені сервери не знімаються. Натомість використайте `opencode debug heap-dump` на тій машині.
- Сервер пише свій знімок безпосередньо в теку, тож нічого великого не переміщується й не копіюється.
- Вкладки браузера не включаються, бо їхні знімки містять вміст сторінок, які ви відвідали.

## Знімання профілів CPU і пам'яті

На macOS і Linux ви можете надіслати сигнал запущеному процесу OpenCode, щоб зняти діагностичні дані. Отримайте PID
фонового сервера з кінцевої точки стану:

```bash
opencode api get /api/info
```

Використайте `pid` із відповіді з одним із цих сигналів:

- `SIGPROF` знімає десятисекундний профіль CPU:

  ```bash
  kill -SIGPROF <pid>
  ```

  Результат записується в каталог логів як `cpu-<pid>-<timestamp>.cpuprofile`.

- `SIGUSR1` знімає знімок пам'яті (купи):

  ```bash
  kill -SIGUSR1 <pid>
  ```

  Результат записується в каталог логів як `heap-<pid>-<timestamp>.heapsnapshot`.

Зачекайте на `CPU profile written` або `heap snapshot written` у `opencode.log`, перш ніж відкривати файл. Відповідний
запис у журналі містить повний шлях. Файли обох типів можна переглянути в Chrome DevTools.

<Callout type="note">
  Профілі за сигналом недоступні на Windows. Натомість використовуйте `opencode debug heap-dump` для знімків купи.
  Запис знімка купи може призупинити процес і тимчасово збільшити використання пам'яті.
</Callout>

## Файли служби

Спільний сервер реєструє себе за адресою:

```text
~/.local/state/opencode/service.json
```

Його приватна конфігурація служби зберігається окремо за адресою:

```text
~/.config/opencode/service.json
```

База даних зазвичай лежить за адресою:

```text
~/.local/share/opencode/opencode.db
```

`OPENCODE_DB` може перекрити розташування бази даних.

<Callout type="warning">
  Не видаляйте й не редагуйте файли служби чи базу даних під час вирішення проблем. Керуйте демоном командами
  служби й робіть резервну копію, перш ніж оглядати постійні дані зовнішніми інструментами.
</Callout>

## Повідомлення про проблему

Додайте таке, повідомляючи про відтворювану проблему:

- Вивід `opencode --version`
- Вивід `opencode service status`
- Найкоротша послідовність кроків, що відтворює проблему
- Чи стосується проблема спільної служби, конкретного клієнта чи одного проєкту
- Доцільні рядки логу, включно з полями `run` і `role`

Видаліть API-ключі, заголовки авторизації, промпти, вміст файлів та інші чутливі дані, перш ніж ділитися логами.

Повідомляйте про відтворювані проблеми в [GitHub Issues](https://github.com/anomalyco/opencode/issues).
