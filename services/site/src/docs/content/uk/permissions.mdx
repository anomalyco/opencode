Дозволи визначають, чи може агент виконати дію над ресурсом.

## Налаштування

Поширена конфігурація: запитувати дозвіл на виконання команд термінала, дозволяти звичайні перевірки в Git і завжди блокувати push. Додайте правила до `opencode.jsonc` у такому порядку:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" },
  ],
}
```

Діє останнє з правил, що відповідають запиту, тому конкретні винятки ставте після загального правила.

<Callout type="warning">
  V1 використовує інші назви полів і дій. У V2 використовуйте `permissions`, `shell` і `subagent` замість `permission`,
  `bash` і `task`.
</Callout>

## Правила

Кожне правило має три обов'язкові поля з рядковими значеннями:

| Поле       | Значення                                                                    |
| ---------- | --------------------------------------------------------------------------- |
| `action`   | Дія інструмента, на яку поширюється правило |
| `resource` | Значення, з яким працює дія: шлях, команда, URL, запит, ID навички або ID агента |
| `effect`   | `allow`, `deny` або `ask`                                                   |

```jsonc
{
  "permissions": [
    { "action": "read", "resource": "*", "effect": "allow" },
    { "action": "read", "resource": "*.env", "effect": "deny" },
  ],
}
```

| Ефект   | Результат                            |
| ------- | ------------------------------------ |
| `allow` | Продовжити без запитання             |
| `deny`  | Заблокувати операцію                 |
| `ask`   | Чекати на рішення від клієнта        |

Якщо жодне правило не збігається, OpenCode використовує `ask`.

## Зіставлення

Дії та ресурси зіставляються цілком за простими шаблонами із символами підстановки:

| Шаблон | Збіг                                    |
| ------ | --------------------------------------- |
| `*`    | Нуль або більше символів, включно з `/`  |
| `?`    | Рівно один символ                       |
| Інше   | Сам символ                              |

```jsonc
{
  "permissions": [
    { "action": "edit", "resource": "packages/docs/*.mdx", "effect": "allow" },
  ],
}
```

Цей шаблон збігається з усім нормалізованим шляхом. Зворотні скісні риски нормалізуються до скісних рисок, а у Windows зіставлення не враховує регістр.

Шаблон команди термінала, що закінчується на ` *`, відповідає цій команді й без аргументів:

```jsonc
{ "action": "shell", "resource": "git status *", "effect": "allow" }
```

Він збігається і з `git status`, і з `git status --short`.

OpenCode об'єднує правила послідовно й використовує останній збіг. Спершу завантажується конфігурація з нижчим пріоритетом, далі додаються глобальні правила, а останніми — правила агентів.

```jsonc
{
  "permissions": [
    { "action": "read", "resource": "*", "effect": "allow" },
    { "action": "read", "resource": "secrets/*", "effect": "deny" },
  ],
}
```

Під час операції можуть перевірятися кілька ресурсів, наприклад якщо патч змінює кілька файлів. Якщо є бодай один `deny`, OpenCode блокує операцію. Якщо заборон немає, але є хоча б один `ask`, OpenCode запитує дозвіл. В інших випадках він дозволяє операцію.

## Дії

Назви дій у V2 — це рядки, тож плагіни можуть визначати більше дій. Вбудовані інструменти наразі використовують такі дії та ресурси:

| Дія                  | Ресурс                                                                      |
| -------------------- | --------------------------------------------------------------------------- |
| `read`               | Внутрішній шлях відносно Location або канонічний абсолютний зовнішній шлях   |
| `edit`               | Цільовий шлях для `edit`, `write` і `patch`                                 |
| `glob`               | Запитаний glob-шаблон                                                       |
| `grep`               | Запитаний регулярний вираз, а не шлях пошуку                                |
| `shell`              | Рядок команди, сформований сканером; складені команди можуть дати кілька     |
| `subagent`           | ID цільового агента                                                         |
| `skill`              | ID навички                                                                  |
| `question`           | `*`                                                                         |
| `webfetch`           | Запитана URL-адреса                                                         |
| `websearch`          | Пошуковий запит                                                             |
| `generate_image` | Вибрана модель генерації зображень у форматі `providerID/modelID` із суфіксом `#variant`, якщо його задано |
| `external_directory` | Канонічна межа зовнішнього каталогу, зазвичай із `/*` у кінці                |
| `<server>_<tool>`    | `*` для інструмента MCP; в обох назвах літери, цифри, `_` і `-` зберігаються, а всі інші символи замінюються на `_` |
| `opencode_list_mcp_resources` | Назва сервера MCP                                                  |
| `opencode_read_mcp_resource`  | `<server>:<uri>`                                                   |
| `execute`            | `*`; заборона прибирає Code Mode і показує його інструменти напряму, а вкладені інструменти застосовують власні правила |

У назвах дій MCP дефіси зберігаються, тому інструменти сервера `mcp-atlassian` відповідають шаблону `mcp-atlassian_*`,
а не `mcp_atlassian_*`.

Наприклад, дозвольте одну навичку й забороніть усі інші:

```jsonc
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "deny" },
    { "action": "skill", "resource": "effect", "effect": "allow" },
  ],
}
```

Наразі `doom_loop` і `lsp` не належать до дій, для яких V2 Core перевіряє дозволи.

## Каталоги

Якщо шлях лежить і поза активним Location, і поза його робочим деревом проєкту (якщо воно не кореневе), OpenCode спочатку перевіряє `external_directory`, а потім правила `read` або `edit` для цього шляху. Базова політика дозволяє `external_directory`, тому OpenCode не запитує дозвіл на зовнішні шляхи, доки ви не додасте відповідне правило. Щоб OpenCode запитував дозвіл перед будь-яким доступом поза проєктом:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "external_directory", "resource": "*", "effect": "ask" },
  ],
}
```

Вужчі правила після нього можуть дозволяти або забороняти конкретні каталоги:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "external_directory", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "read", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "edit", "resource": "~/projects/reference/*", "effect": "deny" },
  ],
}
```

Це стосується зовнішніх шляхів, які використовують `read`, `edit`, `write` і `patch`. Для команд термінала OpenCode спершу перевіряє зовнішній робочий каталог і каталоги, знайдені сканером, а тоді — ресурси `shell`.

Для `external_directory`, `read` і `edit` початкові `~`, `~/`, `$HOME` або `$HOME/` розгортаються під час завантаження конфігурації:

```jsonc
{ "action": "read", "resource": "$HOME/reference/*", "effect": "allow" }
```

Ресурси команд термінала лишаються незміненим текстом команд: позначення домашнього каталогу в ньому не розгортаються.

<Callout type="warning">
  `shell` має ті самі права на доступ до файлової системи, процесів і мережі, що й користувач хоста. Не всі каталоги
  можна визначити з тексту команди, тож краще явно дозволити лише потрібні команди, ніж намагатися розпізнати всі
  небезпечні команди за шаблонами.
</Callout>

Відносний шлях до змінюваного файла може виходити за межі активного Location, але залишатися в робочому дереві проєкту. Явно вказані зовнішні шляхи OpenCode зводить до канонічної форми перед зіставленням, тому дозволяйте доступ лише до каталогів, яким довіряєте.

## Сканер

Щоб перевірити дозволи для команд термінала, OpenCode використовує вбудований сканер, який підтримує Bash, Zsh, POSIX `sh` і PowerShell. Деякі команди не можна безпечно проаналізувати, наприклад через помилки синтаксису або динамічне виконання на кшталт `eval`. Якщо діє правило заборони для `shell`, така команда завершується помилкою сканера: він не може перевірити її підкоманди за цим правилом. Інакше потрібні два дозволи: для всієї команди як одного ресурсу `shell` і для `external_directory` зі значенням `*`. Другий дозвіл може надати лише користувач або правило, що дозволяє всі каталоги. Жоден із цих дозволів не зберігається як шаблон.

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "policies": [
    {
      "permissions": [
        { "action": "shell", "resource": "git status *", "effect": "allow" },
        { "action": "shell", "resource": "rm *", "effect": "deny" },
      ],
    },
  ],
}
```

Для кожної знайденої підкоманди й кожного цільового каталогу `cd` OpenCode застосовує правила дозволів і збережені шаблони схвалень та намагається визначити каталоги з тексту команди. Окремого режиму схвалення чи загального обмеження для невідомих каталогів немає.

## Типові значення

Кожен агент, зокрема власні агенти, починає з цієї впорядкованої базової політики:

```jsonc
[
  { "action": "*", "resource": "*", "effect": "allow" },
  { "action": "read", "resource": "*.env", "effect": "ask" },
  { "action": "read", "resource": "*.env.*", "effect": "ask" },
  { "action": "read", "resource": "*.env.example", "effect": "allow" },
]
```

Вбудовані агенти додають такі політики:

| Агент        | Додаткова політика                                                              |
| ------------ | ------------------------------------------------------------------------------- |
| `build`      | Дозволяє запитання                                                              |
| `plan`       | Дозволяє запитання; забороняє редагування, крім файлів у `~/.opencode/plan`     |
| `general`    | Забороняє запитання й запуск субагентів                                         |
| `explore`    | Забороняє все, крім команд термінала, читання, glob, grep, вебзапитів, вебпошуку та зовнішніх каталогів. Запитує дозвіл на читання `.env` |
| `title`      | Забороняє всі дії                                                               |
| `summary`    | Забороняє всі дії                                                               |
| `compaction` | Зберігає базову політику                                                        |

У базовій політиці немає правила, що запитує дозвіл для `external_directory`, тож читання й редагування поза Location і робочим деревом відбуваються без запиту. Щоб OpenCode запитував дозвіл або блокував зовнішній доступ, додайте правило `ask` чи `deny` для `external_directory`, як показано в розділі [Каталоги](#directories). Глобальні правила й правила агентів застосовуються після базових і мають над ними перевагу.

## Агенти

Розмістіть спільні правила на верхньому рівні, а вужчі — у `agents.<id>.permissions`:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
  ],
  "agents": {
    "reviewer": {
      "description": "Review code without changing it",
      "mode": "subagent",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" },
      ],
    },
  },
}
```

Правила агентів додаються після глобальних правил; вони не замінюють глобальний масив. Власний субагент використовує свої дозволи, а не підмножину дозволів батьківського агента.

## Схвалення

Коли правило визначає `ask`, клієнти можуть відповісти:

| Варіант      | Відповідь | Результат                                                            |
| ------------ | --------- | -------------------------------------------------------------------- |
| Allow once   | `once`    | Схвалити лише поточний запит                                         |
| Allow always | `always`  | Схвалити його й зберегти запропоновані інструментом шаблони для проєкту |
| Reject       | `reject`  | Відхилити його й усі інші поточні запити дозволів у цій сесії        |

Наприклад, якщо вибрати **Allow always** для `git status --short`, OpenCode може зберегти префікс команди, що охоплюватиме й наступні виклики `git status`:

```text
shell: git status * → allow
```

Збережені схвалення діють як постійні правила `allow` у межах проєкту. Вони ніколи не мають переваги над налаштованим `deny`. Інструмент сам пропонує, який шаблон зберегти: деякі пропонують `*`, для команд термінала пропонується префікс команди, для вебзапитів — шаблон для всього сайту (наприклад, `https://opencode.ai/*`), а для навичок і субагентів — їхні ID. Переглядайте дозволи широкої дії й видаляйте непотрібні.

Клієнти можуть додавати відгук під час відхилення. Неінтерактивні клієнти мають самі вирішувати, як обробляти запити схвалення; налаштовані правила `deny` завжди лишаються чинними.

## Політики

Після застосування цих правил і збережених схвалень [політика](/policies) може остаточно заборонити дію. Вона змінює результат `allow` або `ask` на `deny`, але сама доступу не надає.

```jsonc
{
  "policies": [{ "action": "tool.use", "resource": "shell:sudo *", "effect": "deny" }],
}
```

Глобальні політики й політики, якими керує Console, перекривають конфігурацію проєкту — так організація блокує команду, яку репозиторій дозволив би.
