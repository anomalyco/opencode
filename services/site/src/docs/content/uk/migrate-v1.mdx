OpenCode 1 і OpenCode 2 використовують команду `opencode`, і тепер вони типово не встановлюються поряд. Видаліть встановлення V1,
зроблене менеджером пакетів, перш ніж встановлювати V2; інсталятор V2 через curl замінює бінарник V1.

## Несумісні зміни

V2 має три навмисні несумісні зміни:

- [Плагіни](/build/plugins/migrate-v1) використовують новий API плагінів.
- [Серверний API та клієнти](#server-api-and-clients) мають нові контракти.
- [Конфігурація термінального клієнта](/cli/config) автоматично переноситься з файлів `tui.json(c)` на різних рівнях
  до одного глобального файлу `cli.json`.

Підтримувані можливості V1 поза цими областями мають лишатися сумісними з V1. Деякі поля, які приймала схема V1,
ніколи не мали відповідника у V2 і навмисно ігноруються; їх перелічено в розділі
[Прийнятні, але непідтримувані поля](#accepted-but-unsupported-fields).

Наявні підтримувані поля конфігурації сервера, визначення агентів і команд, навички та інші файли в `.opencode/`
мають і далі працювати без змін. Якщо підтримувана поведінка, описана в цьому посібнику, перестає працювати у V2,
вважайте це помилкою сумісності, а не очікуваною вимогою міграції.

<Callout type="tip">
  Якщо підтримувана можливість V1 не працює у V2, скористайтеся порадами зі створення звітів у
  [Усуненні несправностей](/troubleshooting) і створіть звіт про проблему сумісності.
</Callout>

## Встановлення V2

Встановіть термінальний клієнт V2 за [інструкціями зі встановлення](/#cli).

Переписувати все перед запуском V2 не потрібно. Практична міграція виглядає так:

1. Залиште наявну конфігурацію та визначення у файлах.
2. Запустіть V2 і перевірте моделі, облікові дані, агентів, дозволи й сервери MCP.
3. Перенесіть плагіни, бо реалізації плагінів V1 не працюють у V2.
4. Перенесіть інтеграції, які викликають серверний API.
5. Коли будете готові, переведіть конфігурацію в рідну форму V2. Цей крок необов'язковий.

Поки перевіряєте міграцію, зберігайте копію свого налаштування V1. V1 і V2 використовують ті самі розташування
конфігурації, тому не запускайте V1 із файлами, які ви вже перевели у форми, що існують лише у V2.

## Конфігурація

Цей розділ охоплює і конфігурацію JSON/JSONC, і визначення у файлах у `.opencode/`.

### Використовуйте наявну конфігурацію

V2 читає наявну системну, глобальну та проєктну конфігурацію з тих самих розташувань, що й V1:

```text
/Library/Application Support/opencode/opencode.json(c)
/etc/opencode/opencode.json(c)
%ProgramData%\opencode\opencode.json(c)
/Library/Managed Preferences/<user>/ai.opencode.managed.plist
/Library/Managed Preferences/ai.opencode.managed.plist
~/.config/opencode/opencode.json(c)
<project>/opencode.json(c)
<project>/.opencode/opencode.json(c)
```

V2 нормалізує підтримувані поля V1 і рідні поля V2 у пам'яті, не переписуючи вихідний
файл. Наявна підтримувана конфігурація V1 має й далі працювати, тому переводити її не потрібно, щоб спробувати чи
прийняти V2.

Як і у V1, системна конфігурація та керовані налаштування macOS мають найвищий пріоритет, тому їхні параметри
перекривають глобальні та проєктні файли. Їхні [політики](/policies#precedence), зокрема перенесені `enabled_providers` і
`disabled_providers`, теж мають вищий пріоритет за глобальні й проєктні політики. Перекриття параметра не заважає
користувачам додавати провайдерів, сервери MCP, агентів чи плагіни, тому адміністративні обмеження виражайте як `policies`,
а не як звичайні налаштування на кшталт `permissions`.

### Попросіть OpenCode виконати міграцію

Формат конфігурації V1 і далі підтримується. Рідний формат V2 необов'язковий і робить низку налаштувань
явнішими та зручнішими.

Рекомендований шлях міграції — попросити OpenCode оновити конфігурацію за вас:

```text
Migrate my OpenCode configuration, including file-based definitions, from the V1 format to the native V2 format.
Preserve its behavior and all unrelated settings.
```

OpenCode може переглянути весь файл, застосувати відповідні зміни нижче й не переписувати налаштування, які не потребують
змін. Переводити не обов'язково все одразу: підтримувані поля V1 і рідні поля V2 можуть співіснувати на верхньому рівні.
Коли обидві форми задають те саме канонічне значення, чинне рідне значення V2 має пріоритет незалежно від порядку ключів JSON.

Змішування на вкладених рівнях навмисно обмежене. OpenCode розпізнає змішані елементи V1 і V2 всередині `mcp`, `compaction` і
`experimental`, але не визначає формати рекурсивно всередині окремих агентів, провайдерів, команд чи моделей. Тримайте
кожен із цих вкладених записів повністю в одному форматі. Підтримуваний синтаксис V1 сам собою не дає попереджень; некоректні значення,
непідтримувані застарілі поля та суперечливі значення V1/V2 спричиняють попередження, а не пов'язані з ними чинні налаштування
далі завантажуються.

### Дозволи та інструменти

V1 групує ефекти дозволів за інструментом. V2 використовує один упорядкований масив `permissions`, роблячи пріоритети й винятки явними:

```jsonc
// V1
{
  "permission": {
    "bash": {
      "git push *": "ask"
    },
    "edit": "allow"
  },
  "tools": {
    "websearch": false
  }
}

// V2
{
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "edit", "resource": "*", "effect": "allow" },
    { "action": "websearch", "resource": "*", "effect": "deny" }
  ]
}
```

Дії дозволів теж змінилися: `bash` тепер `shell`, `task` тепер `subagent`, а `write` і `patch` тепер `edit`.
Формат упорядкованих правил V2 дивіться в [Дозволах](/permissions).

Todos типово вимкнені у V2. Щоб увімкнути їх, використайте експериментальний прапорець. Він може змінитися або
зникнути в майбутньому випуску; дивіться [Експериментальні можливості](/config#experimental).

```jsonc
{
  "experimental": {
    "todo": true,
  },
}
```

<Callout type="warning">
  V1 запитує дозвіл перед доступом до шляхів поза проєктом. V2 — ні: `external_directory` дозволено типово. Щоб зберегти
  поведінку V1, додайте `{ "action": "external_directory", "resource": "*", "effect": "ask" }` до `permissions`.
</Callout>

### Агенти та режими

Мапи `agent` в однині та застаріла `mode` стають `agents`. Поля агентів стають послідовнішими з рештою
конфігурації V2:

```jsonc
// V1
{
  "agent": {
    "reviewer": {
      "prompt": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-5-5",
      "variant": "high",
      "disable": false,
      "permission": {
        "edit": "deny"
      }
    }
  }
}

// V2
{
  "agents": {
    "reviewer": {
      "system": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-5-5#high",
      "disabled": false,
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
```

`prompt` стає `system`, `disable` стає `disabled`, а окремий `variant` долучається до посилання на модель після `#`.
`maxSteps` стає `steps`. Записи зі старої мапи `mode` стають основними агентами.

[`request.body`](/agents#request) агента зберігається, але не надсилається моделі, тому V1 `temperature`, `top_p` та `options`
там не діють. Задавайте їх у варіанті моделі. DeepSeek застосовує `temperature`, лише коли міркування вимкнено, тому
цей варіант також вимикає міркування:

```jsonc title="opencode.jsonc"
{
  "providers": {
    "opencode": {
      "models": {
        "deepseek-v4.1-flash": {
          "variants": [{ "id": "review", "body": { "thinking": { "type": "disabled" }, "temperature": 0.2 } }],
        },
      },
    },
  },
  "agents": {
    "reviewer": { "model": "opencode/deepseek-v4.1-flash#review" },
  },
}
```

Використовуйте `body` для полів JSON провайдера і `settings` для параметрів пакета провайдера. Дивіться [параметри моделі](/models#options).

### Знімки

Перейменуйте поле `snapshot` в однині на `snapshots`. Його булеве значення не змінюється:

```jsonc
// V1
{ "snapshot": false }

// V2
{ "snapshots": false }
```

### Медіа

Перейменуйте об'єкт `attachment` в однині на `media`. Вкладені налаштування зображень зберігають ті самі назви:

```jsonc
// V1
{ "attachment": { "image": { "auto_resize": true } } }

// V2
{ "media": { "image": { "auto_resize": true } } }
```

### Сервери MCP

V2 групує сервери в `mcp.servers`, замінює `enabled` на протилежний `disabled` і розділяє тайм-аути за призначенням:

```jsonc
// V1
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "@playwright/mcp"],
      "enabled": true,
      "timeout": 30000
    }
  }
}

// V2
{
  "mcp": {
    "servers": {
      "playwright": {
        "type": "local",
        "command": ["npx", "@playwright/mcp"],
        "disabled": false,
        "timeout": {
          "catalog": 30000,
          "execution": 30000
        }
      }
    }
  }
}
```

Поля OAuth для віддалених серверів використовують snake_case: `clientId` стає `client_id`, `clientSecret` стає `client_secret`,
`callbackPort` стає `callback_port`, а `redirectUri` стає `redirect_uri`. Значення V1 `experimental.mcp_timeout`
також стає типовими значеннями `mcp.timeout.catalog` і `mcp.timeout.execution`. Дивіться [Сервери MCP](/mcp-servers).

### Ущільнення

V2 групує бюджет токенів збереженого контексту в `keep` і дає резерву зрозумілішу назву:

```jsonc
// V1
{
  "compaction": {
    "preserve_recent_tokens": 8000,
    "reserved": 20000
  }
}

// V2
{
  "compaction": {
    "keep": {
      "tokens": 8000
    },
    "buffer": 20000
  }
}
```

Кількість токенів V1 переноситься як є. V2 також приймає відсоток вікна моделі, як-от `"buffer": "15%"`,
що підходить для моделей із різним розміром вікна.

`auto` зберігає назву. V2 не має рідних полів `tail_turns` чи `prune`; обидва застарілі поля ігноруються з попередженням. Недавній
контекст натомість зберігається в межах бюджету токенів. Дивіться [Ущільнення](/compaction).

### Навички

V1 розділяє додаткові шляхи до навичок і URL-адреси. V2 об'єднує обидва в один упорядкований масив:

```jsonc
// V1
{
  "skills": {
    "paths": ["./team-skills"],
    "urls": ["https://example.com/skills/"]
  }
}

// V2
{
  "skills": ["./team-skills", "https://example.com/skills/"]
}
```

Наявні файли навичок і автоматичне виявлення `.opencode/skills/` не змінюються. Дивіться [Навички](/skills).

### Команди

Перейменуйте мапу `command` в однині на `commands`, а `subtask` на `subagent`. Долучіть окремий `variant` моделі до посилання на модель:

```jsonc
// V1
{
  "command": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-5-5",
      "variant": "high",
      "subtask": true
    }
  }
}

// V2
{
  "commands": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-5-5#high",
      "subagent": true
    }
  }
}
```

`template`, `description` і `agent` зберігають назви. Застарілий `subtask` і далі приймається; делеговані команди тепер виконуються
автоматично у фоні й повідомляють результати батьківській сесії. Наявні визначення команд у Markdown і далі підтримуються.
Дивіться [Команди](/commands).

### Посилання

Перейменуйте застарілу мапу `reference` в однині на `references`:

```jsonc
// V1
{ "reference": { "docs": "../docs" } }

// V2
{ "references": { "docs": "../docs" } }
```

V1 уже приймає `references`, тому якщо файл його використовує, змін не потрібно. Записи посилань зберігають
ту саму форму. Дивіться [Посилання](/references).

### Провайдери

Перейменуйте мапу `provider` в однині на `providers`. У V2 пакет середовища виконання, ендпоінт і налаштування запитів задаються окремо:

```jsonc
// V1
{
  "provider": {
    "acme": {
      "npm": "@ai-sdk/openai-compatible",
      "api": "https://llm.example.com/v1",
      "options": {
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}

// V2
{
  "providers": {
    "acme": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": {
        "baseURL": "https://llm.example.com/v1",
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}
```

V1 `npm` стає `package`, а пакети AI SDK отримують префікс `aisdk:`. `api` стає `settings.baseURL`. `options` провайдера
розділяються на `settings`, `headers` і `body` залежно від їхньої ролі в запиті. `options.setCacheKey`
стає `compatibility.supportsPromptCacheKey` у провайдера. Дивіться [Провайдери](/providers).

V2 звів два застарілі ідентифікатори провайдерів до канонічних:

| ID провайдера у V1        | Канонічний ID провайдера у V2 |
| -------------------------- | ------------------------ |
| `azure-cognitive-services` | `azure`                  |
| `google-vertex-anthropic`  | `google-vertex`          |

Міграція однозначних полів провайдера, агента, команди й фільтрів провайдерів V1 використовує ці канонічні ID. Спільне
поле верхнього рівня `model` зберігає точний ID провайдера, бо той самий синтаксис чинний і в рідній конфігурації V2; оновіть це поле
до канонічного ID, коли переносите застарілий вбудований провайдер.

### Моделі та варіанти

Моделі лишаються вкладеними у свого провайдера, але кілька полів моделі стають явнішими:

- `id` стає `modelID`.
- `tool_call` і `modalities` стають `capabilities.tools`, `capabilities.input` і `capabilities.output`.
- `status` зі значенням `"deprecated"` стає `disabled: true`.
- Витрати на кеш переходять із `cache_read` і `cache_write` до `cache.read` і `cache.write`.
- Специфічні для провайдера `options` стають `settings`.
- Об'єкт варіантів V1 стає масивом V2 з `id` у кожному записі.

```jsonc
// V1
{
  "variants": {
    "high": {
      "reasoningEffort": "high"
    }
  }
}

// V2
{
  "variants": [
    {
      "id": "high",
      "settings": {
        "reasoningEffort": "high"
      }
    }
  ]
}
```

Повну рідну форму моделі дивіться в [Моделях](/models).

### Підтримувані поля без прямих рідних відповідників

Більшість полів, що зберігають ту саму форму, зокрема `shell`, `model`, `default_agent`, `watcher`, `formatter`,
`instructions`, `enterprise` і `tool_output`, не потребують міграції.

V2 приймає й зберігає конфігурацію `lsp`, але не запускає мовні сервери, не надає інструменти LSP і не створює діагностику LSP.
Замініть робочі процеси, що залежать від цих можливостей, командами lint, перевірки типів чи компілятора проєкту.

Фільтри провайдерів V1 не мають взаємно однозначних рідних полів конфігурації V2, але їхня поведінка й далі підтримується через
[політики](/policies):

- `enabled_providers` стає внутрішньою політикою провайдерів із забороною за замовчуванням, за якою йдуть дозволи для перелічених провайдерів.
- `disabled_providers` стає внутрішніми політиками заборони для перелічених провайдерів.
- `autoupdate` стає `update`: `false` відповідає `"disable"`, `"notify"` відповідає `"notify"`, а `true` відповідає `"auto"`.
- `small_model` стає вибором `model` для вбудованого агента `title`. У рідній конфігурації V2 натомість
  використовуйте `agents.title.model`.

Можете залишити ці поля в синтаксисі V1. OpenCode нормалізує їх без попереджень.

### Прийнятні, але непідтримувані поля

Схема V1 також приймала поля, які не мають підтримуваної поведінки у V2. V2 ігнорує ці значення й видає попередження, щоб
їх не вважали чинною конфігурацією:

- `logLevel`: використовуйте `OPENCODE_LOG_LEVEL` під час запуску OpenCode.
- `server`: використовуйте сервіс V2 і явні параметри сервера; серверний API — навмисна несумісна зміна.
- `subagent_depth` верхнього рівня: натомість використовуйте `experimental.subagent_depth`.
- `compaction.tail_turns` і `compaction.prune`: V2 натомість використовує `compaction.keep.tokens` та ущільнення на основі контрольних точок.
- `name` агента в конфігурації JSON V1.
- Запис MCP V1, де вказано лише ввімкнення, без `type`.
- Експериментальні поля V1 `batch_tool`, `openTelemetry`, `primary_tools` і `continue_loop_on_deny`.
- Поля провайдера V1 `id`, `whitelist` і `blacklist`.
- Поля моделі провайдера V1 `release_date`, `attachment`, `reasoning`, `temperature`, `experimental`, `status` зі значенням,
  відмінним від `deprecated`, і булеве `interleaved`.

Ігнорування цих полів навмисне і не є регресією сумісності. Якщо V2 не зберігає поведінку, позначену
як підтримувана деінде в цьому посібнику, скористайтеся порадами зі створення звітів у [Усуненні несправностей](/troubleshooting).

### Файли агентів

Файли агентів V1 можуть використовувати `agent/`, `agents/`, `mode/` або `modes/`. V2 і далі виявляє всі чотири каталоги. Бажане
розташування у V2:

```text
.opencode/agents/<name>.md
```

Файли в каталозі V1 `mode/` або `modes/` представляють основних агентів. Переносячи такий файл у `agents/`, додайте
`mode: primary` до його frontmatter. Файли з `agent/` можна перенести в `agents/`, не змінюючи їхній ID, похідний від шляху.

Переводячи frontmatter у рідні поля V2:

- Залиште тіло Markdown як системні інструкції агента.
- Перейменуйте `prompt` на `system`, коли він є в конфігурації JSON; тілам файлів поле `system` не потрібне.
- Перейменуйте `disable` на `disabled`, а `permission` на `permissions`.
- Об'єднайте `model` і `variant` як `provider/model#variant`.
- Задавайте параметри семплінгу й провайдера у варіанті моделі, як показано [вище](#agents-and-modes).

Frontmatter агентів V1 застарів, але й далі перетворюється автоматично. Кожен файл читається як один формат. Файл, який
використовує будь-що з `permissions`, `request`, `system` чи `disabled`, читається як V2, а поля V1 у ньому, як-от `name`,
`tools`, `permission` чи `temperature`, ігноруються з попередженням у журналі. Інші файли, що використовують поля V1, читаються
як V1. Перетворюйте frontmatter файлу за один раз, а не змішуйте два формати. Дивіться [Агенти](/agents).

### Файли команд

Файли команд V1 можуть використовувати `command/` або `commands/`. V2 виявляє обидва. Бажане розташування:

```text
.opencode/commands/<name>.md
```

Перенесіть файли з `command/` на той самий відносний шлях у `commands/`, щоб зберегти назви команд. Тіло Markdown лишається
шаблоном команди, а frontmatter `description` і `agent` зберігає ті самі назви. Перейменуйте `subtask` на `subagent`, щоб використати
рідну назву для фонового делегування. Якщо frontmatter має окремі
поля `model` і `variant`, долучіть варіант до моделі й видаліть `variant`:

```yaml
# V1
model: anthropic/claude-sonnet-5-5
variant: high
subtask: true

# V2
model: anthropic/claude-sonnet-5-5#high
subagent: true
```

Дивіться [Команди](/commands).

### Файли навичок

V2 виявляє навички і в `.opencode/skill/`, і в `.opencode/skills/`. Бажана структура:

```text
.opencode/skills/<skill-id>/SKILL.md
```

Переносьте весь каталог навички, а не лише `SKILL.md`, щоб відносні скрипти, посилання та інші допоміжні файли лишалися
доступними. Не змінюйте назву каталогу, щоб зберегти ID навички. Наявні frontmatter навичок і тіла Markdown не
потребують переписування під V2. Дивіться [Навички](/skills).

### Файли інструкцій

Наявні файли `AGENTS.md` лишаються на місці. V2 знаходить глобальний `~/.config/opencode/AGENTS.md` і файли `AGENTS.md`
на шляху від поточного каталогу до домашнього. Для проєктів поза домашнім каталогом пошук зупиняється в корені проєкту.

V2 зберігає запасний варіант `CLAUDE.md` із V1: каталог без `AGENTS.md` використовує свій `CLAUDE.md`, а `~/.claude/CLAUDE.md`
замінює відсутній глобальний `AGENTS.md`. `OPENCODE_DISABLE_CLAUDE_CODE` пропускає кожен `CLAUDE.md`, і так само
чинить `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT`, який у V1 пропускав лише `~/.claude/CLAUDE.md`. На відміну від V1, який зупинявся на
першій знайденій назві файлу десь угору по дереву, V2 вибирає для кожного каталогу, тож `AGENTS.md` у корені більше не приховує вкладений
`CLAUDE.md`. Дивіться [Інструкції](/instructions).

## Конфігурація термінального клієнта

У V2 замість файлів `tui.json(c)` на різних рівнях, як у V1, є один глобальний файл конфігурації термінального клієнта:

```text
~/.config/opencode/cli.json
```

Цей файл належить термінальному клієнту; фоновий сервіс його не завантажує. Коли `cli.json` відсутній, перший запуск
термінального клієнта V2 переносить підтримувані глобальні налаштування `tui.json` і збережені вподобання, не змінюючи файли V1.
Локальна для проєкту конфігурація клієнта не переноситься, бо конфігурація клієнта V2 глобальна. Поточний довідник
налаштувань клієнта дивіться в [Налаштуваннях CLI](/cli/config).

Після створення `cli.json` зміни в `tui.json` ігноруються. Дивіться [Застарілий файл `tui.json`](/cli/config#legacy-tuijson).

## Плагіни

Перейменуйте `plugin` на `plugins`. Замініть кортеж із пакета й параметрів об'єктом:

```jsonc
// V1
{
  "plugin": ["opencode-example-plugin", ["./plugin/local.ts", { "enabled": true }]]
}

// V2
{
  "plugins": [
    "opencode-example-plugin",
    {
      "package": "./plugin/local",
      "options": { "enabled": true }
    }
  ]
}
```

V2 виявляє локальні плагіни і в `.opencode/plugin/`, і в `.opencode/plugins/`; для файлів V2 використовуйте `.opencode/plugins/`.
Налаштовані локальні шляхи мають бути каталогами, тому перемістіть перенесений плагін до `./plugin/local/index.ts`.

<Callout type="warning">
  Реалізації плагінів V1 не працюють у V2. Переміщення файлу або перейменування запису в конфігурації недостатньо.
</Callout>

Переносьте точки входу, хуки, інструменти, події та експорти пакета за окремим
[посібником з міграції плагінів](/build/plugins/migrate-v1).

## Серверний API та клієнти

OpenCode 2 має переглянутий, зручніший серверний API і новий набір клієнтів. Інтеграції, які викликають серверний API V1,
мають перейти на API V2.

Використовуйте пакет `@opencode/client`, щоб працювати з випущеним API V2. Згенерований [довідник API](/api) описує його
ендпоінти, типи запитів і відповіді.

### Автентифікація сервера

Сервери V2 і далі використовують HTTP Basic auth, з такими змінами:

- `OPENCODE_PASSWORD` задає пароль. `OPENCODE_SERVER_PASSWORD` і далі працює.
- `OPENCODE_SERVER_USERNAME` більше не підтримується. Ім'я користувача завжди `opencode`.

```bash
# V1
OPENCODE_SERVER_USERNAME=alice OPENCODE_SERVER_PASSWORD=secret opencode serve

# V2
OPENCODE_PASSWORD=secret opencode serve
```

Дивіться [Web](/cli/web#authentication).

## Перевірте своє налаштування

Перш ніж покладатися на V2 у повсякденній роботі, перевірте в проєкті модель, облікові дані провайдера, агентів, дозволи, сервери MCP
і плагіни. Тримайте налаштування V1, доки не переконаєтеся в потрібній поведінці V2, і не запускайте V1 із
конфігурацією, яку ви вже перевели в рідну форму V2.
