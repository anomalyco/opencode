Mit dem GUI-Plugin-SDK `@opencode/plugin/gui` fügst du OpenCode Desktop Panels, Befehle, Einstellungsseiten
und native Integrationen hinzu. Das GUI-Plugin ist der `./gui-experimental`-Teil eines
[Plugin-Pakets](/build/plugins), allein oder neben einem [Server-Teil](/build/plugins/server) und einem
[TUI-Teil](/build/plugins/cli).

<Callout type="note">
Die GUI-Plugin-API ist experimentell und kann sich von Release zu Release ändern. Der Exportname
`-experimental` macht das im Paket kenntlich.
</Callout>

Die Datei `./gui-experimental` exportiert standardmäßig `Plugin.define`, wie die Server- und TUI-Teile:

```tsx title="src/gui.tsx"
import { Command, Plugin } from "@opencode/plugin/gui"
import { Acme } from "./rpc"

export default Plugin.define({
  i18n: { en: { "command.open": "Open Acme" } },
  setup(ctx) {
    ctx.add(Command, () => ({
      id: "open",
      title: ctx.t("command.open"),
      run: () => void ctx.client.rpc(Acme).open({}),
    }))
  },
  main(ctx) {
    ctx.log.write("info", "acme started")
  },
})
```

Ein GUI-Plugin kann in zwei Prozessen laufen:

- **`setup`** läuft in jedem Fenster der Desktop-App. Damit registrierst du Panels, Befehle,
  Einstellungsseiten, Slots, Serverquellen, Link-Handler und Styles. Siehe [Das Fenster](#the-window).
- **`main`** läuft einmal im Electron-Hauptprozess. Es stellt typisierte `Ipc`-Verträge, native Menüeinträge,
  `WebContentsView`-Einbettungen sowie Node- und Electron-Integrationen bereit. Siehe [Der Hauptprozess](#the-main-process).

## Paket

Ein Plugin-Paket kann Server-, TUI- und GUI-Code aus einem npm-Paket ausliefern. Füge einen `./gui-experimental`-Export neben
`./tui` hinzu, und OpenCode Desktop lädt ihn für jedes Plugin auf seinem eigenen Hintergrundserver.

```json title="package.json"
{
  "name": "opencode-acme-plugin",
  "type": "module",
  "exports": {
    ".": "./src/index.ts",
    "./tui": "./src/tui.tsx",
    "./gui-experimental": "./dist/gui-experimental.cjs"
  },
  "dependencies": {
    "@opencode/plugin": "latest"
  },
  "devDependencies": {
    "solid-js": "^1.9.0",
    "vite": "^7.0.0",
    "vite-plugin-solid": "^2.11.0"
  }
}
```

Nutzer installieren es wie jedes andere Plugin; es gibt keinen separaten GUI-Installationsschritt.

```jsonc title="opencode.jsonc"
{
  "plugins": ["opencode-acme-plugin"],
}
```

Die GUI deklariert keine ID: Sie übernimmt die des Plugins, die `id` des Server-Teils oder bei einem Paket ohne Server-Teil den
Paketnamen (ein lokales Verzeichnis ohne `name` nutzt den Verzeichnisnamen). Lies sie als `ctx.id`.

### Eine Datei, zwei Prozesse

Jeder Prozess wertet die ganze `./gui-experimental`-Datei aus und liest ihren Default-Export. Fenster führen `setup` aus, und der
Hauptprozess der Desktop-App führt `main` aus.

```tsx title="src/gui.tsx"
import { shell } from "electron"
import { Plugin } from "@opencode/plugin/gui"

export default Plugin.define({
  setup(ctx) {
    // Window code: Solid components, ctx.layout, ctx.add(Command, …).
  },
  main(ctx) {
    // Main code: electron, Node built-ins, ctx.windows.
    ctx.windows.on("open", () => shell.beep())
  },
})
```

Weil beide Prozesse dieselbe Datei auswerten, stellt jeder inaktive Platzhalter für die Module des anderen Prozesses bereit:

- **In einem Fenster** sind `electron` und Node-Built-ins inaktive Platzhalter.
- **Im Hauptprozess** sind Solid und die Fenster-only-Module inaktive Platzhalter.

Ein Platzhalter erlaubt auf Modulebene beliebige Eigenschaftszugriffe, Aufrufe und Instanziierungen, etwa die
von Solid nach oben gezogenen Templates oder die vom Bundler nach oben gezogenen `require`-Aufrufe. Lass den
Code für jeden Prozess in dessen eigenem Setup. Läuft er im falschen Prozess, erhält er Platzhalter statt
nutzbarer Werte.

`Plugin.define` und die Vertragshelfer stammen in beiden Prozessen aus demselben SDK. Im Hauptprozess verweist
`@opencode/plugin/gui` auf das SDK für den Hauptprozess. Es exportiert dieselben `Plugin`, `Store`, `Ipc`,
`Contract` und `Registry`. Eine Definition genügt für beide Prozesse. Exporte, die nur in Fenstern verfügbar
sind, etwa `Command`, `bindPlugin` und `createKeyed`, sind im Hauptprozess `undefined`. Nutze sie daher nur in
`setup`.

## Bundle bauen

`./gui-experimental` muss aus einer einzigen vorab gebauten CommonJS-Datei bestehen. Verwende dafür das
Vite-Preset aus `@opencode/plugin/gui/vite`:

```ts title="vite.config.ts"
import { defineConfig } from "vite"
import { gui } from "@opencode/plugin/gui/vite"

export default defineConfig({ plugins: [gui()] })
```

```bash
vite build
```

Das Preset übernimmt Folgendes:

- Kompiliert Solid-JSX mit `vite-plugin-solid`.
- Erzeugt eine CommonJS-Datei und bettet jeden dynamischen `import()` ein, weil die App keinen zweiten Chunk laden kann.
- Hält die [gemeinsamen Module](#shared-modules) der App, Electron und Node-Built-ins external und bündelt jede andere
  Abhängigkeit.
- Lässt den Build bei jedem anderen `effect/*`-, `solid-js/*`- oder `@opencode/*`-Modul fehlschlagen. Die App stellt es nicht bereit, und eine
  gebündelte Kopie würde die Instanz der App nicht teilen.

```text
effect/Schema is not a module the OpenCode app provides to plugin GUIs: effect, @opencode/plugin/gui, …
```

Importiere stattdessen aus dem gemeinsamen Eintrag, zum Beispiel `import { Schema } from "effect"`.

### Optionen der Voreinstellung

Übergib Optionen an `gui()`, um Einstiegspunkt oder Ausgabedatei zu ändern.

```ts title="vite.config.ts"
export default defineConfig({ plugins: [gui({ entry: "src/desktop.tsx", outFile: "dist/desktop.cjs" })] })
```

- `entry` ist die Datei, die `Plugin.define` standardmäßig exportiert. Standard ist `src/gui.tsx`.
- `outFile` ist das Bundle, auf das der Export `./gui-experimental` zeigt. Standard ist `dist/gui-experimental.cjs`.

#### Referenz

```ts
function gui(options?: GuiOptions): Plugin[]

interface GuiOptions {
  entry?: string
  outFile?: string
}
```

### Abhängigkeiten

Füge die Build-Tools als devDependencies hinzu. Die App stellt `@opencode/plugin/gui` zur Laufzeit bereit, das Bundle braucht also nur
seine Typen aus der Abhängigkeit `@opencode/plugin`.

```bash
bun add -d vite vite-plugin-solid solid-js
```

Für die Electron- und Node-Typen in `main` füge außerdem `electron` und `@types/node` hinzu:

```bash
bun add -d electron @types/node
```

### Gemeinsame Module

Jeder Prozess stellt dem Bundle die folgenden Module zur Verfügung. Wenn das Bundle ein Modul anfordert, das
keiner der beiden Prozesse bereitstellt, schlägt das Laden der Plugin-GUI fehl.

```ts
import { Schema } from "effect" // Both processes
import { createSignal } from "solid-js" // Windows; an inert placeholder in the main process
import { readFile } from "node:fs/promises" // The main process; an inert placeholder in windows
```

- **Beide Prozesse:** `effect`, `@opencode/plugin/gui`, `@opencode/plugin/gui/main`, `@opencode/plugin/rpc`,
  `@opencode/schema/rpc`, `@opencode/client` und `@opencode/client/effect`.
- **Nur Fenster:** `solid-js`, `solid-js/web`, `solid-js/store`, `@opencode/client/solid` und
  `@opencode/plugin/gui/{file,review,browser}`. Der Hauptprozess erhält inaktive Platzhalter.
- **Nur Hauptprozess:** `electron` und Node-Built-ins wie `node:fs`. Fenster erhalten inaktive Platzhalter.

## Wo GUI-Einträge laden

OpenCode Desktop lädt GUI-Einstiegspunkte über seinen eigenen Hintergrundserver, der die Plugins aus deiner
Konfiguration bereits lädt. Dadurch kommt keine neue Codequelle hinzu. Konfiguriere das Plugin in der globalen
`opencode.json(c)`, damit seine GUI in jedem Fenster verfügbar ist.

<Callout type="note">
  Die TUI liest ihre Plugins aus `cli.json`, die Desktop-App liest aber nur `opencode.json(c)`. Ein Paket, das nur einen
  TUI-Teil ausgeliefert hat und das Nutzer in `cli.json` aufführen, muss auch in `opencode.json(c)` aufgeführt werden, sobald es
  `./gui-experimental` hinzufügt.
</Callout>

Der Hauptprozess der Desktop-App ruft die Plugin-Liste und die Bundles von seinem eigenen Server ab. Nur er hat
die nötigen Zugangsdaten. Er übermittelt allen Fenstern dieselbe Auswahl. Ein Fenster kann keinen Code für den
Hauptprozess liefern.

Ein Plugin, dessen Server-Teil nicht lädt, hat keine GUI.

## Neu laden und Updates

Lade das Plugin aus seinem lokalen Verzeichnis und baue bei jeder Änderung neu:

```bash
vite build --watch
```

- Ein lokales Verzeichnis, dessen `package.json` `name` und `exports` hat, löst `./gui-experimental` darüber auf. Ohne
  diese lädt es `gui-experimental.cjs` (oder `.js`) in seinem Wurzelverzeichnis. Der Eintrag muss `.cjs` oder `.js` sein; jede andere Datei wird
  ignoriert.
- Nach jedem erneuten Build lädt OpenCode die Plugin-GUI in allen Fenstern und im Hauptprozess neu. Der
  Server-Einstiegspunkt wird dabei nicht neu gestartet.
- Die GUI eines installierten Pakets ändert sich nur mit seiner Version.
- Das Ändern der `options` des Plugins in `opencode.json(c)` lädt das Plugin neu.
- `opencode plugin update` ersetzt die GUI eines Pakets, sobald das Update fertig ist.
- [**Settings > Extensions > Plugins**](/plugins#desktop) listet das Plugin mit einem Schalter, der seine GUI ausschaltet. Um
  es zu entfernen, entferne es aus `opencode.json(c)` oder führe `opencode plugin remove <package>` aus.

<Callout type="note">
Die IDs der mitgelieferten Plugins sind reserviert. Die GUI deines Plugins wird nicht geladen, wenn seine ID
einer reservierten ID entspricht, ihr mit einem `.` untergeordnet ist, eine reservierte ID ihr untergeordnet
ist oder sie im Namespace `opencode` liegt. Unter **Settings > Extensions > Plugins** erscheint das Plugin
dann als nicht geladen.
</Callout>

## GUI-Plugin definieren

`Plugin.define` deklariert die Systeme, auf denen das Plugin läuft, seinen gespeicherten Fensterzustand, seine Icons und seine Texte. Der Host
liest diese Deklarationen, bevor eines der Setups läuft.

```ts title="src/gui/definition.ts"
import { Schema } from "effect"
import { Plugin, Store } from "@opencode/plugin/gui"

export const definition = Plugin.define({
  os: ["macos", "linux"],
  stores: {
    prefs: Store.global(Schema.Struct({ enabled: Schema.Boolean }), { enabled: true }),
  },
  i18n: {
    en: { title: "Acme", "command.open": "Open Acme" },
    de: { title: "Acme", "command.open": "Acme öffnen" },
  },
})
```

- Der Host gibt dem Plugin seine ID, `ctx.id`: die `id` des Server-Teils oder den Paketnamen bei einem Paket ohne
  Server-Teil (den Verzeichnisnamen bei einem lokalen Verzeichnis ohne `name`). Er präfigiert jede ID, die das Plugin erstellt: Befehle (`<id>.<command>`), Panel-Schlüssel (`<id>:<tab>`), gespeicherte
  Schlüssel (`plugin.<id>.<key>`) und die IDs der [Verträge und Ipcs](#contracts-and-tokens), die es bereitstellt.
- `os` beschränkt das Plugin auf einige Betriebssysteme. Lass es weg, um auf jedem OS zu laufen. Ein Plugin, dessen `os` dieses
  System auslässt, läuft nicht, und **Settings > Extensions > Plugins** behält seine Zeile mit „Not available on this system.“
- `stores` deklariert [gespeicherten Zustand](#stored-state) für Fenster. Lies ihn als `ctx.stores.<key>`.
- `icons` deklariert die [eigenen Icons](#icons) des Plugins, jeweils als Text einer SVG-Datei. Lies den Namen eines Icons als
  `ctx.icons.<name>`.
- `i18n` enthält die Texte für jede Spracheinstellung. Gib alle Übersetzungen inline an. Fehlt ein Schlüssel,
  wird der englische Text verwendet. Lies die Texte mit `ctx.t(key, params)` und `ctx.plural(key, count)`. In
  einem Fenster liest `ctx.t` auch die gemeinsamen Schlüssel der App, etwa `common.*`. In `main` wird bei
  einem fehlenden Eintrag der Schlüssel selbst zurückgegeben.
- Definiere `setup`, `main` oder beides. Ohne mindestens eine dieser Funktionen lässt sich die GUI nicht
  laden.
- Ohne Setups gibt `Plugin.define` die Deklarationen als `Plugin.Declarations` zurück, sodass Setups in anderen Dateien daraus typisiert werden können. `Plugin.Definition` ist der Typ der vollständigen Definition.
- Ein Plugin deklariert nicht die Verträge, die es bereitstellt oder nutzt. Es stellt sie zur Laufzeit bereit und liest sie; siehe
  [Verträge und Tokens](#contracts-and-tokens).

#### Referenz

```ts
interface Declarations {
  os?: ("macos" | "windows" | "linux")[]
  stores?: Record<string, StoreDeclaration>
  icons?: Record<string, string>
  i18n?: { en: Messages; [locale: string]: Messages }
}

interface Definition extends Declarations {
  setup?(ctx: SetupContext<this>): Cleanup | void
  main?(ctx: MainContext): Cleanup | void | Promise<Cleanup | void>
}

type Messages = Record<string, string>

type Cleanup = () => void | Promise<void>
```

### Auf Dateien verteilen

Ein kleines GUI-Plugin passt in `src/gui.tsx`. Deklariere bei einem größeren das Plugin in `definition.ts`, lege gemeinsame Tokens in
`contract.ts` ab, schreibe jedes Setup in eine eigene Datei und kombiniere sie in `src/gui.tsx`.

```text
src/
├── index.ts            Server part: Plugin.define from @opencode/plugin
├── rpc.ts              RPC contract between the server part and its clients
├── gui.tsx             ./gui-experimental entry: export default Plugin.define({ ...definition, setup, main })
└── gui/
    ├── definition.ts   Plugin.define: os, stores, icons, i18n
    ├── contract.ts     Tokens other code may import: Ipc, Contract, Registry
    ├── window.tsx      Window setup: Plugin.Setup<typeof definition>
    ├── main.ts         Main setup: Plugin.MainSetup (desktop only)
    ├── page.tsx        Components that panels and pages render
    ├── icons/logo.svg  The plugin's own icons
    └── i18n/en.ts      English copy
```

Beim Start eines Fensters wird die gesamte `./gui-experimental`-Datei ausgewertet. Halte den Code auf
Modulebene und in `setup` deshalb schlank. Registriere deine Beiträge dort und verlagere aufwendige Arbeit in
Komponenten, `createKeyed` oder `createLatest`.

Deklariere bei einem größeren Plugin zuerst das Plugin, typisiere jedes Setup aus den Deklarationen und definiere dann das Plugin damit.

```ts title="src/gui/definition.ts"
import { Schema } from "effect"
import { Plugin, Store } from "@opencode/plugin/gui"

export const definition = Plugin.define({
  stores: { notes: Store.global(Schema.Struct({ count: Schema.Number }), { count: 0 }) },
})
```

```tsx title="src/gui/window.tsx"
import type { Plugin } from "@opencode/plugin/gui"
import { Notes } from "./contract"
import type { definition } from "./definition"

export const setup: Plugin.Setup<typeof definition> = (ctx) => {
  ctx.provide(Notes, { count: () => ctx.stores.notes.value.count })
}
```

```ts title="src/gui/main.ts"
import type { Plugin } from "@opencode/plugin/gui"

export const main: Plugin.MainSetup = (ctx) => {
  ctx.log.write("info", "acme started")
}
```

```tsx title="src/gui.tsx"
import { Plugin } from "@opencode/plugin/gui"
import { definition } from "./gui/definition"
import { main } from "./gui/main"
import { setup } from "./gui/window"

export default Plugin.define({ ...definition, setup, main })
```

- `Plugin.Setup<typeof definition>` ist der Typ eines Fenster-Setups. Es typisiert `ctx.stores` aus den deklarierten Stores und
  `ctx.icons` aus den deklarierten Icons.
- `Plugin.MainSetup` ist der Typ eines Haupt-Setups und `Plugin.Cleanup` der Typ der Cleanup-Funktion, die beide Setups
  zurückgeben können.
- Importiere Registries, Tokens und Helfer wie `Command`, `SettingsPage`, `Panel`, `Slot`, `Contract`, `Ipc`,
  `Registry`, `Store`, `createKeyed`, `usePlugin` und `bindPlugin` aus `@opencode/plugin/gui`.
- Importiere Registries, die nur im Hauptprozess verfügbar sind, etwa `MenubarItem`, aus
  `@opencode/plugin/gui/main`.

## Gemeinsamer Kontext

Beide Setups erhalten die Optionen des Plugins, einen Client für den OpenCode-Server und App-Metadaten, wie die Server- und TUI-
Teile.

### Optionen

`ctx.options` enthält die `options` aus dem `opencode.json(c)`-Eintrag des Plugins: dieselben Werte, die der Server-Teil erhält.

```jsonc title="opencode.jsonc"
{
  "plugins": [{ "package": "opencode-acme-plugin", "options": { "team": "core" } }],
}
```

```ts
setup(ctx) {
  const team = ctx.options.team
}
```

- Das Ändern der Optionen lädt das Plugin neu.

### Server-Client

`ctx.client` ist der OpenCode-Client des Servers, der das Plugin ausführt: der eigene Server der Desktop-App. Nutze ihn, um
deinen Server-Teil über seinen [RPC](/build/plugins/rpc) aufzurufen.

```ts
import { Command } from "@opencode/plugin/gui"
import { Acme } from "./rpc"

ctx.add(Command, () => ({
  id: "search",
  title: ctx.t("command.search"),
  run: async () => {
    const result = await ctx.client.rpc(Acme).search({ query: "todo" })
    console.log(result)
  },
}))
```

- Lies `ctx.client` unmittelbar vor der Verwendung. Nach einem Neustart des Servers liefert es einen anderen
  Client.
- Solange der Server nicht erreichbar ist, werden alle Aufrufe abgelehnt.

### App-Metadaten

`ctx.app` beschreibt die laufende App.

```ts
if (!ctx.app.packaged) console.log(`Acme on ${ctx.app.name} ${ctx.app.version} (${ctx.app.channel})`)
```

- `name` ist `"opencode"`, wie `ctx.app.name` eines Server-Plugins.
- `platform` ist `"desktop"` in der Electron-App und in `main` und `"web"` in einem Browser-Tab.
- `packaged` ist `true`, wenn die Desktop-App paketiert läuft. Im Web ist es immer `false`.
- Server-Plugins erhalten `name`, `version` und `channel`; TUI-Plugins erhalten `version` und `channel`.

#### Referenz

```ts
interface App {
  name: string
  version: string
  channel: "local" | "dev" | "beta" | "prod"
  platform: "web" | "desktop"
  packaged: boolean
}
```

## Verträge und Tokens

Tokens lassen GUI-Plugins prozessübergreifend und miteinander kommunizieren, ohne den Laufzeitcode des anderen zu importieren. Lege jedes
Token in `contract.ts` ab. Ein Token enthält nur seine Art und ID sowie die Schemas eines `Ipc`, sodass andere Plugins es importieren können,
ohne deinen Laufzeitcode.

- `ctx.provide(token, impl)` stellt eines deiner eigenen Tokens bereit: einen `Contract` aus dem Fenster-Setup oder ein `Ipc` aus
  `main`.
- Mit `ctx.use(token)` verfolgst du den Zustand eines Vertrags oder `Ipc`, das ein anderes Plugin
  bereitstellt. Der Aufruf gibt einen [`Live`](#live-dependencies-and-failure-handling)-Accessor zurück.
- `ctx.main(ipc)` gibt einen Client für ein `Ipc` zurück, das dein eigenes `main` bereitstellt.

Ein Plugin stellt nur Tokens bereit, deren ID seine eigene ist oder damit beginnt, als `<id>.<name>`. `ctx.provide` wirft bei jeder
anderen ID, und `ctx.main` wirft bei einem `Ipc` außerhalb deiner ID. Die Beispiele auf dieser Seite nutzen die Plugin-ID `acme`, ihre Token-IDs
beginnen also mit `acme.`.

```ts
Contract.define<AcmeBadge, "acme.badge">("acme.badge") // Plugin acme can provide it.
Contract.define<AcmeBadge, "badge">("badge") // ctx.provide throws in plugin acme.
```

### Verträge

Nutze `Contract.define`, wenn das Fenster-Setup eines Plugins eine API oder eine Solid-Komponente für die Fenster-
Setups anderer Plugins bereitstellt.

```ts title="src/gui/contract.ts"
import type { JSX } from "solid-js"
import { Contract } from "@opencode/plugin/gui"

export interface AcmeBadge {
  Badge(props: { readonly label: string }): JSX.Element
  count(): number
}

export const AcmeBadge = Contract.define<AcmeBadge, "acme.badge">("acme.badge")
```

Stelle es aus dem Fenster-Setup mit `ctx.provide` bereit. Wenn der Vertrag eine Komponente enthält, wickle sie während des Setups mit `bindPlugin`
ein. Dann liest `usePlugin()` darin den Kontext des Anbieters, nicht den des Konsumenten.

```tsx title="src/gui.tsx"
import { bindPlugin, Plugin } from "@opencode/plugin/gui"
import { AcmeBadge } from "./gui/contract"

export default Plugin.define({
  i18n: { en: { title: "Acme" } },
  setup(ctx) {
    ctx.provide(AcmeBadge, {
      Badge: bindPlugin((props: { readonly label: string }) => (
        <span>
          {ctx.t("title")}: {props.label}
        </span>
      )),
      count: () => 42,
    })
  },
})
```

- Annotiere die Props einer Komponente, die du mit `bindPlugin` wickelst, wie in `bindPlugin((props: FileTreeProps) => ...)`.
  TypeScript kann sie in `ctx.provide` nicht ableiten.
- Datenmethoden wie `count` brauchen keinen Wrapper.
- `ctx.provide` gibt eine Funktion zurück, mit der du den Vertrag vorzeitig zurückziehen kannst. Der Host
  zieht ihn auch zurück, wenn der aktuelle Owner endet. Gibt es keinen Owner, geschieht das beim Beenden des
  Plugins.

### Den Vertrag eines anderen Plugins nutzen

Exportiere `contract.ts` aus deinem Paket, zum Beispiel als `./contract`, damit andere Plugins seine Tokens importieren können. Ein anderes
Plugin folgt dem Vertrag mit `ctx.use(token)`. Der Wert des Accessors ändert sich, wenn der Anbieter startet, stoppt und
neu startet, lies ihn also dort, wo du ihn nutzt.

```tsx title="src/gui.tsx"
import { Plugin, Slot } from "@opencode/plugin/gui"
import { AcmeBadge } from "opencode-acme-plugin/contract"

export default Plugin.define({
  setup(ctx) {
    const badge = ctx.use(AcmeBadge)

    const count = () => {
      const live = badge()

      return live.status === "active" ? live.value.count() : 0
    }

    ctx.add(Slot, { at: "window.bottom", render: () => <span>{count()}</span> })
  },
})
```

- `ctx.use` gibt für jeden Aufruf mit dem Token denselben Accessor zurück.
- Der Konsument funktioniert weiter, während der Anbieter aus ist. Siehe
  [Live-Abhängigkeiten und Fehlerbehandlung](#live-dependencies-and-failure-handling).

### IPC zwischen Hauptprozess und Fenstern

Nutze `Ipc.define` mit Effect-`Schema`-Codecs, um eine typisierte Brücke zwischen `main` und `setup` zu definieren. `main` implementiert sie
mit `ctx.provide`, und das Fenster ruft sie über `ctx.main` auf.

```ts title="src/gui/contract.ts"
import { Schema } from "effect"
import { Ipc } from "@opencode/plugin/gui"

export const KeepAwake = Ipc.define({
  id: "acme.awake",
  methods: {
    screenActive: { output: Schema.Boolean },
    setScreenActive: { input: Schema.Boolean },
  },
})
```

```ts
const awake = ctx.main(KeepAwake)

await awake.setScreenActive(true)
```

- Andere Plugins folgen deinem `Ipc` mit `ctx.use(KeepAwake)`, wie einem Vertrag.
- Siehe [Ein Ipc definieren und bereitstellen](#define-and-provide-an-ipc) für Zustand, Events und den Anbieter.

### Registries, die dein Plugin besitzt

Nutze `Registry.define` für eine Liste, die dein Plugin besitzt. Andere Plugins tragen Elemente mit `ctx.add` bei, und dein Plugin liest
sie mit `ctx.list`.

```ts title="src/gui/contract.ts"
import { Registry } from "@opencode/plugin/gui"

export interface Exporter {
  readonly id: string
  readonly title: string
  run(text: string): void
}

export const Exporter = Registry.define<Exporter>("acme.exporter")
```

```tsx
// Another plugin contributes an item.
ctx.add(Exporter, () => ({ id: "gist", title: ctx.t("exporter.gist"), run: (text) => upload(text) }))

// The owner lists every contribution. Reactive: read it in render or in a memo.
const exporters = () => ctx.list(Exporter)
```

## Das Fenster

Das `setup` eines Plugins läuft in jedem Fenster der Desktop-App. Übergib es in der
[`./gui-experimental`-Datei](#define-the-gui-plugin) des Plugins an `Plugin.define` aus
`@opencode/plugin/gui`. `setup` läuft synchron und kann eine Cleanup-Funktion zurückgeben; siehe
[Lebensdauer und Bereinigung](#lifetimes-and-cleanup).

```tsx title="src/gui.tsx"
import { Command, Plugin } from "@opencode/plugin/gui"

export default Plugin.define({
  i18n: { en: { open: "Open Acme" } },
  setup(ctx) {
    ctx.add(Command, () => ({
      id: "open",
      title: ctx.t("open"),
      run: () => ctx.system.openExternal("https://acme.example"),
    }))
  },
})
```

## Komponenten

Rufe in Solid-Komponenten `usePlugin<typeof definition>()` für dasselbe Kontextobjekt auf, das `setup` erhält. Typisiere
es aus den Deklarationen in ihrer eigenen Datei ([auf Dateien verteilt](#split-across-files)), damit
Komponente und Definition einander nicht importieren.

```tsx title="src/gui/window.tsx"
import { Slot, usePlugin, type Plugin } from "@opencode/plugin/gui"
import type { definition } from "./definition"

function StatusLabel() {
  const ctx = usePlugin<typeof definition>()

  return <span>{ctx.t("title")}</span>
}

export const setup: Plugin.Setup<typeof definition> = (ctx) => {
  ctx.add(Slot, { at: "window.bottom", render: () => <StatusLabel /> })
}
```

`usePlugin` wirft außerhalb eines Plugin-Beitrags. In einer Komponente, die ein anderes Plugin rendert, gibt es den Kontext dieses Plugins
zurück, wickle eine Komponente, die du über einen Vertrag bereitstellst, also mit `bindPlugin` ein; siehe [Verträge](#contracts).

## Icons

Jedes `icon`-Feld des SDK und `ctx.ui.Icon` nimmt einen `IconName`: den Namen eines Icons der App oder eines
Icons, das dein Plugin deklariert. Jeder andere String lässt die Kompilierung fehlschlagen.

```ts
ctx.add(TitlebarItem, () => ({ id: "sync", label: ctx.t("sync"), icon: "server", run: () => sync() }))
```

### Eigene Icons deklarieren

Behalte für Grafik, die die App nicht hat, etwa die Marke deines Produkts, die SVG-Datei in deinem Paket und deklariere sie in
`icons`. Importiere die Datei mit `?raw`, was die Voreinstellung `gui()` als Text bündelt.

```ts title="src/gui/definition.ts"
import { Plugin } from "@opencode/plugin/gui"
import logo from "./icons/logo.svg?raw"

export const definition = Plugin.define({
  icons: { logo },
})
```

Übergib dann den Namen des Icons aus `ctx.icons`, wo immer ein `IconName` hingehört.

```tsx title="src/gui/window.tsx"
import { ComposerPill, Slot, type Plugin } from "@opencode/plugin/gui"
import type { definition } from "./definition"

export const setup: Plugin.Setup<typeof definition> = (ctx) => {
  ctx.add(ComposerPill, {
    id: "sync",
    show: () => ({ label: ctx.t("synced"), icon: ctx.icons.logo, tone: "success" }),
  })

  ctx.add(Slot, { at: "window.bottom", render: () => <ctx.ui.Icon name={ctx.icons.logo} size="small" /> })
}
```

- `ctx.icons` hat einen Namen für jedes Icon, das du deklarierst. Ein nicht deklarierter Name lässt die Kompilierung fehlschlagen.
- Der Host registriert deine Icons, bevor `setup` läuft, und zieht sie zurück, wenn das Plugin verschwindet.
- Ein Wert, der kein SVG-Dokument ist, lässt das Plugin beim Start fehlschlagen.
- Damit der `?raw`-Import typprüft, füge `"vite/client"` zu `types` in deiner `tsconfig.json` hinzu.

### Ein Icon zeichnen

Der Host zeichnet dein Icon wie seine eigenen: in der Größe und Farbe der Stelle, die es zeigt.

```xml title="src/gui/icons/logo.svg"
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 16 16" fill="none">
  <circle cx="8" cy="8" r="6.5" stroke="currentColor" />
  <path d="M5 8.5 7 10.5 11 6" stroke="currentColor" stroke-linecap="round" stroke-linejoin="round" />
</svg>
```

- Die `viewBox` rahmt die Zeichnung, oder `width` und `height`, wenn es keine gibt. Der Host skaliert sie auf 14, 16 oder
  20 Pixel, zeichne also auf einem 16-Pixel-Raster.
- Zeichne mit `currentColor`. Das Icon nimmt dann die Farbe seiner Stelle an, etwa den `tone` eines Chips oder die gedämpfte
  Icon-Farbe einer Menüzeile.
- Eine `id` in der Zeichnung gehört zum ganzen Fenster. Halte IDs eindeutig oder lass sie weg.

### Ein Icon animieren

Ein Icon kann sich bewegen, zum Beispiel um laufende Arbeit zu zeigen. Nutze SVG-Animationselemente wie `animate` und
`animateTransform` in der Datei.

```xml title="src/gui/icons/working.svg"
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 16 16" fill="none">
  <circle cx="8" cy="8" r="6.5" stroke="currentColor" />
  <circle cx="8" cy="8" r="2" fill="currentColor">
    <animate attributeName="r" values="2;4.5;2" dur="2.4s" repeatCount="indefinite" />
  </circle>
</svg>
```

- Überall, wo das Icon angezeigt wird, läuft die Animation synchron.
- Die Animation läuft weiter, während der Host die Stelle erneut rendert, etwa wenn `show` eines Chips erneut läuft.
- Bei aktivierter Einstellung für reduzierte Bewegung hält der Host jedes Icon auf seinem ersten Frame an. Mach den ersten Frame
  zur ruhenden Zeichnung.
- Icons, die nirgends angezeigt werden, verursachen keinen Aufwand.

### Gespeicherte Icon-Namen

Der Name eines Icons ist ein String im Format `<plugin id>:<name>`. Der Host speichert ihn wie den Namen eines eigenen
Icons. Für einen [Hinweis oder ein Zitat am Eingabefeld](#attach-to-the-composer) speichert er den Namen im Entwurf
und in der gesendeten Nachricht, für einen [geschlossenen Tab](#reopen-closed-tabs) im Layout der Session.

```ts
ctx.screen.current()?.composer.attach({
  type: "note",
  origin: ctx.id,
  commentID: crypto.randomUUID(),
  label: "button#submit",
  icon: ctx.icons.logo,
  subject: 'element <button id="submit">Save</button>',
  comment: "",
})
```

- Solange dein Plugin nicht aktiv ist, zeichnet das Icon nichts und behält seine Größe.
- Lies den Namen aus `ctx.icons`, wo du ihn nutzt. Ein von Hand geschriebener Name lässt die Kompilierung fehlschlagen.

#### Referenz


## Registries

Übergib ein Registry-Token und ein Element an `ctx.add`, um zur Fenster-Shell beizutragen. Übergib das Element als Funktion,
`() => item | undefined`, wenn es reaktivem Zustand wie der Sprache folgt. Der Host führt die Funktion erneut aus, wenn sich
das Gelesene ändert. Gib `undefined` zurück, um das Element zurückzuziehen, bis die Funktion wieder eines zurückgibt.

```ts
ctx.add(Command, () => ({ id: "open", title: ctx.t("command.open"), run: () => open() }))
```

- Lies Beschriftungen mit `ctx.t` innerhalb der Funktion. Eine Beschriftung, die du für ein statisches Element
  nur einmal abfragst, bleibt in der damals eingestellten Sprache.
- Wenn das Element ein Feld mit Literaltyp hat, etwa `hidden: true`, eine `section`, ein `icon` oder einen Menünamen, annotiere
  den Rückgabetyp der Funktion: `(): Command => ({ ... })`. Ohne das erweitert TypeScript das Feld auf `string` oder
  `boolean`, und keine Überladung passt.
- Übergib ein festes Element, wenn es sich nie ändert, etwa einen [Style](#styles).
- Der Host hält einige Objekte stabil: die Tabs, die ein Panel aus `list` zurückgibt, und Elemente mit einem `render`, etwa Panels
  und Einstellungsseiten. Lies ihre Labels aus Gettern, etwa `get title() { return ctx.t("title") }`.
- `ctx.add` gibt eine Funktion zurück, die das Element vorzeitig zurückzieht.

### Befehle

`Command` fügt eine Aktion zur Befehlspalette, zu **Settings > Shortcuts** und optional zum `/`-Menü des Eingabefelds
hinzu. Der Host veröffentlicht den Befehl als `<plugin id>.<command id>`.

```ts
import { Command } from "@opencode/plugin/gui"

ctx.add(
  Command,
  (): Command => ({
    id: "toggle",
    title: ctx.t("command.toggle"),
    keywords: "notes scratch",
    group: ctx.t("command.category.view"),
    section: "terminal",
    bind: "ctrl+`",
    slash: { name: "notes", after: "open" },
    featured: true,
    enabled: !!ctx.sessions.current(),
    run: () => {
      const session = ctx.sessions.current()

      if (session) ctx.layout.toggle(`${ctx.id}:main`, session)
    },
  }),
)
```

- `title` ist das Label der Palette, `description` ihre zweite Zeile und `group` ihre Kategorie als übersetzter Text.
- `keywords` enthält zusätzliche Wörter, die die Palette abgleicht, getrennt durch Leerzeichen.
- `section` ist der Abschnitt in **Settings > Shortcuts**. Standard ist `general`.
- `bind` legt die Standard-Tastenbelegung fest, zum Beispiel `mod+shift+t`. Nutzer können sie ändern.
- `slash` bietet den Befehl auch im `/`-Menü an. Mit `arguments: true` geht der Text nach dem Namen an
  `run(input)`.
- `hidden` hält den Befehl aus der Palette, seine Tastenbelegung funktioniert aber weiterhin.
- `suggested` listet den Befehl zusätzlich unter **Suggested**, solange er aktiviert ist. `featured` listet ihn, wenn die Palette
  ohne Abfrage geöffnet wird.
- `enabled: false` nimmt den Befehl aus der Palette und schaltet seine Tastenbelegung aus. Es ist reaktiv.
- `scope` ist ein CSS-Selektor, in dem der Tastaturfokus liegen muss, damit die Bindung gilt. Mit `editable` löst die Bindung
  auch aus, während ein Textfeld den Fokus hat.
- Um einen Befehl aus deinem eigenen Code auszuführen, nutze `ctx.commands.run`; siehe [Befehle ausführen](#run-commands).

Wird `run` über eine Tastenbelegung aufgerufen, kann es `false` zurückgeben, um das Tastenereignis nicht
selbst zu behandeln. Das Ereignis wird dann an sein Ziel weitergereicht, als gäbe es für den Befehl keine
Tastenbelegung. Dieser Befehl setzt die Session fort, wenn der Nutzer bei leerem Prompt Enter drückt. In allen
anderen Fällen verarbeitet der Prompt Enter wie gewohnt:

```ts
ctx.add(Command, () => ({
  id: "continue",
  title: ctx.t("command.continue"),
  bind: "enter",
  editable: true,
  hidden: true,
  run: () => {
    const composer = ctx.screen.current()?.composer
    const session = ctx.sessions.current()

    if (!composer?.focused() || composer.text().trim() || !session) return false
    void session.server.client.session.prompt({ sessionID: session.id, text: ctx.t("continue") })
  },
}))
```

- Gib `false` synchron zurück. Bei einem Promise als Rückgabewert gilt das Tastenereignis als behandelt.
- `false` aus der Palette oder einem Slash-Befehl bewirkt nichts weiter.

#### Referenz

```ts
interface Command {
  id: string
  title: string
  description?: string
  keywords?: string
  group?: string
  section?: "general" | "session" | "navigation" | "model" | "terminal" | "prompt"
  bind?: string
  slash?: { name: string; arguments?: true; after?: string }
  hidden?: true
  suggested?: boolean
  featured?: true
  enabled?: boolean
  scope?: string
  editable?: true
  run(input?: string): void | false | Promise<void>
}
```

### Panels

`Panel` fügt dem Seitenbereich einer Session Tabs hinzu (`region: "side"`). Nutzer können einen Tab in den
Bereich unter der Timeline ziehen.

```tsx
import { Panel, type PanelTab } from "@opencode/plugin/gui"

const mainTab: PanelTab = {
  id: "main",
  get title() {
    return ctx.t("panel.title")
  },
  closable: "compact",
  fallback: true,
}

ctx.add(Panel, {
  id: "main",
  region: "side",
  mobile: {
    get title() {
      return ctx.t("panel.title")
    },
    order: 45,
    kind: "menu",
    icon: "file-tree",
  },
  list: (input) => (input.open.includes("main") ? [mainTab] : []),
  render: (props) => <NotesView session={props.session} screen={props.screen} tab={props.tab} />,
})
```

Alle Panel-Callbacks (`list`, `render`, `focus`, `enter`, `close`, `closed`, `restore`, `normalize`) erhalten ein einziges
Eingabeobjekt:

- Lies `props.session` und `props.tab` als reaktive Getter, wo du sie nutzt. Destrukturiere sie nie am Anfang von
  `render`: Wenn der Nutzer von Session A zu Session B wechselt, bleibt das Panel eingebunden und `props.session` aktualisiert sich
  an Ort und Stelle.
- `props.screen` ist der konstante `SessionScreen`, der `file`, `comment` und `composer` besitzt. Seine Aktionen zielen immer auf die
  geroutete Session.
- Gib dasselbe `PanelTab`-Objekt aus `list` zurück, solange ein Tab unverändert ist, damit der Host seinen Trigger nicht neu einbindet.
  Lies seine Labels aus Gettern, damit sie der Sprache ohne neues Objekt folgen.

Die Callbacks eines Panels:

- `list` liefert die anzuzeigenden Tabs. `input.open` enthält die Tab-IDs dieses Plugins, die in der Session
  gespeichert sind. Der Wert ist reaktiv.
- `render` rendert den Inhalt eines Tabs einmal.
- `focus` läuft, wenn ein Tab gewählt wird. `restored` ist `true` für die Auswahl, mit der der Bereich eingebunden wird.
- `enter` läuft, wenn der Nutzer den Seitenbereich mit seinem Schalter auf dem Tab öffnet, sobald der Tab auf dem Bildschirm ist. Verschiebe den Tastatur-
  fokus auf das eigene Ziel des Tabs, etwa ein Textfeld. Wenn der Fokus noch außerhalb des Bereichs ist, fokussiert der Host den
  Bereich.
- `close` läuft, nachdem der Host einen Tab entfernt hat.
- `closed` und `restore` lassen den Nutzer einen geschlossenen Tab wieder öffnen; siehe [Geschlossene Tabs wieder öffnen](#reopen-closed-tabs).
- `normalize` gibt die kanonische Form einer gespeicherten Tab-ID zurück, die auf mehr als eine Weise gespeichert werden kann.

Die Optionen eines Panels:

- `mobile` ergänzt eine Ansicht für schmale Bildschirme. Mit `cached: true` bleibt sie auch dann eingebunden,
  wenn der Nutzer zu einer anderen Ansicht wechselt. Standardmäßig wird sie bei jedem Anzeigen neu
  eingebunden.
- `wide` fordert die größere Mindestbreite für die Session an, solange der Seitenbereich geöffnet ist.
- `width` gibt dem Panel eine eigene Breite im Seitenbereich; siehe [Panelbreite](#panel-width).
- Die Tabs von `transient`-Panels werden nicht wiederhergestellt.

#### Panelbreite

Standardmäßig teilen alle Tabs im Seitenbereich die Breite der Unterhaltung. Setze `width`, wenn dein Panel weniger Platz braucht
als eine Review oder ein Browser, oder mehr. Übergib CSS-Pixel oder `"narrow"` für die schmalste Breite des Bereichs.

```ts
ctx.add(Panel, {
  id: "quota",
  region: "side",
  width: "narrow",
  list: (input) => (input.open.includes("quota") ? [tab] : []),
  render: () => <Quota />,
})
```

- Die Breite gilt, solange der Seitenbereich einen der Tabs des Panels zeigt. Andere Tabs behalten die Breite der Unterhaltung.
- Wenn der Nutzer den Trenner auf einem der Tabs des Panels zieht, behält der Host diese Breite für das Panel appweit anstelle
  von `width`.
- Der Host hält die Unterhaltung auf ihrer Mindestbreite und den Bereich mindestens auf `"narrow"`.
- `ctx.layout.side.width(panel)` liest die gespeicherte Breite, und `ctx.layout.side.resize(panel, width)` speichert eine, wie ein Ziehen
  es tut. Eine gespeicherte Breite gilt auch für ein Panel ohne `width`.

Die Optionen eines Tabs:

- `id` ist die Tab-ID; ihr Host-Schlüssel ist `<plugin id>:<id>`. `title` ist ihr zugänglicher Name, und `label` rendert eigenen
  Trigger-Inhalt.
- `pinned` Tabs werden aufgelistet, ohne geöffnet zu werden, kommen zuerst und werden nie geschlossen oder gezogen.
- `draggable` lässt den Nutzer den Tab neu anordnen. Standard ist `true`.
- `closable` setzt das Aussehen der Schließen-Schaltfläche: `"compact"`, `"hover"` oder `false` für keine.
- `transient` markiert einen Launcher-Tab wie **Open file**, den die nächste Vorschau ersetzt.
- `fallback` aktiviert die Fallback-Auswahl, wenn die gespeicherte Auswahl fehlt.
- Tabs in einer `group` teilen sich ein Render, das eingebunden bleibt.
- `missing` streicht den Tab durch, zum Beispiel für eine Datei, die nicht mehr existiert.
- `hidden` hält einen wiederhergestellten Tab aufgelistet und wählbar, aber nicht gezeichnet, solange sein Inhalt noch nicht bekannt ist.
- `file` ist der Workspace-Pfad, den der Tab zeigt, aufgelistet als eine der offenen Dateien der Session.
- `tabbable` nimmt das Tab-Panel in die Tab-Reihenfolge auf, für Inhalte ohne fokussierbare Elemente.

#### Referenz

```ts
interface Panel {
  id: string
  region: "side"
  mobile?: MobileView
  wide?: boolean
  width?: number | "narrow"
  transient?: boolean
  list(input: { session: MountedSession; screen: SessionScreen; open: string[] }): PanelTab[]
  render(props: PanelProps): JSX.Element
  focus?(input: PanelProps & { restored: boolean }): void
  enter?(input: PanelProps): void
  close?(input: PanelProps): void
  closed?(input: PanelProps): ClosedPanelTab | false | undefined
  restore?(input: { session: MountedSession; screen: SessionScreen; id: string; data?: string }): void
  normalize?(input: { id: string; session: MountedSession; screen: SessionScreen }): string
}

interface PanelProps {
  tab: PanelTab
  session: MountedSession
  screen: SessionScreen
}

interface PanelTab {
  id: string
  title: string
  label?(state: { active: boolean; preview: boolean; session: MountedSession }): JSX.Element
  pinned?: boolean
  draggable?: boolean
  closable?: "compact" | "hover" | false
  transient?: boolean
  fallback?: boolean
  group?: string
  missing?: boolean
  hidden?: boolean
  file?: string
  tabbable?: boolean
}

interface MobileView {
  title: string
  order: number
  kind: "tab" | "menu" | "drawer"
  icon?: IconName
  cached?: boolean
}
```

### Geschlossene Tabs wieder öffnen

Für jeden geschlossenen Tab im Seitenbereich speichert der Host einen Eintrag. Liegt der Fokus im
Seitenbereich, öffnet ⌘⇧T den zuletzt geschlossenen Tab erneut. In der Ansicht **New tab** stehen geschlossene
Tabs mit einer `file` unter **Recently closed**. Mit `closed` und `restore` legst du fest, wie der Tab dort
angezeigt und wie er wieder geöffnet wird.

```tsx
ctx.add(Panel, {
  id: "page",
  region: "side",
  list: (input) => input.open.map(pageTab),
  render: (props) => <PageView tab={props.tab} />,
  closed: (input) => {
    const url = pages.get(input.tab.id)

    return url ? { icon: "globe", detail: new URL(url).host, data: url } : false
  },
  restore: (input) => {
    if (input.data) openPage(input.session, input.data)
  },
})
```

- `closed` läuft beim Schließen eines Tabs. Gib die Angaben für die Zeile und die `data` zurück, die `restore`
  zum Wiederöffnen benötigt. Kann der Tab nicht wieder geöffnet werden, gib `false` zurück.
- `title` ist standardmäßig der Titel des Tabs und `icon` das mobile Icon des Panels. Ein Tab mit einer `file` zeigt sein Datei-Icon
  und seinen Ordner als `detail`.
- Der Host speichert den Eintrag, halte `data` also klein, etwa eine URL.
- `restore` erhält die `id` des geschlossenen Tabs und die `data`, die `closed` zurückgegeben hat. Ohne `restore` öffnet der Host
  denselben Schlüssel erneut.
- Ohne `closed` wird ein Tab, der nicht `transient` ist, unter seinem Titel aufgelistet und unter demselben Schlüssel wieder geöffnet.

#### Referenz

```ts
interface ClosedPanelTab {
  title?: string
  icon?: IconName
  detail?: string
  data?: string
}
```

### Einstellungsseiten

`SettingsPage` ergänzt **Settings** um eine Seite, fügt einer vorhandenen Seite einen Abschnitt hinzu
(`page: "general"` oder `page: "servers"`) oder ergänzt Zeilen im Bereich General des Hosts
(`page: "general", section: "general"`).

```tsx
import { SettingsPage } from "@opencode/plugin/gui"
import { AcmeSettings } from "./settings"

ctx.add(SettingsPage, {
  id: "acme",
  icon: "server",
  get title() {
    return ctx.t("title")
  },
  get entries() {
    return [{ id: "sync", title: ctx.t("settings.sync"), keywords: "sync remote" }]
  },
  render: (input) => <AcmeSettings highlight={input.target} />,
})
```

- `id` ist der Tab-Wert der Seite in den Einstellungen (`/settings?tab=<id>`) und das Argument für `ctx.layout.settings`.
- `page` fügt einen Abschnitt zu einer Host-Seite hinzu statt einer Seite. Mit `section: "general"` fügt es Zeilen zum General-
  Abschnitt dieser Seite hinzu.
- `title` und `icon` sind Navigationslabel und Icon einer Seite.
- `entries` sind Suchmetadaten, indiziert, ohne die Seite einzubinden. Wenn die Suche einen Eintrag zeigt, erhält `render` seine
  ID als `target`.
- Eine Einstellungsseite hat ein `render`, der Host hält sie also stabil. Lies ihre Labels und Einträge aus Gettern.

Rendere die Seite mit den Einstellungskomponenten der App, damit sie wie die eigenen Seiten der App aussieht und die Suche ihre
Zeilen zeigen kann:

```tsx
const ui = ctx.ui

const AcmeSettings = () => (
  <ui.SettingsLayout title={ctx.t("title")} description={ctx.t("description")}>
    <ui.SettingsSection title={ctx.t("settings.section")}>
      <ui.SettingsRow id="sync" title={ctx.t("settings.sync")} description={ctx.t("settings.sync.description")}>
        <ui.Switch label={ctx.t("settings.sync")} hideLabel checked={sync()} onChange={setSync} />
      </ui.SettingsRow>
    </ui.SettingsSection>
  </ui.SettingsLayout>
)
```

- Eine eigene Seite rendert `SettingsLayout`, ein Abschnitt auf einer Host-Seite (`page`) rendert `SettingsSection`, und Zeilen
  in einem Host-Abschnitt (`section`) rendern `SettingsRow`s.
- Die `id` einer Zeile ist die `SettingEntry.id`, die sie zeigt: Die Suche scrollt zur Zeile und hebt sie hervor.
- Siehe [Einstellungskomponenten](#settings-components) für ihre Props.

#### Referenz

```ts
interface SettingsPage {
  id: string
  page?: "general" | "servers"
  section?: "general"
  title: string
  icon?: IconName
  entries?: SettingEntry[]
  render(input: { target?: string }): JSX.Element
}

interface SettingEntry {
  id: string
  title: string
  description?: string
  keywords?: string
}
```

### Slots

`Slot` rendert UI in einen von vier Fenster-Slots.

```tsx
import { Slot } from "@opencode/plugin/gui"

ctx.add(Slot, {
  at: "session.header",
  order: 10,
  render: (input) => <UsageRing session={input.session} active={input.active} />,
})
```

- `window.bottom` ist ein Streifen über die volle Breite am unteren Fensterrand, über Toasts.
- `session.header` ist die Titelzeile der Session-Timeline. Eine zwischengespeicherte Timeline bleibt eingebunden, während sie verborgen ist, mit `active`
  `false`.
- `session.location.menu` fügt Elemente zum Projektmenü hinzu, nach seinen Location-Details.
- `session.panel.end` enthält Aktionen am hinteren Ende der Tab-Leiste des Seitenbereichs.
- `order` sortiert die Elemente in einem Slot.

`session.location.menu` erhält `shown`, das `true` ist, solange das Projektmenü offen ist. Abonniere Location-Daten
nur, solange es `true` ist:

```tsx
ctx.add(Slot, {
```

### Menüelemente

`MenuItem` fügt einen Eintrag zum **+**-Menü des Seitenpanels (`"session.panel"`), zum Menü **Add server** (`"server.add"`)
oder zum Zeilenmenü jedes Servers in den Einstellungen (`"server.row"`) hinzu.

```ts
import { MenuItem } from "@opencode/plugin/gui"

ctx.add(MenuItem, (): MenuItem => {
  const session = ctx.sessions.current()

  return {
    menu: "session.panel",
    id: "open",
    title: ctx.t("menu.open"),
    icon: "folder",
    keybind: `${ctx.id}.open`,
    opened: !!session && ctx.layout.state(`${ctx.id}:main`, session) !== "closed",
    run: () => {
      if (session) ctx.layout.open(`${ctx.id}:main`, session)
    },
  }
})
```

- `order` sortiert die Elemente aufsteigend. Standard ist `0`.
- Das `run` eines `server.row`-Elements erhält den Server-Schlüssel der Zeile. `when` listet das Element nur in einigen Zeilen, und `enabled`
  zeigt es in anderen deaktiviert.

Ein `session.panel`-Element ist auch ein Launcher. Wenn der Nutzer den Seitenbereich ohne Tabs öffnet oder **+** klickt, während kein
Element `primary` ist, zeigt der Host eine Ansicht **New tab**, die die Launcher auflistet.

- `icon` ist das Icon des Elements und `keybind` eine veröffentlichte Befehls-ID, deren Tastenkürzel das Element zeigt.
- `description` ist ein kurzes gedämpftes Detail nach dem Titel in einer Launcher-Zeile, etwa eine Anzahl.
- `opened: true` bedeutet, der Tab, den das Element öffnet, ist bereits offen. Launcher-Listen lassen das Element weg, das **+**-Menü
  listet es weiterhin.
- `primary: true` lässt **+** das Element direkt ausführen, statt die Launcher zu zeigen. Das erste primäre Element in `order`
  gewinnt. Das Öffnen des Seitenbereichs ohne Tabs zeigt weiterhin die Ansicht **New tab**, die die Elemente auflistet, die nicht
  primär und nicht offen sind.
- `ctx.layout.side.menu()` listet die `session.panel`-Elemente jedes Plugins, für einen eigenen Launcher; siehe
  [Layout](#layout).

### Status-Chips am Eingabefeld

`ComposerPill` ergänzt die Zeile über dem Eingabefeld einer Session um einen Chip neben den Chips für
Hintergrundaktivitäten und Aufgaben. Nutze ihn für Statusinformationen zur aktuellen Session, etwa zu den Pull
Requests des Branches. Die Chips liegen über der Timeline, sodass ihr Ein- und Ausblenden die Größe des
Eingabefelds nicht verändert. Die Zeile übernimmt die vom Nutzer gewählte Ausrichtung der Hintergrundaktivitäten
und erscheint nicht in Sessions von Subagenten.

`show` liefert den Chip für eine Session oder `undefined`, wenn dort keiner angezeigt werden soll. Der Host
ruft die Funktion für jedes eingebundene Eingabefeld auf und erneut, wenn sich die von ihr gelesenen Werte
ändern. Dieses Plugin fragt über den [RPC](/build/plugins/rpc) seines Server-Teils die offenen Pull Requests
im Verzeichnis der jeweiligen Session ab und zeigt sie in einem Chip an:

```tsx
import { createStore } from "solid-js/store"
import { ComposerPill, createKeyed } from "@opencode/plugin/gui"
import { GitHub, type Pull } from "./rpc"

const [pulls, setPulls] = createStore<Record<string, readonly Pull[]>>({})

createKeyed(
  () => ctx.sessions.current()?.directory,
  (directory) =>
    void ctx.client
      .rpc(GitHub)
      .pulls({ directory })
      .then((list) => setPulls(directory, list)),
)

ctx.add(ComposerPill, {
  id: "pulls",
  show: (input) => {
    const list = pulls[input.session.directory] ?? []

    if (list.length === 0) return undefined

    return {
      icon: "github",
      label: ctx.plural("pulls", list.length),
      tone: list.some((pull) => pull.checks === "failure") ? "danger" : undefined,
      title: ctx.t("pulls.title"),
      rows: list.map((pull) => ({
        id: String(pull.number),
        label: `#${pull.number} ${pull.title}`,
        icon: pull.checks === "failure" ? "circle-x" : "circle-check",
        tone: pull.checks === "failure" ? "danger" : "success",
        detail: pull.branch,
        run: () => ctx.system.openExternal(pull.url),
      })),
    }
  },
})
```

- `label` enthält den Text des Chips. Ist er zu lang, wird er gekürzt. `icon` ist optional.
- `tone` färbt das Icon: `"success"`, `"warning"` oder `"danger"`.
- Für ein Glyph, das die App nicht hat, etwa eine Statusmarke, die sich bewegt, [deklariere dein eigenes Icon](#icons) und übergib
  `ctx.icons.<name>`. Es nimmt den `tone` wie jedes Icon an, und seine Animation läuft, während `show` erneut läuft.
- Mit `rows` öffnet der Chip ein Menü mit `title` als Überschrift, ersatzweise mit `label`. Jede Zeile hat ein
  eigenes `icon`, einen eigenen `tone` und ein dezentes `detail`. Bei Auswahl wird `run` ausgeführt. Eine
  Zeile ohne `run` dient nur zur Anzeige.
- Ohne `rows` führt der Chip beim Klick `run` aus.
- `title` ist auch der zugängliche Name des Chips, wenn er von `label` abweicht.
- `order` sortiert deine Chips zwischen denen anderer Plugins, beginnend mit dem niedrigsten Wert. Die Chips
  der App stehen davor.
- Löst `show` einen Fehler aus, fällt nur dieser Beitrag deines Plugins aus.

#### Referenz

```ts

}

interface ComposerPillProps {
  session: MountedSession

}

  icon?: IconName
  tone?: ComposerPillTone

  run?(): void
}
```

### Codeblöcke

`CodeBlock` zeigt abgegrenzte Codeblöcke für die angegebenen Sprachen in deiner eigenen UI an, statt den Code
mit Syntaxhervorhebung darzustellen. Nutze es für Inhalte, die in gerenderter Form leichter zu lesen sind,
etwa eine Tabelle (` ```csv `) oder eine Formel (` ```latex `):

```tsx
import { For } from "solid-js"
import { CodeBlock } from "@opencode/plugin/gui"

ctx.add(CodeBlock, {
  languages: ["csv"],
  render: (props) => {
    const rows = props.code.split("\n").map((line) => line.split(","))

    if (rows.length < 2) return undefined

    return (
      <table>
        <tbody>
          <For each={rows}>
            {(row) => (
              <tr>
                <For each={row}>{(cell) => <td>{cell}</td>}</For>
              </tr>
            )}
          </For>
        </tbody>
      </table>
    )
  },
})
```

- `languages` werden mit dem ersten Wort der Sprach- und Metadatenangabe des Codeblocks verglichen, in
  Kleinbuchstaben: ` ```CSV title="Q3" ` passt zu `csv`. Der Host löst keine Aliase auf. Führe daher alle
  Namen auf, die du akzeptierst.
- `render` erhält den `code` des Blocks, seine `language` und die `session`, die ihn zeigt. Gib `undefined` oder `null` zurück, um
  den hervorgehobenen Code zu behalten, zum Beispiel wenn die Quelle nicht parst.
- Ein Render, der wirft, zeichnet den Fehler unter deinem Plugin auf, und der Block zeigt seinen Code. Deine anderen Beiträge
  funktionieren weiter.
- Wenn mehrere Plugins eine Sprache auflisten, rendert sie der erste Beitrag. Dein Renderer ersetzt auch das eigene
  Mermaid-Diagramm der App, wenn du `mermaid` auflistest.

#### Streaming

Der Host verwendet deinen Renderer erst, wenn die schließende Markierung des Codeblocks eingeht. Solange der
Block gestreamt wird oder wenn die Nachricht mitten im Block abbricht, sieht der Nutzer den Code mit
Syntaxhervorhebung. Sobald der Block vollständig ist, ersetzt deine UI den Code an derselben Stelle. Der
Renderer erhält nie einen unvollständigen Block.

#### Wo es gilt

| Oberfläche                                                     | Codeblock-Inhalt |
| -------------------------------------------------------------- | ---------------- |
| Timeline: Assistententext und Tool-Ausgabe                     | Ja               |
| Seitenpanels auf dem Session-Bildschirm, etwa die Markdown-Vorschau | Ja          |
| `ctx.ui.Markdown` auf dem Session-Bildschirm gerendert         | Ja               |
| `ctx.ui.Code` und Markdown in deinem eigenen `CodeBlock`-Render | Nein            |
| Einstellungsseiten, Dialoge und andere Oberflächen außerhalb des Bildschirms | Nein |

#### Layout und Leistung

- Blöcke von Sprachen, die kein Plugin auflistet, kosten nichts; nur ein Block einer aufgelisteten Sprache rendert deine UI, und nur, solange
  seine Timeline-Zeile auf dem Bildschirm ist.
- Der Block wächst und schrumpft mit deiner UI. Gib asynchronem Inhalt eine Mindesthöhe, damit sich die Timeline weniger verschiebt,
  wenn er eintrifft.
- Der Block behält seine Copy-Schaltfläche zum Kopieren des Quelltexts. Deine `CodeBlockAction`-Schaltflächen
  erscheinen in der oberen Ecke am Zeilenende.

### Codeblock-Aktionen

`CodeBlockAction` fügt eine Schaltfläche neben der Copy-Schaltfläche der Codeblöcke der Sprachen hinzu, die du auflistest. `run` erhält denselben
Block, den ein `CodeBlock`-Render erhält:

```ts
import { CodeBlockAction } from "@opencode/plugin/gui"

ctx.add(CodeBlockAction, {
  id: "run",
  languages: ["sh", "bash", "shell", "zsh"],
  icon: "terminal",
  get title() {
    return ctx.t("run")
  },
  run: (input) => runInTerminal(input.code, input.session),
})
```

- Die Schaltfläche erscheint erst mit der schließenden Markierung des Codeblocks. Sie wird daher nie auf einen
  unvollständigen Befehl angewendet.
- Schaltflächen erscheinen mit Copy bei Hover oder Tastaturfokus, davor, in aufsteigender `order`.
- Lies `title` aus einem Getter, damit es der Locale folgt.
- Ein `run`, das wirft oder ablehnt, wird unter deinem Plugin protokolliert und ändert nichts anderes.

### Link-Handler

`LinkHandler` öffnet Links zu lokalen Dateien oder benutzerdefinierte Links, die Nutzer in Nachrichten oder
Chips am Eingabefeld anklicken. Der Handler mit der höchsten `priority`, dessen `match` wahr zurückgibt, öffnet den Link.

```ts
import { LinkHandler } from "@opencode/plugin/gui"

ctx.add(LinkHandler, {
  priority: 10,
  match: (link) => link.href.endsWith(".acme"),
  open: (link) => openAcmeFile(link.href, link.session),
  exists: (link) => acmeFileExists(link.href),
})
```

- `href` ist das Ziel: ein Pfad, eine URL oder ein `file://`-Link.
- `origin` ist das Plugin, das das verlinkte Element erzeugt hat.
- `exact` bedeutet, der Pfad ist eine bekannte Workspace-Datei, keine Vermutung aus Text.
- Ein `background`-Link darf die Ansicht für schmale Bildschirme nicht wechseln.
- `base` ist das workspace-relative Verzeichnis, in dem der Link geschrieben wurde.
- Ohne `exists` antwortet `ctx.links.exists` mit `false`, damit Text nie wie ein Link aussieht, den der Handler nicht öffnen kann.

```ts
interface LinkHandler {
  priority?: number
  match(link: Link): boolean
  open(link: Link): void
  exists?(link: Link): boolean | Promise<boolean>
}

interface Link {
  href: string
  origin?: string
  exact?: boolean
  background?: boolean
  base?: string
  session?: SessionRef
}
```

### Server

`Server` trägt eine Liste von Serververbindungen bei, etwa Servern, die dein Plugin auf anderen Maschinen startet.

```ts
import { Server } from "@opencode/plugin/gui"

ctx.add(
  Server,
  (): Server => ({
    ready: loaded(),
    entries: machines().map((machine) => ({
      id: machine.id,
      name: machine.name,
      label: "Acme",
      state: machine.url ? "ready" : "starting",
      http: machine.url ? { url: machine.url } : undefined,
    })),
  }),
)
```

- Der Start wartet, bis jede Quelle `ready` ist. Die Einträge einer bereiten Quelle sind ihr vollständiges Inventar.
- `order` sortiert die Quellen aufsteigend.
- Der Schlüssel jedes Eintrags ist `<plugin id>:<id>`. `label` ist ein kurzes Badge neben seinem `name`.
- `auth` bedeutet, der Server wartet auf die Anmeldung des Nutzers, und `incompatible`, dass er eine Version ausführt, die diese App nicht
  unterstützt.
- `listed: false` hält den Eintrag aus der Serverliste der App. Die Einstellungen zeigen ihn weiterhin.
- `http` ist der Endpunkt, sobald der Server `ready` ist.
- `reconnect` löst einen verlorenen Endpunkt erneut auf, `connect` bereitet einen Server vor, der nicht bereit ist, und `remove` läuft, bevor
  der Eintrag entfernt wird.
- `row` rendert die Einstellungszeile des Servers, und `cover` deckt die geroutete Session ab, solange der Server nicht bereit ist.
- Eine `row` erhält den Status-`Indicator` des Hosts, den letzten `health()`-Check und die `Items` des
  Zeilenmenüs `server.row`. Ihr `remove()` ruft `remove` für den Eintrag auf und schließt dann die Tabs des
  Servers.

```ts
  state: "stopped" | "starting" | "auth" | "ready" | "failed" | "incompatible"
```

### Themes

`Theme` fügt ein Farb-Theme zu Settings › Appearance › Theme hinzu. Es nutzt dasselbe Format wie die Theme-Dateien der App, eine
Theme-Datei lässt sich also unverändert importieren.

```ts
import { Theme } from "@opencode/plugin/gui"
import midnight from "./midnight.json"

ctx.add(Theme, midnight)
```

Eine Theme-Datei benennt sich selbst und gibt eine helle und eine dunkle Variante an. Jede Variante startet von einer `palette` oder von `seeds`,
nie beidem, und kann einzelne Tokens mit `overrides` festlegen.

```json
{
  "$schema": "https://opencode.ai/desktop-theme.json",
  "name": "Midnight",
  "id": "midnight",
  "light": {
    "palette": {
      "neutral": "#eceff4",
      "ink": "#2e3440",
      "primary": "#5e81ac",
      "success": "#8fbcbb",
      "warning": "#d08770",
      "error": "#bf616a",
      "info": "#81a1c1"
    }
  },
  "dark": {
    "palette": {
      "neutral": "#1b1f27",
      "ink": "#e5e9f0",
      "primary": "#88c0d0",
      "success": "#a3be8c",
      "warning": "#d08770",
      "error": "#bf616a",
      "info": "#81a1c1"
    },
    "overrides": { "syntax-keyword": "#88c0d0" }
  }
}
```

- Der Picker listet Plugin-Themes unter den Themes der App, alphabetisch nach `name`.
- Der Host vergibt für jedes Theme den Schlüssel `<plugin id>:<theme id>`. So überschreibt es weder ein Theme
  der App noch das eines anderen Plugins.
- Das Zurückziehen des Themes oder Deaktivieren des Plugins nimmt es aus dem Picker. Ein Nutzer, der es gewählt hat, behält die Wahl: Das
  Fenster zeigt das Standard-Theme, bis das Theme zurückkehrt.
- Beim Start zeigt das Fenster die aus dem letzten Lauf gespeicherten Farben, bis das Plugin das Theme erneut beiträgt.

## Host-APIs

Host-APIs sind Eigenschaften von `ctx`. Bevor die App-Oberfläche eingebunden ist, lösen sie keine Fehler aus.
Lesezugriffe liefern die dokumentierten Standardwerte. Frühe Schreibzugriffe wie `ctx.layout.open`,

```ts
ctx.add(Command, () => ({
```

### Layout

`ctx.layout.open(key, session, options?)` öffnet einen Panel-Tab über seinen Schlüssel, `<plugin id>:<tab id>`. Es funktioniert für Sessions,
die nicht eingebunden sind.

```ts
const session = ctx.sessions.current()

if (session) ctx.layout.open(`${ctx.id}:main`, session, { tab: "select", background: true })
```

- `tab: "open"`, der Standard, wählt den Tab im Vorschau-Slot. `"preview"` macht ihn zur neuen Vorschau, `"append"` fügt
  ihn hinzu, ohne ihn zu wählen, und `"select"` fügt ihn hinzu und wählt ihn, wobei die Vorschau bleibt.
- `background: true` behält die aktuelle Ansicht auf schmalen Bildschirmen und öffnet den Seitenbereich, für eine Aktion, die der Nutzer
  nicht vom Panel aus gestartet hat.
- `close(key, session)` entfernt den Tab und ruft `close` seines Panels auf. `toggle(key, session)` schließt einen sichtbaren Tab, sonst
  öffnet es ihn.
- `hide(key, session)` verbirgt den Bereich, der einen sichtbaren Tab zeigt, ohne den Tab zu schließen: den Seitenbereich oder den unteren
  Bereich für einen Tab, den der Nutzer dorthin verschoben hat. Das erneute Öffnen des Tabs zeigt seinen Bereich.
- `state(key, session)` ist `"closed"`, wenn der Tab nicht in der Leiste ist, `"open"`, wenn er es ist, aber sein Bereich einen anderen
  Tab zeigt, `"active"`, wenn sein Bereich ihn zeigt, der Bereich aber verborgen ist (der Seitenbereich ist geschlossen oder der untere Bereich ist
  verborgen), und `"visible"`, wenn er auf dem Bildschirm ist.
- `stored(session)` sind die Tab-IDs dieses Plugins, die in der Seitenleiste der Session gespeichert sind.
- `ready()` ist `true`, sobald das gespeicherte Layout geladen ist, und `narrow()` ist es, wenn der Viewport
  schmaler als 768 px ist.
- `side.opened(session)` ist `true`, solange der Seitenbereich offen ist, und `side.toggle(session)` öffnet oder schließt ihn.
- `side.menu()` listet die `session.panel`-[Menüelemente](#menu-items) jedes Plugins in `order`, für einen eigenen Launcher.
- `side.width(panel)` und `side.resize(panel, width)` lesen und speichern die Breite des Seitenbereichs eines deiner Panels; siehe
  [Panelbreite](#panel-width).
- `sidebar.opened()` ist die Einstellung der inneren Seitenleiste, die alle Seitenpanels teilen.
- `scroll` speichert Scroll-Offsets pro Session und Schlüssel.

### Sessions und der Session-Bildschirm

`ctx.sessions.current()` gibt die über die Route ausgewählte Session zurück, `ctx.screen.current()` den
zugehörigen Bildschirm. Auf Home und in einem Entwurf sind beide `undefined`. Lies die Werte dort, wo du sie
verwendest, nicht einmalig in `setup`.

```ts
const session = ctx.sessions.current()
const file = ctx.screen.current()?.file

if (session && file) void file.sync("README.md")
```

- `key` ist `<server id>\n<session id>`, eindeutig über Server hinweg. Speichere Zustand pro Session unter ihm.
- `tab` ist der Schlüssel des Shell-Tabs, dem die Session gehört. `pending` ist `true`, solange der Server sie noch erstellt.
- `directory` ist das Workspace-Verzeichnis der Session, und `local` ist `true`, wenn es die Projektwurzel ist.
- `listedProject` ist das Sidebar-Projekt, zu dem die Session gehört.
- `visit` ist ein neues Objekt, jedes Mal wenn die Session geroutet wird.
- `background` listet die laufenden Subagenten und Shell-Befehle der Session auf.
- `ctx.sessions.list()` gibt die Sessions der offenen Shell-Tabs zurück.
- `file` des Bildschirms liest die Dateien des Workspace, und `comment` enthält die Zeilenkommentare des nächsten Prompts.
  `composer` ist der nächste Prompt: sein Text, angehängte Teile und Modell; siehe
  [Anhänge zum Eingabefeld hinzufügen](#attach-to-the-composer).
- `file.sync(path)` lädt eine Datei und bittet den Server, sie auf Änderungen zu beobachten. Rufe `file.unwatch(path)` auf, wenn der Tab

### Anhänge zum Eingabefeld hinzufügen

Nutze `ctx.screen.current()?.composer` in einem Event-Handler oder Befehl, um eine Datei, einen Hinweis oder ein Zitat an den nächsten
Prompt des Nutzers anzuhängen.

```ts
const composer = ctx.screen.current()?.composer

composer?.attach({
  type: "note",
  origin: ctx.id,
  commentID: crypto.randomUUID(),
  label: "button#submit",
  icon: "globe",
  subject: 'element <button id="submit">Save</button>',
  comment: "Make this button primary and disable it while saving.",
  href: "http://localhost:3000/settings",
})
```

- `attach` lässt den Tastaturfokus, wo er ist. Rufe `focus()` auf, um ihn zum Prompt zu bewegen.
- `update(commentID, { comment?, preview? })` ändert einen angehängten Teil; ein Hinweis oder ein Zitat nimmt nur einen neuen `comment`.
- `detach(commentID)` entfernt einen angehängten Teil.
- Das `live` eines Hinweises ersetzt sein `subject` und `href`, solange der Hinweis in diesem App-Prozess bleibt, für Referenzen, die nur
  dieser Prozess auflösen kann, etwa ein Seitenelement. Ein gespeicherter Entwurf lässt es fallen, ebenso eine gesendete Nachricht, die ein Revert oder
  ein Fork wiederherstellt.

Ein Nutzer kann Text zitieren, den dein Plugin anzeigt, etwa eine Log-Ausgabe, und das Zitat kommentieren. Das Zitat
erscheint wie ein Zitat aus der Session-Timeline, unter dem Icon und der Beschriftung der Quelle. Prüfe zuerst
`quotable()`: Es ist `false` in Sessions von Subagenten, die kein Eingabefeld haben, und während das Eingabefeld
Shell-Befehle ausführt.

```ts
const composer = ctx.screen.current()?.composer

if (composer?.quotable()) {
  const commentID = crypto.randomUUID()

  composer.attach({
    type: "quote",
    commentID,
    text: selection,
    source: { label: ctx.t("source.label"), icon: "console", subject: "the Acme log" },
  })
  composer.focus(commentID)
}
```

- `source.subject` benennt die Quelle für das Modell, zum Beispiel `the terminal`. Es wird nicht lokalisiert.
- Lass `comment` weg, damit der Nutzer einen aus dem Chip hinzufügen kann.
- `focus(commentID)` öffnet den Kommentareditor eines angehängten Zitats. Ist das Eingabefeld ausgeblendet, etwa
  weil auf einem schmalen Bildschirm ein Panel angezeigt wird, öffnet sich der Editor erst, wenn das Eingabefeld
  wieder sichtbar ist.
- Das Modell liest `The user quoted the following from <subject>:`, dann den Text mit jeder Zeile, der `> ` vorangestellt ist,
  dann den Kommentar, falls vorhanden.

### Den Prompt lesen und schreiben

Lies den eingegebenen Text mit `text()` und prüfe mit `focused()`, ob das Eingabefeld gerade den Tastaturfokus
hat:

```ts
const composer = ctx.screen.current()?.composer
const empty = !composer?.text().trim()
```

- `text()` liefert den Prompt als reinen Text: Erwähnungen erscheinen als `@`-Text, Anhänge und angehängte Teile fehlen.
  Im Shell-Modus liefert es den Shell-Befehl. Bis der Entwurf der Session geladen ist und in Sessions von Subagenten,
  die kein Eingabefeld haben, gibt es `""` zurück. Der Wert ist reaktiv.
- `focused()` ist `true`, solange der Tastaturfokus im Prompt ist. Es ist nicht reaktiv, lies es also dort, wo du handelst, etwa in
  einem `run` eines Befehls.

`insert(text)` fügt Text in den Prompt ein, damit der Nutzer ihn prüfen und absenden kann. Keine Methode des
Eingabefelds sendet den Prompt ab.

```ts
const composer = ctx.screen.current()?.composer

composer?.insert(`Explain ${path}`)
composer?.focus()
```

- `insert` fügt den Text an der Stelle ein, an der der Nutzer den Cursor zuletzt im Prompt ließ, sonst am Ende, und bewegt den Cursor dahinter.
  Es ersetzt keinen ausgewählten Text.
- Der Text wird nicht geparst: `@path` bleibt Text, keine Erwähnung.
- `setText(text)` ersetzt den Text des Prompts, Erwähnungen eingeschlossen. Anhänge und angehängte Teile bleiben. `setText("")`
  leert den Text.
- Beide lassen den Tastaturfokus, wo er ist. Rufe `focus()` auf, um ihn zum Prompt zu bewegen.
- Ein Schreibvorgang, bevor der gespeicherte Entwurf der Session lädt (`insert`, `setText`, `attach`, `update` oder `detach`), wartet auf
  ihn. Er gilt dann für die Session, die geroutet war, als du ihn aufgerufen hast, in Aufrufreihenfolge. Er ersetzt nie den gespeicherten
  Entwurf.
- Sessions von Subagenten haben kein Eingabefeld. Schreibvorgänge bleiben dort wirkungslos.

### Das Modell wählen

`model()` ist das Modell, mit dem der nächste Prompt gesendet wird, und `setModel` wählt eines wie der Modell-Picker:

```ts
const composer = ctx.screen.current()?.composer

if (composer && !composer.setModel({ providerID: "anthropic", modelID: "claude-sonnet-4-5", variant: "high" })) {
  ctx.toast.show({ variant: "error", title: ctx.t("model.unavailable") })
}
```

- `model()` ist die Wahl des Nutzers für die geroutete Session, sonst der Standard des Agenten, sonst der Standard der App. Es ist
  `undefined`, während der Modellkatalog lädt, wenn kein verbundener Anbieter das Modell anbietet, und in der Session eines Subagenten.
  Es ist reaktiv.
- `setModel` wählt das Modell für die Session aus und setzt es an die erste Stelle der zuletzt verwendeten
  Modelle. Ohne `variant` behält das Modell die Variante, die in der Modellauswahl dafür angezeigt würde.
- `setVariant(variant)` wählt eine Variante des aktuellen Modells. `undefined` wählt die Standardvariante des Modells.
- `setModel` gibt `false` zurück und ändert nichts, während der Katalog lädt, wenn kein verbundener Anbieter das
  Modell anbietet oder wenn das Modell keine solche Variante hat.
- `setVariant` gibt `false` zurück und ändert nichts, wenn es kein aktuelles Modell gibt oder das Modell keine solche Variante hat.
- Beide geben in der Session eines Subagenten `false` zurück.

### Server und Server-Events

`ctx.servers.get(id)` gibt einen Live-`ServerRef` zurück. Der eigene Server der Desktop-App, der dein Plugin ausführt, hat die ID
`"sidecar"`. Reagiere auf seine Events mit `data.on`:

```ts
import { onCleanup } from "solid-js"
import { createKeyed } from "@opencode/plugin/gui"

createKeyed(
  () => ctx.servers.get("sidecar")?.data,
  (data) => onCleanup(data.on("session.created", (event) => console.log(event))),
)
```

- `id` ist der Host-Schlüssel: `"sidecar"`, eine http-URL oder `<plugin id>:<id>` für einen [beigetragenen Server](#servers).
- `data` sind die synchronisierten Daten des Servers, etwa Sessions und Projekte, und `on(type, handler)` für seine Events. Es ist
  reaktiv.
- `builtin` ist `true` für den eigenen Server der App.
- `compatible` ist `true`, wenn die Version des Servers mit dieser App funktioniert, und `connected`, solange seine Event-Verbindung
  steht.
- `password` ist das konfigurierte HTTP-Basic-Passwort des Nutzers, falls vorhanden.
- Lies `client`, `data` und `url` jedes Mal aus dem Live-`ServerRef`: Ein neu gestarteter Server erhält einen neuen Client unter
  derselben ID.
- `ctx.servers.list()` gibt die IDs der Server zurück, die die App auflistet.

### Dialoge

`ctx.dialogs.open(render, { replace? })` öffnet einen Dialog über den offenen und gibt ein Handle zurück, dessen `close()` ihn schließt.
Der Dialog schließt auch, wenn sein besitzender Scope endet.

```tsx
const handle = ctx.dialogs.open((dialog) => <ConfirmDialog onDone={dialog.close} />)
```

- `replace: true` schließt zuerst jeden offenen Dialog, einschließlich der Dialoge des Hosts und anderer Plugins.
- `ctx.dialogs.active()` ist `true`, solange ein Dialog offen ist.
- Rendere den Inhalt in `ctx.ui.Dialog` für den Dialograhmen der App; siehe [App-Komponenten](#app-components).

### Den Nutzer fragen

`confirm`, `alert`, `prompt` und `select` nutzen die Dialoge der App. Dein Plugin braucht daher keine eigene
Dialog-UI. Jede Methode gibt ein Promise für die Antwort zurück.

```ts
const ok = await ctx.dialogs.confirm({ title: ctx.t("end.title"), confirm: ctx.t("end"), danger: true })
```

- Das Promise von `confirm` wird nur mit `true` erfüllt, wenn der Nutzer bestätigt. `danger` hebt die
  Schaltfläche für die Bestätigung als destruktive Aktion hervor und setzt den Fokus zunächst auf Cancel.
- Jeder Dialog öffnet wie `open` und schließt mit dem Owner, der gefragt hat, sonst mit deinem Plugin.
- Bei Abbruch, Escape, einem Klick außerhalb, dem Öffnen eines ersetzenden Dialogs oder wenn der Owner endet,
  liefert `confirm` den Wert `false`, `prompt` und `select` liefern `undefined`.

`alert` teilt dem Nutzer etwas mit, das er bestätigen muss, mit einer Schaltfläche. Es löst auf, sobald der Dialog schließt, wie auch immer er
schließt:

```ts
await ctx.dialogs.alert({ title: ctx.t("export.done"), description: path })
```

`prompt` fragt nach einer Zeile Text. Sein anfänglicher `value` ist ausgewählt, Tippen ersetzt ihn also. Es löst nie einen leeren
String auf: Absenden bewirkt nichts, solange das Feld leer ist. `secret: true` verbirgt, was der Nutzer tippt, für ein Passwort oder
Token:

```ts
const token = await ctx.dialogs.prompt({ title: ctx.t("token.title"), placeholder: "ghp_…", secret: true })
```

`select` zeigt wie die Befehlspalette eine durchsuchbare Liste. Das Promise wird mit dem `value` der
ausgewählten Option erfüllt:

```ts
const url = await ctx.dialogs.select({
  title: ctx.t("links.title"),
  options: links.map((link) => ({ title: link.title, description: link.url, value: link.url, group: link.host })),
})

if (url) ctx.system.openExternal(url)
```

- Die Suche gleicht `title` und `description` jeder Option ab.
- Optionen mit derselben `group` werden zusammen unter dieser Überschrift aufgelistet.
- `current` ist der Wert der Option, die zuerst hervorgehoben wird.

### App-Komponenten

Ein Plugin-Bundle kann `@opencode/ui` nicht importieren, daher gibt `ctx.ui` ihm die eigenen Komponenten der App. Sie rendern im
Theme, in den Schriften und in der Sprache des Nutzers, die UI deines Plugins sieht also aus und verhält sich wie die der App.

```tsx
import { Show } from "solid-js"
import { createLatest, Panel } from "@opencode/plugin/gui"

const ui = ctx.ui
const summary = createLatest(
  () => ctx.sessions.current()?.directory,
  (directory, signal) => fetchSummary(directory, signal),
)

ctx.add(Panel, {
  id: "summary",
  region: "side",
  list: () => [summaryTab],
  render: () => (
    <div>
      <ui.Tooltip value={ctx.t("copy")}>
        <ui.IconButton icon="copy" label={ctx.t("copy")} onClick={() => void ctx.system.copy(summary.latest ?? "")} />
      </ui.Tooltip>
      <Show when={summary.latest} fallback={<ui.Loader size="large" />}>
        {(text) => <ui.Markdown text={text()} />}
      </Show>
    </div>
  ),
})
```

- `Icon`, `Button` und `IconButton` nehmen jeden `IconName` wie jedes `icon`-Feld des SDK: eines der Icons der App oder eines
  [deiner eigenen](#icons) aus `ctx.icons`. Das `label` eines `IconButton` ist sein zugänglicher Name; wickle ihn in
  `Tooltip`, um es beim Hover zu zeigen.
- `busy` an einer Schaltfläche ersetzt ihr Icon durch den Ladeindikator und deaktiviert sie, bis es wieder `false` ist.
- Verwende `Loader` für Ladezustände, die nichts mit der Arbeit der AI zu tun haben, etwa beim Laden eines
  Bereichs oder bei einer laufenden Suche oder einem Verbindungsaufbau.
- `Menu` öffnet eine Liste von `items`: Aktionen, `{ type: "separator" }` und `{ type: "group", label, items }`.
- `Switch` und `TextInput` halten keinen Zustand: Übergib den Wert aus `onChange` oder `onInput` zurück an `checked` oder `value`.
- `Keybind` zeigt Tasten als Chips, etwa `ctx.keybinds.keybind(command)`.
- `Markdown` rendert wie die Timeline eine Nachricht rendert, und `Code` zeigt einen hervorgehobenen, schreibgeschützten Codeblock. Beide füllen sich
  kurz nach dem Einbinden.

`Dialog` ist der Dialograhmen der App: ein Titel, Inhalt und Schaltflächen. Rendere ihn aus `ctx.dialogs.open`; anderswo
rendert er nichts Nützliches.

```tsx
const ui = ctx.ui

ctx.dialogs.open((dialog) => (
  <ui.Dialog
    title={ctx.t("rename.title")}
    footer={
      <ui.Button variant="contrast" onClick={dialog.close}>
        {ctx.t("done")}
      </ui.Button>
    }
  >
    <ui.TextInput label={ctx.t("rename.label")} value={name()} onInput={setName} onSubmit={dialog.close} autofocus />
  </ui.Dialog>
))
```

- `size` ist standardmäßig `"fit"`: 480px breit und so hoch wie sein Inhalt. `"normal"`, `"large"` und `"x-large"` sind feste
  Größen.
- Escape und ein Klick außerhalb schließen den Dialog. `closable: false` verbirgt die Schließen-Schaltfläche der Kopfzeile.

#### Menüzeilen

`MenuItem`, `MenuSub`, `MenuGroup` und `MenuSeparator` sind Zeilen für Menüs, die der Host rendert, etwa im
Slot `session.location.menu`. Sie lassen sich per Tastatur bedienen, zeigen die dezenten Icons und
Tastenkürzel-Chips des Hosts und schließen das Menü bei Auswahl.

```tsx
import { For } from "solid-js"

const ui = ctx.ui

ctx.add(Slot, {
  at: "session.location.menu",
  render: (input) => (
    <>
      <ui.MenuItem
        label={ctx.t("usage")}
        icon="status"
        keys={["Ctrl", "U"]}
        onSelect={() => openUsage(input.session)}
      />
      <ui.MenuSub label={ctx.t("openIn")} icon="outline-share">
        <For each={apps()}>{(app) => <ui.MenuItem label={app.name} onSelect={() => launch(app, input.session)} />}</For>
      </ui.MenuSub>
    </>
  ),
})
```

- `MenuItem` nimmt dieselben Felder wie ein Eintrag von `Menu`s `items`.
- `MenuSub` öffnet seine Kinder in einem Untermenü neben der Zeile. `onOpenChange` sagt dir, wann, damit du seine Zeilen
  nur laden kannst, solange es offen ist.
- `MenuGroup` stellt Zeilen unter eine Überschrift, und `MenuSeparator` zieht eine Linie zwischen Zeilen.
- `MenuItem`, `MenuSub` und `MenuGroup` werfen außerhalb eines Menüs: Der Host zeichnet den Fehler auf und rendert nichts von diesem
  Beitrag.

#### Selects

`Select` wählt eine aus einer Liste von Möglichkeiten, wie die Einstellungszeilen der App eine Sprache wählen. Sein Wert ist ein String; der Typ von
`options` schränkt ihn ein.

```tsx
const [period, setPeriod] = createSignal<"day" | "month">("day")

<ui.Select
  label={ctx.t("period")}
  options={[
    { value: "day", label: ctx.t("period.day") },
    { value: "month", label: ctx.t("period.month") },
  ]}
  value={period()}
  onChange={setPeriod}
/>
```

- `label` ist der zugängliche Name des Selects; das `label` der gewählten Option ist das, was er zeigt.
- Ein `value`, das keine Option hat, zeigt `placeholder`. Die gewählte Wahl erneut zu wählen, ruft `onChange` nicht auf.

```tsx
<ui.SettingsLayout title={ctx.t("title")} description={ctx.t("description")} actions={<HelpButton />}>
```

### Toasts

`ctx.toast.show` zeigt eine kurze Nachricht in der Fensterecke und gibt ein Handle zurück, dessen `dismiss()` sie schließt.

```ts
ctx.toast.show({ variant: "success", title: ctx.t("invite.copied") })
```

- `variant` ist `"default"`, `"success"`, `"error"` oder `"loading"`. Ein `success`-Toast zeigt ein Häkchen-Icon, sofern du kein
  `icon` setzt.
- `duration` ist, wie lange der Toast angezeigt wird, in Millisekunden. Standard sind 5 Sekunden.
- `persistent: true` hält den Toast, bis der Nutzer oder `dismiss()` ihn schließt, und ignoriert `duration`.
- Ein Toast, der einem noch sichtbaren entspricht, ersetzt ihn, statt eine Kopie zu stapeln.
- Die Toasts deines Plugins schließen, wenn es stoppt, keine Schaltfläche überlebt also den Code, den sie ausführt. Ein Toast schließt nicht mit der
  Komponente oder dem `createKeyed`-Lauf, der ihn zeigte.

Zeige einen `loading`-Toast, während Arbeit läuft, und schließe ihn, wenn die Arbeit endet:

```ts
const saving = ctx.toast.show({ variant: "loading", title: ctx.t("saving"), persistent: true })
await save()
saving.dismiss()
```

`actions` fügt Schaltflächen hinzu. Ein Klick führt die Aktion aus und schließt den Toast:

```ts
ctx.toast.show({
  variant: "error",
  title: ctx.t("sync.failed"),
  actions: [{ label: ctx.t("retry"), run: () => void sync() }],
})
```

### Benachrichtigungen

`ctx.attention.notify` holt die Aufmerksamkeit des Nutzers, während er woanders hinsieht: eine Systembenachrichtigung und ein Ton, mit
denselben Regeln wie die eigenen Benachrichtigungen der App.

```ts
const session = ctx.sessions.current()

if (session) {
  void ctx.attention.notify({
    title: ctx.t("tests.done"),
    message: ctx.t("tests.summary", { failed: 0 }),
    session: { server: session.server.id, id: session.id },
    id: run.id,
  })
}
```

- Die Systembenachrichtigung erscheint nur, solange kein App-Fenster den Fokus hat. Der Ton spielt in beiden Fällen.
- Beide folgen **Settings > Notifications**. `variant: "default"` folgt den **Agent**-Zeilen und `variant: "error"` den
  **Errors**-Zeilen. Desktop-Benachrichtigungen für beide sind standardmäßig aus; ihre Töne sind an.
- `sound: false` spielt nie einen Ton.
- Ein Klick auf die Benachrichtigung holt die App nach vorn und öffnet `session`, wenn du eine angibst.
- Jedes App-Fenster führt seine eigene Kopie deines Plugins aus. Übergib eine `id` des Events, etwa die ID eines Laufs, damit nur das erste
  Fenster, das sie sendet, benachrichtigt und den Ton spielt. Ohne `id` benachrichtigt jeder Aufruf.
- Bevor die App-Oberfläche eingebunden ist, wartet `notify` auf sie.

Das Promise von `notify` wird nie abgelehnt. Das Ergebnis zeigt, was passiert ist: `notification` ist `true`,
wenn die App das System um die Anzeige der Benachrichtigung gebeten hat; `sound` ist `true`, wenn die
Wiedergabe des Tons begonnen hat.

```ts
const result = await ctx.attention.notify({ title: ctx.t("deploy.failed"), variant: "error" })

if (!result.notification) ctx.toast.show({ variant: "error", title: ctx.t("deploy.failed") })
```

- `notification` ist `false`, wenn der Nutzer es ausgeschaltet hat, ein App-Fenster den Fokus hat oder ein anderes Fenster bereits
  `id` gesendet hat. Das System kann eine Benachrichtigung, um deren Anzeige die App gebeten hat, trotzdem verbergen, zum Beispiel wenn der Nutzer die
  Berechtigung eines Browsers verweigert hat.

### Tabs

`ctx.tabs` liest und ändert die Tab-Leiste der Shell: die Sessions und Entwürfe, die als Tabs offen sind. Dies verschiebt den Tab einer Session
nach vorn, wenn ihr Lauf endet:

```ts
import { onCleanup } from "solid-js"
import { createKeyed } from "@opencode/plugin/gui"

createKeyed(
  () => ctx.servers.get("sidecar")?.data,
  (data) =>
    onCleanup(
      data.on("session.execution.succeeded", (event) => {
        const tab = ctx.tabs.list().find((item) => item.session?.id === event.data.sessionID)

        if (tab) ctx.tabs.move(tab.key, 0)
      }),
    ),
)
```

- `list()` gibt die offenen Tabs in Leistenreihenfolge zurück. Es ist reaktiv. Die `session` eines Tabs ist `undefined` für einen Entwurf, und
  `active` ist `true` für den Tab auf dem Bildschirm.
- `open({ server, id }, { focus? })` öffnet eine Session am Ende der Tab-Leiste. Sie bleibt im Hintergrund,
  sofern `focus` nicht `true` ist. Eine bereits offene Session behält ihren Tab. Das gilt auch für einen
  Subagenten, der im Tab der übergeordneten Session angezeigt wird.
- `focus(key)` zeigt einen Tab, `move(key, index)` verschiebt ihn, und `close(key)` schließt ihn wie der Nutzer.
- Ein Schlüssel, den kein offener Tab hat, bewirkt nichts. Schreibvorgänge vor dem Einbinden der App-Oberfläche warten auf sie.

### Befehle ausführen

```ts
if (!ctx.commands.run("terminal.toggle")) ctx.toast.show({ title: ctx.t("terminal.unavailable") })
```

### System und Umgebung

`ctx.system` funktioniert auf jeder Plattform. `ctx.desktop` ergänzt Funktionen für die Desktop-App und ist im
Web `undefined`.

```ts
const show = async (path: string) => {
  if (ctx.desktop && (await ctx.desktop.reveal(path))) return
  await ctx.system.copy(path)
}
```

- `system.save` zeigt auf dem Desktop einen Speichern-Dialog und lädt im Web herunter. Es gibt `false` zurück, wenn der Nutzer den
  Dialog abbricht.
- `system.openExternal` öffnet eine URL im Systembrowser. Für Links innerhalb der App nutze `ctx.links.open`, das einen
  `Link` an seinen [Link-Handler](#link-handlers) routet.
- `desktop.launch(path, app?)` öffnet einen Pfad mit einer App oder mit der Standard-App. `desktop.reveal(path)` zeigt ihn im
  Dateimanager.
- `ctx.embeds` rendert eine Webansicht des Hauptprozesses in einem Fenster; siehe
  [Eingebettete Webansichten](#embedded-web-views).
- `ctx.locale` liest die Oberflächensprache und ihre Schreibrichtung. `ctx.appearance.font("mono")` ist die CSS-Schriftfamilie
  der Terminal-Schrift des Nutzers.
- `ctx.router` liest den aktuellen Routenpfad und ob ein Routenübergang läuft.
- `ctx.workspaces.on("remove", handler)` läuft, wenn der Nutzer ein Workspace-Verzeichnis von einem Server entfernt, damit du
  daran gebundene Stores bereinigen kannst.

`desktop.pick(options)` fragt den Nutzer mit dem Öffnen-Dialog des Systems nach Dateien oder Ordnern und löst ihre absoluten
Pfade auf:

```ts
const [folder] = (await ctx.desktop?.pick({ directory: true, title: ctx.t("pick.folder") })) ?? []

if (folder) await ctx.client.rpc(Acme).index({ directory: folder })
```

- `directory: true` wählt Ordner statt Dateien, und `multiple: true` lässt den Nutzer mehr als einen wählen.
- `extensions` beschränkt die angebotenen Dateien ohne Punkt, etwa `["json"]`. Ordner ignorieren es.
- `title` ist der Titel des Dialogs. Nicht jedes System zeigt ihn.
- Die Pfade sind leer, wenn der Nutzer abbricht. `pick` lehnt ab, wenn der Dialog nicht öffnen kann.
- `pick` gibt es nur auf dem Desktop: Ein Browser sagt der Seite nie, wo eine gewählte Datei liegt.

```ts
const background = () => (ctx.appearance.mode() === "dark" ? "#000" : "#fff")
```

## Gespeicherter Zustand

Desktop-Fenster laden gespeicherten Zustand über IPC, während das Web `localStorage` sofort liest. Deklariere Stores in
`Plugin.define({ stores })`, damit der Host sie für dich lädt.

- **`Store.global`** behält einen Wert für die App. Er lädt, bevor `setup` läuft, `ctx.stores.name.value` ist also nie
  `undefined`.
- **`Store.session`** behält einen Wert pro Session. Er lädt, wenn die Session eingebunden wird; `ctx.stores.name(session).value`
  ist bis dahin `undefined`.

Deklarierte Stores sind für Fenster. `main` öffnet seinen Zustand mit `ctx.storage.store`, das synchron liest; siehe
[Hauptkontext](#main-context).

Ändere einen Wert an Ort und Stelle mit `update(draft => …)`, das nichts zurückgeben darf, oder ersetze ihn mit `set(next)`:

```ts
const enabled = ctx.stores.prefs.value.enabled

ctx.stores.prefs.update((draft) => {
  draft.enabled = !draft.enabled
})
```

- `ready()` ist `true`, sobald der Wert geladen ist. Schreibvorgänge davor warten und werden in Aufrufreihenfolge angewendet.
- `from` nennt andere gespeicherte Schlüssel, aus denen der Wert einmal importiert wird, solange der Store keinen hält, etwa den Schlüssel eines
  umbenannten Stores: `"plugin.acme.settings"`. Übergib eine Liste, um mehrere Schlüssel zu probieren, neueste zuerst. Der andere Schlüssel behält seine
  Kopie, bis der Store entfernt wird.

```ts
stores: {
  prefs: Store.global(Prefs, { enabled: true }, ["plugin.acme.settings.v2", "plugin.acme.settings"]),
}
```

#### Referenz

```ts
const Store: {
  global(schema: Schema, initial: T, from?: string | string[]): StoreDeclaration
  session(schema: Schema, initial: T, from?: string | string[]): StoreDeclaration
}

interface Persisted<T, V = T | undefined> {
  value: V
  ready(): boolean
  update(mutate: (draft: T) => undefined): void
  set(next: T): void
}
```

### Laufzeit-Stores

`ctx.storage.store(key, options)` öffnet einen Store für einen Schlüssel, der erst zur Laufzeit bekannt ist. `scope` behält einen Wert pro Server,
Verzeichnis oder Session.

```tsx
import { Schema } from "effect"
import { usePlugin, type MountedSession } from "@opencode/plugin/gui"
import type { definition } from "./definition"

function DraftView(props: { readonly session: MountedSession }) {
  const ctx = usePlugin<typeof definition>()

  const draft = ctx.storage.store("draft", {
    schema: Schema.Struct({ text: Schema.String }),
    initial: { text: "" },
    scope: { server: props.session.server.id, directory: props.session.directory },
  })

  return <p>{draft.value?.text}</p>
}
```

- `scope: "global"`, der Standard, behält einen Wert für die App.
- `scope: { server, directory? }` behält einen Wert pro Server oder pro Workspace-Verzeichnis darauf.
- `scope: { session }` behält einen Wert pro Session, erneut geöffnet, wenn die Session in ein neues Verzeichnis wechselt.
- Der `value` eines Laufzeit-Stores ist `undefined`, bis er lädt.
- `ctx.storage.memory(key, { initial })` behält fensterlokalen Zustand, der Plugin-Neuladen überlebt, aber kein Fenster-Neuladen.
- `ctx.storage.remove(key, { scope, from })` löscht den Wert, der Schlüssel liest sich also wieder als `initial`.

#### Referenz

```ts
interface Storage {
  store(key: string, options: StoreOptions): Persisted<T>
  memory(key: string, options: { initial: T }): [Store<T>, (mutation: (draft: T) => void) => void]
  remove(key: string, options?: { scope?: StorageScope; from?: string | string[] }): void
}

interface StoreOptions {
  schema: Schema
  initial: T
  scope?: StorageScope
  from?: string | string[]
}
```

## Reaktive Primitive

Nutze diese Helfer statt direkter Aufrufe von `createEffect`, `createRenderEffect` oder `createComputed`. Sie
berücksichtigen die Lebensdauer des Plugins und Neustarts seiner Abhängigkeiten. Bei selbst geschriebenen
Effects wird das leicht übersehen.

### createKeyed

`createKeyed(source, fn, { otherwise?, equals? })` führt `fn` in einem frischen Owner für jeden Schlüssel aus: jede aktive Generation eines
`ctx.use`-Accessors oder jeden Wert eines einfachen Accessors. Alles, was in `fn` registriert wird, endet mit diesem Lauf.

```tsx
import { onCleanup } from "solid-js"
import { createKeyed, usePlugin, type SessionScreen } from "@opencode/plugin/gui"
import { Changes } from "@opencode/plugin/gui/review"

function ChangedFiles(props: { readonly screen: SessionScreen }) {
  const ctx = usePlugin()

  // Each active generation of Changes keeps this view's changes loaded; the watch ends with it.
  createKeyed(ctx.use(Changes), (changes) => onCleanup(changes.watch(props.screen, "files")))

  return <FileMarkers screen={props.screen} />
}
```

- `otherwise` läuft, solange die Quelle keinen Schlüssel hat: ein `Live`-Accessor, der nicht aktiv ist, oder ein einfacher Accessor, dessen Wert
  `undefined`, `null` oder `false` ist.
- `equals` entscheidet, ob der neue Wert eines einfachen Accessors derselbe Schlüssel ist, damit `fn` nicht erneut läuft. Nutze es, wenn die
  Quelle jedes Mal ein neues Objekt baut. Ein `Live`-Accessor schlüsselt immer nach Generation.

#### Referenz

```ts
function createKeyed<T>(
  source: () => Live<T> | T,
  fn: (value: T) => void,
  options?: { otherwise?(): void; equals?(previous: T, next: T): boolean },
): void
```

### createLatest

`createLatest(source, (value, signal) => promise)` ruft bei jeder Änderung von `source` neue Daten ab, bricht
überholte Anfragen ab und löst nie Suspense aus.

```ts
const summary = createLatest(
  () => ctx.sessions.current()?.directory,
  (directory, signal) => fetchSummary(directory, signal),
)
const text = () => summary.latest ?? ""
```

- `latest` ist das letzte Ergebnis, behalten, während eine neuere Anfrage läuft. Es ist `undefined` vor dem ersten.
- `loading` ist `true`, während eine Anfrage für den aktuellen Wert läuft.

### Änderungen prüfen

`@opencode/plugin/gui/review` exportiert `Changes`, die Ansicht der App auf die Änderungen einer Session, und `ChangeKind`
(`"add"`, `"del"` oder `"mix"`).

```ts
import { Changes } from "@opencode/plugin/gui/review"

const changes = ctx.use(Changes)

const count = () => {
  const live = changes()
  const session = ctx.sessions.current()

  return live.status === "active" && session ? live.value.diffs(session).length : 0
}
```

- `diffs(session)` sind die Diffs des aktuellen Review-Modus, und `ready(session)` ist `true`, sobald sie geladen sind. Beide sind
  reaktiv. Nur die geroutete Session hat Änderungen; andere Sessions lesen sich als leer.
- `kinds(session)` ordnet jeder geänderten Datei und jedem Ordner seinen `ChangeKind` zu.
- `active(session)` ist die Datei, die das Review-Panel zeigt.
- `details(session)` sind die nicht committeten Änderungen des Session-Verzeichnisses, unabhängig vom Review-Modus.
- `focus(session, path)` zeigt eine Datei im Review-Panel, und `open(session)` zeigt alle Änderungen.
- `watch(screen, source)` hält die Änderungen geladen, solange die Ansicht sie zeigt, auch wenn die Ansicht
  zwischen Sessions wechselt. Übergib den zugehörigen Bildschirm aus dem Eingabeobjekt des Panels oder Slots.
  Die zurückgegebene Funktion beendet die Überwachung; siehe [createKeyed](#createkeyed).
- Ein `tree`-Watch ist eine dauerhafte Änderungsliste: Das Öffnen des Seitenbereichs aktualisiert sie. Ein `details`-Watch lädt
  `details(session)`.

## Der Hauptprozess

In OpenCode Desktop läuft das `main`-Setup eines Plugins einmal im Electron-Hauptprozess als appweites Singleton. Es hat
vollen Zugriff auf Node.js-Built-ins, `electron` und die Haupt-Host-APIs. Übergib es in der
[`./gui-experimental`-Datei](#define-the-gui-plugin) des Plugins an `Plugin.define`, neben dem Fenster-`setup` oder allein.

```tsx title="src/gui.tsx"
import { Schema } from "effect"
import { powerSaveBlocker } from "electron"
import { Plugin } from "@opencode/plugin/gui"
import { KeepAwake } from "./gui/contract"

export default Plugin.define({
  main(ctx) {
    const stored = ctx.storage.store("keepScreenActive", { schema: Schema.Boolean, initial: false })
    let blockerId: number | undefined

    const release = () => {
      if (blockerId === undefined) return
      powerSaveBlocker.stop(blockerId)
      blockerId = undefined
    }

    const setActive = (enabled: boolean) => {
      if (enabled && blockerId === undefined) blockerId = powerSaveBlocker.start("prevent-display-sleep")
      if (!enabled) release()
      stored.set(enabled)
    }

    if (stored.value) setActive(true)

    ctx.provide(KeepAwake, {
      screenActive: () => blockerId !== undefined && powerSaveBlocker.isStarted(blockerId),
      setScreenActive: (enabled) => setActive(enabled),
    })

    return release
  },
})
```

In einem Fenster ist `electron` ein inaktiver Platzhalter, der Import in der gemeinsamen `./gui-experimental`-Datei ist also sicher. Siehe
[Eine Datei, zwei Prozesse](#one-file-two-processes).

## Hauptkontext

`main` erhält einen `MainContext`. Anders als das Fenster-`setup` darf `main` `async` sein. Es kann eine
Cleanup-Funktion direkt oder als Ergebnis eines Promise zurückgeben.

```ts
main(ctx) {
  ctx.log.write("info", "acme started", { version: ctx.app.version })
}
```

- `ctx.options`, `ctx.client` und `ctx.app` sind der [gemeinsame Kontext](#shared-context). In `main` ist
  `ctx.app.platform` immer `"desktop"`.
- `ctx.storage.store(key, { schema, initial })` öffnet einen Store synchron im Namespace des Plugins. Sein `value` ist
  immer definiert, und jedes `set` oder `update` erreicht die Datenbank, bevor es zurückkehrt. `ctx.storage.remove(key)` löscht
  den Wert.
- `ctx.signal` wird abgebrochen, wenn das Plugin deaktiviert, neu geladen oder entfernt wird oder die App beendet wird. `ctx.onCleanup(fn)` führt `fn`
  dann aus; siehe [Lebensdauern und Bereinigung](#lifetimes-and-cleanup).
- `ctx.provide` implementiert ein `Ipc` unter der ID des Plugins; siehe [Ein Ipc definieren und bereitstellen](#define-and-provide-an-ipc).
- `ctx.add` trägt zu Hauptprozess-Registries wie [`MenubarItem`](#native-app-menu) bei.
- `ctx.windows` listet die Fenster der App auf und meldet, wenn eines öffnet oder schließt.
- `ctx.embeds` platziert eine `WebContentsView` im Layout eines Fensters; siehe [Eingebettete Webansichten](#embedded-web-views).
- `ctx.serverEndpoints.get(id)` gibt URL und Zugangsdaten eines Servers zurück. Der eigene Server der Desktop-App ist `"sidecar"`.
- `ctx.cli` beschreibt die OpenCode CLI, die die Desktop-App ausführt.
- `ctx.log.write` schreibt in die Desktop-Logdatei.

#### Referenz

`@opencode/plugin/gui/main` exportiert `MainStorage` und `MainEmbeds` unten als `Storage` und `Embeds`.


## Ein Ipc definieren und bereitstellen

Eine `Ipc`-Spezifikation kann `state` pro Fenster, aufrufbare `methods` und gepushte `events` deklarieren. Effect-`Schema` validiert und
kodiert jeden Wert, der die Brücke überquert.

```ts title="src/gui/contract.ts"
import { Schema } from "effect"
import { Ipc } from "@opencode/plugin/gui"

export const Counter = Ipc.define({
  id: "acme.counter",
  state: Schema.Struct({ count: Schema.Number }),
  methods: {
    increment: {
      input: Schema.Number,
      output: Schema.Number,
    },
    reset: {},
  },
  events: {
    overflow: Schema.Struct({ limit: Schema.Number }),
  },
})
```

- Die ID ist die ID deines Plugins oder beginnt damit, als `acme.counter`. `ctx.provide` in `main` und `ctx.main` in einem Fenster
  werfen bei jeder anderen ID.
- Lass `input` für eine Methode ohne Argument weg und `output` für eine Methode, die nichts zurückgibt.

#### Referenz

```ts
interface IpcSpec {
  id: string
  state?: Schema
  methods: Record<string, { input?: Schema; output?: Schema }>
  events?: Record<string, Schema>
}
```

### Den Anbieter in main implementieren

Jede Methode erhält die dekodierte Eingabe und einen `Caller` (`{ window, signal }`). Rufe `provider.changed(window?)` auf, wenn sich
`state` ändert, um den neuen Snapshot an abonnierte Fenster zu pushen, oder `provider.emit(name, payload, window?)`, um ein
Event zu senden.

```ts title="src/gui/main.ts"
import type { Plugin } from "@opencode/plugin/gui"
import { Counter } from "./contract"

export const main: Plugin.MainSetup = (ctx) => {
  const counts = new Map<number, number>()

  const provider = ctx.provide(Counter, {
    state: (window: number) => ({ count: counts.get(window) ?? 0 }),
    increment: (step, caller) => {
      const next = (counts.get(caller.window) ?? 0) + step
      counts.set(caller.window, next)
      provider.changed(caller.window)

      if (next > 100) provider.emit("overflow", { limit: 100 }, caller.window)

      return next
    },
    reset: (_input, caller) => {
      counts.set(caller.window, 0)
      provider.changed(caller.window)
    },
  })
}
```

- Eine Spezifikation mit `state` braucht auch `state(window)` in der Implementierung. Main liest es, wenn ein Fenster abonniert, und bei
  jedem `changed`.
- Eine Methode, die wirft, lehnt den Aufruf des Fensters ab.
- `changed` und `emit` erreichen jedes Fenster, wenn du `window` weglässt.
- `dispose()` zieht das `Ipc` vorzeitig zurück. Fenster sehen es als `pending`, und `ctx.main`-Aufrufe warten, bis das Plugin es
  erneut bereitstellt oder stoppt. Der Host zieht es auch zurück, wenn das Plugin stoppt.

#### Referenz

```ts
type IpcImpl<S extends IpcSpec> = {
  [Name in keyof S["methods"]]: (input: Input<Name>, caller: Caller) => Output<Name> | Promise<Output<Name>>
} & { state(window: number): State }

interface Caller {
  window: number
  signal: AbortSignal
}

interface IpcProvider<S extends IpcSpec> {
  changed(window?: number): void
  emit(name: keyof S["events"], data: EventData, window?: number): void
  dispose(): void
}
```

### Das Ipc in einem Fenster nutzen

In einem Fenster gibt `ctx.main(Counter)` den Client des `Ipc` zurück, das dein `main` bereitstellt. Eine Methode ohne `input`-
Schema nimmt nur optionale `{ signal }`-Aufrufoptionen. Übergib nicht `undefined` als erstes Argument.

```tsx title="src/gui/window.tsx"
import { Command, type Plugin } from "@opencode/plugin/gui"
import { Counter } from "./contract"
import type { definition } from "./definition"

export const setup: Plugin.Setup<typeof definition> = (ctx) => {
  const counter = ctx.main(Counter)

  // Follows main across restarts; removed when the plugin stops.
  counter.on("overflow", (data) => console.log(`Counter exceeded ${data.limit}`))

  ctx.add(Command, () => ({
    id: "increment",
    title: ctx.t("command.increment"),
    enabled: ctx.app.platform === "desktop",
    run: async () => {
      await counter.increment(1, { signal: ctx.signal })
      await counter.reset({ signal: ctx.signal })
    },
  }))
}
```

- Aufrufe warten, solange `main` startet. Das Promise wird abgelehnt, wenn `main` nicht antworten kann: im
  Web, bei deaktiviertem oder fehlgeschlagenem `main` des Plugins oder wenn die Methode einen Fehler auslöst.
  Fange den Fehler dort ab, wo der Nutzer eine Rückmeldung braucht.
- `state()` und `on()` folgen `main` über Neustarts hinweg. Ein Listener endet mit dem aktuellen Owner, sonst mit dem Plugin.
- `ctx.main` gibt für jeden Aufruf mit dem Token denselben Client zurück.

Lies den `state` dieses Fensters mit `client.state()`. Er ist `undefined`, bis der erste Snapshot eintrifft, und aktualisiert sich jedes
Mal, wenn `main` `changed` aufruft.

```tsx
const count = () => ctx.main(Counter).state()?.count ?? 0
```

#### Referenz

```ts
type IpcClient<S extends IpcSpec> = {
  [Name in keyof S["methods"]]: S["methods"][Name] extends { input: Schema }
    ? (input: Input<Name>, options?: { signal?: AbortSignal }) => Promise<Output<Name>>
    : (options?: { signal?: AbortSignal }) => Promise<Output<Name>>
} & {
  state(): State | undefined
  on(name: keyof S["events"], listener: (data: EventData) => void): Cleanup
}
```

Definiere das Plugin mit beiden Setups in `src/gui.tsx`: `Plugin.define({ ...definition, setup, main })`.

### Andere Plugins

Ein anderes Plugin folgt deinem `Ipc` mit `ctx.use(Counter)`, wie es einem Vertrag folgt. Solange es `active` ist, ist sein Wert
derselbe `IpcClient`.

```ts

  return live.status === "active" ? (live.value.state()?.count ?? 0) : 0

```

- Jedes `Ipc` ist im Web `inactive`, wo kein Hauptprozess läuft.

## Eingebettete Webansichten

Um eine isolierte `WebContentsView` in ein Panel einzubetten, erstelle sie in `main` und rendere im Fenster
den Bereich, in dem sie angezeigt werden soll.

```ts title="src/gui/main.ts"
import { type BrowserWindow, WebContentsView } from "electron"
import type { Plugin } from "@opencode/plugin/gui"

export const main: Plugin.MainSetup = (ctx) => {
  const attach = (window: BrowserWindow) => {
    const view = new WebContentsView()
    const embed = ctx.embeds.create(view, window)
    void view.webContents.loadURL("https://acme.example")
    embed.show(true)
    // Send embed.id to the window over your Ipc.
  }
  ctx.windows.list().forEach(attach)
  ctx.windows.on("open", attach)
}
```

```tsx title="src/gui/pane.tsx"
<ctx.embeds.View id={embedId} visible radius={8} />
```

- `"open"` feuert nur für Fenster, die später öffnen, hänge dich also zuerst an `ctx.windows.list()`.
- Ein Fenster übergibt die `id` des Embeds an `ctx.embeds.View` und `ctx.embeds.capture`.
- Mit `show(visible)` steuert die Seite ihren Teil der Sichtbarkeit. Die Ansicht erscheint nur, wenn das
  Fenster Platz für sie vorsieht und `show(true)` gilt.
- `on("visible", handler)` läuft, wenn die Ansicht auf oder außerhalb des Bildschirms geht, auch wenn das Fenster an ihrer
  Stelle ein Standbild zeichnet.
- `capture()` gibt ein Standbild der Seite zurück oder `undefined`, während sie verborgen ist.
- `dispose()` entfernt die Ansicht aus dem Fenster, schließt aber nicht ihre Seite; rufe `view.webContents.close()` auf, wenn
  du fertig bist. Der Host verwirft das Embed auch, wenn das Plugin verschwindet.
- Im Fenster füllt `View` den vorgesehenen Bereich mit der eingebetteten Ansicht. Der Host hält Abmessungen,
  Zoom, abgerundete Ecken und die Überdeckung durch Dialoge synchron. Er blendet die Ansicht aus, solange das
  Fenster verborgen oder ein Dialog geöffnet ist.
- `frozen` zeichnet ein Standbild anstelle der Live-Ansicht, damit DOM-Inhalt darüber schweben kann. `radius` rundet die unteren
  Ecken, und `background` ist die Farbe, die die Ecken zeigen.
- `page` ist, was das Embed zeigt, etwa seine URL. Während ein Panel wechselt, zeichnet der Host ein Standbild des Embeds an seiner
  Stelle und verwirft ein Standbild, das aufgenommen wurde, als `page` einen anderen Wert hatte.
- Das `capture(id)` des Fensters gibt ein JPEG-Standbild zurück oder `undefined`, während das Embed verborgen ist, und im Web immer.

## Live-Abhängigkeiten und Fehlerbehandlung

`ctx.use(token)` gibt einen Accessor für ein reaktives `Live<T>` zurück: den Zustand des Plugins, das das
Token bereitstellt. Dein Plugin läuft weiter, wenn das bereitstellende Plugin deaktiviert ist. Berücksichtige
daher auch Zustände außer `active`. Lass keine Bedienelemente ohne Funktion und keine Ladeanzeige endlos
weiterlaufen.

```ts
import { Browser } from "@opencode/plugin/gui/browser"

const browser = ctx.use(Browser)

ctx.add(Command, () => {
  const live = browser()
  const session = ctx.sessions.current()

  return {
    id: "preview",
    title: ctx.t("command.preview"),
    enabled: live.status === "active" && !!session,
    run: () => {
      if (live.status === "active" && session) live.value.open(session, "http://localhost:3000")
    },
  }
})
```

- **`pending`:** Der Anbieter ist noch nicht gestartet, etwa während sein Plugin lädt oder neu startet. Zeige einen Ladezustand
  oder verberge optionale Steuerungen.
- **`active`:** Der Anbieter läuft, und `value` ist sein Vertrag oder `Ipc`-Client. `generation` zählt Aktivierungen, ein
  neu startender Anbieter kommt also mit einer neuen zurück.
- **`inactive`, `disabled`:** Der Anbieter ist ausgeschaltet, fehlt oder ist auf dieser Plattform nicht verfügbar, wie jedes
  `Ipc` im Web. Zeige einen Nicht-verfügbar-Zustand oder lass die Steuerung weg.
- **`inactive`, `failed`:** Das Setup des Anbieters hat einen Fehler geworfen. Zeige einen Nicht-verfügbar-Zustand.
- Dein eigenes `main` hat keinen `Live`-Zustand. Aufrufe über [`ctx.main`](#use-the-ipc-in-a-window) warten, während es startet, und
  lehnen ab, wenn es nicht antworten kann.

#### Referenz

```ts
type Live<T> =
  | { status: "pending" }
  | { status: "active"; value: T; generation: number }
  | { status: "inactive"; reason: "disabled" | "failed" }
```

## Lebensdauer und Bereinigung

Alles, was über `ctx` registriert wird (`ctx.add`, `ctx.provide`, `ctx.dialogs.open`, `ctx.embeds.create` und `Ipc`-
Event-Listener), wird zurückgezogen, wenn sein besitzender Scope endet:

- In einer Komponente oder einem `createKeyed`-Callback enden Registrierungen, wenn diese Komponente oder dieser `createKeyed`-Lauf verworfen wird.
- Auf oberster Ebene von `setup` enden Registrierungen, wenn das Plugin deaktiviert, neu geladen oder entfernt wird oder sein Fenster
  schließt.
- In `main` enden Registrierungen, wenn das Plugin deaktiviert, neu geladen oder entfernt wird oder die App beendet wird. Ein Embed endet auch,
  wenn sein Fenster schließt.

Gib für andere Ressourcen wie Timer oder Sockets eine Cleanup-Funktion aus dem Setup zurück. Sie läuft zur selben Zeit.

- **Fenster-`setup`** darf nicht `async` sein, weil es unter einem Solid-Owner läuft. Gib eine Cleanup-Funktion zurück oder nutze
  `onCleanup` oder `ctx.signal`.
- **`main`** darf `async` sein. Gib eine Cleanup-Funktion direkt oder als Ergebnis eines Promise zurück oder
  nutze `ctx.onCleanup(fn)`.

### Fenster-Setup

Fenster-`setup` muss synchron sein. Starte asynchrone Arbeit in `createKeyed` oder `createLatest`.

```tsx title="src/gui.tsx"
import { Command, createKeyed, Plugin } from "@opencode/plugin/gui"
import { Changes } from "@opencode/plugin/gui/review"

export default Plugin.define({
  i18n: { en: { changes: "Show changes" } },
  setup(ctx) {
    // Runs once per active generation of Changes; the command is withdrawn with it.
    createKeyed(ctx.use(Changes), (changes) => {
      ctx.add(Command, () => ({
        id: "changes",
        title: ctx.t("changes"),
        run: () => {
          const session = ctx.sessions.current()

          if (session) changes.open(session)
        },
      }))
    })

    const timer = setInterval(() => console.log("still here"), 60_000)

    return () => clearInterval(timer)
  },
})
```

### Haupt-Setup

`main` darf `async` sein. Gib die Cleanup-Funktion für die von ihm geöffneten Ressourcen direkt oder als
Ergebnis eines Promise zurück oder registriere sie mit `ctx.onCleanup(fn)`.

```ts
async main(ctx) {
  const socket = await connect(ctx.options)

  ctx.onCleanup(() => socket.close())
}
```

- `ctx.onCleanup` führt seine Funktionen aus, wenn das Plugin deaktiviert, neu geladen oder entfernt wird oder die App beendet wird, zuletzt
  registrierte zuerst. Es führt eine Funktion sofort aus, wenn das Plugin bereits weg ist.
- Kehre nach einem `await` zurück, wenn `ctx.signal` abgebrochen wurde, bevor du etwas registrierst oder änderst.
- Eine `async`-Cleanup-Funktion verzögert das Beenden der App, bis sie abgeschlossen ist, höchstens jedoch um
  3 Sekunden.
