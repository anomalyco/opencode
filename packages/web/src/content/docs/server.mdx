The `opencode serve` command runs a headless HTTP server that exposes an OpenAPI endpoint that an opencode client can use.

---

### Usage

```bash
opencode serve [--port <number>] [--hostname <string>]
```

#### Options

| Flag         | Description           | Default     |
| ------------ | --------------------- | ----------- |
| `--port`     | Port to listen on     | `4096`      |
| `--hostname` | Hostname to listen on | `127.0.0.1` |
| `--mdns`     | Enable mDNS discovery | `false`     |

---

### How it works

When you run `opencode` it starts a TUI and a server. Where the TUI is the
client that talks to the server. The server exposes an OpenAPI 3.1 spec
endpoint. This endpoint is also used to generate an [SDK](/docs/sdk).

:::tip
Use the opencode server to interact with opencode programmatically.
:::

This architecture lets opencode support multiple clients and allows you to interact with opencode programmatically.

You can run `opencode serve` to start a standalone server. If you have the
opencode TUI running, `opencode serve` will start a new server.

---

#### Connect to an existing server

When you start the TUI it randomly assigns a port and hostname. You can instead pass in the `--hostname` and `--port` [flags](/docs/cli). Then use this to connect to its server.

The [`/tui`](#tui) endpoint can be used to drive the TUI through the server. For example, you can prefill or run a prompt. This setup is used by the OpenCode [IDE](/docs/ide) plugins.

---

## Spec

The server publishes an OpenAPI 3.1 spec that can be viewed at:

```
http://<hostname>:<port>/doc
```

For example, `http://localhost:4096/doc`. Use the spec to generate clients or inspect request and response types. Or view it in a Swagger explorer.

### Streaming (Experimental)

:::caution
These endpoints require `experimental.durableStreams` to be enabled in your config.
:::

| Method | Path             | Description                                  | Response                                    |
| ------ | ---------------- | -------------------------------------------- | ------------------------------------------- |
| `GET`  | `/stream/events` | Stream session events with catch-up support  | <a href={typesUrl}><code>StreamEvent[]</code></a> or SSE stream |

#### GET /stream/events

Stream events for a session with support for both catch-up and live modes.

**Query Parameters:**

- `sessionId` (required) - Session identifier
- `offset` (optional, default: `-1`) - Starting offset. Use `-1` to start from the beginning, or a ULID offset from a previous response
- `live` (optional) - Set to `"true"` for live SSE streaming with real-time events

**Catch-up Mode** (default):

Returns a JSON array of events from the specified offset onwards.

**Response Headers:**
- `Stream-Next-Offset` - Latest offset for subsequent requests
- `Stream-Up-To-Date` - `"true"` if caught up, `"false"` otherwise

**Live Mode** (`live=true`):

Returns an SSE stream that:
1. Sends all catch-up events from the offset
2. Transitions to real-time event streaming
3. Stays open for new events as they occur

**Example:**

```bash
# Catch-up mode: Get events from the beginning
curl "http://localhost:4096/stream/events?sessionId=abc123&offset=-1"

# Catch-up mode: Resume from specific offset
curl "http://localhost:4096/stream/events?sessionId=abc123&offset=01HQXYZ..."

# Live mode: Catch-up + real-time streaming
curl "http://localhost:4096/stream/events?sessionId=abc123&offset=-1&live=true"
```

**Use Cases:**

- Build resilient clients that can reconnect without losing events
- Resume streaming from last known offset after network interruption
- Sync multiple clients to the same session state

| Method   | Path           | Description                     | Response                                    |
| -------- | -------------- | ------------------------------- | ------------------------------------------- |
| `GET`    | `/servers`     | List all registered servers     | <a href={typesUrl}><code>ServerEntry[]</code></a> |
| `POST`   | `/servers`     | Manually register a server      | `boolean`                                   |
| `DELETE` | `/servers/:id` | Unregister a server by ID       | `boolean`                                   |

#### Server Registry

The server registry enables multi-server discovery for distributed OpenCode deployments.

**Server Entry Schema:**

```json
{
  "id": "unique-server-id",
  "hostname": "192.168.1.100",
  "port": 4096,
  "lastSeen": 1735481234567,
  "metadata": {
    "version": "1.0.0",
    "platform": "darwin"
  }
}
```

**Auto-Registration:**

When `experimental.durableStreams` is enabled, `opencode serve` automatically:
1. Registers itself in the server registry
2. Sends heartbeat updates every 15 seconds
3. Unregisters on clean shutdown

Stale servers (no heartbeat for >30s) are automatically pruned.

**Manual Registration:**

Use `POST /servers` to manually register an external server:

```bash
curl -X POST http://localhost:4096/servers \
  -H "Content-Type: application/json" \
  -d '{
    "id": "remote-server-1",
    "hostname": "192.168.1.200",
    "port": 4096,
    "metadata": { "region": "us-west" }
  }'
```
