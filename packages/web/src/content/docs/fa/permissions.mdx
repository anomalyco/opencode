title: Permissions
description: کنترل اینکه کدام اقدامات برای اجرا نیاز به تأیید دارند.
---

OpenCode از پیکربندی `permission` استفاده می‌کند تا تصمیم بگیرد که آیا یک اقدام خاص باید به طور خودکار اجرا شود، از شما تأیید بخواهد، یا مسدود شود.

از نگارش `v1.1.1`، پیکربندی بولی قدیمی `tools` منسوخ شده و در `permission` ادغام شده است. پیکربندی قدیمی `tools` همچنان برای سازگاری با نسخه‌های قبل پشتیبانی می‌شود.

---

## اقدامات

هر قانون مجوز به یکی از موارد زیر حل می‌شود:

- `"allow"` — اجرا بدون نیاز به تأیید
- `"ask"` — درخواست تأیید
- `"deny"` — مسدود کردن اقدام

---

## حالت خودکار

OpenCode را با `--auto` شروع کنید تا درخواست‌های مجوزی که صراحتاً رد نشده‌اند را به طور خودکار تأیید کند.

```bash
opencode --auto
```

همچنین می‌توانید از حالت خودکار با [`opencode run`](/docs/cli#run) استفاده کنید.

```bash
opencode run --auto "Refactor this module"
```

قوانین صریح `"deny"` همچنان اعمال می‌شوند. حالت خودکار فقط درخواست‌هایی را تغییر می‌دهد که در غیر این صورت درخواست تأیید می‌کردند.

در TUI، پالت دستورات را باز کنید و **Enable auto-approve permissions** یا **Disable auto-approve permissions** را برای تغییر حالت انتخاب کنید. وقتی حالت خودکار فعال است، درخواست یک نشانگر کمرنگ `auto` را در کنار عامل فعلی نمایش می‌دهد.

---

## پیکربندی

می‌توانید مجوزها را به صورت سراسری (با `*`) تنظیم کنید، و ابزارهای خاص را بازنویسی کنید.

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "*": "ask",
    "bash": "allow",
    "edit": "deny"
  }
}
```

همچنین می‌توانید تمام مجوزها را یکجا تنظیم کنید:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": "allow"
}
```

## قوانین دانه‌ای (نحو شیء)

برای اکثر مجوزها، می‌توانید از یک شیء استفاده کنید تا اقدامات مختلفی را بر اساس ورودی ابزار اعمال کنید.

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "bash": {
      "*": "ask",
      "git *": "allow",
      "npm *": "allow",
      "rm *": "deny",
      "grep *": "allow"
    },
    "edit": {
      "*": "deny",
      "packages/web/src/content/docs/*.mdx": "allow"
    }
  }
}
```

قوانین با تطبیق الگو ارزیابی می‌شوند، با اینکه **آخرین قانون مطابق برنده است**. الگوی رایج این است که قانون همه‌کاره `"*"` را ابتدا، و قوانین مشخص‌تر را پس از آن قرار دهید.

### کاراکترهای جایگزین

الگوهای مجوز از تطبیق ساده کاراکتر جایگزین استفاده می‌کنند:

- `*` با صفر یا بیشتر از هر کاراکتر مطابقت دارد
- `?` دقیقاً با یک کاراکتر مطابقت دارد
- تمام کاراکترهای دیگر به طور تحت‌اللفظی مطابقت دارند

### بسط فهرست خانگی

می‌توانید از `~` یا `$HOME` در ابتدای یک الگو برای اشاره به فهرست خانگی خود استفاده کنید. این به ویژه برای قوانین [`external_directory`](#external-directories) مفید است.

- `~/projects/*` -> `/Users/username/projects/*`
- `$HOME/projects/*` -> `/Users/username/projects/*`
- `~` -> `/Users/username`

### فهرست‌های خارجی

از `external_directory` برای مجاز کردن فراخوانی‌های ابزاری استفاده کنید که به مسیرهای خارج از فهرست کاری که OpenCode در آن شروع شده است برخورد می‌کنند. این مورد برای هر ابزاری که یک مسیر را به عنوان ورودی می‌گیرد اعمال می‌شود (به عنوان مثال `read`، `edit`، `glob`، `grep`، و بسیاری از دستورات `bash`).

بسط خانگی (مانند `~/...`) فقط بر نحوه نوشتن یک الگو تأثیر می‌گذارد. این کار مسیر خارجی را بخشی از فضای کاری فعلی نمی‌کند، بنابراین مسیرهای خارج از فهرست کاری باید همچنان از طریق `external_directory` مجاز شوند.

به عنوان مثال، این دسترسی به همه موارد زیر `~/projects/personal/` را مجاز می‌کند:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "external_directory": {
      "~/projects/personal/**": "allow"
    }
  }
}
```

هر فهرستی که در اینجا مجاز شود، همان پیش‌فرض‌های فضای کاری فعلی را به ارث می‌برد. از آنجا که [`read` به طور پیش‌فرض `allow` است](#defaults)، خواندن‌ها نیز برای موارد زیر `external_directory` مجاز هستند مگر اینکه بازنویسی شوند. وقتی ابزاری باید در این مسیرها محدود شود، مانند مسدود کردن ویرایش‌ها در حالی که خواندن‌ها باقی می‌مانند، قوانین صریح اضافه کنید:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "external_directory": {
      "~/projects/personal/**": "allow"
    },
    "edit": {
      "~/projects/personal/**": "deny"
    }
  }
}
```

فهرست را روی مسیرهای مورد اعتماد متمرکز نگه دارید، و در صورت نیاز برای ابزارهای دیگر (به عنوان مثال `bash`) قوانین allow یا deny اضافی لایه‌بندی کنید.

## مجوزهای موجود

مجوزهای OpenCode با نام ابزار کلید می‌شوند، به علاوه چند محافظ ایمنی:

- `read` — خواندن یک پرونده (با مسیر پرونده مطابقت دارد)
- `edit` — تمام تغییرات پرونده (شامل `edit`، `write`، `patch`)
- `glob` — گلوبینگ پرونده (با الگوی glob مطابقت دارد)
- `grep` — جستجوی محتوا (با الگوی regex مطابقت دارد)
- `bash` — اجرای دستورات shell (با دستورات تجزیل‌شده مانند `git status --porcelain` مطابقت دارد)
- `task` — راه‌اندازی زیرعامل‌ها (با نوع زیرعامل مطابقت دارد)
- `skill` — بارگذاری یک مهارت (با نام مهارت مطابقت دارد)
- `lsp` — اجرای پرس‌وجوهای LSP (در حال حاضر غیردانه‌ای)
- `question` — پرسیدن سوالات از کاربر در حین اجرا
- `webfetch` — واکشی یک URL (با URL مطابقت دارد)
- `websearch` — جستجوی وب (با پرس‌وجو مطابقت دارد)
- `external_directory` — وقتی یک ابزار به مسیرهای خارج از فهرست کاری پروژه برخورد می‌کند فعال می‌شود
- `doom_loop` — وقتی یک فراخوانی ابزار یکسان ۳ بار با ورودی یکسان تکرار می‌شود فعال می‌شود

## پیش‌فرض‌ها

اگر چیزی را مشخص نکنید، OpenCode از پیش‌فرض‌های آزاد شروع می‌کند:

- اکثر مجوزها به طور پیش‌فرض `"allow"` هستند.
- `doom_loop` و `external_directory` به طور پیش‌فرض `"ask"` هستند.
- `read` مقدار `"allow"` دارد، اما پرونده‌های `.env` به طور پیش‌فرض رد می‌شوند:

```json title="opencode.json"
{
  "permission": {
    "read": {
      "*": "allow",
      "*.env": "deny",
      "*.env.*": "deny",
      "*.env.example": "allow"
    }
  }
}
```

## آنچه «Ask» انجام می‌دهد

وقتی OpenCode برای تأیید درخواست می‌کند، رابط کاربری سه نتیجه را پیشنهاد می‌دهد:

- `once` — فقط این درخواست را تأیید کن
- `always` — درخواست‌های آینده‌ای را که با الگوهای پیشنهادی مطابقت دارند تأیید کن (برای باقی ماندن نشست فعلی OpenCode)
- `reject` — درخواست را رد کن

مجموعه الگوهایی که `always` تأیید می‌کرد، توسط ابزار ارائه می‌شود (به عنوان مثال، تأییدهای bash معمولاً یک پیشوند دستور ایمن مانند `git status*` را در فهرست سفید قرار می‌دهند).

## عوامل

می‌توانید مجوزها را به تفکیک عامل بازنویسی کنید. مجوزهای عامل با پیکربندی سراسری ادغام می‌شوند، و قوانین عامل اولویت دارند. [بیشتر بیاموزید](/docs/agents#permissions) درباره مجوزهای عامل.

:::note
به بخش [قوانین دانه‌ای (نحو شیء)](#granular-rules-object-syntax) در بالا برای مثال‌های تطبیق الگوی دقیق‌تر مراجعه کنید.
:::

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "bash": {
      "*": "ask",
      "git *": "allow",
      "git commit *": "deny",
      "git push *": "deny",
      "grep *": "allow"
    }
  },
  "agent": {
    "build": {
      "permission": {
        "bash": {
          "*": "ask",
          "git *": "allow",
          "git commit *": "ask",
          "git push *": "deny",
          "grep *": "allow"
        }
      }
    }
  }
}
```

همچنین می‌توانید مجوزهای عامل را در Markdown پیکربندی کنید:

```markdown title="~/.config/opencode/agents/review.md"
---
description: Code review without edits
mode: subagent
permission:
  edit: deny
  bash: ask
  webfetch: deny
---

Only analyze code and suggest changes.
```

:::tip
از تطبیق الگو برای دستوراتی با آرگومان استفاده کنید. `"grep *"` عبارت `grep pattern file.txt` را مجاز می‌کند، در حالی که `"grep"` به تنهایی آن را مسدود می‌کند. دستوراتی مانند `git status` برای رفتار پیش‌فرض کار می‌کنند، اما وقتی آرگومان‌ها ارسال می‌شوند نیاز به مجوز صریح (مانند `"git status *"`) دارند.
:::
