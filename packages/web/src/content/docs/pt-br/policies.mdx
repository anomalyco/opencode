---
title: Políticas
description: Controle quais recursos configurados o opencode pode usar.
---

Políticas controlam se o opencode pode executar uma ação em um recurso nomeado. Esta funcionalidade é experimental e é configurada com o array `experimental.policies` em `opencode.json`.

Políticas são separadas das [permissões](/docs/permissions). Permissões controlam o que as ferramentas podem fazer durante uma sessão, enquanto as políticas controlam se o opencode pode usar um recurso, como um provedor de LLM.

---

## Configuração

Cada declaração de política tem três campos:

- `effect` — `"allow"` ou `"deny"`.
- `action` — a operação que está sendo controlada.
- `resource` — o ID do recurso ou padrão curinga ao qual a declaração se aplica.

Por exemplo, para negar o uso do provedor `openai`:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "experimental": {
    "policies": [
      {
        "effect": "deny",
        "action": "provider.use",
        "resource": "openai"
      }
    ]
  }
}
```

Um provedor negado por política não fica disponível para seleção nem para uso de modelos, mesmo que tenha credenciais ou esteja configurado corretamente de outra forma.

---

## Políticas disponíveis

Atualmente, o opencode oferece suporte a uma ação de política:

| Ação           | Recurso                       | Descrição                                    |
| -------------- | ----------------------------- | -------------------------------------------- |
| `provider.use` | ID do provedor, como `openai` | Permite ou nega o uso de um provedor de LLM. |

Mais ações de política podem ser adicionadas no futuro.

---

## Correspondência

O campo `resource` oferece suporte à correspondência com curingas. Use `*` para corresponder a zero ou mais caracteres e `?` para corresponder a exatamente um caractere.

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "experimental": {
    "policies": [
      {
        "effect": "deny",
        "action": "provider.use",
        "resource": "company-*"
      }
    ]
  }
}
```

Isso nega provedores como `company-us` e `company-eu`.

---

## Ordem das regras

Quando várias declarações correspondem, a última declaração correspondente vence. Coloque as regras amplas primeiro e, depois delas, as exceções mais específicas.

Por exemplo, para permitir apenas a Anthropic:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "experimental": {
    "policies": [
      {
        "effect": "deny",
        "action": "provider.use",
        "resource": "*"
      },
      {
        "effect": "allow",
        "action": "provider.use",
        "resource": "anthropic"
      }
    ]
  }
}
```

Se nenhuma política corresponder a um provedor, o uso do provedor é permitido por padrão.

Políticas podem ser definidas tanto na configuração global quanto na configuração do projeto. Se políticas dos dois locais corresponderem ao mesmo provedor, sua política global tem prioridade sobre a política do projeto. Isso impede que um repositório reative um provedor que você nega globalmente.

## Listas de provedores

Use políticas em vez das configurações mais antigas `disabled_providers` e `enabled_providers` ao controlar o acesso a provedores.

Para substituir `disabled_providers`:

```json title="opencode.json"
{
  "experimental": {
    "policies": [
      { "effect": "deny", "action": "provider.use", "resource": "openai" },
      { "effect": "deny", "action": "provider.use", "resource": "google" }
    ]
  }
}
```

Para substituir `enabled_providers`, negue todos os provedores primeiro e permita os provedores selecionados depois:

```json title="opencode.json"
{
  "experimental": {
    "policies": [
      { "effect": "deny", "action": "provider.use", "resource": "*" },
      { "effect": "allow", "action": "provider.use", "resource": "anthropic" },
      { "effect": "allow", "action": "provider.use", "resource": "openai" }
    ]
  }
}
```
