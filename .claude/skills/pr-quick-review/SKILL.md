# pr-quick-review

`$ARGUMENTS` で指定された PR の軽量レビューを行う。引数が空なら現在 checkout 中のブランチに紐づく PR をレビューする。

## 趣旨 (これを必ず守る)

- **目的はマージ可否の最低判定**。詳細レビューはしない。
- 開発速度を上げるためのスキル。致命的でない小さいバグは「動かして気づいた人が直す」前提。
- 大きい PR には使わない。バグフィックスや小さい機能追加向け。
- 提案 (命名・スタイル・リファクタ・将来の改善等) を出してもよいが、**1 件ごとに必ず「必須」か「任意」かを明記する**。任意の指摘がマージを止めてはいけない。
- 最終的に「現時点でマージ可能か」を判定として必ず明示する。
- 出力は簡潔に。冗長な前置きや結論の繰り返しはしない (長さの厳密な上限は設けない)。

## 手順

### 1. PR 情報の取得

`gh` CLI には必ず `-R acompany-develop/securecode` を付ける (CLAUDE.md 参照)。

```bash
# 引数で PR 番号が指定されたとき
gh pr view <番号> -R acompany-develop/securecode --json number,title,body,author,additions,deletions,changedFiles,files,headRefName,baseRefName,url
gh pr diff <番号> -R acompany-develop/securecode

# 引数が空のとき (現在のブランチ)
gh pr view -R acompany-develop/securecode --json number,title,body,author,additions,deletions,changedFiles,files,headRefName,baseRefName,url
gh pr diff -R acompany-develop/securecode
```

PR が見つからない場合はその旨を伝えて終了。

### 2. PR サイズの確認

`changedFiles > 10` の場合、このスキルの対象外と判断する。以下を表示してユーザーに続行確認する:

> この PR は変更ファイル数が <N> 個あります。pr-quick-review はバグフィックス・小機能追加 (目安: 変更ファイル 10 個以下) 向けです。このサイズだと「致命的な見落としがない」ことを軽量レビューで保証するのは難しいので、`/security-review` や `/code-review` (effort=high) など丁寧なレビュー手段を推奨します。それでも quick review を続行しますか?

ユーザーが続行を選んだ場合のみ次に進む。続行する場合も、出力末尾に「サイズが大きいため見落としリスクあり」と明記する。

### 3. レビュー観点 (この 3 点のみ)

以下の 3 観点だけをチェックする。これ以外の観点では指摘を出さない。

#### A. 致命的なバグ・脆弱性

「マージしたら本番が壊れる / セキュリティ事故になる」レベルだけを拾う。例:

- ハードコードされた secret / API キー / 認証情報
- SQL / shell / command injection の余地
- 認可チェック漏れ (権限なしで叩けるパスが追加されている等)
- 明らかなリソースリーク・無限ループ・確実に踏む null reference
- 暗号鍵の弱い使い方、不適切な乱数源 (`Math.random` を秘密値に使う等)
- 破壊的なマイグレーション / 無条件 `DROP` / 無条件 `rm -rf`
- 既存 API の後方互換性を黙って壊している

「呼び出し方によっては落ちるかも」レベルは **拾わない**。

#### B. PR 説明文と実装のズレ

- 説明文に書かれた変更が diff に実在するか
- 説明文に書かれていない大きな変更 (新規依存追加・別機能の修正・設定ファイル変更・スキーマ変更等) が紛れていないか
- Fixes/Closes されている issue の主旨と diff が噛み合っているか

軽微な差分 (typo 修正の同梱等) はズレとしてカウントしない。

#### C. ざっくりしたコードレビュー

明らかにおかしい箇所、または改善提案を 0〜5 件程度挙げる。各項目に **[必須]** または **[任意]** のラベルを付ける。

- **[必須]**: マージ前に直すべきもの (動かない・壊れる・後方互換性破壊など)
  - 型不一致 / 呼び出し方が API と合っていない
  - 条件式が逆 / off-by-one が明らか
  - 追加されたコードが一度も呼ばれない (dead code)
- **[任意]**: 提案。マージは止めない。後でやってもよいし、やらなくてもよい。
  - 命名・スタイル・コメント不足
  - リファクタ提案
  - 「こう書いた方が読みやすい」系
  - 将来こうなったときに困りそう系

任意の指摘は「提案: ◯◯」のように書き、必須の指摘と混ざらないようにする。該当なしなら「なし」と書く。

### 4. 出力フォーマット

以下のフォーマットを厳守し、簡潔に日本語で出力する。

```
## PR Quick Review: #<番号> <タイトル>
<PR URL>

マージ判定: マージOK / 要修正
(任意の提案がある場合は「マージOK (任意の提案あり)」と書く)

### 致命的なバグ・脆弱性
- なし
  または
- [必須] <ファイル:行>: <一文で>

### 説明文と実装のズレ
- なし
  または
- [必須] <一文で>
- [任意] <一文で>

### コードレビュー
- なし
  または
- [必須] <ファイル:行>: <一文で>
- [任意] 提案: <ファイル:行>: <一文で>
```

マージ判定基準:

- **マージOK**: [必須] の指摘がゼロ。[任意] の提案があってもマージしてよい。
- **マージOK (任意の提案あり)**: [必須] はゼロだが、[任意] の提案を併記している。
- **要修正**: [必須] の指摘が 1 件以上ある (致命的バグ・脆弱性、または説明文と diff の大きなズレ、または明らかに壊れているコード)。

判定は **[必須] 指摘の有無だけ** で決める。[任意] の提案でマージを止めない。

## 禁止事項 (再掲)

- ラベル ([必須]/[任意]) のない指摘を出さない。すべての指摘に必ずラベルを付ける。
- [任意] の提案を理由にマージを止めない (判定は [必須] の有無だけで決める)。
- テスト追加を [必須] にしない (バグフィックス本体で壊れているなら別だが、原則 [任意])。
- 観点 A/B/C 以外の独自観点を増やさない。
- 出力を冗長にしない (前置き・結論の繰り返しを書かない)。
