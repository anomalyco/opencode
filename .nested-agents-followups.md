# Follow-up-Issues: Nested-Agent-Spawning (Phase 2)

Quelle: `design-final.md` §9/§10 (Branch `feat/nested-agents`). Jedes Kapitel ist als
eigenständiges GitHub-Issue gedacht. Keines dieser Themen ist Teil von V1.

---

## Issue 1: Parallelitäts-Cap für Subagent-Spawns

**Kontext:** V1 hat bewusst keinen Semaphor (design-final §2.2): Foreground-Tasks blockieren
ihren Eltern-Step ohnehin, Background bleibt flag-gated
(`OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`), Lifetime-Cap (200/Baum) + Tiefenlimit
begrenzen den Fan-out. Ein Parallelitäts-Cap ist ein reines Phase-2-Thema.

**Scope:** Begrenzung gleichzeitig laufender Subagents pro Session-Baum bzw. pro Ebene.

**BINDENDE DESIGN-NOTIZ (design-final.md §10, wörtlich — bei der Umsetzung zwingend beachten):**

> **NIEMALS ein einzelner baumweiter Semaphor über Foreground-Ketten.** Beweisbares
> Gegenbeispiel: Cap 2, zwei parallele L2-Foreground-Tasks halten beide Permits und warten auf
> L3-Kinder, die nie ein Permit bekommen → Deadlock (wartende Eltern halten Permits, die ihre
> Kinder brauchen). Zulässige Varianten: (a) Per-Ebene-Permits — Pools strikt nach Ebene
> geordnet, ein Halter von Ebene N wartet nie auf Ebene ≤ N, Ebene `max_depth` spawnt nie ⇒ per
> Induktion drainieren alle Pools; (b) Fail-Fast-Breiten-Cap pro Session mit klarem Fehlertext
> (kein stilles Queuing). In beiden Fällen muss das Warten interrupt-fähig sein (Abort-Kaskade
> darf nie an einem Permit hängen). Diese Notiz gehört wörtlich in das Follow-up-Issue.

**Akzeptanzkriterien:**
- Implementierung ist Variante (a) Per-Ebene-Permits ODER (b) Fail-Fast-Breiten-Cap pro
  Session — KEIN baumweiter Semaphor über Foreground-Ketten.
- Warten ist interrupt-fähig: Die Abort-Kaskade darf nie an einem Permit hängen
  (Regressionstest analog Abort-Kaskaden-Test in `test/session/nested-task.test.ts`).
- Deadlock-Gegenbeispiel aus der Notiz (Cap 2, zwei parallele L2-Foreground-Tasks mit
  L3-Kindern) als Test abgedeckt.

## Issue 2: Config-Key für das Tree-Limit

**Kontext:** `SUBAGENT_TREE_LIMIT = 200` ist in V1 eine Konstante mit Test-Seam
(`__testHooks.treeLimit` in `packages/opencode/src/session/subagent-limits.ts`, Vorbild
`__testHooks.agentLimit` in workflow.ts). design-final §2.5: Config-Key = Phase 2.

**Scope:** `experimental`-Config-Key (z. B. `subagent_tree_limit`), Konsum ausschließlich
über einen Clamp-Helper in `subagent-limits.ts` (Single Source of Truth, analog `maxDepth(cfg)`).
Der Zähler bleibt in-memory pro Prozess-Lebensdauer (Safety-Ceiling, kein Abrechnungszähler —
DB-Priming wurde in design-final §1.3 explizit verworfen).

## Issue 3: `depth`/`rootID` als additive Wire-Felder

**Kontext:** V1 leitet Tiefe und Root rein aus der `parentID`-Kette ab (`Session.lineage`),
null Schema-Änderungen. Phase 2 kann beide Werte als Convenience-Felder am Wire nachrüsten
(design-final §3/§9) — jederzeit additiv möglich, Wire-Format bleibt kompatibel.

**Scope:**
- `depth` und `rootID` als additive Felder an `Session.Info` / OpenAPI / SDK (Regeneration).
- **Backfill für Bestandsdaten: einmalige Migration per rekursiver CTE** (Vorlage in
  design-robust). **NICHT Lazy-Backfill-on-read** (Write in Lesepfaden = Wartbarkeits-Smell,
  zwei Wahrheitsquellen — in design-final §1.3 explizit verworfen).
- `recursive`-Param für `GET /session/:id/children`.

## Issue 4: TUI-Baumansicht / Breadcrumbs / Tiefen-Badges

**Kontext:** V1 verzichtet bewusst auf den UI-Umbau (größte Regressionsoberfläche,
design-final §1.3). Root-Routing der Permission-Asks macht die TUI bereits ohne Umbau
funktionsfähig; Ebene-3+-Navigation läuft pro Ebene über die bestehenden
`session_child_*`-Keybinds.

**Scope (Komfort, Folge-PRs):** Baumansicht für Session-Hierarchien, Breadcrumb-Kette in der
Kopfzeile, Tiefen-Badges an Task-Cards, Run-Footer-Gruppierung nach Teilbaum, Tree-Dialog.
UIs können "asked by @agent (depth N)" aus `metadata.originSessionID`/`originAgent`/
`originDepth` der Permission-Requests rendern. Profitiert von Issue 3 (Wire-Felder), hängt
aber nicht hart daran (Lineage-Walk reicht).

## Issue 5: Per-Task-Timeout

**Kontext:** V1 hat kein Timeout pro Ebene (design-final §2.2): Abort-Kaskade + Budget genügen;
der Zyklen-Deadlock ist durch die `task_id`-Ancestry-Validierung (nur direkte Kinder)
geschlossen.

**Scope:** Optionales Timeout pro Task-Spawn (Config und/oder Tool-Param). Muss sauber in die
Abort-Kaskade integrieren (Timeout = Abort des Teilbaums, kein verwaister Job) und darf
Foreground-Eltern nicht in undefinierte Zustände bringen.

---

## Issue 6: Kosten-Rollup über den Session-Baum

**Kontext:** V1 zählt Kosten wie heute pro Session, keine Doppelzählung, kein Rollup
(design-final §4.6). Für tiefe Bäume fehlt die aggregierte Sicht.

**Scope:** Anzeige-Rollup der Kind-Kosten in der Task-Part-Metadata (Anzeige, keine
Doppel-Abrechnung); Aggregation über `Session.descendants` oder die Wire-Felder aus Issue 3.

## Issue 7: Root-Scoping der `always`-Approved-Liste

**Kontext:** Adversarial-Review-Finding (MEDIUM): Die Doku behauptete ursprünglich, eine
`always`-Antwort "sticks to the root session and applies tree-wide". Real hängt die
Approved-Liste am Instance-State (`packages/opencode/src/permission/index.ts`: `State.approved`
trägt keinen Session-Schlüssel; `reply` pusht Regeln ungescoped, `ask` evaluiert sie für jede
Anfrage) — sie gilt also **instanzweit für die restliche Prozess-Lebensdauer**, auch für
Sessions außerhalb des Baums, der die Frage gestellt hat. Die Doku (agents.mdx,
permissions.mdx, sdk.mdx) wurde auf den Ist-Zustand korrigiert ("applies instance-wide for
the rest of the process"); dieses Issue trackt das eigentlich gewünschte Verhalten.

**Scope:**

- Approved-Rules pro Root-Session scopen (Schlüssel = Root der `Session.lineage`-Kette),
  `reply` und `ask`/`evaluate` entsprechend anpassen. Rein in-memory, keine Persistenz nötig.
- Doku anschließend wieder auf "tree-wide" zurückdrehen (agents.mdx
  `#permissions-in-nested-trees`, permissions.mdx "What Ask Does", sdk.mdx
  "Permission requests in nested session trees").

**Akzeptanzkriterien:**

- Ein `always` in Baum A schaltet keine identische Anfrage in Baum B frei.
- Wiederholte Anfragen im selben Baum (beliebige Tiefe) bleiben nach `always` frei.
- Pending-Auto-Resolve in `reply` (gleiches-Session-Matching) respektiert das neue Scoping.

## Issue 8: Vollwertiger Headless-E2E gegen den echten run.ts-Loop

**Kontext:** Die V1-Integrationssuite (`packages/opencode/test/session/nested-task.test.ts`,
T7) testet gegen Test-Seams und gemockte Modelle; kein Test fährt den echten `run.ts`-Loop
headless durch einen verschachtelten Spawn. Adversarial-Review-Follow-up.

**Scope:** Headless-E2E (z. B. via `opencode run` bzw. Server-API) mit deterministischem
Fake-/Replay-Provider: Spawn-Kette bis Tiefe ≥ 3 durch den echten Prompt-Loop, Verifikation
von Tiefenlimit (Tool-Entfernung am Limit), `SubagentDepthError`/`SubagentTreeLimitError`
am Wire und sauberem Abschluss der Task-Parts.

**Akzeptanzkriterien:**

- Test startet den echten Loop (keine direkten Tool-Aufrufe an den Seams vorbei).
- Deterministisch in CI (kein echtes Modell, keine Netz-Abhängigkeit).

## Issue 9: Background-Abort-Mix-Test

**Kontext:** Die Abort-Kaskade ist für Foreground-Ketten getestet (inkl. Release-Race-Fix,
Commit `5582da5a8`). Der Mix aus Background-Subagents
(`OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`) und Foreground-Kindern unter einem
Eltern-Abort ist nicht abgedeckt. Adversarial-Review-Follow-up.

**Scope:** Regressionstest: Eltern-Session mit gleichzeitig laufenden Background- UND
Foreground-Kindern (idealerweise gemischt über mehrere Ebenen) wird abgebrochen.

**Akzeptanzkriterien:**

- Alle Kinder beider Modi terminieren, keine verwaisten Background-Jobs.
- Das Release-Race aus `5582da5a8` bleibt geschlossen (Abort während Spawn-Übergabe).
- Abort wartet nie auf ein Permit/einen Budget-Slot (vgl. Issue 1).
