### 3.2 零冲突合并

#6 的 CLI ASCII commit 混入 brand 变更在 diff review 阶段被识别并修复，避免了后续合并冲突。

- 每个 Issue 范围精准（XS/S 为主）

## 四、改进空间 (What Could Be Improved)

### 4.1 P5 评审两轮才通过

**问题**: P5 R1 总体 3/7 Go（未达 ≥5/7 门控）
- 架构 7/7 Go ✅
- 接口 7/7 Go ✅
- 发布风险 4/7 NoGo ❌

**根因**: P5 提交物只覆盖了架构和接口设计，缺少"发布就绪"维度的自检。三个缺失项（批次回滚、Linux 适配、版本锁定）是 LLM Panel 发现而非设计师自查。

**改进**: P5 模板增加 Deploy Readiness 自检表，提交者逐项打勾后再提审。

### 4.2 Feature Branch 污染

**问题**: #6 的 commit 混入了 brand + i18n 文件变更（属于 #3 的范围）

**根因**: 并发开发时 working tree 不干净——在已有修改的分支上直接 commit

**改进**: 
- P6 开始前强制 clean working tree (`git stash -u`)
- 考虑 pre-push 钩子校验变更文件是否超出 Issue scope

### 4.3 XS/S Issue 集合效应

**问题**: 单个 Issue 是 XS/S（跳过 P4/P5/P8），但 5 个 XS/S 合在一起构成了 L 级的跨平台影响

**根因**: 当前工作流的 P8 Canary 只对 L/XL 强制。但 XS/S 的集合效应无门控覆盖

**改进**: v0.3.0 作为整体是 L 级，走完了 P8 流程，但 Issue 级别的门控没有体现集合风险

## 六、改进 Issue

### Issue A: P5 提交模板增加 Deploy Readiness 自检 [P1]

**问题**: P5 第一轮 NoGo 的根因是提交者未自检发布风险维度

**方案**: 在 P5 设计文档模板末尾增加：

```
## Deploy Readiness（提交前必须自检）
- [ ] 所有新增依赖已锁定到精确版本
- [ ] 所有平台（Linux/macOS/Windows）已覆盖
- [ ] 失败回滚策略明确
- [ ] CI 可复现所有构建步骤
```

### Issue B: P5 Release Risk Matrix 模板 [P1]

**问题**: 跨平台发布风险没有系统化检查

**方案**: 在 P5 设计文档中增加 Risk Matrix 表，逐平台列出依赖工具、版本、CI 可复现性。≥2 ⚠️ 自动触发 NoGo。

### Issue C: Feature Branch Scope 校验 [P2]

**问题**: #6 commit 污染了不属于 Issue #6 的文件

**方案**: Pre-push 钩子比较当前分支变更文件与 Issue 声明的影响范围。超出范围的文件列表输出到告警。
