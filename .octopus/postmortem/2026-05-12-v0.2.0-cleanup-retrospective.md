## 可改进的地方

### 问题 1：P0 范围估算不准

| Issue | 初始估算 | 实际范围 | 偏差 |
|-------|:-------:|:--------:|:----:|
| #15 i18n | 16 JSON | 3 dirs × 51 files | **3× 低估** |
| #16 CI/CD | ~20 文件 | ~25 文件（含 4 个 Dockerfile） | +25% |
| #12 代码清洗 | L (540 文件) | 需拆 6 子 Issue | XL 级拆解不足 |

**根因**：P0 探索只做了 `rg -c 'opencode'` 的文件级统计，没有深入到包内部的文件分布。i18n 分散在 4 个目录（web/app/ui/desktop），CI/CD 分布在 workflows/containers/infra 三个域，P0 只看了一个维度。

**改进**：P0 影响范围判定应同时从「文件类型」和「包/目录拓扑」两个维度展开。

### 问题 2：P2 Round 1 评审可以更高效

Round 1 评审结果：5/7 NoGo。但核心批评（保留清单不足、缺少符号级冲突检测）实际上在初始版本中已经被部分覆盖，只是呈现方式不够突出。

**根因**：评审 prompt 只有 300 字的摘要，评审模型只能看到摘要而不是完整版本计划。部分批评是因为"信息缺失"而非"架构缺陷"。

**改进**：P2 评审的 prompt 应包含关键决策的摘要（如：保留清单有哪些类别、执行协议在哪里），而不是只描述 Issue 列表。

### 问题 3：P7 才发现 SDK 文档残留

SDK 文档 `sdk.mdx` 和 `openapi.json` 中的 `createOpencodeClient` 引用在 P6 编码阶段没有被 feature-dev 发现，直到 QA 的 G2 检查才暴露。

**根因**：P6 分派时，feature-dev 负责文档清洗 (#13/#14) 但不负责 SDK 文档，core-dev 负责代码清洗 (#12) 但不负责文档。SDK 文档是代码和文档的交叉地带，没有被任何 Issue 明确覆盖。

**改进**：交叉地带的归属应在版本计划中明确标注。建议在 Issue 划分时增加「代码↔文档交叉引用」检查点。
