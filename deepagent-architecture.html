The Journey of a Query
A chronological walkthrough — from the moment the user types a message, through LLM reasoning, tool execution, sub-agent delegation, to the final answer delivered. Each phase below tells the story of what happens inside the agent system, step by step.
1
The Trigger — User Sends a Query arrival
It starts when the user types a message — anything from "explain this code" to "build a new feature". The CLI receives the input and feeds it into the running session. At this point, no agent has been selected yet. The session component — packages/opencode/src/session/ — takes the raw message and begins its processing pipeline.
The input lands in the conversation history buffer. Before any LLM call happens, the system performs a token-budget check: if the conversation has grown too large, it may trigger a session overflow — the oldest messages get compacted into a summary by the summary sub-agent (see Phase 7). This ensures the LLM never exceeds its context window.

2
Context Assembly — The Deepagent Wakes Up loading
The processor loads the full conversation history from session.txns — every prior user message, assistant response, and tool result is pulled into a structured array. This is the agent's memory of what happened before.
Next, the deepagent's system prompt is injected. This isn't a single string — it's built from multiple sources: the agent's baked-in instructions, any opencode.json overrides, plugin additions, and user-level configurations. These four layers are merged in order (defaults → config file → plugins → user overrides), with each later layer overriding the earlier one.
Finally, tool definitions are attached to the prompt. Each agent has a different toolset — the deepagent (general) gets all 12 tools including the critical task tool. Sub-agents like plan or build get restricted subsets. The complete context — messages + system prompt + tool definitions — is now ready for the LLM.

4
The Fork in the Road — Deepagent Decides to Delegate orchestration
For complex tasks — researching a topic, exploring a codebase, or executing a multi-file edit — the deepagent may decide the work is better handled by a specialist sub-agent. It makes a task tool call, passing the task description, agent type, and any context needed.
This is the most consequential decision point in the system. The task tool is special: it's the only tool that spawns another agent. Most sub-agents (build, explore, plan, scout) don't have access to this tool — they cannot spawn further agents. Only the deepagent itself (general agent type) and plan carry the task tool.
Why this restriction? It's enforced by three independent blocking points (see the Permission System section below). subagent-permissions.ts:22 injects { permission: "task", action: "deny" } into every spawned sub-agent's session. task.ts:199-202 hides the tool from the LLM. prompt.ts:1226-1233 overwrites the permission set entirely. The result: built-in sub-agents are guaranteed leaf nodes — they can't spawn anything deeper.

5
Sub-agent in Action — The Spawned Agent Works execution
When the deepagent calls task, a new sub-agent session is created. This child agent has its own restricted toolset — defined by its type in agents.ts. For example, the build agent gets read, write, edit, shell, grep, glob, and terminal — everything it needs to implement code changes, but crucially no task tool, no websearch, no repo_clone.
The sub-agent goes through its own LLM loop — same streamObject pipeline, same permission checks, same tool execution cycle — but with its specialized system prompt and toolset. The deepagent pauses (the task tool awaits the sub-agent's completion), its own LLM stream waiting.
Inside the sub-agent session, history is isolated. The sub-agent doesn't see the deepagent's full conversation — only the task description and any context the deepagent passed. This prevents context pollution and keeps the sub-agent focused. The sub-agent runs its tools, makes its own LLM calls, and eventually completes.

7
Final Answer & Context Hygiene — Mission Accomplished completion
The deepagent produces its final response — the text streams in real-time to the user. At this point two things happen behind the scenes:
Context compaction — if the conversation has grown large enough to approach the token budget, processor.ts may silently trigger the summary sub-agent. This agent reads the conversation history and produces a condensed summary that replaces the older messages, keeping the context window healthy for future turns.
Session persistence — every message and tool result is recorded in session.txns. The session stores the full conversation, agent configurations, and state. When the user returns, everything is restored from this transaction log — the deepagent picks up exactly where it left off.
Mission accomplished. The user has their answer, the code has been changed, or the research is done — and the deepagent is ready for the next query.

Three Blocking Points for Sub-agent Spawning

1. subagent-permissions.ts:22 — deriveSubagentSessionPermission injects { permission: "task", action: "deny" } into every sub-agent session (exact string check === "task", wildcard doesn't match).

2. task.ts:199–202 — tool is hidden from the LLM if a deny exists for its permission name.

3. prompt.ts:1226–1233 — toolsAvailable overwrites the permission set so sub-agents never even see the task tool.

Custom Agent Exception

Custom agents configured with explicit task: "allow" in opencode.json bypass all three blocking points. They can spawn arbitrary-depth sub-agent chains — no recursion guard exists in the codebase. The depth limit is purely governed by the permission system.

You are OpenCode, the best coding agent on the planet.

You are an interactive CLI tool that helps users with software engineering tasks. Use the instructions below and the tools available to you to assist the user.

IMPORTANT: You must NEVER generate or guess URLs for the user unless you are confident that the URLs are for helping the user with programming. You may use URLs provided by the user in their messages or local files.

If the user asks for help or wants to give feedback inform them of the following:
- ctrl+p to list available actions
- To give feedback, users should report the issue at
  https://github.com/anomalyco/opencode

When the user directly asks about OpenCode (eg. "can OpenCode do...", "does OpenCode have..."), or asks in second person (eg. "are you able...", "can you do..."), or asks how to use a specific OpenCode feature (eg. implement a hook, write a slash command, or install an MCP server), use the WebFetch tool to gather information to answer the question from OpenCode docs. The list of available docs is available at https://opencode.ai/docs

# Tone and style
- Only use emojis if the user explicitly requests it. Avoid using emojis in all communication unless asked.
- Your output will be displayed on a command line interface. Your responses should be short and concise. You can use GitHub-flavored markdown for formatting, and will be rendered in a monospace font using the CommonMark specification.
- Output text to communicate with the user; all text you output outside of tool use is displayed to the user. Only use tools to complete tasks. Never use tools like Bash or code comments as means to communicate with the user during the session.
- NEVER create files unless they're absolutely necessary for achieving your goal. ALWAYS prefer editing an existing file to creating a new one. This includes markdown files.

# Professional objectivity
Prioritize technical accuracy and truthfulness over validating the user's beliefs. Focus on facts and problem-solving, providing direct, objective technical info without any unnecessary superlatives, praise, or emotional validation. It is best for the user if OpenCode honestly applies the same rigorous standards to all ideas and disagrees when necessary, even if it may not be what the user wants to hear. Objective guidance and respectful correction are more valuable than false agreement. Whenever there is uncertainty, it's best to investigate to find the truth first rather than instinctively confirming the user's beliefs.

# Task Management
You have access to the TodoWrite tools to help you manage and plan tasks. Use these tools VERY frequently to ensure that you are tracking your tasks and giving the user visibility into your progress.
These tools are also EXTREMELY helpful for planning tasks, and for breaking down larger complex tasks into smaller steps. If you do not use this tool when planning, you may forget to do important tasks - and that is unacceptable.

It is critical that you mark todos as completed as soon as you are done with a task. Do not batch up multiple tasks before marking them as completed.

# Doing tasks
The user will primarily request you perform software engineering tasks. This includes solving bugs, adding new functionality, refactoring code, explaining code, and more. For these tasks the following steps are recommended:
-
- Use the TodoWrite tool to plan the task if required

- Tool results and user messages may include <system-reminder> tags. <system-reminder> tags contain useful information and reminders. They are automatically added by the system, and bear no direct relation to the specific tool results or user messages in which they appear.

# Tool usage policy
- When doing file search, prefer to use the Task tool in order to reduce context usage.
- You should proactively use the Task tool with specialized agents when the task at hand matches the agent's description.

- When WebFetch returns a message about a redirect to a different host, you should immediately make a new WebFetch request with the redirect URL provided in the response.
- You can call multiple tools in a single response. If you intend to call multiple tools and there are no dependencies between them, make all independent tool calls in parallel. Maximize use of parallel tool calls where possible to increase efficiency. However, if some tool calls depend on previous calls to inform dependent values, do NOT call these tools in parallel and instead call them sequentially. For instance, if one operation must complete before another starts, run these operations sequentially instead. Never use placeholders or guess missing parameters in tool calls.
- If the user specifies that they want you to run tools "in parallel", you MUST send a single message with multiple tool use content blocks. For example, if you need to launch multiple agents in parallel, send a single message with multiple Task tool calls.
- Use specialized tools instead of bash commands when possible, as this provides a better user experience. For file operations, use dedicated tools: Read for reading files instead of cat/head/tail, Edit for editing instead of sed/awk, and Write for creating files instead of cat with heredoc or echo redirection. Reserve bash tools exclusively for actual system commands and terminal operations that require shell execution. NEVER use bash echo or other command-line tools to communicate thoughts, explanations, or instructions to the user. Output all communication directly in your response text instead.
- VERY IMPORTANT: When exploring the codebase to gather context or to answer a question that is not a needle query for a specific file/class/function, it is CRITICAL that you use the Task tool instead of running search commands directly.

IMPORTANT: Always use the TodoWrite tool to plan and track tasks throughout the conversation.

RLM Fork Improvement Plan
Explanation-rich implementation plan for github.com/grishahq/recursive-llm. The RLM library lets an LLM process long documents by writing and executing Python code in a RestrictedPython sandbox — the LLM peeks at context via print(context[:500]) and recurses via recursive_llm(). This plan addresses the 8 core weaknesses found during codebase analysis: no retry logic, no caching, no streaming, no timeout enforcement, no structured output, no token/usage tracking, fragile async bridging, and missing config pass-throughs.
Phase 1 Foundation — Config Surface & Stability 3 changes · core.py/repl.py · backward-compatible
Why: REPLExecutor accepts max_output_chars and timeout but RLM.__init__() exposes neither. The timeout is stored but never enforced — an infinite loop in generated code hangs forever.
1.1 — Expose max_output_chars through RLM: Add max_output_chars: int = 2000 to RLM.__init__() and pass it to self.repl = REPLExecutor(max_output_chars=...). Currently the truncation limit is hardcoded at the REPL level; the RLM user has no way to control it. Test: RLM(max_output_chars=100).complete(query) truncates output at 100 chars.
1.2 — Enforce REPL timeout: Use signal.SIGALRM (Unix) or threading.Timer (Windows) to enforce self.timeout seconds during exec(). The current REPLExecutor(timeout=5) accepts the parameter but never applies it — generated code like while True: pass hangs forever. Test: REPLExecutor(timeout=0.1).execute("while True: pass") raises REPLError.
1.3 — Expose repl_timeout through RLM: Add repl_timeout: int = 5 to RLM.__init__() and pass it to REPLExecutor(timeout=repl_timeout). Completes the config surface — both truncation and timeout are now controllable from the top-level API.

Phase 2 Reliability — Retry & Recovery 2 changes · core.py · MAX_RETRIES=3 gate

Algorithm Overview & Pseudocode The RLM loop from the paper (Fig. 2, §3)
Core Loop: The RLM repeatedly asks a frontier LLM to (1) read the accumulated context via a REPL context variable, (2) write Python code to explore the context, and (3) signal completion by setting answer["content"] and answer["ready"] = True. Between iterations, the (question, answer) pair is appended to the conversation. If the LLM fails to produce a final answer within limits, safeguards terminate the loop and return whatever partial answer exists.
Pseudocode (paper Fig. 2, adapted): 
function RLM(question, context):
  conversation = [system_prompt]
  stats = {calls: 0, tokens: 0, start: now()}

  while not is_final(answer):
    check_budget(stats)                     # U1 guardrails

    prompt = build_query_prompt(            # recursive query prompt
      question=question,
      conversation=conversation,
      iteration=stats.calls
    )
    response = LLM(prompt)                  # call frontier model
    stats.calls += 1; stats.tokens += count(response)

    code = extract_code(response)
    if not code:
      response = retry_with_correction()    # phase 2 retry
      code = extract_code(response)

    result = REPL.execute(code)             # exec in RestrictedPython
    conversation += f"## Result:\n{result}"

    if should_compact(conversation):        # U6 compaction
      summary = LLM(compact_prompt(conversation))
      conversation = [system_prompt, summary]

  return answer["content"], stats

function recursive_llm(sub_question, sub_context):
  key = hash(sub_question, sub_context[:200]) # phase 3 cache
  if key in cache: return cache[key]

  if depth >= max_depth:                    # U7 fallback
    return LLM(f"Answer using context:\n{sub_context[:max_chars]}")
  
  child = RLM(sub_question, sub_context)    # recursive call
  cache[key] = child.result
  return child.result
REPL Environment Specification Sandbox contract (§3.2, App. B.1)
RestrictedPython (default): The LLM's generated code is executed via RestrictedPython, which compiles Python AST into a restricted bytecode form. The sandbox allows most builtins but blocks __import__, filesystem access, network I/O, exec/eval, os/subprocess/sys, class definitions, and attribute deletion. The paper uses RestrictedPython 7.3+.
Reserved Names (scaffold): The REPL injects these names into the global scope before every exec(). After execution, the scaffold is restored to prevent LLM-generated code from corrupting it across iterations. 
reserved = {
  "context":        str,        # the input document (accessible via slicing)
  "answer":         dict,       # {"content": str, "ready": bool}
  "recursive_llm":  callable,   # spawns child RLM (sub_question, sub_context)
  "llm_query":      callable,   # plain LLM completion (no recursion)
  "SHOW_VARS":      callable,   # U15 helper — lists available names
}
Answer Dict Protocol (U4): The LLM signals completion by executing answer["content"] = "..." followed by answer["ready"] = True. The main loop checks answer["ready"] after each exec(). This replaces the FINAL() string-parsing approach. On timeout or cancellation, the partial answer["content"] is returned (paper §3.2).
Scaffold Restoration: After each exec(), the reserved names (context, answer, recursive_llm, llm_query, SHOW_VARS) are re-bound to their original values. This prevents LLM-generated code from overwriting them across iterations (upstream U8, U15).

Recursion Strategy & Termination Deep context exploration (§3.1, §4.2)
recursive_llm() Protocol: The LLM can call recursive_llm(sub_question, sub_context) from within its generated Python code. This spawns a child RLM instance with the sub-question and sub-context. The child runs the full RLM loop and returns answer["content"]. The parent's REPL receives the result as a string variable. This is how the RLM decomposes complex questions into manageable sub-problems.

AnthropicTool Search Tool — Server-Side Dynamic Tool Discovery

The Tool Search Tool is an Anthropic-proposed mechanism (announced alongside Claude Code's defer_loading support) that allows the LLM to search for the right tool on-demand rather than receiving every tool definition in every request. This solves a critical scaling bottleneck: as the number of available tools grows (native + MCP servers), the context consumed by tool schemas dominates the prompt budget. For opencode — where a single session can load 18+ built-in tools plus tools from multiple MCP servers — this is directly applicable.

1How It Works
Current (eager) flow — opencode today 
Session start
  → ToolRegistry initializes ALL 18+ built-in tools (each: init, validate schema)
  → MCP client connects to each server and calls tools/list → caches ALL definitions
  → SessionTools.resolve() passes EVERY tool as a full JSON Schema block in the LLM request
  → LLM sees 50k-80k tokens of tool schemas before the first user message
Tool Search flow — how it would work 
Session start
  → ToolRegistry initializes tools, but marks all with defer_loading: true
  → Only basic tool metadata (name + 1-line description) is included in the prompt (~85% fewer tokens)
  → LLM decides: "I need to read config files" → calls tool_search_tool({ query: "read file" })
  → Server responds with full schema for matched tools (tool_reference blocks)
  → LLM can now call the matched tool with correct parameters
  → Unused tools never enter the context window
Anthropic's implementation variants 
tool_search_tool_regex_20251119 — Regex-based pattern matching on tool names + descriptions.
  Fast, deterministic, no model download needed. Good for hundreds of tools.

tool_search_tool_bm25_20251119 — BM25 ranking on tool names + descriptions.
  Bag-of-words retrieval, accounts for term frequency. Good for thousands of tools.

Both return tool_reference { id, name, description, input_schema } blocks.
Server-side only. The client sends defer_loading: true and the tool_search_tool
definition; the model uses it to fetch schemas lazily.
2Feasibility Assessment for opencode

The opencode codebase already has well-separated layers that map cleanly onto the Tool Search architecture. Implementation requires changes in 4 areas, all within existing module boundaries.

A. Protocol layer — packages/llm/src/protocols/anthropic-messages.ts

This file already defines AnthropicTool and handles three server_tool_use types (web_search, code_execution, web_fetch). Adding tool_search_tool_regex_20251119 (or bm25) as a 4th server tool type follows the exact same pattern: 

// In the tool schema — Add alongside existing serverTool variants
tool_search_tool: z.object({
  query: z.string().describe("Natural language or regex to find tools"),
  max_results: z.number().optional(),
}).optional(),

// In the request builder — Include when defer_loading is active
if (request.deferLoading) {
  requestBody.tools.push({ type: "tool_search_tool_regex_20251119", ... });
}

// In the response decoder — Handle tool_reference blocks
if (block.type === "tool_reference") {
  // Schema is now available; subsequent calls can use it
}

~80 lines of new code. This is the smallest and most contained change.

B. Tool definition schema — packages/opencode/src/tool/tool.ts 
Add defer_loading?: boolean to Tool.Def type. This is a per-tool flag:
- Built-in tools: defer_loading = true (only name + 1-line desc in prompt)
- Custom/user tools: defer_loading = false (include schema normally)
- MCP tools: defer_loading = true (massive savings for multi-server setups)

~5 lines in the type definition, ~10 lines in the registry to apply defaults.

C. Registry integration — packages/opencode/src/tool/registry.ts 
Two changes:
1. When defer_loading: true, resolve() emits a stripped tool entry:
   { id, name, description: firstLine } instead of the full JSON Schema.

2. A new method resolveDeferred(id: string): Tool.Def lazily returns the full
   schema on-demand — called when the LLM uses tool_reference to request it.

The MCP layer (mcp/index.ts) similarly returns only { id, name, description }
for each tool until a tools/get call (or cached lookup) resolves the schema.

~40 lines in registry.ts, ~20 lines in mcp/index.ts.

D. Session tool resolution — packages/opencode/src/session/tools.ts 
SessionTools.resolve() currently gathers ALL tools and wraps them in AI SDK
tool() calls. With defer_loading:
1. Pass a deferredTools: Tool.Def[] to the LLM alongside regular tools.
2. When an LLM returns a tool_reference response, call registry.resolveDeferred(id)
   or mcp.resolveDeferred(id) to get the full schema and allow subsequent calls.
3. The LLM's tool_search_tool call itself is handled like any other tool call —
   delegate to registry.search(query) or mcp.search(query).

~60 lines in session/tools.ts + ~30 lines in session/llm/request.ts.
