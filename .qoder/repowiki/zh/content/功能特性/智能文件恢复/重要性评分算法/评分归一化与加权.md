## 评分归一化与维度映射

评分归一化处理流程旨在将各维度的原始分值映射到统一的0-100分区间，确保不同维度的评分具有可比性。该流程通过五维度评分系统实现，每个维度的评分都经过特定的归一化算法处理。

### 时间维度归一化

时间维度的原始数据是文件的最后访问时间，通过计算与当前时间的时间差来确定分值。时间越近的文件分值越高。具体归一化规则如下：
- 1小时内访问：100分
- 6小时内访问：90分
- 24小时内访问：75分
- 24小时后开始指数衰减，最低10分

该算法确保最近访问的文件获得最高分，体现了时间因素的重要性。

### 频率维度归一化

频率维度的原始数据是文件的访问次数，包括读、写、编辑操作的总次数。归一化过程分为两部分：
1. 基于总操作次数的评分：每操作一次加5分，最高80分
2. 最近一小时操作频率加成：每操作一次加10分，最高20分加成

最终分值为两部分之和，上限为100分。这种设计既考虑了长期使用频率，也强调了近期活跃度。

### 操作类型维度归一化

操作类型维度根据文件的操作历史进行评分，不同操作类型具有不同的权重：
- 写操作：每次15分
- 编辑操作：每次10分
- 读操作：每次3分

此外，如果最后一次操作是写操作，则额外加25分；如果是编辑操作，则额外加15分。这种设计突出了修改性操作的重要性，因为它们通常代表了更深入的文件交互。

### 文件类型维度归一化

文件类型维度根据文件扩展名赋予不同的基础分值，体现了不同类型文件的重要性差异：
- 代码文件（如.js, .ts）：100-95分
- 配置文件（如.json, .yaml）：70-50分
- 文档文件（如.md, .txt）：40-25分
- 其他文件：30分

这种分类确保了代码文件等核心开发文件获得最高分，而文档文件等辅助性文件分值较低。

### 项目关联度维度归一化

项目关联度维度通过文件路径和文件名来评估其与项目核心的关联程度：
- 在`/src/`或`\\src\\`目录中：+30分
- 在`/components/`或`/modules/`目录中：+20分
- 在`/test/`或`/spec/`目录中：+10分
- 是关键文件（如package.json, README.md等）：+25分

基础分为50分，通过路径和文件名特征进行加分，最高可达100分。

## 加权求和公式与权重配置

综合评分通过加权求和公式计算，将五个维度的归一化分值按照预设权重组合成最终的综合评分。权重配置反映了各维度对文件重要性判断的相对重要性。

### 加权求和公式

综合评分的计算公式如下：
```
综合评分 = Σ(维度分值 × 维度权重)
```

具体到五个维度：
```
综合评分 = 
  时间分值 × 35% +
  频率分值 × 25% +
  操作分值 × 20% +
  类型分值 × 15% +
  关联度分值 × 5%
```

最终评分经过四舍五入并限制在0-100分范围内。

### 权重配置说明

当前的权重配置为：
- **时间（35%）**：反映文件的时效性，最近使用的文件更可能与当前任务相关
- **频率（25%）**：反映文件的使用习惯，频繁访问的文件通常是项目核心
- **操作（20%）**：反映文件的修改程度，写操作比读操作更重要
- **类型（15%）**：反映文件的本质重要性，代码文件比文档文件更重要
- **关联度（5%）**：反映文件在项目结构中的位置，核心目录中的文件更重要

这种权重分配体现了"近期使用"和"频繁使用"是最重要指标的设计理念，同时兼顾了操作深度、文件类型和项目结构等因素。

## 综合评分计算示例

以下是一个完整的综合评分计算示例，展示如何从原始数据到最终评分的全过程。

### 示例文件信息

假设有一个React组件文件，其相关信息如下：
- **文件路径**：`./src/components/Cart.jsx`
- **最后访问时间**：30分钟前
- **操作历史**：读取3次，编辑5次，写入2次
- **最后一次操作**：编辑
- **文件类型**：`.jsx`（代码文件）
- **文件位置**：在`/src/`目录中，是项目核心组件

### 各维度分值计算

1. **时间分值**：30分钟内访问，得100分
2. **频率分值**：
   - 总操作次数：3+5+2=10次，10×5=50分
   - 最近一小时操作：假设2次，2×10=20分
   - 总频率分值：50+20=70分
3. **操作分值**：
   - 写操作：2×15=30分
   - 编辑操作：5×10=50分
   - 读操作：3×3=9分
   - 最后一次操作是编辑：+15分
   - 总操作分值：30+50+9+15=104分，上限100分
4. **类型分值**：`.jsx`文件，得95分
5. **关联度分值**：
   - 基础分：50分
   - 在`/src/`目录中：+30分
   - 是关键组件：+25分
   - 总关联度分值：50+30+25=105分，上限100分

### 加权求和计算

```
综合评分 = 
  100 × 0.35 +  // 时间：35.0
  70 × 0.25 +   // 频率：17.5
  100 × 0.20 +  // 操作：20.0
  95 × 0.15 +   // 类型：14.25
  100 × 0.05    // 关联度：5.0
= 35.0 + 17.5 + 20.0 + 14.25 + 5.0
= 91.75
```

最终综合评分为92分（四舍五入），表明这是一个非常重要且需要优先恢复的文件。

## 权重配置结构与修改方法

权重配置是评分系统的核心参数，决定了各维度对最终评分的影响程度。了解其结构和修改方法对于系统调优至关重要。

### 权重配置结构

权重配置在`IntelligentFileRestorer`类中以`scoringWeights`对象的形式存在，其结构如下：
```javascript
this.scoringWeights = {
  temporal: 0.35,      // 时间因素权重 35%
  frequency: 0.25,     // 频率因素权重 25%
  operation: 0.20,     // 操作类型权重 20%
  fileType: 0.15,      // 文件类型权重 15%
  project: 0.05        // 项目关联度权重 5%
};
```

该配置对象包含了五个维度的权重，总和为1.0（100%）。每个权重值都是0到1之间的浮点数，代表该维度在总评分中的占比。

### 权重配置修改方法

权重配置可以通过以下几种方式修改：

1. **构造函数参数**：在创建`IntelligentFileRestorer`实例时，可以通过配置对象传入自定义权重：
```javascript
const restorer = new IntelligentFileRestorer({
  maxFiles: 20,
  maxTokensPerFile: 8192,
  totalTokenLimit: 32768,
  scoringWeights: {
    temporal: 0.30,
    frequency: 0.30,
    operation: 0.20,
    fileType: 0.15,
    project: 0.05
  }
});
```

2. **运行时修改**：对于已创建的实例，可以直接修改`scoringWeights`属性：
```javascript
restorer.scoringWeights.temporal = 0.40;
restorer.scoringWeights.frequency = 0.20;
```

3. **配置文件加载**：系统可以从外部配置文件加载权重设置，实现动态配置。

### 配置验证与约束

系统在使用权重配置时会进行验证，确保：
- 所有权重值在0到1之间
- 权重总和接近1.0（允许微小的浮点误差）
- 所有必需的维度都有权重定义

如果配置无效，系统会使用默认权重或抛出错误。

## 权重调整对文件恢复优先级的影响

权重配置的调整会显著影响文件的综合评分，从而改变文件恢复的优先级顺序。不同的权重分配策略适用于不同的使用场景和项目类型。

### 不同权重策略的影响

#### 1. 强调近期使用的策略
```javascript
{
  temporal: 0.50,    // 时间权重提高到50%
  frequency: 0.20,   // 频率权重降低到20%
  operation: 0.15,
  fileType: 0.10,
  project: 0.05
}
```
这种策略适用于快速迭代的开发场景，优先恢复最近编辑的文件，即使它们不是最频繁使用的。适合功能开发阶段。

#### 2. 强调核心文件的策略
```javascript
{
  temporal: 0.25,
  frequency: 0.25,
  operation: 0.20,
  fileType: 0.20,    // 文件类型权重提高到20%
  project: 0.10      // 项目关联度权重提高到10%
}
```
这种策略适用于维护现有系统，优先恢复核心代码文件和配置文件，确保系统架构的完整性。适合代码审查或重构阶段。

#### 3. 强调操作深度的策略
```javascript
{
  temporal: 0.30,
  frequency: 0.20,
  operation: 0.30,    // 操作权重提高到30%
  fileType: 0.15,
  project: 0.05
}
```
这种策略适用于调试和问题修复场景，优先恢复被修改过的文件，因为它们更可能包含当前问题的上下文。

### 实际影响示例

假设有两个文件：
- **文件A**：`utils/helper.js`，最近频繁使用但主要是读取
- **文件B**：`src/main.js`，上周修改过一次，但它是项目入口文件

在默认权重下：
- 文件A可能因高频率得分而优先
- 文件B可能因是核心文件而得分较高

如果将操作权重提高到30%，文件B的评分会显著提升，可能超过文件A，从而改变恢复优先级。

### 权重调整的最佳实践

1. **根据项目阶段调整**：开发阶段强调近期使用，维护阶段强调核心文件
2. **监控恢复效果**：观察恢复的文件是否真正有助于当前任务
3. **用户反馈**：收集开发者对恢复文件相关性的反馈
4. **渐进调整**：避免大幅调整权重，应逐步优化
5. **场景化配置**：为不同类型的项目或任务设置不同的权重配置

通过合理调整权重配置，可以优化文件恢复策略，确保最重要的上下文信息能够被有效保留和恢复。
