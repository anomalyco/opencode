# 审查意见答辩工作流

本 Skill 引导完成审查意见通知书的分析与答辩，严格遵循审查指南第四部分要求。

## 工作流步骤

### 步骤 1/6：审查意见解析

调用 `oa_response`（action: `parse`），传入审查意见通知书内容。

提取关键信息：
- OA 编号、申请号
- 驳回类型（新颖性 A22.2 / 创造性 A22.3 / 公开不充分 A26.3 / 不清楚 / 超范围 A33）
- 引用的对比文件列表
- 被驳回的权利要求
- 审查员论点摘要
- 答复期限

**⚠️ 人机交互点**：确认解析是否完整准确。

### 步骤 2/6：深度技术分析

调用 `oa_response`（action: `analyze`），传入审查意见和当前权利要求。

分析框架：
- **新颖性（A22.2）**：单独对比原则，逐特征比对
- **创造性（A22.3）**：三步法（最接近现有技术 → 区别特征 → 技术启示）
- 其他驳回理由

系统自动检索相关法规、先例判决和复审无效决定作为论据支撑。

**⚠️ 人机交互点**：确认技术分析结论。

### 步骤 3/6：审查员视角模拟（可选）

调用 `oa_response`（action: `simulate`），从审查员角度预判答辩可能性和反驳论点。

用途：识别答辩薄弱环节，提前准备应对方案。

### 步骤 4/6：答辩策略与意见陈述书

调用 `oa_response`（action: `respond`），撰写意见陈述书。

结构要求：
```
一、关于驳回理由N（类型）
  1. 审查员观点概述
  2. 申请人的意见（逐条回应）
  3. 技术对比分析（表格）
  4. 法律依据（法条 + 审查指南引用）
  5. 结论

二、权利要求修改说明（如修改）
```

**⚠️ 人机交互点**：逐条审阅修改。确认后继续。

### 步骤 5/6：权利要求修改

调用 `oa_response`（action: `revise_claims`），生成修改对照表。

修改原则：
- 修改不超范围（A33），必须基于原始申请文件
- 修改能克服驳回理由
- 输出修改对照表：原文 vs 修改后 + 修改依据

**⚠️ 人机交互点**：权利要求修改必须经用户**逐条批准**。

### 步骤 6/6：验证与打包

调用 `oa_response`（action: `validate`），执行完整性验证。

验证清单：
- [ ] 所有驳回理由均已回应
- [ ] 权利要求修改不超范围（A33）
- [ ] 格式符合国知局要求
- [ ] 法律依据引用完整
- [ ] 技术对比分析完整
- [ ] 权利要求有说明书支持

## 输出规范

最终产出答辩文件（Markdown 格式），包含：
- 意见陈述书
- 权利要求修改对照表
- 修改后的完整权利要求书
- 验证报告

⚠️ 所有产出均为**草案**状态，需经专业审校后提交。

## 重要提醒

- 答复期限：审查意见发文日起 4 个月内（第一次）或 2 个月内（后续）
- 权利要求修改必须不超范围（A33）
- 法律依据引用必须准确到具体条款和段落
- 涉及未公开发明内容的操作需用户明确审批
