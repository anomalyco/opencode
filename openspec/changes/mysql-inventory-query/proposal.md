## Why

员工已经在飞书中查询商品库存和货架位置，但当前回答会暴露内部商品编码，并以表格、汇总说明和字段分段返回，难以快速阅读。项目现已明确业务查询直接使用迁移后的 MySQL，需要用可测试的查询边界和确定性格式化规则固定回答口径。

## What Changes

- 新增只读的 MySQL 商品库存与货架查询能力，只处理员工提出的商品库存或位置问题。
- 查询商品业务名称或型号、属性、规格、结构化货架、供应商库存和备注；供应商优先使用结构化库存来源，来源缺失时回退到迁移后 MySQL 中该商品最近一张已审核、非红字、正数量进货单的实际供应商，并继续显示商品当前总库存；没有可靠进货供应商时省略供应商。
- 使用确定性格式化器生成最终文本，不把原始数据库行交给模型自由改写。
- 最终回答不包含 `Product.s_ID`、`Product.u_Code`、`SP000...` 或其他内部编码，不使用表格、标题、前言、汇总或结尾追问。
- 每个回答对象只占一行，多个对象只用换行分隔；标准格式固定为 `6001ZZ（清油）（12×28×8）（货架号：B-11-13）上海涂众轴承库存200，备注：xxx`。
- 飞书受信接入上下文缺失、过期、伪造或不可验证时失败关闭，不进入 MySQL 查询。
- 将用户问题、业务意图、参数化 SQL、执行结果、格式化回答和人工纠正追加到同一个 trace，并用四层 gold cases 验收；读取类总体准确率不得低于 95%。
- **BREAKING**：删除 T1 SQL Server 运行链路和回退语义。运行代码、配置、测试与发布均不得连接或依赖 T1；历史排查文档仅保留供人工查阅。

## Capabilities

### New Capabilities

- `mysql-inventory-read`: 受信飞书上下文下的 MySQL 商品库存与货架只读查询、数据映射、失败关闭、追踪和准确率行为。
- `inventory-answer-format`: 隐藏内部编码并按固定字段顺序生成一商品一行最终文本的确定性回答行为。

### Modified Capabilities

无。

## Impact

- 在 `packages/feishu` 中新增库存查询端口、MySQL 适配器、业务结果映射、确定性格式化器、追踪事件及测试；实际接入依赖 `feishu-chat-gateway` 提供的飞书会话、任务和日志基础。
- 需要目标 MySQL 的连接配置、只读 schema 探针和参数化查询；不新增 SQL Server 驱动、连接配置或回退分支。
- 在受信任飞书网关中新增模型执行前的库存/货架前置路由；库存请求直接进入固定只读服务并发送确定性文本，`feishu-chat` Agent 继续保持零工具和默认拒绝策略。
- 更新项目 OpenSpec 上下文、协作流程和飞书网关后续路线，移除 T1 运行阶段；两份 T1 历史排查文档保持不变。
