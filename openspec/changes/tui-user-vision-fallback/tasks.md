## 10. Crash fix: drop JSX-in-details experiment after dogfooding (`/models` crashed)

- [x] 10.1 Dogfooding revealed `/models` crashed on first open. The structured-segment JSX path in `modelRow` (each `details` entry a `JSX.Element` containing `<text>` children) caused a Solid render error in `<For each={option.details}>` for the two-pane row renderer at `dialog-model-twopane.tsx:1184` and the generic renderer at `dialog-select.tsx:708`. Revert the experiment and ship the simpler single-string detail.
- [x] 10.2 In `packages/tui/src/util/model-row.tsx`, drop `globalFallback` and `perModelEntry` from `ModelRowOptions`; add a single `capabilityLineText?: string` field. `modelRow` no longer builds a multi-color JSX capability line; it uses the pre-joined string from `capabilityLineJoined` (or falls back to `capabilityLine` when the caller does not supply the pre-joined form).
- [x] 10.3 In `packages/tui/src/util/model.ts`, export `capabilityLineJoined(segs)` that maps `CapabilitySegment[]` to a `" · "-joined` string (drops `colorHint`). `capabilityLineSegments` still emits the per-model-override `colorHint` for any future caller that wants it, but no caller does today.
- [x] 10.4 In `packages/tui/src/component/dialog-model-twopane.tsx`, the `buildModelRow` chokepoint now computes `capabilityLineJoined(capabilityLineSegments(model, fallback, globalFallback, perModelEntry))` once per row and passes the result via `capabilityLineText` to `modelRow`. The custom `RowContent` body no longer has the JSX-vs-string-or-object `isJsx` discriminator; it just renders a `<text fg={theme.textMuted}>` so the capability line is visually identical to its pre-change state (the same color as `reasoning` / `tools` / `vision` / `+N variants`).
- [x] 10.5 In `packages/tui/src/ui/dialog-select.tsx`, narrow `DialogSelectOption.details` back to `string[]`. The renderer at the `For each={option.details}` block is now a single straight-line callback. The `capabilityLineText` field is still in `ModelRowOptions` so callers can override; default callers get `capabilityLine(model, fallback)`.
- [x] 10.6 Trade-off accepted: the per-model-override `fallback-vision` token no longer uses a different color from the inherited / global `fallback-vision` token. Both render in the row's default `theme.textMuted`, indistinguishable from `reasoning` / `tools` / `vision` / `+N variants`. The user can no longer tell from a row alone whether a model is inheriting or overriding; the `DialogConfig` submenu carries the current state in the `Set fallback vision model (<suffix>)` parenthetical. This is acceptable for v1: the row never made this distinction before this change (per `util/model.ts:53-79` plain-string `capabilityLine` with no per-token color), so the trade-off is a return to the pre-change row appearance, not a new regression.
